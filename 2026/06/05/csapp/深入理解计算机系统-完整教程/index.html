深入理解计算机系统——通俗易懂的学习教程

发表于 2026-06-05 分类于 计算机系统

你写了一行代码，然后呢？

你有没有想过一件事：

你敲下 printf("hello world")，回车。不到一眨眼，屏幕上蹦出字来。

就这一瞬间，你那个价值几千块的 CPU 到底在忙活什么？

答案说出来你可能不信——它忙了至少几千万次。

一行 hello world，背后是一整套精心设计的流水线在运转。不理解这套流水线，你就永远在”猜”程序为什么慢、为什么崩、为什么同样的代码在别人机器上跑得好好的。

这篇文章，就是帮你拆开这个黑盒子。

比特不会说话

在深入之前，先记住全书最重要的一句话：

同样的 4 个字节，换一种”读法”，意思就完全不一样。

比如这串十六进制：0x48656C6C

  • 当成整数读 → 1214606444
  • 当字符串读 → Hell
  • 当成一条 CPU 指令读 → 某条加法操作

这就像中文里的”意思”——同一个词，在”你什么意思”和”小意思小意思”里是完全不同的东西。上下文决定含义。

计算机里也一样。比特就是比特，0 和 1 不会告诉你它们是干嘛的。是你的程序用”上下文”给了它们生命。

记住这一点。后面讲到整数溢出、浮点精度、缓冲区溢出，根子都在这里。

编译器内部做了什么？三大阶段：

1. 词法分析：把源代码拆成最小单元（token）——关键字（int、return）、标识符（main、printf）、运算符（+、=）、常量（"hello"）。你可以想象它把一句话”我是一个程序员”拆成”我 / 是 / 一个 / 程序员”。

  • printf 的地址是多少？——还不知道
  • 程序启动后 main 函数怎么被调用？——需要启动代码（crt0）

当然平时你不会手动敲这么多——这是 gcc hello.o -o hello 背后默默做的事情：

  1. 把 hello.o 和几十个系统库（libc.so、ld-linux.so、crt 启动文件……）拼在一起

你的电脑只是一条流水线

让我们打开机箱看看。

我保证不画复杂的电路图。你只需要认识四个角色：

CPU——流水线工人

CPU 内部有一个叫 PC（程序计数器） 的东西。它不是电脑，是一个小寄存器，只存一个数字：下一条要执行的指令在内存的哪个位置。

从你开机到你关机，CPU 就在这套死循环里跑了数以万亿次。这六个步骤（或简化后的五个）构成了后文要讲的流水线的基础。

CPU 里还有几个关键子部件：

  • ALU（算术逻辑单元）：加减乘除、比较大小、位运算，都归它管。每次只能算一个数对——当然，多条 ALU 可以并行工作。
  • 寄存器文件（Register File）：几十个寄存器——CPU 自己的”贴身口袋”，访问速度最快（1 个周期），但只能装一点点东西（每个 8 字节，共几十个）。
  • 分支预测单元：猜”这个 if 走哪个分支”，猜对了流水线丝滑，猜错了要付 10~20 个周期的”罚金”。
  • 缓存控制器：管理 L1/L2/L3 缓存，决定什么数据该留在缓存里、什么该踢出去。

内存——流水线旁边的货架

CPU 干活需要数据和指令，这些东西都放在内存里。内存就是一个巨大的字节数组，每个字节有自己的门牌号（地址）。你在 C 里写的 int *p = 0x7fff...，p 存的就是那个地址。

但注意——内存是 DRAM（动态随机存取存储器），靠电容存电来表示 0 或 1，电容会漏电，所以需要不断刷新。这也意味着：

  • 易失性：关机断电就全忘。这就是为什么你要 Ctrl+S ——把内存写到不丢数据的硬盘上。
  • 比 CPU 慢很多：CPU 算一次只需 ~0.3 纳秒，去内存取一次数据要 ~100 纳秒。
  • 容量比缓存大得多：几个 GB 起步，现在 16GB/32GB 是标配。

除了 DRAM 主存，还有 SRAM（静态随机存取存储器）——不需要刷新，比 DRAM 快 10 倍以上，但体积大、贵、功耗高。SRAM 主要用来做 CPU 的 L1/L2/L3 缓存。

I/O 设备——车间的大门

键盘、鼠标、硬盘（HDD/SSD）、网卡、显卡、显示器……这些都是 I/O 设备。计算机通过它们与外部世界交互。没有 I/O 设备，你的计算机就是一台没有输入输出的算盘——速度快但毫无意义。

I/O 设备通常比内存慢得多。机械硬盘的一次读写（~10ms）够 CPU 执行几千万条指令。这也是为什么系统设计者发明了中断机制：设备准备好数据后主动通知 CPU，而不是让 CPU 轮询”你好了没你好了没你好了没”。

总线——传送带

CPU、内存、I/O 设备之间需要互相通信。总线就是连接它们的高速公路。总线传输的内容分三类：

  • 地址线：指定”我要读/写内存的哪个位置”或”我要跟哪个 I/O 设备说话”
  • 数据线：实际传输的数据（指令、数值、设备数据等）
  • 控制线：同步信号，”读还是写？””现在开始传输””传输完成”

现代 CPU 和内存之间的连接通常是一套独立的高速通道（叫内存总线或前端总线），比连接其他 I/O 设备的通道快得多。

就这四样东西——CPU、内存、I/O 设备、总线——加上操作系统提供的软件抽象，构成了你今天用的这台机器的全部骨架。

为什么你打游戏不卡？——缓存的智慧

现在我们来聊一个让你痛心的事实：

你在等什么 要多久（换算成人类时间）
CPU 算一次加法 1 秒
从 L1 缓存取数据 4 秒
从 L2 缓存取数据 10 秒
从内存取数据 200 秒（3 分多钟！）
从 SSD 读数据 20000 秒（5 个多小时！）
从机械硬盘读数据 1000 万秒（115 天！）

看到了吗？让 CPU 去内存取数据，比让 CPU 自己算点东西要慢 200 倍。

这就像一个顶级大厨，切菜只需要 1 秒，但每次拿食材要等 3 分钟——他一天下来其实没炒几个菜，全在等食材了。

缓存的”偷懒”哲学

解决方法是：把常用的东西放在手边。

CPU 的设计者们早就想到了这一点。他们在 CPU 和内存之间，加了三层”贴身仓库”——L1、L2、L3 缓存。

程序运行时，CPU 会预判你要用什么数据，提前把它从内存搬到缓存里。猜对了——数据已经在缓存里（缓存命中，cache hit），性能起飞。猜错了——不得不出远门取数据（缓存不命中，cache miss），乖乖等几百个周期。

命中率 99% 和 98% 之间，看起来只差 1 个百分点，但性能差别可能非常大。因为那 1% 的不命中每次要付出 200 个周期的代价。举个例子：

  • 命中率 99%：100 次访问 = 99×1 周期 + 1×200 周期 = 299 周期
  • 命中率 98%：100 次访问 = 98×1 周期 + 2×200 周期 = 498 周期

差了 1 个百分点的命中率，总耗时差了近 70%。

这背后有一个根本原因：程序的访问模式是有规律的。

  • 刚用过的数据，很可能马上又要用 → 这叫时间局部性。循环里的 sum 变量反复被读写。
  • 用了一个地址的数据，它旁边的数据也很快会被用到 → 这叫空间局部性。遍历数组时 arr[0], arr[1], arr[2]... 连续访问。

比如你遍历一个数组，从 arr[0] 读到 arr[99]，这就是典型的空间局部性。缓存会一次性把一整块连续的数据（通常 64 字节，叫一个 cache line）搬上来，而不是一个个去取。

现代 CPU（比如 Intel Core i7）的缓存规格：

缓存级 容量 延迟 共享方式
L1 指令缓存 32KB ~4 周期 每核私有
L1 数据缓存 32KB ~4 周期 每核私有
L2 缓存 256KB ~10 周期 每核私有
L3 缓存 8~32MB ~40 周期 所有核共享
TLB 几十~几百条 ~1 周期 各种级别都有

写高效程序的秘诀之一：顺着缓存的脾气来。 后面讲到代码优化时会具体展开。

操作系统：地球上最成功的「骗子」

上面的硬件已经够复杂了。如果让你直接操作它们——自己管理内存地址、自己轮转 CPU、自己读硬盘扇区——你可能第一天就要辞职了。

操作系统站了出来。它对程序员说：别管那些破事，我给你三个”假象”，你照着用就行。

假象一：CPU 是你一个人的

你打开任务管理器，看到几百个进程同时在跑。但你的电脑可能只有 4 个核。

真相是：操作系统让每个进程跑一小段（比如几毫秒——叫一个时间片），然后快速切换到下一个进程。切换快到你以为它们是”同时”在跑。

上下文切换就是这个过程：CPU 暂停进程 A、保存 A 的所有寄存器状态、加载进程 B 的寄存器状态、跳转到 B 上次停下的位置。这个操作本身有开销——通常几微秒到几十微秒，但如果切换太频繁，系统的大部分时间就花在”切换”而不是”干活”上了。

就像一个服务员同时招待好几桌客人——他不是真的长了八只手，只是跑得快而已。但如果桌数太多，光跑路就耗尽了他的体力。

假象二：内存也是一整个给你用

每个进程都觉得自己拥有从地址 0 开始的一大片连续内存。实际上物理内存被切成无数小块，分给了各个进程——甚至有些块根本不是物理内存，而是暂存在硬盘上的。

操作系统维护了一张”翻译表”（叫页表），悄悄把每个进程的”假地址”翻译成真实的物理地址。

就像你看电影院的座位号是 3 排 5 座，但整个城市有几十个影厅——你的”3 排 5 座”不用跟别人的冲突，因为每个影厅有自己独立的编号系统。

假象三：硬盘、网卡、键盘……统统长得一模一样

在 Unix/Linux 的世界里，万物皆文件。

你要写日志到磁盘？write(fd, data, len)
你要往网络发数据？write(sockfd, data, len)
你要打印到控制台？write(1, data, len)（1 是标准输出的文件描述符）

同样的 write，操作系统在背后帮你做了完全不同的底层操作。但对程序员来说——都是对一个”文件”写东西。

这三个假象，是程序员幸福生活的基石。你每天调用的 malloc、fork、fopen，底层都是这套逻辑在运转。

优化之前，先背下这条公式

Amdahl 定律。名字很唬人，道理很简单：

你拼命优化的那部分，如果不占程序的大头，效果会很尴尬。

例子一：加速计算，忽略 I/O

你的程序总耗时 100 秒。其中 40 秒在算矩阵，60 秒在等硬盘。
你花了一个月，把矩阵计算的速度提升了 100 倍。了不起！

40 秒变成了 0.4 秒。总耗时从 100 秒变成了 60.4 秒。快了 1.66 倍。

……就这？

对，就这。因为那 60 秒等硬盘的时间，你碰都没碰。

例子二：加速 80% 的部分——这才是正解

程序总耗时 100 秒。其中 80 秒在等待数据库查询，20 秒在渲染页面。

方案 A：优化渲染，加速 10 倍。20 秒变 2 秒，总耗时 82 秒。快了 1.22 倍。不值得。
方案 B：加个缓存，数据库查询加速 2 倍（只是加个 Redis）。80 秒变 40 秒，总耗时 60 秒。快了 1.67 倍。就改了几行代码。

看到差别了吗？方案 B 的加速倍数只有 2，但实际效果远超方案 A 的 10 倍加速。

公式

$$
S = \frac{1}{(1 - \alpha) + \frac{\alpha}{k}}
$$

  • α = 你优化的部分占总耗时的比例（例子一：0.4；例子二的方案 B：0.8）
  • k = 你把那部分加速了多少倍（例子一：100；例子二的方案 B：2）
  • S = 整体加速比

例子一代入：S = 1 / (0.6 + 0.4/100) = 1 / 0.604 ≈ 1.66 倍
例子二代入：S = 1 / (0.2 + 0.8/2) = 1 / 0.6 ≈ 1.67 倍

终极推论

如果 α = 0（你优化的部分完全不影响整体），不管你加速多少倍，S = 1。零收益。
如果 k → ∞（你把一部分加速到无限快），S = 1/(1-α)。即使把 60% 的部分加速到零耗时，整体也只能快 2.5 倍。

教训：优化之前先 profile，找到真正吃时间的”大头”，别跟一个已经不占多少时间的部分死磕。优化的上限不是你的技术，是 Amdahl 定律。

并发和并行，真的不是一回事

好多面试题爱问这个。一句话说清楚：

并发 (Concurrency) 并行 (Parallelism)
啥意思 一个 CPU 快速切换，看起来像同时 多个 CPU 核真的同时干活
现实类比 一个厨师边煮面边切葱 两个厨师一个煮面一个切葱
核心是 任务的调度和切换 任务的真正同时执行

单核 CPU 也可以并发——时间片轮转嘛。但并行必须有多核。

有趣的是，现代 CPU 甚至在单核内部也在搞并行：

  • 一条指令还没执行完，下一条已经开始了（这叫流水线）
  • 一条指令可以同时操作多个数据（这叫 SIMD——比如一次把 4 对浮点数加起来）

二进制：因为电路只认识两个状态

计算机用二进制，只有一个原因：电路开关只有两种状态——通电和断电。

1 比特（bit）就是一根电线：0 表示没电，1 表示有电。8 根线捆在一起就是 1 字节（byte）。

问题是，8 个比特能表示的范围只有 0~255。要表示更大的数怎么办？多捆几根线：

类型 字节数 比特数 能表示多少种状态
char 1 8 256
short 2 16 65536
int 4 32 ~42 亿
long 8 64 巨大

所谓”字长”就是 CPU 一次性能处理多少比特。64 位 CPU 一次处理 64 比特，指针（内存地址）也是 64 位。

表示负数最简单的方法：把最高位当作符号位，0 是正，1 是负。这叫”原码”。

  2. 加减法用一套电路：a - b = a + (-b)，省硬件
  3. 范围不对称：8 位下，正数最大是 127（0111 1111），负数最小是 -128（1000 0000）

防御三件套

现代系统有三道防线：

  1. 栈随机化（ASLR）：每次程序启动，栈的位置随机偏移。攻击者不知道返回地址在哪，就很难精确覆盖。

  2. 金丝雀值（Stack Canary）：在返回地址旁边放一个随机数（金丝雀）。函数返回前检查金丝雀还在不在——不在了就说明有人动了栈内存。这个名字来自煤矿工人：矿井里放一只金丝雀，如果金丝雀死了，说明有毒气，赶紧撤。

  3. 不可执行栈（NX/XD）：标记栈内存为”不可执行”。即使攻击者在栈上放了恶意代码，CPU 也会拒绝执行。

这三道防线让缓冲区溢出攻击难了很多，但并没有让它们消失——ROP（Return-Oriented Programming）攻击就是利用程序中已有的合法代码片段来绕过 NX 保护。

数据冒险——我等着你的结果呢

指令 2 需要指令 1 的结果，但指令 1 还没走到”写回”那一步。怎么办？

  • 暂停（Stalling）：让指令 2 等一等。简单粗暴，但浪费了时间。
  • 转发（Forwarding）：不等了，直接把指令 1 的执行结果”抄近道”传给指令 2。硬件多拉了几根线，效果完美。

控制冒险——下一个路口往哪拐？

遇到条件跳转，CPU 不知道下一条指令该取谁。等 cmp 算完？那流水线就空了。

解决方案：分支预测。CPU 根据历史记录”猜”这个跳转会往哪走。猜对了，流水线畅通。猜错了，前面几条指令全报废，重新来——这叫”误预测惩罚”，可能浪费 10~20 个时钟周期。

CPU 的分支预测准确率通常在 95% 以上。策略很简单：

  • 向后跳转（循环底部跳回顶部）→ 猜会跳
  • 向前跳转（if-else 的跳过）→ 猜不跳

编程启示：尽量让循环里的分支预测友好。把常见情况放在 if 分支，把罕见情况放在 else 分支。

写策略

读缓存很简单——查到就命中，查不到就去下级取。但写复杂得多：

写命中时（数据在缓存里）：

  • 写回（Write-back）：只更新缓存内容，标记为”脏”（dirty bit）。该行被替换出缓存时，才把脏数据写回下一级存储。性能好，但一致性复杂。
  • 写直达（Write-through）：同时更新缓存和下一级存储。简单但慢（每次写都要等慢速存储）。

写不命中时（数据不在缓存里）：

  • 写分配（Write-allocate）：先把数据块从下一级存储加载进缓存，再在缓存中写。配合写回策略使用。
  • 非写分配（No-write-allocate）：直接绕过缓存，写到下一级存储。配合写直达策略使用。

现代 CPU 的 L1 缓存通常使用写回 + 写分配策略。

缓存一致性（多核场景）

当核 A 修改了它 L1 缓存中的一个地址，核 B 的 L1 缓存中同一地址的副本就是”过期的”。缓存一致性协议（如 MESI，Modified/Exclusive/Shared/Invalid）确保各个核看到一致的数据。这套协议是硬件自动处理的，但它的代价是——频繁的跨核写操作会导致大量的”共享不命中”。

程序优化的缓存视角

假设 N=4096，元素是 int(4字节)，每个 cache line 64 字节 = 16 个 int。按行遍历：每 16 次访问才一次 miss（命中率 93.75%）。按列遍历：每次访问都跳到下一个不相关的行，几乎每次都是 miss（命中率接近 0%）。同样的计算量，速度可能差 30~50 倍。

分块（Blocking / Tiling）的进阶威力：

对于矩阵乘法 C = A × B，不仅 A 需要按行遍历，B 和 C 的访问模式同样影响缓存命中。分块将三个矩阵都切成小块（如 32×32），保证每次处理的小块能完整装入 L1 缓存。对于 1024×1024 的矩阵，6×6 的分块可以把性能从”直接三重循环”的几百 MFLOPS 提升到几个 GFLOPS——几倍到几十倍的提升。这就是”存储器山”实验的核心结论：算法的性能不仅取决于运算次数，更取决于数据在存储器层次中的位置。

写时复制（Copy-on-Write） 是 fork() 能高效运转的关键：fork 之后父子进程共享同一块物理内存，直到有一方尝试写入——那时内核才真正复制那一页。

fork 是”分身”，execve 是”夺舍”——用另一套程序完全替换当前进程的代码和数据。

这就是你从终端输入命令后 shell 做的事：fork → execve → waitpid → 显示下一个提示符。

进程的一生：状态转换

一个进程从创建到消亡，经历多种状态：

子进程死亡时，并不完全消失——它变成一个僵尸进程，残留一个包含了退出状态和资源使用统计的进程表条目。父进程需要用 waitpid() 来收取这个”讣告”。如果父进程不回收，僵尸就永远占着进程表不释放，积累多了系统会拒绝创建新进程。

孤儿进程——父进程先死，子进程还没死。init 进程（pid=1）会”收养”所有孤儿，并自动 wait 它们。所以孤儿不会变僵尸，父进程还在但不 wait 才会变僵尸。

编程启示：fork 子进程后一定要 wait。如果不想等（让子进程独立运行），用 signal(SIGCHLD, SIG_IGN) 告诉内核”子进程死完自己收尸，别叫我”。

信号：进程间的”拍肩膀”

信号是 Unix 里进程间异步通知的机制。内核可以给进程发信号（比如段错误），进程也可以给其他进程发信号（kill 命令）。

每个信号有默认行为：终止、终止+core dump、暂停、忽略。程序可以用 signal() 或 sigaction() 注册自己的处理函数，但有例外：

  • SIGKILL (9) 和 SIGSTOP (19) 无法被捕获、忽略或阻塞——这两位是”最后通牒”
  • 信号处理函数中只应做最简单的事：设置一个 flag 变量（如 volatile sig_atomic_t），然后返回。不要在信号处理函数里调 printf、malloc 等非信号安全的函数

为什么？因为信号随时可能到来，你的程序可能在 malloc 内部锁着互斥锁时被打断——如果信号处理函数又去调 malloc，就死锁了。这就是所谓的”异步信号安全”问题。

虚拟内存——计算机史上最伟大的”谎言”

为什么需要虚拟内存？

如果你写了一个程序，想访问内存地址 0x400000。问题来了：

  • 你的电脑上同时跑着 200 个进程
  • 每个进程都可能想访问 0x400000
  • 物理内存只有 8GB，但 200 个进程每个都需要空间
  • 不能让进程 A 覆盖进程 B 的数据，否则就是安全灾难

虚拟内存的解决方案：给每个进程发一张”虚拟地址地图”，进程在地图上随便画，操作系统负责翻译成真实的物理地址。

虚拟内存一举解决了三个问题：

  1. 隔离：每个进程有独立的地址空间，A 的 0x400000 和 B 的 0x400000 是完全不同的物理地址
  2. 超越物理限制：你可以写一个需要 20GB 内存的程序，操作系统会把用不到的页交换到硬盘
  3. 简化编程：每个程序都从 0 开始编址，不需要考虑别的进程用了哪个地址段

页表：翻译全靠它

虚拟内存把地址空间切成固定大小的块叫”页”（通常 4KB）。物理内存也被切成同样大小的”页帧”（page frame）。页表就是虚拟页号到物理页号的映射字典。

每个页表条目（PTE，Page Table Entry）除了存物理页号，还有几个控制位：

  • 有效位（Valid）：这页在物理内存里吗？
  • 读写权限：可读？可写？可执行？
  • 用户/内核：这页只能内核访问还是用户程序也能访问？
  • 脏位（Dirty）：这页被修改过吗？（决定了写回硬盘时要不要更新）

缺页（Page Fault）：查页表发现目标页面的有效位是 0——不在物理内存里！可能的情况：

  • 这页从未被分配过（程序写了空指针）→ 段错误 SIGSEGV
  • 这页在硬盘 swap 区 → 触发缺页异常，操作系统从硬盘读入内存，重新执行失败指令
  • 这页是 mmap 映射的文件的一部分 → 从磁盘读文件内容进内存

除了慢一点（硬盘访问是毫秒级的），程序完全不知道发生了缺页。这就是虚拟内存的”透明性”。

malloc 的真相：延迟分配

当你调用 malloc(100)：

  1. malloc 从它管理的空闲链表中找一块合适的内存，切一块给你
  2. 你拿到一个指针，指向某虚拟地址
  3. 但此时，这个虚拟地址后面可能根本没有对应的物理页！
  4. 操作系统只在页表里记录”这个地址范围是有效的、可写的”
  5. 你真写入数据时，CPU 触发缺页异常
  6. 内核分配一页物理内存（4KB），更新页表，重新执行写操作
  7. 你的程序继续运行，完全不知道刚才发生了什么

这就是虚拟内存的”延迟分配”策略：承诺给你，但不一定现在给，等你真正要用了再说。这让你可以 malloc(1GB) 而系统不会有任何压力——只要你别真的写入所有 1GB。

写时复制（Copy-on-Write, COW）

fork() 之后，父子进程共享同一块物理内存。页表条目标记为只读。任何一方尝试写入时，CPU 触发缺页异常，内核才真正复制那一页。大部分 fork 出来的子进程马上 execve，根本不会写入——所以这个优化省掉了近乎所有的内存复制开销。

  • 为什么多个进程可以同时写同一个文件而不冲突——它们各自有独立的文件表条目（不同的文件位置）

并发编程——让多个活儿同时进行

为什么需要并发？

不是因为”酷”，而是三个很现实的需求：

  1. 提高吞吐量：一个线程在等磁盘 I/O（毫秒级），另一个可以去处理别的请求。如果串行等待，CPU 有 99% 的时间在发呆
  2. 利用多核：8 核 CPU，串行只能用一个核，浪费 87.5% 的算力
  3. 响应性：GUI 程序主线程做重活，界面会卡死、用户点什么都无响应——必须把重活丢到后台线程

死锁需要四个条件同时成立（缺一不可）：

  2. 持有并等待：拿着一些资源，还在等另一些
  3. 不可抢占：别人不能强行拿走你的资源，只能自己主动放
  4. 循环等待：线程 A 等线程 B 持有的资源，线程 B 等线程 A 持有的资源，形成环

打破任意一个条件就能防止死锁：

打破条件 做法 代价
打破互斥 用无锁数据结构、原子操作 实现复杂
打破持有并等待 一次性申请所有需要的锁（trylock 失败就全放掉重来） 可能导致活锁
打破不可抢占 允许系统强制收回锁（通常不现实） 很难安全实现

最常用的策略是打破循环等待：给所有互斥锁编号，永远先拿小编号的再拿大编号的。这样就不会出现”A 有锁 1 等锁 2，B 有锁 2 等锁 1”这种循环。

贯穿全文的五条金线：

  1. 抽象是计算机科学的核心武器。 文件、进程、虚拟内存都是操作系统制造的”假象”，但正是这些假象让你不需要关心每个硬件的具体操作。每一层抽象都屏蔽了下一层的复杂性，让程序员可以专注于自己要解决的问题。
  2. 速度鸿沟驱动一切设计。 CPU 太快（0.3ns/指令），内存太慢（100ns），磁盘更是慢得离谱（~10ms）。缓存、流水线、预取、乱序执行、异步 I/O、DMA……所有这些技术的出发点都是同一个：别让快的东西等慢的东西。
  3. 局部性是性能的根本。 程序的访问模式天然有规律（时间局部性和空间局部性）。缓存和虚拟内存都靠这个规律来”预判”。写代码时遵循局部性，就是在跟硬件”合作”；破坏局部性，就是在跟硬件”对着干”——而硬件永远不会输。
  4. 并发没有银弹。 线程、事件、进程——每种并发模型都有不可消除的代价。竞态条件是最难排查的 bug 类型之一，信号量是经典但容易被误用的同步工具。理解底层机制（原子操作、内存序、缓存一致性）是写出正确并发代码的前提。
  5. 理解底层让你写出更好的上层代码。 知道浮点数为什么不精确，你就不会在金融计算中用 ==。知道栈的布局，你就理解为什么局部变量不能返回指针。知道缓存的工作原理，你就懂得为什么按行遍历比按列遍历快几十倍。知道 fork 的写时复制，你就能预测 fork 之后内存不会立即翻倍。知道编译和链接的四阶段，你就能根据报错信息快速定位问题在哪个环节。
