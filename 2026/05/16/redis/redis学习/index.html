1，Redis 简介

Redis（Remote Dictionary Server）是一个开源的、基于内存的键值存储系统，由 Salvatore Sanfilippo 于 2009 年发布。它常被用作数据库、缓存、消息代理和流处理引擎。

核心特点：

  • 基于内存：所有数据存放在内存中，读写速度极快（读 11 万/s，写 8 万/s）
  • 单线程模型：使用单线程处理命令，避免上下文切换和锁竞争（6.0 后引入多线程 I/O，但命令执行仍是单线程）
  • 持久化支持：支持 RDB 快照和 AOF 日志两种持久化方式
  • 丰富的数据类型：String、Hash、List、Set、Sorted Set、Bitmap、HyperLogLog、Geo、Stream
  • 高可用：支持主从复制、哨兵模式、集群模式
  • 原子操作：所有命令都是原子性的
  • 过期策略：支持为 key 设置过期时间，到期自动删除

与 Memcached 的对比：

特性 Redis Memcached
数据结构 丰富（String/List/Set 等） 仅 String
持久化 支持 RDB + AOF 不支持
集群 原生 Cluster + Sentinel 客户端分片
线程模型 单线程 + IO 多线程 多线程
内存管理 jemalloc slab allocation
事务 支持（非严格 ACID） 不支持

应用场景：

  • 缓存（热点数据、页面缓存、Session 共享）
  • 排行榜/计数器（Sorted Set 实现实时排行）
  • 分布式锁（SETNX + 过期时间）
  • 消息队列（List 阻塞队列 + Stream）
  • 社交关系（Set 实现关注/粉丝/共同好友）
  • 地理位置（Geo 实现附近的人）
  • 限流（滑动窗口 + 令牌桶）
  • 布隆过滤器（Bitmap + Hash 函数）

5，五大数据类型深度解析

5.1 String（字符串）

String 是 Redis 最基本的数据类型，一个 key 对应一个 value。value 最大 512MB，可以存放文本、数字、序列化后的对象、甚至是图片的二进制数据。

内部编码：

  • int：8 字节以内的整数
  • embstr：≤ 44 字节的字符串（一次内存分配）
  • raw：> 44 字节的字符串（两次内存分配）

应用场景：

  • 缓存：序列化对象缓存（JSON / Protobuf）
  • 计数器：文章阅读量、点赞数、库存扣减
  • 分布式锁：SET NX EX
  • Session 共享：集中存储用户登录态
  • 限流：固定窗口计数器

5.2 Hash（哈希）

Hash 是一个 field-value 映射表，适合存储对象。每个 hash 最多 2^32-1 个 field。

内部编码：

  • ziplist（7.0 后为 listpack）：元素少且短时使用，节省内存
  • hashtable：元素多或长时自动转换
    • hash-max-listpack-entries 512
    • hash-max-listpack-value 64

应用场景：

  • 存储对象：用户信息、商品详情（比 String 序列化更灵活，可按字段单独读写）
  • 购物车：HSET cart:user:1 sku:001 3，用户的购物车，field 为 SKU，value 为数量
  • 计数器分组：单篇文章各渠道的阅读量统计

5.3 List（列表）

List 是一个双向链表，按插入顺序排序，可以添加元素到头部或尾部。每个 list 最多 2^32-1 个元素。

内部编码：

  • quicklist：Redis 3.2 起使用，是 ziplist 和 linkedlist 的混合体
    • list-max-ziplist-size -2（每个 quicklist 节点的 ziplist 大小）
    • list-compress-depth 0（压缩深度，0 不压缩）

应用场景：

  • 消息队列：LPUSH + BRPOP 简单可靠的消息传递（可靠性要求高建议用 Stream）
  • 最新列表：最新文章、最新评论（LPUSH + LTRIM 保持固定长度）
  • 栈：LPUSH + LPOP
  • 队列：LPUSH + RPOP

5.4 Set（集合）

Set 是无序的、不重复的字符串集合。底层是哈希表，支持集合间的交并差运算。每个 set 最多 2^32-1 个元素。

内部编码：

  • intset：元素全为整数且数量少时使用
  • hashtable：元素多或包含非整数时自动转换
    • set-max-intset-entries 512

应用场景：

  • 标签系统：用户标签、文章标签
  • 点赞：SADD like:article:1 user:1001，天然去重
  • 共同好友：SINTER friends:user:1 friends:user:2
  • 抽奖：SRANDMEMBER 或 SPOP
  • 用户关注/粉丝：关注集合 + 粉丝集合，用集合运算推导关系

5.5 Sorted Set（有序集合）

有序集合和 Set 一样元素唯一，但每个元素关联一个 double 类型的 score，按 score 从小到大排序。score 相同时按 member 字典序排序。

内部编码：

  • ziplist/listpack：元素少且短时使用
  • skiplist + hashtable：元素多时
    • 跳表用于范围查询和排序
    • 哈希表用于 member→score 的 O(1) 查找

跳表原理：

跳表（Skip List）是一种多层链表结构，通过在上层建立索引来加速查找。查找时间复杂度 O(log N)，实现比红黑树简单。

应用场景：

  • 排行榜：游戏积分排行、文章热榜
  • 延迟队列：score 存储任务执行时间戳，ZRANGEBYSCORE 取出到期任务
  • 滑动窗口限流：score 存时间戳，member 存请求标识
  • 带权重的标签：文章标签 + 权重分数
6，高级数据类型

6.1 Bitmap（位图）

Bitmap 本质上是用 String 来存储位信息，适合大量布尔值的存储。一个 512MB 的 String 可以表示 2^32 个 bit。

应用场景：

  • 用户签到：每天一个 bit，记录用户签到情况
  • 在线状态：用户在线/离线
  • 布隆过滤器：结合多个 hash 函数实现

6.2 HyperLogLog

HyperLogLog 是一种基数估计的概率数据结构，用于统计不重复元素的个数。单个 HyperLogLog 仅占用约 12KB 内存，误差率约 0.81%。

应用场景：

  • UV 统计：页面独立访客数
  • 搜索关键词去重统计

注意：HyperLogLog 不存储元素本身，无法获取具体元素。需要精确去重或需要元素列表时不能用。

6.3 Geo（地理位置）

基于 Sorted Set 实现，使用 GeoHash 算法将经纬度编码为 score，支持地理位置相关计算。

应用场景：

  • 附近的人：GEOSEARCH
  • 外卖骑手位置追踪：GEOADD + GEODIST
  • 门店搜索：按距离排序展示门店列表

6.4 Stream（流）

Redis 5.0 引入的持久化消息队列数据结构，支持消费者组、ACK 确认、消息回溯。比 List 更适合做消息队列。

消息 ID 格式：<millisecondsTime>-<sequenceNumber>，如 1680000000123-0。

应用场景：

  • 异步消息队列：可靠的消息传递
  • 事件溯源：存储完整的业务事件序列
  • 聊天系统：消费者组可实现多端消息同步

7，发布订阅（Pub/Sub）

Redis 的发布订阅是一种消息通信模式：发布者发送消息到频道，所有订阅该频道的订阅者都会收到。

注意：

  • Pub/Sub 的消息没有持久化，订阅者离线期间的消息会丢失
  • 消息无法回溯，发后即忘（fire and forget）
  • 如需可靠消息传递，应使用 Stream 或 List
  • 订阅状态下客户端只能执行 SUBSCRIBE 相关命令
8，事务（Transaction）

Redis 事务通过 MULTI / EXEC 实现，保证一系列命令按顺序执行且不会被其他客户端的命令打断。但 Redis 事务不支持回滚。

事务特点：

  • 不具备原子性回滚：某条命令执行失败，不影响其他命令，不回滚
  • 命令入队时检查：语法错误（错误命令）会在入队时就报错，整个事务不执行
  • 执行时错误：如对 String 执行 LPOP，只影响那条命令，其他命令正常执行
  • 隔离性：事务中的命令在 EXEC 前不会被其他客户端命令插入

10，持久化

10.1 RDB（Redis Database）

RDB 是某一时刻内存数据的二进制快照，默认持久化方式。

触发方式：

RDB 执行流程：

  1. 父进程 fork() 子进程（Copy-on-Write）
  2. 子进程将内存数据写入临时 RDB 文件
  3. 写完后替换旧的 RDB 文件

优点：

  • 文件紧凑，适合备份和灾难恢复
  • 恢复大数据集时比 AOF 快
  • 对性能影响小（子进程操作，父进程只处理 COW）

缺点：

  • 两次快照间的数据可能丢失（fork 间隔长）
  • fork 时内存翻倍风险（COW 拷贝）

10.2 AOF（Append Only File）

AOF 记录所有写操作命令，重启时重放命令恢复数据。

AOF 重写原理：

  1. 父进程 fork() 子进程
  2. 子进程基于当前内存数据，生成新的 AOF 文件
  3. 父进程在此期间的新写入记录到 AOF 重写缓冲区
  4. 子进程完成后，父进程将缓冲区数据追加到新 AOF
  5. 原子替换旧 AOF 文件

优点：

  • 数据安全性更高（最多丢 1 秒）
  • AOF 可以修复（redis-check-aof）
  • 可读性好，直接查看写入命令

缺点：

  • 文件比 RDB 大
  • 恢复速度比 RDB 慢
  • 对性能有轻微影响（everysec 模式约下降 10%）

10.3 混合持久化（Redis 4.0+）

Redis 4.0 引入了混合持久化：AOF 重写时生成一个 RDB 快照 + 后续的 AOF 增量日志，结合两者优势。

11，主从复制

主从复制是 Redis 高可用的基础，实现数据冗余和读写分离。

复制过程：

  1. 连接阶段：从节点连接主节点，发送 PSYNC 命令
  2. 同步阶段：主节点执行 BGSAVE 生成 RDB，发送给从节点；同时缓存期间的写命令
  3. 增量同步：RDB 加载完毕，主节点发送缓存的写命令；此后持续同步新命令
  4. 断线重连：主从节点各自维护 replication offset，断线重连后根据 offset 决定是全量同步还是增量同步

PSYNC 流程：

  • replication backlog buffer：主节点维护的环形缓冲区，默认 1MB
  • 如果断线期间的命令还在 buffer 中 → 增量同步
  • 否则 → 全量重同步

拓扑结构：

  • 一主一从：简单的热备份
  • 一主多从：读写分离
  • 树形结构：从节点下面再接从节点，减轻主的复制压力

问题：

  • 主节点宕机需手动切换（Sentinel 解决）
  • 写都在主节点，存在单点
  • 异步复制，存在复制延迟
12，哨兵模式（Sentinel）

Sentinel 是 Redis 高可用方案，监控主节点并在故障时自动执行故障转移。

核心概念：

  • 主观下线（SDOWN）：单个 Sentinel 认为节点不可达
  • 客观下线（ODOWN）：quorum 个 Sentinel 都认为主节点不可达，触发故障转移

故障转移过程：

  1. 多个 Sentinel 发现主节点不可达
  2. 达到 quorum 后判定为客观下线
  3. Sentinel 之间进行领导者选举（Raft 算法）
  4. 选出的 Sentinel 领导者执行故障转移：
    • 选出一个最优从节点（优先级高、数据新）
    • 将其提升为新主节点
    • 其他从节点切换到新主节点
    • 旧主节点恢复后自动变为新主节点的从节点

选举从节点优先级：

  1. 复制偏移量最大的从节点（数据最新）
  2. 优先级最小的从节点（replica-priority 配置，值越小优先级越高）
  3. 复制偏移量相同时，runid 最小的

注意事项：

  • Sentinel 至少部署 3 个（且应为奇数个）
  • Sentinel 本身也需高可用部署在不同物理机上
  • 客户端需要通过 Sentinel 发现当前主节点地址
  • Spring Data Redis / Jedis / Lettuce 都支持 Sentinel 模式自动发现
13，集群模式（Cluster）

Redis Cluster 是官方提供的分布式方案，支持数据自动分片和部分节点故障时继续服务。

关键特性：

  • 数据自动分片（16384 个哈希槽）
  • 每个节点分管一部分槽位
  • 客户端可连接任意节点，节点会自动将请求重定向到正确节点
  • 每个分片可配置主从（主节点故障时从节点自动提升）

14，内存淘汰策略

当 Redis 内存达到 maxmemory 上限时，根据配置的策略淘汰 key。

8 种淘汰策略：

策略 描述
noeviction 不淘汰，写操作报错（默认）
volatile-lru 在设置了过期时间的 key 中，按 LRU 淘汰
volatile-lfu 在设置了过期时间的 key 中，按 LFU 淘汰
volatile-random 在设置了过期时间的 key 中，随机淘汰
volatile-ttl 淘汰即将过期的 key
allkeys-lru 在所有 key 中，按 LRU 淘汰（推荐缓存场景）
allkeys-lfu 在所有 key 中，按 LFU 淘汰
allkeys-random 在所有 key 中，随机淘汰

LRU vs LFU：

  • LRU（最近最少使用）：最近没有被访问的优先淘汰。适合缓存的通用场景
  • LFU（最不经常使用）：访问频率最低的优先淘汰。解决偶发性访问导致热门数据被误淘汰的问题

近似算法：Redis 的 LRU/LFU 是近似算法（采样对比），不是精确的全局排序。

过期键删除策略：

  • 惰性删除：访问 key 时检查是否过期，过期则删除
  • 定期删除：每 100ms 随机抽查一部分 key，删除其中过期的
  • 两者结合，平衡 CPU 和内存
15，缓存问题与解决方案

15.1 缓存穿透

查询一个不存在的数据（既不在缓存也不在数据库），请求直接打到数据库。

解决方案：

  • 布隆过滤器：用 bitmap + 多个 hash 函数判断 key 是否存在（有误判率，说”不存在”一定是准确的）
  • 缓存空值：将不存在的 key 也缓存，值为 null，设置短过期时间
  • 参数校验：对请求参数做合法性校验

15.2 缓存击穿

一个热点 key 过期瞬间，大量并发请求打到数据库。

解决方案：

  • 逻辑过期：不设 Redis 过期，在 value 中存过期时间，发现过期后异步刷新
  • 互斥锁：缓存未命中时，只让一个请求去查数据库并重建缓存，其他请求等待

15.3 缓存雪崩

大量缓存 key 在同一时间段过期，或 Redis 宕机，导致请求全部打到数据库。

解决方案：

  • 过期时间加随机值：避免大量 key 同时过期
  • 多级缓存：本地缓存（Caffeine/Guava）+ Redis 缓存
  • 限流降级：数据库前加限流，超量请求直接返回降级结果
  • Redis 高可用：Cluster / Sentinel，保障 Redis 本身不宕机

15.4 缓存一致性问题

更新数据时，缓存和数据库如何保持一致？

Cache Aside Pattern（旁路缓存，最常用）：

  • 读：先查缓存，命中则直接返回；未命中则查数据库，写入缓存
  • 写：先更新数据库，再删除缓存（延迟双删可应对极端并发）

为什么是删除缓存而不是更新缓存？—— 更新操作可能涉及多个表，直接更新缓存的计算成本高；删除后等下次读时自然重建更简单。

最终一致性方案：

  • 延时双删：写完数据库后先删缓存，等一小段时间（如 100ms）再删一次（应对并发）
  • binlog 订阅：订阅 MySQL binlog，异步更新/删除 Redis 缓存
  • 消息队列：更新数据库后发 MQ 消息，消费端更新 Redis

18，常见面试问题
  • Redis 为什么快？ — 基于内存、单线程避免锁竞争、高效的数据结构、IO 多路复用
  • Redis 6.0 多线程是什么？ — 多线程 I/O（网络读写），命令执行仍是单线程
  • Redis 与数据库如何保证一致性？ — 先更新数据库再删除缓存 + 延迟双删
  • Redis 如何实现分布式锁？ — SET key value NX EX 30，释放用 Lua 校验 value
  • RDB 和 AOF 的区别？ — RDB 是快照，文件小恢复快但间隔长；AOF 是写日志，数据安全但文件大
  • 哨兵和集群的区别？ — 哨兵解决高可用（自动故障转移），集群解决扩展性（数据分片）
  • 为什么用跳表而不是红黑树？ — 跳表实现更简单，范围查询友好，插入删除只需修改相邻节点
  • 缓存雪崩、击穿、穿透的区别？ — 雪崩是大面积 key 同时过期；击穿是热点 key 过期；穿透是查询不存在的数据
  • Pipeline vs 事务？ — Pipeline 减少 RTT，不保证原子性；事务保证原子性但无回滚
