mysql索引原理与优化

发表于 2023-01-24 分类于 mysql
1. 索引原理

MySQL 最常用的存储引擎 InnoDB 使用 B+Tree 作为索引结构。理解 B+Tree 是理解索引原理的核心。

B+Tree 的特点：

  • 所有数据都存储在叶子节点，非叶子节点只存键值和指针，因此非叶子节点可以存储更多索引键，树的高度更低。
  • 叶子节点之间通过双向链表连接，天然支持范围查询和排序。
  • 对于 N 阶 B+Tree，每个节点最多 N 个键、N+1 个指针。InnoDB 中一页默认 16KB，阶数由键值大小决定。

InnoDB 中的两种索引：

  • 聚簇索引（Clustered Index）：以主键构建 B+Tree，叶子节点存储完整的数据行。每张表只有一个聚簇索引。若未定义主键，InnoDB 会选第一个非空唯一索引，或自动生成隐藏的 row_id。
  • 二级索引（Secondary Index）：以索引列构建 B+Tree，叶子节点存储的是主键值。通过二级索引查找数据需要 回表——即先通过二级索引找到主键，再通过聚簇索引找到完整行。

回表与索引覆盖：
回表是随机 IO，代价较高。当查询的列全部包含在索引中时，不需要回表，称为覆盖索引，Using index 即表示覆盖索引。

联合索引与最左前缀原则：
联合索引按字段顺序构建，第一列全局有序，后续列仅在上一列相同时有序。因此查询条件必须从最左列开始才能利用索引，这就是最左前缀原则。举例：INDEX(a,b,c) 可用于 WHERE a=1、WHERE a=1 AND b=2，但不能单独用于 WHERE b=2（除非 a 使用范围查询的宽松条件下）。

2. Explain 性能分析

EXPLAIN 是分析 SQL 执行计划的工具，用于判断查询是否使用了索引以及执行效率。

核心字段解读：

字段 含义
id 查询序号，同一 id 从上到下执行；id 不同时，值越大优先级越高
select_type 查询类型：SIMPLE（简单查询）、PRIMARY（主查询）、SUBQUERY（子查询）、DERIVED（派生表）、UNION 等
table 访问的表名
type 访问方式（从好到差）：system > const > eq_ref > ref > range > index > ALL
possible_keys 可能用到的索引
key 实际使用的索引
key_len 使用的索引长度（字节），可用于判断联合索引用了哪些列
ref 与索引列比较的列或常量
rows 预估扫描行数
Extra 额外信息，非常重要

type 访问方式详解：

  • const：主键或唯一索引等值查询，最多返回一行。
  • eq_ref：连表查询时，驱动表每行在另一表用主键或唯一索引匹配一行。
  • ref：非唯一索引等值匹配，可能返回多行。
  • range：索引范围扫描（>、<、BETWEEN、IN、LIKE 'abc%'）。
  • index：全索引扫描，比 ALL 好但仍是扫描全部索引。
  • ALL：全表扫描，性能最差，需要优化。

Extra 关键值：

  • Using index：覆盖索引，不回表，性能好。
  • Using where：MySQL 服务器层对存储引擎返回的数据做过滤。
  • Using index condition：ICP（索引条件下推），存储引擎层先过滤，减少回表。
  • Using temporary：使用了临时表，常见于 GROUP BY、DISTINCT、ORDER BY，需要优化。
  • Using filesort：额外排序操作（未利用索引有序性），需要优化。
  • Using join buffer：连表时使用了 join buffer，说明被驱动表没有可用索引。
3. 高性能索引创建与使用

选择合适的索引列：

  • WHERE、JOIN、ORDER BY、GROUP BY 涉及到的列考虑加索引。
  • 选择区分度高的列（COUNT(DISTINCT col)/COUNT(*) 越接近 1 越好）。
  • 枚举类型、性别这类区分度很低的列不适合单独建索引。

联合索引设计原则：

  • 等值查询条件列放前面，范围查询条件列放后面。
  • 区分度高的列尽量放前面。
  • 排序/分组列可考虑纳入联合索引。
  • 善用覆盖索引避免回表，常见做法是把 SELECT 的列也加入索引末尾。

前缀索引：
对字符串列，可为前 N 个字符建索引以减少索引体积。但前缀索引无法用于 ORDER BY 和 GROUP BY，且覆盖索引失效。

避免索引失效的场景：

  • 对索引列使用函数或计算：WHERE YEAR(create_time) = 2023 应改为 WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31'。
  • 隐式类型转换：VARCHAR 列用数字查询 WHERE phone = 13800138000 会失效。
  • LIKE 以 % 开头：LIKE '%abc' 无法用索引。
  • 不等于（!=、<>）、NOT IN、IS NULL（视情况而定）可能不走索引。
  • OR 条件中若有不带索引的列，整体不走索引，可用 UNION 改写。

索引下推（ICP）：
MySQL 5.6+ 特性。对于联合索引中无法直接用到的列条件，存储引擎先按该条件过滤再回表，减少回表次数。Extra 中显示 Using index condition。

MRR（Multi-Range Read）：
将二级索引回表的随机 IO 转化为按主键排序后的顺序 IO，减少磁盘寻道开销。

5. 多表 JOIN 优化

Nested-Loop Join（NLJ）：
MySQL JOIN 大多采用嵌套循环算法。驱动表取一行，去被驱动表匹配。被驱动表的 JOIN 列必须有索引，否则每次匹配都是全表扫描，复杂度为 O(M×N)。

Block Nested-Loop Join（BNLJ）：
被驱动表无索引时，MySQL 将驱动表的一部分行加载到 join buffer，一次性扫描被驱动表进行批量匹配。这种情况下 Extra 会显示 Using join buffer。

JOIN 优化原则：

  • 小表驱动大表：数据量小的表作为驱动表，减少被驱动表循环次数。
  • 被驱动表 JOIN 列加索引：这是最重要的优化，确保 eq_ref 或 ref 级别。
  • 减少驱动表扫描行数：驱动表加上 WHERE 条件索引。
  • **避免 SELECT ***：只取需要的列，减少网络传输和内存占用。
  • 关联查询拆解：有时拆成多条简单查询在应用层组装，比一条复杂的 JOIN 更高效且可维护。
  • 控制 JOIN 表数量：建议不超过 3 张表联查，过多可考虑拆解或冗余设计。

JOIN 顺序与优化器：
MySQL 优化器会根据统计信息自动选择驱动表。可通过 EXPLAIN 输出的顺序查看实际驱动表。STRAIGHT_JOIN 可强制指定驱动顺序，但一般不建议干预优化器。

6. 排序与分组优化

排序的两种方式：

  • 索引排序（Index）：利用索引天然有序性，直接从索引树按序读取，Extra 无 Using filesort。
  • 文件排序（filesort）：无法用索引时需要额外排序，分内存排序（sort_buffer）和磁盘排序（归并排序），Extra 显示 Using filesort。

索引排序的生效条件：

  1. ORDER BY 列匹配索引的最左前缀（与 WHERE 共用时需注意）。
  2. WHERE 条件与 ORDER BY 组合满足最左前缀：如 INDEX(a,b,c)，WHERE a=const ORDER BY b,c 可利用索引排序。
  3. 排序方向一致：均 ASC 或均 DESC，混用无法用索引。
  4. 覆盖索引或表中仅排序涉及的列。

分组与排序的相似性：
GROUP BY 底层也依赖排序（或利用 Loose Index Scan）。GROUP BY 与 ORDER BY 的优化策略基本一致：

  • 为 GROUP BY 列建立联合索引。
  • 用 WHERE 替代 HAVING 做过滤，HAVING 在分组之后执行，无法用到索引。

filesort 优化：

  • 增大 sort_buffer_size，让更多排序在内存完成。
  • max_length_for_sort_data：控制排序时单行数据大小，较小值使用”双路排序”（只排序排序列和主键，再回表），较大值使用”单路排序”（取全字段排序）。需要根据场景调整。
7. 查询成本计算

MySQL 优化器基于 成本模型 选择执行计划，计算的是 IO 成本和 CPU 成本的加权总和。

成本估算因子：

  • IO 成本：从磁盘读取一页数据的成本，默认 1.0。
  • CPU 成本：处理一行数据的成本，默认 0.2。
  • 索引 dives：对于范围查询，优化器会探测索引页面估算行数（index dive）。

查看查询成本：

输出中 rows_estimation 给出预估行数，considered_execution_plans 展示每个备选方案的成本。优化器会选择总成本最低的方案。

统计信息的重要性：
优化器依赖 innodb_stats 统计数据（页面采样估算）。统计信息不准会导致选错索引。

常见选错索引的原因：

  • 统计信息过时（ANALYZE TABLE 修复）。
  • 成本计算不准确，优化器高估了全表扫描的代价。
  • 优化器倾向于使用选择性高的列建索引，但实际数据倾斜严重。

强制使用索引：
FORCE INDEX(index_name) 可强制使用某索引，但仅用于临时验证，不建议在生产环境硬编码。

长事务持有的旧版本数据导致 Undo 膨胀，聚簇索引叶子节点链式存放多个版本，变相增加扫描开销。优化长查询、及时提交/回滚事务是索引优化的重要辅助手段。

日常索引优化清单：

  1. 定期抓取慢查询日志，分析 top SQL。
  2. 用 EXPLAIN 验证 type 至少为 range，避免 ALL 和 index。
  3. 检查 Extra 中是否存在 Using filesort / Using temporary。
  4. 评估联合索引是否满足最左前缀，是否可优化为覆盖索引。
  5. 关注 rows 与实际返回行数的差距——差距大说明索引过滤效果差。
  6. 定期 ANALYZE TABLE 更新统计信息。
  7. 删除冗余和长期不用的索引（写入性能有代价）。
