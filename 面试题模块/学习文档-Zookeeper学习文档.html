Zookeeper 面试学习文档

Zookeeper = 分布式陪审团。3~5 位法官（节点），过半同意才算数。首席法官（Leader）挂了就重选，选出来之前法庭暂停。ZooKeeper 帮所有分布式系统解决共识问题。

整理日期：2026-06-26

1. Zookeeper 是什么？解决什么问题？

1.1 核心问题

分布式系统的共识四难：

1. 选主（Leader Election）—— 多个节点谁干活？
2. 服务注册 —— 节点 A 说在线，节点 B 说挂了，信谁？
3. 配置同步 —— 配置文件改了怎么通知所有节点？
4. 数据一致性 —— 多节点读同一份数据，怎么保证结果相同？

1.2 技术定义

ZooKeeper = 开源的分布式协调服务，三大能力：

能力 描述 典型用途
数据存储 树形命名空间，类文件系统 配置、元数据
通知机制 Watcher 订阅数据变化 服务发现、动态配置
一致性保证 ZAB 协议保证副本一致 选主、分布式锁

1.3 ZK 不适合做什么

不要做 适合做
存大数据（节点限 1MB，推荐 < 1KB） 存元数据、配置、服务地址
做消息队列（存储量有限） 做服务注册与发现
做数据库（强一致但写性能低） 做分布式锁、选主

面试话术："Zookeeper 做协调不做存储。存数据用数据库，做队列用 MQ，ZooKeeper 只管让分布式系统达成共识。"

2. 数据模型——类文件系统的树

2.1 树结构

ZK 的数据模型 = 类文件系统的树，每个 ZNode 既能存数据又能有子节点。

/ (根节点)
├── /services              ← 持久节点
│   ├── /order-service     ← 持久节点
│   │   ├── /node-1        ← 临时节点（Provider 在线）
│   │   └── /node-2        ← 临时节点（Provider 在线）
│   └── /user-service
├── /config                ← 持久节点
│   └── /db-config         ← 持久节点
└── /locks                 ← 持久节点
    └── /order-lock        ← 临时顺序节点

2.2 四种节点类型

类型 行为 典型用途
持久节点 创建后一直存在，除非主动删除 存配置、元数据
持久顺序节点 名字自动加递增序号 分布式锁排队
临时节点 客户端断连自动删除 服务注册
临时顺序节点 临时 + 自动编号 分布式锁、选主

2.3 关键限制

  • 每个 ZNode 默认最大 1MB，推荐 < 1KB
  • ZNode 更新是整个覆盖（不可 append）
  • 所有数据存储在内存中

面试话术："ZK 的数据全在内存里，单节点建议 < 1KB。定位是『存地址的通讯录』不是『存档案的档案馆』。"

3. ZAB 协议——分布式一致性的核心

3.1 什么是 ZAB？

ZAB（ZooKeeper Atomic Broadcast）= ZK 内部的副本一致性协议。核心：过半即可提交，不要求全票。ZK 集群推荐奇数台（3/5/7），容忍 (N-1)/2 台宕机。

3.2 ZAB 协议完整流程


                 ZAB 协议 —— 两阶段流程
    ====================================================

    ┌──────────────────────────────────────────────────────┐

    │                                                      │

    └──────────────────┬───────────────────────────────────┘
                       │

    │                  Phase 2: 消息广播                     │

    │  Client 写请求                                        │

    │       │                                              │

    │  Follower 收到 Proposal:                              │
    │    1. 写入事务日志 (txn log)                           │
    │    2. 回复 ACK 给 Leader                              │
    │       │                                              │
    │       ▼                                              │
    │  Leader 统计 ACK 数量:                                │
    │    · 过半 ACK → 本地 Commit                           │

    关键规则:
    · 过半原则: 无论选主还是提交，都需要 > N/2 票
    · 顺序性: 所有 Proposal 按 zxid 严格递增
    · 原子性: 一个 Proposal 要么在所有节点成功，要么都不成功

3.3 ZAB vs Raft

维度 ZAB Raft
选主依据 ZXID（日志新旧） Term（任期先后）
消息方向 Leader → 所有 Follower Leader → 所有 Follower
主要差异 崩溃恢复时保证已提交提案不丢 选主更严格，日志复制更清晰

3.4 为什么 ZK 选 CP 不是 AP？

ZK = CP 系统:
宁可短暂不可用，也不让数据不一致。

网络分区示例 (5节点集群):
  分区 A（2 节点）→ 不够过半 → 拒绝对外服务
  分区 B（3 节点）→ 过半 → 正常提供服务

结论: 局部不可用 → 数据绝对一致 ✅

面试话术："ZAB 的灵魂是过半原则。3 台挂 1 台正常，5 台挂 2 台正常；再多就整体不可用——CP 系统的典型特征，用可用性换一致性。"

4. Leader 选举——怎么选出 Leader？

4.1 选举流程图


              Leader 选举 —— 完整流程（3 节点为例）
    =========================================================

    初始状态: 3 节点同时启动，均为 LOOKING 状态

    Node1 (myid=1, zxid=100)   Node2 (myid=2, zxid=200)   Node3 (myid=3, zxid=100)

         │ 投自己(1,100)              │ 投自己(2,200)              │ 投自己(3,100)
         ▼                            ▼                            ▼
    ┌─────────┐                 ┌─────────┐                 ┌─────────┐
    │ 广播投票 │                 │ 广播投票 │                 │ 广播投票 │
    └────┬────┘                 └────┬────┘                 └────┬────┘
         │                            │                            │
         └────────────────────────────┼────────────────────────────┘
                                      │
                                      ▼
    ┌──────────────────────────────────────────────────────────────┐
    │                      交换投票结果                             │
    │                                                              │
    │  Node1 收到 Node2 的票 (2,200):                              │
    │    100 ＜ 200 → Node2 zxid 更大 → Node1 改投 Node2           │
    │                                                              │
    │  Node3 收到 Node2 的票 (2,200):                              │
    │    100 ＜ 200 → Node2 zxid 更大 → Node3 改投 Node2           │
    │                                                              │
    │  Node2 收到 Node1 和 Node3 的票:                             │
    │    保持投自己                                                  │
    └──────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
    ┌──────────────────────────────────────────────────────────────┐
    │                      计票结果                                │
    │                                                              │
    │  Node2 获得: 自己 + Node1 + Node3 = 3 票                     │
    │  3 票 ＞ 3/2 = 1.5（过半！）                                  │
    │                                                              │
    │  → Node2 当选 Leader (LEADING)                               │
    │  → Node1, Node3 变为 Follower (FOLLOWING)                    │
    └──────────────────────────────────────────────────────────────┘

    选举规则:
    · 先比 zxid: 大的当选（数据最新不丢失）
    · zxid 相同比 myid: 打破平局
    · 必须 ＞ N/2 票才能当选

4.2 选主规则

先比 zxid（事务 ID），再比 myid（节点编号）

  • zxid 大的当选：zxid 大 = 数据最新，选它保证最新数据不丢失
  • zxid 相同比 myid：myid 只用于打破平局

4.3 为什么集群推荐奇数台？

集群大小 容忍宕机 说明
3 台 1 台 2 台 = 过半，正常
4 台 1 台 3 台 = 过半正常，但 2vs2 平局时无法选主
5 台 2 台 3 台 = 过半，正常

3 台和 4 台一样都只能挂 1 台，4 台还多了平局风险。所以奇数台省钱又安全。

面试话术："过半原则决定 ZK 集群推荐奇数台。3 台和 4 台的容错能力一样（都只能挂 1 台），4 台多了一台开销还有平局风险。生产上 3 台起步，规模大了上 5 台或 7 台。"

5. Watcher 机制——发布/订阅

5.1 工作原理

Watcher = 订阅推送，但只通知一次——每次触发后自动销毁，需要重新注册。

生命周期:
  Client 注册 Watcher → getData(path, watcher)
      ↓
  ZNode 数据变化 → ZK Server 通知 Client
      ↓
  Watcher 触发 → 自动销毁（关键！）
      ↓
  Client 在回调中重新注册 Watcher

5.2 三大坑

# 坑 说明 解决
1 一次性触发 触发后自动销毁，忘记重注册 = 丢事件 回调里重新注册
2 串行通知 同一 Client 的 Watcher 串行处理，一个慢的全堵 Watcher 里不做耗时操作
3 先通知后读 收到通知后去读，数据可能又变了 业务层做好幂等

5.3 正确用法

// Watcher 正确使用：回调里重新注册
Watcher watcher = event -> {
    if (event.getType() == EventType.NodeDataChanged) {
        byte[] newData = zk.getData(path, false, null);
        zk.getData(path, this, null);  // 关键：重新注册
    }
};

面试话术："Watcher 最大坑是一次性触发——必须在回调里重新注册。生产上永远用 Curator 的 NodeCache/TreeCache，它们内部自动处理反复注册。"

6. 会话机制——门禁卡制度

6.1 Session 生命周期

Session = ZK 给客户端的"门禁卡"，过期就自动清理临时节点。

流程:
  Client 连接 → Server 分配 SessionID + Timeout
      ↓
  Client 定期心跳（ping）
      ↓
  Server 在 timeout/2 内未收到心跳 → Session 过期
      ↓
  该 Client 创建的临时节点全部自动删除
      ↓
  其他 Client 的 Watcher 收到子节点变化事件

6.2 临时节点 vs 持久节点

类型 生命周期 子节点 典型用途
临时节点 跟随 Session，断连自动删除 不能有子节点 服务注册、分布式锁
持久节点 永远存在（除非主动删） 可以有 配置、元数据目录

临时节点不能有子节点：父节点断连后子节点变成"孤儿"，不可管理。

7. 分布式锁——公平排队的实现

7.1 一句话实现

// Curator 一句话实现分布式锁
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");

lock.acquire();     // 获取锁（阻塞直到拿到）
processOrder();
lock.release();     // 释放锁

    │    → Client B 拿锁                                       │

    │  优势: 临时节点保证锁不会"死锁"                           │
    └──────────────────────────────────────────────────────────┘

7.3 羊群效应

错误做法: 所有等待者 watch /lock 子节点变化
  → /lock 变更 → 通知所有人 → 全部抢锁 → 惊群

正确做法: 只 watch 前一个节点
  → seq-0001 释放 → 只通知 seq-0002 → 链式通知，无惊群

面试话术："ZK 分布式锁的核心：临时顺序节点 + watch 前一个节点。这保证公平性（排队拿锁）和解决羊群效应（链式通知）。这是 ZK 锁相比 Redis 锁最大的设计优势。"

8. 脑裂问题——过半机制根治

8.1 什么是脑裂？

网络分区导致集群分裂成两个子集群，各自选出 Leader，互相认为对方已死。

脑裂场景: 5 节点集群，ZK1/2 和 ZK3/4/5 网络不通

  分区 A（ZK1, ZK2）:              分区 B（ZK3, ZK4, ZK5）:
    2 票 ＜ 3 (不过半)               3 票 ≥ 3 (过半！)
    无法选主                         正常选出 Leader

结论: 通过过半机制，两个分区不可能同时选出 Leader

8.2 ZK 的解决方案

机制 作用
过半选举 票数 < N/2+1 无法当选 Leader
ZXID 比较 优先选数据最新的节点
Fencing Token 每次选举 epoch+1，旧 Leader 指令被拒绝

面试话术："ZK 靠过半选举根除脑裂——任何时刻最多只有一个分区有过半票数，不可能出现两个 Leader。代价是：如果集群只剩不到一半节点，整体不可用。这是用可用性换一致性。"

9. ZK vs Nacos——注册中心怎么选？

9.1 功能对比

维度 Zookeeper Nacos
一致性 CP（强一致，ZAB 协议） AP 为主（也支持 CP）
健康检查 临时节点 + 会话超时 心跳保活
大规模 Watch 机制大集群性能差 支持百万级实例
功能 仅服务发现 服务发现 + 配置中心一体化

9.2 架构差异

ZK（CP）：
  → Leader 挂了 → 重新选举 → 期间不可写
  → 必须过半同意才能写

Nacos（AP）：
  → 一个节点挂了 → 其余继续工作 → 最终一致
  → 各记各的，定期同步

9.3 选型建议

已有 ZK 且稳定       → 继续用，别为换而换
新项目               → 直接 Nacos
大规模集群           → Nacos（ZK Watch 性能跟不上）
服务发现 + 配置中心  → Nacos 一体化

Nacos 的巧妙设计：AP 做服务发现（不能因选主发现不了服务），CP 做配置中心（配置绝对不能错）。同一系统对不同的数据用不同一致性策略。

10. ZK vs Redis——分布式锁怎么选？

维度 ZK 锁 Redis 锁
公平性 公平锁（排队拿锁） 非公平锁（SETNX 抢锁）
自动释放 会话断开自动删临时节点 超时自动过期
性能 低（ZAB 协议开销） 高（纯内存操作）
可靠性 高（强一致） 中（ap 模式，脑裂可能丢锁）
使用复杂度 简单（Curator 封装） 中等（Redisson 封装）

选型决策：

公平性要求高、锁持有时间长  → ZK 锁 (Curator InterProcessMutex)
高并发、短时间持锁           → Redis 锁 (Redisson)
不能容忍锁丢失              → ZK 锁
性能瓶颈在锁                → Redis 锁

11. Curator——ZK 客户端最佳实践

11.1 为什么用 Curator 而不是原生 ZK？

// 原生 ZK：样板代码多，Watcher 需手动重新注册
zk.getData(path, event -> {
    zk.getData(path, this, null);  // 忘了就丢事件
}, null);

// Curator：一行搞定，内部自动重新注册
NodeCache cache = new NodeCache(client, path);

});
cache.start();

12. 高频面试题

12.1 基础篇

1. Zookeeper 是什么？

分布式协调服务。解决：选主、服务注册、配置同步。核心：ZAB 协议保证强一致，树形 ZNode 存数据，Watcher 实现发布/订阅。

2. ZK 的节点类型？

四种：持久节点（配置/元数据）、持久顺序节点（锁排队）、临时节点（服务注册，断连自动删）、临时顺序节点（分布式锁/选主）。记住：临时节点没有子节点，跟随 Session 生命周期。

3. ZAB 协议的核心流程？

两阶段：Leader 选举 + 消息广播。Leader 收到写请求 → Proposal 发给 Follower → Follower 写日志后 ACK → 过半 ACK → Leader Commit → 通知 Follower Commit。过半原则是核心。

4. Leader 选举规则？

先比 zxid（大的当选，数据最新），再比 myid（打破平局）。获得过半票数当选。推荐奇数台（3/5/7）。

12.2 进阶篇

5. Watcher 有哪些坑？

三个坑：一次性触发（必须回调里重注册）、串行通知（一个慢的全堵）、先通知后读（数据可能又变了）。最佳实践：用 Curator 的 NodeCache/TreeCache。

6. Session 过期的影响？

该 Client 创建的所有临时节点自动删除。服务注册信息 → 服务下架；分布式锁节点 → 锁自动释放，下一个等待者拿到。

7. ZK 分布式锁原理？如何解决羊群效应？

临时顺序节点 + watch 前一个节点 = 公平锁 + 链式通知。每个 Client 在 /lock 下创建临时顺序节点，序号最小的拿锁，其他 watch 前一个。释放时只通知下一个——链式传递，无惊群。

8. ZK 集群脑裂怎么解决？为什么推荐奇数台？

过半选举：票数 < N/2+1 不能当选。任何时刻最多一个分区有过半票数，不会出现两个 Leader。奇数台：3 台和 4 台容错一样（都只挂 1 台），4 台多了平局风险。

9. ZK 和 Nacos 的区别？

ZK 是 CP（强一致，选主期间不可用），Nacos 是 AP（最终一致，高可用）。新项目推荐 Nacos：服务发现用 AP，配置中心用 CP，一套系统两套一致性策略。

10. ZK 锁 vs Redis 锁？

ZK 锁是公平锁（排队拿锁，靠临时顺序节点），Redis 锁是非公平锁（SETNX 抢锁）。ZK 锁更可靠（会话断连自动释放），性能较低。公平性要求高、锁持有时间长 → ZK；高并发、短持锁 → Redis。

12.3 源码篇

11. ZK 为什么不适合大规模服务注册？

Watch 机制在大集群下性能差。每有 Provider 上下线，ZK 触发所有订阅者的 Watcher。1000 服务 x 1000 实例 = 百万级推送风暴。Nacos 用 Pull + 长轮询避免此问题。

12. InterProcessMutex 底层实现？

在 /locks/lock-name 下创建临时顺序节点，检查自己是否最小：是 → 拿锁；不是 → watch 前一个节点。前一个释放（删除）时，ZK 通知它 → 再检查自己是否最小 → 是则拿锁。

13. 如何保证 ZK 分布式锁可重入？

Curator InterProcessMutex 用 ConcurrentHashMap 记录当前线程锁持有次数。同一线程多次 acquire() 不阻塞，需同样次数 release() 才真正释放。务必在 finally 里调用 release()。

总结：Zookeeper 面试核心四块——ZAB 协议（过半原则 + Leader 选举）、数据模型（持久/临时/顺序节点 + Session）、Watcher 机制（一次性触发 + Curator 最佳实践）、分布式锁（临时顺序节点 + 公平锁 + 避免羊群效应）。理解这四块，面试稳了。
