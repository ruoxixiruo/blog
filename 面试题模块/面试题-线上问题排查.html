线上问题排查

1. CPU 飙高怎么排查?

# 1. 找到 CPU 最高的 Java 进程
top -c
# 2. 找到该进程中 CPU 最高的线程(TID)
top -Hp <pid>
# 3. 线程 ID 转 16 进制
printf "%x\n" <tid>
# 4. 打印线程堆栈,根据 nid= 匹配定位代码行
jstack <pid> | grep -A 30 <hex_tid>

定位思路:多次 jstack 对比,看哪个方法一直在执行,基本就能定位到问题代码。

排查链路:

top -c → 找到 Java 进程 (PID=12345)
         │
         ▼
top -Hp 12345 → 找到线程 (TID=12388, CPU=95%)
         │
         ▼
printf "%x\n" 12388 → 0x3064
         │
         ▼
jstack 12345 | grep -A 30 0x3064 → 定位到具体代码行

常见原因与修复:

原因 现象 修复
死循环 某个线程 CPU 一直 100% 修代码
频繁 GC jstat -gcutil 显示 Full GC 频繁 查内存泄漏或调大堆
正则回溯 复杂正则 + 恶性输入 简化正则或加超时
JSON 序列化 大对象频繁序列化 优化对象或用更快库
批量运算 大量计算未异步化 拆分或异步

即时止损:限流、重启、回滚。根治:定位代码优化算法。

扩展:top -Hp 看到的是内核级线程,Java 线程和内核线程是一一对应的(Thread::start → native → pthread_create)。另外推荐 arthas 的 thread -n 3 命令--一键找出 CPU 最高的 3 个线程并打印堆栈,比手动 jstack 方便得多。

2. 内存泄漏怎么排查?

  1. jmap -dump:live,format=b,file=heap.bin PID 导出堆转储
  2. 用 MAT / JProfiler 分析 heap dump
  3. 看 Histogram(按类统计对象数),找数量异常多的对象
  4. 追踪 GC Root 路径,找到谁持有引用导致无法回收
排查思路:

堆内存持续增长 → Full GC 后也不降
         │
         ▼
jmap dump 堆文件
         │
         ▼
MAT 分析:
  ├── Leak Suspects(自动检测泄漏嫌疑)
  ├── Histogram(看哪个类对象数异常多)
  └── Merge Shortest Paths to GC Roots(找到谁在持有引用)

常见原因:ThreadLocal 没 remove、静态集合一直 add 不清、连接/流没关。

扩展:生产环境 jmap -dump 会触发 STW(Stop The World),大堆可能停顿几十秒。建议加 -XX:+HeapDumpOnOutOfMemoryError 参数,OOM 时自动 dump,不额外影响线上。另 arthas 的 heapdump 命令也一样能 dump。分析时先用 MAT 的 Leak Suspects 自动报表,它能直接告诉你"可能是 XXX 类泄漏了"。

3. 数据库连接池耗尽怎么排查?

  1. 看连接池监控(Druid/HikariCP 都自带),当前活跃连接数是否打满
  2. 查慢 SQL 日志,有没有 SQL 执行时间过长阻塞了连接
  3. jstack 看线程状态,大量线程 WAITING 在拿连接 → 连接池不够
  4. 检查事务是否有没提交/没回滚的(连接没释放)
连接池耗尽排查链:

现象:接口报错 "Cannot get connection"
         │
         ▼
看连接池监控 → 活跃连接 = 最大连接数(打满)
         │
         ▼
为什么连接不释放?
  ├── 慢 SQL 阻塞?(看慢查询日志)
  ├── 事务忘了提交/回滚?(查代码 + DB processlist)
  ├── 连接池配置太小?(对比平时 QPS 和连接数)
  └── 流量突然暴涨?(看 QPS 监控)

扩展:HikariCP 的连接池监控可以通过 /actuator/health 查看(配合 Spring Boot Actuator),也可以直接开启 HikariCP 的 JMX 监控。Druid 自带内置监控页面,/druid/datasource.html 可以实时看到活跃连接数、等待线程数、SQL 执行统计。

4. 死锁怎么排查?

MySQL 死锁:

SHOW ENGINE INNODB STATUS;

看 LATEST DETECTED DEADLOCK 部分,它会画出事务 1 等什么锁、事务 2 等什么锁。

死锁示意图:

事务 A:拿锁1 → 等锁2                  事务 B:拿锁2 → 等锁1
                  │                                    │
                  └──────── 互相等待 ← 死锁 ────────────┘

Java 死锁:

jstack PID | grep "deadlock"

jstack 能自动检测死锁,输出中会明确标注 Found one Java-level deadlock。

扩展:MySQL 死锁无法完全避免(InnoDB 自动检测并回滚一个事务来打破死锁),关键是业务能重试。另外减小事务范围(锁持有时间短)、固定加锁顺序(所有事务都按 A→B 的顺序加锁)能大幅降低死锁概率。

5. 接口响应突然从 50ms 涨到 3s,怎么排查?

分层排查--从外到内定位边界:

  1. 网络层:ping / curl -w 测试网络延迟和 DNS 解析时间
  2. Nginx/网关层:access log 看 $request_time 和 $upstream_response_time,确认是上游慢还是网关慢
  3. 应用层:APM(SkyWalking/Pinpoint)看调用链路,找到耗时最高的 span;打日志记录每个步骤耗时
  4. 中间件层:
  5. 数据库:SHOW PROCESSLIST 看是否有慢查询、锁等待;EXPLAIN 分析当前 SQL
  6. Redis:slowlog get 100 查看慢命令,检查是否有 big key(hgetall 几万条)
  7. MQ:是否积压导致消费延迟
  8. 下游服务:是否有耗时异常
  9. 排查 JVM:jstat -gcutil 看是否 Full GC 导致 STW 停顿
分层排查思路:

慢在哪?
    │
    ├── 网络慢? → ping / traceroute / curl -w
    │
    ├── Nginx 慢? → access log 对比 request_time vs upstream_response_time
    │
    ├── 应用慢? → APM 链路追踪 / 日志打点
    │       │
    │       ├── CPU 飙高? → 转"CPU 飙高排查"
    │       ├── 内存满? → GC 日志 / jstat
    │       └── 线程阻塞? → jstack
    │
    ├── DB 慢? → 慢查询日志 / EXPLAIN / processlist
    │
    ├── Redis 慢? → slowlog / big key 扫描
    │
    └── 下游慢? → APM 看下游调用耗时

扩展:SkyWalking 这类 APM 工具是查接口变慢的利器--它能把一次请求经过的所有服务、数据库、Redis、MQ 的耗时画成调用链,一眼看到是谁拖了后腿。如果没有 APM,在代码的关键步骤打耗时日志(long start = System.currentTimeMillis()),然后 grep 每条步骤的时间差,虽然土但管用。

常见元凶:SQL 突然不走索引(统计信息变化导致选错计划)、大事务持锁阻塞、Redis big key 阻塞、第三方接口超时、Full GC 停顿。

7. OOM 有哪些类型?分别怎么排查?

类型 报错信息 原因 排查思路
堆溢出 java.lang.OutOfMemoryError: Java heap space 对象太多,堆不够用 jmap -dump + MAT 分析
元空间溢出 OOM: Metaspace 动态生成的类太多(如 CGLIB 代理) 调大 -XX:MaxMetaspaceSize
直接内存溢出 OOM: Direct buffer memory NIO 堆外内存没释放 检查 ByteBuffer 是否忘调 Cleaner.clean()
线程过多 OOM: unable to create new native thread 线程数超 OS 限制 ulimit -u + 排查线程池 
堆溢出最常见:

1. jmap -dump → MAT 分析 → Histogram 看什么类对象数异常
2. 找到创建这些对象的代码路径
3. 判断是"需要这么多"(堆配置太小)还是"不该这么多"(内存泄漏)

关键:`-XX:+HeapDumpOnOutOfMemoryError` 参数在 OOM 时自动 dump

扩展:元空间溢出的典型场景--大量使用动态代理(CGLIB、动态生成类)、Groovy 脚本热加载未缓存。JDK 8 默认元空间不设上限(用多少占多少),生产环境必须设 -XX:MaxMetaspaceSize=256m。

8. Arthas 常用的诊断命令?

命令 作用 示例
dashboard 实时面板(CPU、内存、GC、线程) 一目了然看系统状态
thread 查看线程堆栈 thread -n 3(CPU 最高的 3 个线程)
watch 观察方法调用的入参和返回值 watch com.xxx.UserService getUser '{params,returnObj}'
trace 追踪方法内部调用,统计每步耗时 trace com.xxx.UserService getUser
jad 反编译类源码 jad --source-only com.xxx.UserService
stack 输出方法的调用路径 stack com.xxx.UserService getUser
logger 动态修改日志级别(不需重启!) logger --name com.xxx --level debug 
trace 命令示例--揪出慢在哪:

$ trace com.xxx.OrderService createOrder
+---[100.5ms] OrderService:createOrder()
    +---[80.3ms] checkStock()          ← 主要耗时在这里
    +---[15.2ms] insertOrder()
    +---[3.1ms] sendNotify()
    └---[1.9ms] return

扩展:Arthas 最大的优势是不重启、不修改代码、不打断点就能诊断线上问题。watch 可以加条件过滤(如只观察特定用户 ID 的调用),trace 会高亮显示耗时超过阈值的方法。Arthas 的底层原理是 Java Instrumentation API + ASM 字节码增强--运行时动态注入代码,用完就卸载。

9. 慢 SQL 怎么排查?

第一步:找到慢 SQL

-- MySQL 慢查询日志
-- my.cnf: slow_query_log=1, long_query_time=1
-- 或在 Druid 监控页面直接看

第二步:分析执行计划

EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 'paid';

-- 关键字段:
-- type: ALL(全表扫描)→index→range→ref→const(最快)
-- key: 用到的索引名(NULL = 没走索引)
-- rows: 预估扫描行数
-- Extra: Using filesort(需排序) / Using temporary(需临时表) → 需要优化

第三步:判断并修复

type=ALL, rows 很大 → 没走索引 → 加索引
key 有值但 type=ALL → 索引失效了 → 检查失效原因(函数/隐式转换/OR等)
Extra=Using filesort → 排序字段没索引 → 加复合索引覆盖排序字段

扩展:慢查询不一定是 SQL 的问题--也可能是统计信息过期导致 MySQL 选错了执行计划。ANALYZE TABLE 更新统计信息。大表加索引时注意用 pt-online-schema-change(Percona Toolkit)在线加,避免锁表。

10. 磁盘空间满了怎么排查?

# 1 确认:哪个分区满了?
df -h
# /dev/sda1  use% 95%  ← 找出满的分区

# 2 定位:哪个目录占用最多?
du -sh /* 2>/dev/null | sort -rh | head -10
# 一层层往下钻:du -sh /var/* → du -sh /var/log/*

# 3 特殊:删了大文件但空间没释放
lsof | grep deleted    # 找到被进程持有的已删除文件
# 原因:进程还拿着文件句柄,空间没真正释放
# 解决:重启对应进程 或 echo "" > /proc/PID/fd/N

排查链路:

df -h 看哪个分区满了
    │
    ├── du -sh /* 逐层定位大目录
    │       │
    │       └── 找到大文件/大目录
    │           要么清理,要么确认是否需要
    │
    └── lsof | grep deleted → 已删除但未释放
        重启进程释放空间

扩展:最常见的磁盘杀手--1 日志文件(没做 logrotate,一个日志文件几十 GB);2 Docker 镜像/Volume(docker system prune -a 清理);3 Core Dump 文件(JVM 崩溃留下的 dump 文件)。生产环境配置 logrotate 和监控告警(磁盘使用率 > 80% 告警)是基本功。

11. CPU/内存正常但响应变慢,怎么排查?

IO 瓶颈(iostat)、网络带宽(sar -n DEV)、锁竞争(jstack)、连接池耗尽、外部依赖超时、GC STW。推荐自上而下排查法。

自上而下排查法(就像查不响的电视机--从电源开始一层层排查):

1 看网络层
   ping / telnet 目标端口 → 网络通不通?
   不通 → 防火墙/安全组/路由问题

2 看依赖层
   数据库连接池有没有耗尽?(HikariCP 的 active 指标)
   Redis 响应超时?(慢查询日志 SLOWLOG GET 10)
   下游服务是否超时?(看调用链中的耗时分布)

3 看应用层
   jstack 看线程都在干什么 → 大量线程 BLOCKED?→ 锁竞争
   数据库连接池 Active=Max?→ 连接池不够或慢 SQL 占用
   GC 日志 → STW 时间是否过长?

4 看操作系统层
   iostat -x 1 → await 很高?→ 磁盘 IO 瓶颈
   sar -n DEV 1 → 网络带宽打满?

常见非 CPU/内存瓶颈及特征:

原因 特征 排查命令
数据库连接池耗尽 线程全在等数据库连接 jstack 看到 HikariPool$PoolEntryCreator
Redis 慢查询 请求耗时尖刺 SLOWLOG GET 10
下游服务超时 调用链中某下游 P99 很高 SkyWalking/Pinpoint 链路追踪
锁竞争 大量线程 BLOCKED jstack | grep BLOCKED
GC STW 周期性的所有请求变慢 jstat -gcutil 看 GC pauses
磁盘 IO 瓶颈 await 很高(>10ms) iostat -x 1
网络带宽打满 流量峰值错峰 sar -n DEV 1

12. 内存泄漏有哪些常见场景?如何避免?

内存泄漏 = 不用的东西占着抽屉不扔--对象已经不用了,但 GC Roots 还间接引用着它,GC 无法回收。时间长了内存慢慢涨,最终 OOM。

Java 7 大内存泄漏场景(按出现频率排序):

1 静态集合类(罪魁祸首 No.1)
   static Map<String, Object> cache = new ConcurrentHashMap<>();
   cache.put(key, data);  // 一直往里塞,从来不删

   为什么泄漏:static 变量是 GC Root → 它引用的所有东西永不被回收
   解决:
   - 缓存要有上限(Guava Cache / Caffeine,设 maxSize + TTL)
   - 不用缓存了手动 clear()
   - 或者用 WeakHashMap(key 没外部引用时自动清除)

2 ThreadLocal 没 remove(线程池场景)
   public static ThreadLocal<UserInfo> userHolder = new ThreadLocal<>();
   userHolder.set(userInfo);
   // 用完了没调 remove()!

   为什么泄漏:线程池的线程是复用的,
              ThreadLocalMap 的 key 是弱引用但 value 是强引用
              线程不死 → ThreadLocalMap 不回收 → value 一直在
   解决:finally { userHolder.remove(); }

3 连接没关(数据库连接、HttpClient、文件流)
   解决:Java 7+ try-with-resources 自动关闭
   try (Connection conn = dataSource.getConnection()) { ... }

4 监听器/回调没注销
   eventBus.register(listener);  // 注册了
   // 对象不用了,但没调 eventBus.unregister(listener);
   解决:组件销毁时(@PreDestroy / destroy() )反注册

5 单例持有短生命周期对象
   @Service
   public class OrderService {
       private User currentUser;  // 单例持有 request 级别的对象!
   }
   解决:用 ThreadLocal 传递 request 级别的数据,不要存为单例的成员变量

6 内部类(匿名类/非静态内部类)持有外部类引用
   class Outer {
       void doSomething() {
           new Thread(() -> { ... }).start();  // 匿名内部类隐式持有 Outer.this
       }
   }
   解决:如果不需要外部引用,声明为 static 内部类

7 本地缓存无上限
   ConcurrentHashMap<String, byte[]> cache = new ConcurrentHashMap<>();
   // 疯狂 put,从不 evict → 最终 OOM
   解决:用 Caffeine(Window TinyLFU 算法)+ 设 maxSize

Python 4 大内存泄漏场景:

# 1 循环引用(虽然有 GC,但引用计数归零才立即回收)
class Node:
    def __init__(self):
        self.ref = None
a = Node(); b = Node()
a.ref = b; b.ref = a  # 循环引用!靠标记清除定期回收
# 解决:用 weakref.ref 创建弱引用

# 2 全局变量/类变量不停增长
cache = {}  # 模块级别,永远不删除
cache[key] = value  # 一直加 → 泄漏

# 3 闭包持有大对象
def outer():
    big_data = [0] * 10000000
    def inner():
        return big_data[0]  # big_data 整个被 inner 持有,即使只用一个元素
    return inner

# 4 C 扩展内存泄漏
# 某些 C 扩展库手动管理内存,忘记释放 → 泄漏

扩展:面试中如何说得"不像背的"?--最好结合一个你实际踩过的坑。比如:"我们项目里有个静态 Map 做本地缓存,运营活动期间访问量暴增,Map 里的 key 从几千涨到几百万--内存飙到 95%,触发了告警。后来改成 Caffeine 设了 maxSize + TTL 自动淘汰,内存才稳住了。"如果你没真实经历,至少理解六种场景并准备一两个"能讲出细节"的例子。

13. 线上接口偶发超时报错,但重试又正常,怎么排查?

核心结论:偶发性超时 = 瞬时瓶颈或资源竞争。排查三板斧:

# 1. 看是否有瞬时连接池满
watch -n 1 'netstat -an | grep ESTABLISHED | wc -l'

# 2. 看 TCP 重传率(网络瞬时抖动)
sar -n EDEV 1 5  # 看 %retrans

# 3. 看 GC 是否偶发长 STW
jstat -gcutil <pid> 1000  # 观察 FGCT/FCTG 是否偶发跳高

最常见原因:(1)下游数据库偶发慢查询导致连接池等待超时;(2)GC 偶发长 STW 暂停应用;(3)网络瞬时抖动丢包重传。根治:加链路追踪(SkyWalking/Zipkin)定位具体是哪层慢,再对症下药。

14. 线上服务突然开始返回 500,但代码没发布,怎么排查?

核心结论:代码没变但出 500 = 外部因素变化。按概率排序排查:

排查优先级:
1. 下游服务挂了/超时 → 看日志里的feign超时/连接拒绝
2. 数据库连接异常 → 看Druid/HikariCP监控面板
3. 配置中心(Nacos)配置被改 → diff 最新配置
4. Redis/MQ 不可达 → 看连接池状态
5. 磁盘满导致写日志失败 → df -h
6. 证书过期(JWT/HTTPS) → 看证书有效时间

# 快速定位500错误
# 1. 看错误日志最近10行
tail -100 /app/logs/error.log | grep -A 5 'Exception'
# 2. 统计最近1小时各类型异常数量
grep 'Exception' /app/logs/error.log | awk '{print $NF}' | sort | uniq -c | sort -rn | head

面试话术:"线上500第一时间不是看代码,而是看日志里有没有下游超时、连接拒绝这类外部依赖问题。我遇到过一次,线上突然大量500,最后发现是Nacos上有个配置被同事在线上环境改了,Redis连接地址写错了。从此以后,所有配置变更必须走CR+审批流程。"

15. 如何做线上故障的应急止血和回滚?

应急止血三板斧:

优先级从高到低:
1. 限流/熔断 → Sentinel 热配置降级(不断服务,只降非核心)
2. 配置降级 → Nacos 动态关闭故障功能开关
3. 版本回滚 → Jenkins/K8s rollback(最彻底但影响最大)

生产回滚规范:

# K8s 滚动回滚
kubectl rollout undo deployment/app-service

# 如果是蓝绿部署,直接切流量
kubectl patch service app-service -p '{"spec":{"selector":{"version":"v1.0-stable"}}}'

# Docker Compose 回滚
 docker-compose up -d app-service:v1.0-stable

面试话术:"止血讲究'快而不慌'。我的原则是:先限流保核心链路,再降级非核心功能,最后才考虑回滚。回滚是最后手段,因为会丢失回滚期间的数据。每次故障必须写复盘报告(5W2H),从流程上防止二次发生。"

16. 如何用 Arthas 在生产环境做在线热修复？

Arthas 热修复三步走：定位 → 修改 → 验证：

# 1. 启动 Arthas
java -jar arthas-boot.jar

# 2. 定位问题：trace 跟踪方法耗时
trace com.example.OrderService createOrder '#cost > 100' --skipJDKMethod

# 3. 重新定义方法（热修复）
redefine /path/to/fixed/OrderService.class

# 或者用 jad + mc + redefine 组合：
# Step A: 反编译当前代码
jad --source-only com.example.OrderService > /tmp/OrderService.java
# Step B: 修改后编译
mc /tmp/OrderService.java -d /tmp/
# Step C: 热加载
redefine /tmp/com/example/OrderService.class

生产热修复注意事项：

场景 建议
方法签名变化 ❌ 不支持热修，需重启
静态变量修改 ⚠️ 需谨慎，可能导致不一致
新增方法 [OK] 支持
删除方法 ❌ 不支持，需重启
构造函数修改 ⚠️ 受限

扩展：ognl 命令可直接修改内存中的对象值（无需发版紧急修配置）；heapdump 生成堆转储文件分析内存；Arthas 3.6+ 支持在线生成火焰图（profiler 命令）。
