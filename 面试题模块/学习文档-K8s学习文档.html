1. Kubernetes 概述

1.1 什么是 Kubernetes

Kubernetes（简称 K8s）是 Google 开源的容器编排平台，用于自动化部署、扩展和管理容器化应用。它是 CNCF（Cloud Native Computing Foundation）的毕业项目，当前业界容器编排的事实标准。

核心职责：将多台服务器聚合成一台"逻辑服务器"，提供声明式 API 管理应用的部署、伸缩、服务发现、负载均衡、滚动更新和自愈。

面试话术：Kubernetes 本质上是一个声明式 + 控制器模式的系统。用户描述"想要什么状态"，控制器不断对比实际状态与期望状态，通过调谐循环（Reconcile Loop）驱动物理状态向期望状态逼近。

1.2 核心优势

特性 说明
服务发现与负载均衡 内置 DNS + Service 抽象，自动分发流量
自动伸缩 HPA（Pod 水平伸缩）、VPA（垂直伸缩）、Cluster Autoscaler
自愈能力 自动重启失败的容器、替换节点故障的 Pod
滚动更新 & 回滚 Deployment 零停机更新，随时回滚到历史版本
存储编排 PV/PVC/StorageClass 动态挂载存储卷
配置管理 ConfigMap & Secret 实现配置与镜像分离
声明式 API YAML 描述期望状态，控制器自动调谐

2. 核心架构

2.1 Control Plane 组件

组件 说明 关键点
kube-apiserver 集群的网关，所有组件通信的中枢 唯一与 etcd 交互的组件；提供 RESTful API；认证/授权/准入控制
etcd 分布式 KV 存储，保存集群全部数据 基于 Raft 一致性协议；需要定期备份；建议 SSD 存储
kube-scheduler 为未调度的 Pod 选择合适的 Node 调度算法：预选（Predicates）+ 优选（Priorities）
kube-controller-manager 运行所有控制器（Deployment/ReplicaSet/Node 等） 控制器模式的核心，约 30+ 个控制器
cloud-controller-manager 云厂商集成（LB/Storage/Route） 可选组件，自建集群不部署

2.2 Worker Node 组件

组件 说明
kubelet 节点代理，负责管理 Pod 的生命周期，向 API Server 注册节点并上报状态
kube-proxy 网络代理，实现 Service 的负载均衡（iptables/IPVS/userspace 模式）
Container Runtime 容器运行时（containerd / CRI-O / Docker），负责拉取镜像、启停容器

2.3 架构通信流程

                     etcd
                       ^
                       | watch / write
                       v
    +----------+    +---------+    +----------+
    | Scheduler+-->|   API   |<---+Controller |
    +----------+   |  Server |    +----------+
         |          +----+----+          ^
    watch|               |               |watch
         v               v               |
    +----------+    +---------+          |
    | kubelet  |<---|  Node   |----------+
    | on Node  |    | Network |
    +----------+    +---------+

    Communication flow:
    1. All components talk ONLY to API Server (no direct peer-to-peer)
    2. kubelet watches API Server for Pod assignments on its Node
    3. Scheduler watches unscheduled Pods, binds them to Nodes
    4. Controller watches resources, ensures desired state

面试话术：K8s 所有组件只与 API Server 通信，不直接交互。API Server 是集群的"总线"，也是唯一读写 etcd 的组件。这种去耦合架构使得任意组件可以独立扩缩。

3. 核心资源对象

3.1 Pod

Pod 是 K8s 最小的可部署单元，封装一个或多个容器。同 Pod 的容器共享网络栈（同一 IP/端口空间）和存储卷（共享 Volume）。

apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "500m"
          memory: "256Mi"

关键特性：

  • Pod 是"逻辑主机"，不是单个进程
  • Sidecar 模式：同一 Pod 放入辅助容器（日志收集、代理等）
  • Pod 是"脆弱的"——应通过 Workload 控制器管理，不要直接创建

3.2 Workload 控制器

控制器 说明 适用场景
Deployment 无状态应用，管理 ReplicaSet Web 服务、API 服务（最常用）
StatefulSet 有状态应用，保持 Pod 身份和存储 数据库、消息队列、ZooKeeper
DaemonSet 每个 Node 运行一个 Pod 日志采集（Fluentd）、监控（Node Exporter）
Job 一次性任务 数据迁移、批处理
CronJob 定时任务 定时备份、清理日志
ReplicaSet 确保指定数量的 Pod 运行 一般不直接使用，被 Deployment 管理 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "200m"
              memory: "256Mi"

3.3 Service

Service 为一组 Pod 提供稳定的网络入口（VIP），实现服务发现和负载均衡。

Service 类型 说明 访问方式
ClusterIP 分配集群内部虚拟 IP 集群内访问（默认）
NodePort 在每个 Node 上暴露端口 集群外访问：<NodeIP>:<NodePort>
LoadBalancer 云厂商 LB 集成 公网访问（需云平台支持）
ExternalName CNAME 到外部域名 访问外部服务 
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: ClusterIP
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80

3.4 Ingress

Ingress 是七层（HTTP/HTTPS）路由，提供域名和路径级别的流量分发。

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /users
            pathType: Prefix
            backend:
              service:
                name: user-service
                port:
                  number: 80
          - path: /orders
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 80
    - host: admin.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: admin-service
                port:
                  number: 80

4. 网络模型

4.1 网络模型规则

K8s 网络模型要求（CNI 规范）：

  1. 所有 Pod 可以不使用 NAT 直接通信（跨 Node 互通）
  2. 所有 Node 可以不使用 NAT 直接访问所有 Pod
  3. Pod 自己看到的 IP 和他人看到的 IP 相同（扁平网络）

4.2 CNI 插件

CNI 插件 网络模式 特点
Flannel VXLAN / host-gw 简单易用，性能一般，不支持 NetworkPolicy
Calico BGP / IPIP 支持 NetworkPolicy，性能好，复杂配置
Cilium eBPF 高性能，支持 L7 策略和服务网格，新兴方案
Weave VXLAN + fast datapath 简单易用，内建 DNS

4.3 Service 通信模型

                    +-----------+
                    |   Client  |
                    +-----+-----+
                          |
                    ClusterIP: 10.0.0.1
                          |
                  +-------v--------+
                  |   kube-proxy   |
                  |  (iptables OR  |
                  |   IPVS)        |
                  +-------+--------+
                          |
             +------------+-------------+
             |            |             |
             v            v             v
         +--------+  +--------+  +--------+
         | Pod A  |  | Pod B  |  | Pod C  |
         | Node-1 |  | Node-2 |  | Node-3 |
         +--------+  +--------+  +--------+

    kube-proxy mode comparison:
      userspace  : userspace proxy (legacy, slow)
      iptables   : kernel-space NAT rules (default, medium)
      ipvs       : kernel-space L4 LB (fast, consistent hash)

5. 调度系统

5.1 调度流程

+----------+    +-----------+    +----------+    +----------+
| Unsched  |    |   Pre-   |    |  Priority|    |  Bind to |
| Pod Watch|-->|  filter   |-->|   Score   |-->|   Node    |
+----------+   (Predicates)    (Priorities)    +----------+

Filter (Predicates):
  - PodFitsResources (CPU/Memory 充足)
  - PodMatchNodeSelector (节点选择器)
  - PodFitsHostPorts (端口不冲突)
  - NoDiskConflict (存储卷不冲突)
  - CheckNodeCondition (节点健康)

Score (Priorities):
  - LeastRequestedPriority (资源利用率低的优先)
  - BalancedResourceAllocation (CPU/内存平衡)
  - ImageLocalityPriority (已有镜像的节点优先)
  - NodeAffinityPriority (亲和性规则)

5.2 调度策略

概念 说明
nodeSelector 最简单的节点选择，匹配 Label
nodeAffinity 节点亲和性，支持 required（硬）和 preferred（软）
podAffinity Pod 亲和性，同拓扑键上靠近部署
podAntiAffinity Pod 反亲和性，同拓扑键上分散部署
Taints & Tolerations 节点打污点，Pod 容忍才能调度

5.3 节点亲和性 / 污点容忍

apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: gpu-type
                operator: In
                values:
                  - "nvidia-a100"
  tolerations:
    - key: "gpu"
      operator: "Exists"
      effect: "NoSchedule"
  containers:
    - name: gpu-container
      image: nvidia/cuda:12.0

7. 安全体系

7.1 RBAC

基于角色的访问控制（RBAC）是 K8s 默认授权模式。

# 创建 ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-sa
---
# 创建 Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "watch", "list"]
---
# 绑定
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
  - kind: ServiceAccount
    name: my-sa
    namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

7.2 Namespace 隔离

Namespace 实现逻辑隔离（非网络隔离），适用于多环境、多团队场景。默认提供四个初始 Namespace：

  • default — 默认命名空间
  • kube-system — 系统组件
  • kube-public — 公共资源（所有用户可读）
  • kube-node-lease — 节点心跳租约

7.3 NetworkPolicy

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api
spec:
  podSelector:
    matchLabels:
      app: api
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - port: 8080

7.4 ServiceAccount

  • 每个 Namespace 自动创建 default ServiceAccount
  • ServiceAccount 关联 Secret（包含 CA 证书和 Token）
  • Token 挂载到 Pod 的 /var/run/secrets/kubernetes.io/serviceaccount/
  • 用于 Pod 与 API Server 的认证

12.2 Pod 排错流程

Pod 状态异常排错：

1. Pending ──> 检查资源不足 / 节点选择器 / PVC 未绑定
   kubectl describe pod <name>
   kubectl get events

2. ImagePullBackOff ──> 检查镜像名/标签 / 仓库认证 / 网络
   kubectl describe pod <name> | grep -A5 Events

3. CrashLoopBackOff ──> 应用启动失败
   kubectl logs <name>
   kubectl logs --previous <name>   # 查看上次重启日志

4. Running 但不通 ──> 检查 Service / NetworkPolicy / 端口
   kubectl exec -it <name> -- curl localhost:<port>
   kubectl port-forward <name> <local>:<remote>

5. Evicted ──> 节点资源不足被驱逐
   kubectl describe node <node> | grep -A5 Conditions

12.3 节点维护（drain/cordon）

# 节点维护流程

kubectl drain <node-name>           # 驱逐 Pod + cordon

# 维护完成后恢复
kubectl uncordon <node-name>        # 恢复调度

# Delete Node
kubectl delete node <node-name>     # 从集群中移除节点

13.2 etcd 高可用

# etcd 集群推荐配置
- 奇数节点（3 或 5），容忍 (N-1)/2 个节点故障
- SSD 存储，推荐 NVMe
- 独立的磁盘 IO，不与 API Server 共享
- 定期快照备份
- 网络延迟 < 10ms（跨 AZ 部署需注意）

# etcd 快照备份
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-snapshot-$(date +%Y%m%d).db

# etcd 快照恢复
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot.db \
  --data-dir=/var/lib/etcd-restored

15. 高频面试题

Q1：Kubernetes 核心组件有哪些？

Control Plane：kube-apiserver（网关）、etcd（存储）、kube-scheduler（调度）、kube-controller-manager（控制器）。
Worker Node：kubelet（节点代理）、kube-proxy（网络代理）、Container Runtime（容器运行时）。

Q2：etcd 在 K8s 中的作用？

集群的唯一数据源，存储所有资源对象的状态。基于 Raft 保证一致性，建议奇数节点部署。只有 API Server 直接与 etcd 交互，其他组件通过 API Server 间接读写。

Q3：Pod 是如何创建的？

1. kubectl apply -f pod.yaml --> API Server
2. API Server 认证/授权/准入 --> 写入 etcd
3. Scheduler 通过 watch 发现未调度 Pod --> 选择 Node --> 回写绑定信息
4. Node 上的 kubelet watch 到 Pod 绑定到本节点
5. kubelet 通知 Container Runtime 拉取镜像并启动容器
6. kubelet 持续上报 Pod 状态给 API Server

Q4：Deployment 如何实现滚动更新？

滚动更新策略：
  maxSurge: 25%       # 可超出期望副本数的最大比例
  maxUnavailable: 25% # 更新中最大不可用比例

流程：
  1. 创建新 ReplicaSet，初始 replicas=0
  2. 渐进增加新 RS 的 replicas
  3. 渐进减少旧 RS 的 replicas
  4. 直到新 RS 完全替换旧 RS

回滚：
  kubectl rollout undo deployment/nginx-deployment
  kubectl rollout history deployment/nginx-deployment

Q5：Service 有哪些类型？

类型 说明
ClusterIP 集群内部虚拟 IP，仅集群内访问
NodePort 在每个节点上暴露端口，外部可访问
LoadBalancer 云厂商负载均衡器（如 CLB/ALB）
ExternalName CNAME 映射到外部域名

Q6：Ingress 和 Service 的区别？

  • Service：四层（L4）负载均衡，基于 IP + 端口，工作在内核空间（iptables/IPVS）
  • Ingress：七层（L7）路由，基于 HTTP 域名、路径，工作在用户空间
  • Ingress 依赖 Ingress Controller（如 Nginx、Traefik）实现
  • 生产中通常 Service + Ingress 配合使用

Q7：CNI 网络模型原理？

K8s 要求所有 Pod 无需 NAT 直接互通。CNI 插件在 Pod 创建时：创建 veth pair（一端在 Pod 内，一端在宿主机网卡），分配 Pod IP，配置路由规则。跨节点通信通过 Overlay（VXLAN）或 BGP 实现。

Q8：PV 和 PVC 是什么关系？

PV 是集群存储资源（管理员预先分配或 StorageClass 动态供给）。PVC 是用户的存储需求声明。PVC 根据存储大小、访问模式、StorageClass 匹配 PV，绑定后 Pod 通过 PVC 挂载使用。绑定是一对一的。

Q9：如何实现蓝绿发布和灰度发布？

# 蓝绿发布 — 两个独立的 Deployment + Service 切换
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-blue  # 当前运行版本
spec:
  replicas: 5
  selector:
    matchLabels:
      app: my-app
      version: blue
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-green  # 新版本，验证后切换
spec:
  replicas: 5
  selector:
    matchLabels:
      app: my-app
      version: green
---
# Service selector 从 blue 切换到 green 完成发布
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector:
    app: my-app
    version: green  # 切换点

# 灰度发布 — Service Mesh 或 Ingress 权重路由
# (通过 Istio VirtualService 或 Nginx Ingress Canary 实现)

Q10：kube-proxy 的三种模式？

模式 原理 特点
userspace 用户态代理监听端口 性能差，已废弃
iptables 内核态 NAT 规则 默认模式，规则多时性能下降
IPVS 内核态 L4 负载均衡 性能最好，支持多种调度算法（rr/wrr/lc等）

学习建议：Kubernetes 学习路径建议：先掌握 Pod/Deployment/Service/Ingress 四大核心资源 -> 理解控制器模式（调谐循环）-> 深入学习网络模型（CNI）和调度器 -> 最后掌握RBAC/存储/监控等运维体系。搭配实际集群操作（建议用 KinD 或 Minikube 本地搭建）加深理解。
