Kubernetes

1. Docker 和虚拟机的区别?

维度 Docker 容器 虚拟机
启动速度 秒级 分钟级
资源占用 MB 级 GB 级
隔离性 宿主机内核共享,弱隔离 完整 OS,强隔离
原理 Namespace(隔开视野)+ Cgroups(限制资源) 硬件虚拟化(Hypervisor)

容器本质上只是宿主机上的一个"特殊进程",不是真的装一个系统。

虚拟机架构:                    Docker 架构:

  App A    App B                App A    App B
  ┌────┐  ┌────┐               ┌────┐  ┌────┐
  │Guest│  │Guest│               │容器 │  │容器 │
  │ OS  │  │ OS  │               └──┬─┘  └──┬─┘
  └──┬─┘  └──┬─┘                  │       │
     │       │                    └───┬───┘
  ┌──┴───────┴──┐                    │
  │ Hypervisor  │              Docker Engine
  └──────┬──────┘                    │
         │                    ┌──────┴──────┐
    Host OS                   │   Host OS   │
         │                    └──────┬──────┘
    Hardware                        │
                                Hardware

扩展:容器的"弱隔离"意味着什么?如果你在容器里用 root 权限跑进程,它实际上在宿主机上就是 root--共享内核意味着内核漏洞会打到所有容器。所以生产环境通常用非 root 用户运行容器、启用 seccomp/AppArmor 加固。真正强隔离场景(多租户)还是得用虚拟机。

2. K8s 是什么?解决什么问题?

K8s 是容器界的总指挥--几百个容器怎么管理?

  • 容器挂了 → 自动重启(自愈)
  • 流量暴涨 → 一条命令扩容(弹性伸缩)
  • 发新版本 → 滚动更新,不停机(零停机部署)
  • 容器之间怎么通信 → 内置服务发现(网络管理)
  • 容器该放哪个机器 → 自动调度(资源调度)
你声明期望状态:"我要 3 个 nginx Pod 一直跑着"

         ┌──────────────┐
         │   K8s 控制面   │  ← 不断对比
         │  期望 vs 实际   │
         └──────┬───────┘
                │ 实际只有 2 个 → 调度 1 个
                │ 挂了 1 个     → 自动重启
                │ 流量涨了      → 自动扩容
                ▼
         ┌──────────────┐
         │   工作节点集群   │
         └──────────────┘

扩展:K8s 的核心思想是声明式 API--你只管说"我要什么",不用一步步教它怎么做。就像打车--你说"去机场"(声明),不用自己挂挡踩油门(命令)。这种范式让系统更简单、更自愈。

3. K8s 核心组件有哪些?

Master(大脑):

组件 作用 类比
API Server 唯一入口,所有操作都通过它 公司前台--所有请求先到这儿
etcd 记忆库,存储所有集群状态 公司的数据库--记录一切
Scheduler 调度员,决定 Pod 放哪个节点 排班表--新任务分给谁
Controller Manager 监工,对比期望状态和实际状态 主管--发现偏差就纠正

Node(手脚):

组件 作用 类比
kubelet 节点总管,管理 Pod 生命周期 每个分公司的负责人
kube-proxy 网络代理,实现 Service 负载均衡 公司的内线总机 
         ┌──────────────────────────┐
         │  Master (控制面)           │
         │  ┌──────────┐ ┌─────────┐ │
         │  │API Server│ │  etcd   │ │
         │  └────┬─────┘ └─────────┘ │
         │  ┌────┴─────┐ ┌─────────┐ │
         │  │Scheduler │ │Control Mgr│ │
         │  └──────────┘ └─────────┘ │
         └────────────┬─────────────┘
                      │
         ┌────────────┼─────────────┐
         │  Node 1    │    Node 2   │
         │  ┌──────┐  │   ┌──────┐  │
         │  │kubelet│ │   │kubelet│ │
         │  │kube-  │ │   │kube-  │ │
         │  │proxy  │ │   │proxy  │ │
         │  └──────┘  │   └──────┘  │
         └────────────┴─────────────┘

扩展:etcd 是 K8s 的"唯一真相来源"(single source of truth)。如果 etcd 崩了,集群就"失忆"了--虽然已有 Pod 还能跑,但不能做任何新操作。所以生产环境 etcd 必须高可用部署(3/5 节点),定期备份。

4. Pod 是什么?

Pod 是 K8s 最小调度单元。一个 Pod 可以放多个容器,共享网络(用 localhost 互访)和存储。

典型用法:主应用容器 + Sidecar 容器(日志采集/代理)。

Pod: "一个共享命运的小团队"

┌─────────────────────────────┐
│           Pod                │
│  ┌──────────┐ ┌──────────┐  │
│  │  App     │ │ Sidecar  │  │
│  │ 容器     │←─→ 容器    │  │  ← localhost 互访
│  └──────────┘ └──────────┘  │
│       共享网络 (同一个 IP)     │
│       共享存储 (同一个 Volume)  │
└─────────────────────────────┘

扩展:K8s 从不直接操作容器,最小单位是 Pod。为什么?因为很多场景需要"绑死在一起"的容器组--比如日志收集 Agent 和业务容器必须生活在一台机器上、用同一个网络。但大多数场景一个 Pod 就一个容器,简单够用。

5. Deployment、Service、Ingress 各做什么?

资源 作用 一句话
Deployment 管理 Pod 副本数、滚动更新、回滚 "我要 3 份 v2 版本"
Service 给 Pod 提供稳定 IP(Pod IP 会变) 内部负载均衡 + 服务发现
Ingress HTTP/HTTPS 七层路由 外部流量守门人

访问链路:外部请求 → Ingress → Service → Deployment → Pod

用户 → Ingress → Service → Pod1 (10.0.1.1)
  │        │         │      Pod2 (10.0.2.3)
  │        │         │      Pod3 (10.0.3.5)
  │        │         │
  │        │         └── Service IP 10.96.0.1 (固定不变)
  │        │             即使 Pod IP 变了也不影响
  │        └── Ingress: "根据域名/路径路由"
  │            api.example.com/user → user-service
  │            api.example.com/order → order-service
  └── 外部用户

扩展:为什么需要 Service?因为 Pod IP 是临时的--Pod 重启、扩缩容,IP 都变。Service 给一个固定 IP + DNS 名,不管你 Pod 怎么变,消费者只管找 Service。Service 底层是基于 kube-proxy + iptables/ipvs 实现的四层负载均衡。

6. 三种健康检查探针?

探针 失败后果 作用
Liveness 重启容器 "你还活着吗?"(死锁/僵死检测)
Readiness 从 Service 摘流 "你能干活了吗?"(启动中不接流量)
Startup 重启容器 慢启动保护,先让你慢慢初始化 
容器启动时间线:

启动 ──▶ Startup 探针检测中 ──▶ Liveness + Readiness 开始生效
         (最长等待时间)          (正常运作阶段)

如果 Startup 探针一直失败 → 重启容器
如果 Startup 成功 → 切换到常规探针

扩展:Liveness 和 Readiness 最容易搞混--Liveness 决定杀不杀容器(死了就重启),Readiness 决定摘不摘流量(病了就休息,但不用杀)。Liveness 不要太敏感(比如连续 3 次失败才判定),否则一个短暂 GC 停顿就重启了整个容器。Readiness 失败比 Liveness 失败更常见也更温和--只是暂时不接客。

7. 滚动更新怎么工作?

一个一个来,不让服务中断:

旧 Pod: [v1] [v1] [v1]
          ↓ 新建 v2
       [v1] [v1] [v1] [v2]
          ↓ 删一个 v1
       [v1] [v1] [v2]
          ↓ 循环...
          ↓ 最终
       [v2] [v2] [v2]

关键参数:maxSurge(最多超几个)和 maxUnavailable(最多少几个)。比如 maxSurge=1, maxUnavailable=0 意味着:升级过程中永远至少 3 个 Pod 在线。

扩展:滚动更新不是你发了新版本就自动开始的--是 Deployment 检测到 Pod 模板变了(镜像版本、配置等),然后触发 ReplicaSet 更新。如果新 Pod Readiness 探针一直失败,K8s 会暂停滚动(不会全量换新),旧 Pod 继续服役--这就是自动回滚前的缓冲。

8. PV 和 PVC 是什么关系?

  • PV(PersistentVolume) = 管理员预先建好的停车位
  • PVC(PersistentVolumeClaim) = 用户的申请表("我要 10GB 存储")
  • K8s 自动匹配 PVC 和可用的 PV,Pod 挂载 PVC 就能用
管理员:建 PV                           用户:建 PVC
┌──────────────┐                    ┌──────────────┐
│ PV-A: 100GB  │                    │ "我要 50GB    │
│ PV-B: 50GB   │  ←── 匹配 ──→     │  读写模式"    │
│ PV-C: 200GB  │                    └──────────────┘
└──────────────┘

扩展:PV/PVC 的绑定是一对一的--一个 PVC 绑定一个 PV 后,PV 就被独占,释放之前不能再被绑定。动态供给(StorageClass)可以省去管理员手动建 PV--用户建 PVC 时自动按模板创建 PV。

9. ConfigMap 和 Secret 区别?

ConfigMap Secret
用途 非敏感配置(端口号、日志级别) 敏感数据(密码、Token)
存储 明文 Base64(注意:不是加密!) 
运行中的 Pod
     │
     ├── 挂载 ConfigMap → /etc/config/app.properties (明文)
     │
     └── 挂载 Secret    → /etc/secrets/db-password   (Base64)

扩展:Base64 编码不是加密!任何人拿到 Base64 字符串都能解码。生产环境 Secret 应配合 Vault(HashiCorp)/ KMS(云厂商密钥管理)/ Sealed Secrets 加密使用。另外 Secret 数据有 1MB 大小限制。

10. 镜像分层是什么?为什么快?

Docker 镜像像千层蛋糕--每个 Dockerfile 指令(FROM/RUN/COPY)产生一层只读层:

容器运行时的层:

┌─────────────────────┐
│  容器可写层(薄薄一层)  │ ← 只在运行时存在
├─────────────────────┤
│  COPY app.jar        │ ← 应用层
├─────────────────────┤
│  RUN apt install ... │ ← 依赖层
├─────────────────────┤
│  FROM openjdk:11     │ ← 基础层
└─────────────────────┘
     只读层(多个容器可共享)

多个容器共用底层镜像,省存储、拉镜像快。如果 100 个容器全用同一个基础镜像,那基础层只在磁盘存一份。

扩展:分层带来的一个坑--层太大拉镜像慢。优化技巧:1 不常变的放上面(依赖安装),常变的放下面(COPY 代码);2 合并 RUN 指令减少层数(apt update && apt install -y);3 用 .dockerignore 排除不需要的文件。

11. K8s Pod 的调度过程是怎样的?

过滤(Predicates)筛除不合格节点 > 打分(Priorities)最高分 > 绑定(Bind)。自定义:nodeSelector、nodeAffinity、taints+tolerations。

12. K8s 如何实现服务网格(Istio)?

核心结论:Sidecar 注入 + Envoy 代理 + 控制面配置下发 = 无侵入式服务治理。

传统 K8s 服务通信:

Pod A ──直接调用──▶ Pod B

Istio 架构(每个 Pod 多个容器):

Pod A                      Pod B
┌──────────────┐          ┌──────────────┐
│ App 容器     │          │ App 容器     │
│ Envoy Sidecar│◀──代理──▶│ Envoy Sidecar│
└──────────────┘          └──────────────┘
       ▲                        ▲
       │      控制面(Istiod)      │
       └─────────────────────────┘
            配置下发、证书管理

Envoy 职责: - 拦截所有进出流量 - 负载均衡、熔断、限流 - mTLS 加密 - 链路追踪、指标收集

Istiod 核心组件:

组件 作用
Pilot 服务发现 + 流量管理规则下发
Citadel 证书签发 + mTLS 管理
Galley 配置验证 
# VirtualService 示例:按比例分流
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
  - reviews
  http:
  - route:
    - destination:
        host: reviews
        subset: v1
      weight: 90
    - destination:
        host: reviews
        subset: v2
      weight: 10  # 灰度发布:10% 流量走新版本

扩展:Istio 的性能开销约 10-20%(Envoy 代理),高并发场景要权衡是否真的需要。轻量级替代方案:Linkerd(更省资源)、Kuma。如果你只是需要灰度发布和监控,用 K8s 原生的 Service + Deployment 就够了,不必上 Istio。

13. K8s 集群故障排查思路?

核心结论:从下往上排查(Node→Pod→Service→Ingress),用好 kubectl describe/logs/events。

排查层次:

1. Node 层
   kubectl get nodes
   kubectl describe node <node-name>  ← 看 Conditions、Events

   常见问题:NotReady、磁盘满、内存不足

2. Pod 层
   kubectl get pods -o wide
   kubectl describe pod <pod-name>   ← 看 Events,知道为什么 Pending/CrashLoopBackOff
   kubectl logs <pod-name> -c <container> --previous  ← 看上个容器的日志

   状态解读:
   - Pending: 资源不足或调度失败
   - CrashLoopBackOff: 容器启动失败(反复重启)
   - ImagePullBackOff: 镜像拉取失败
   - Completed: Job 执行成功

3. Service 层
   kubectl get endpoints <svc-name>  ← 看 Pod 是否被关联
   kubectl get svc                   ← 看 ClusterIP、Port

   常见问题:selector 不匹配、targetPort 错误

4. Ingress 层
   kubectl get ingress
   kubectl describe ingress <name>
   kubectl logs -n ingress-nginx <ingress-controller-pod>

CrashLoopBackOff 排查模板:

# 1. 看事件
cubectl describe pod <pod-name>

# 2. 看日志
cubectl logs <pod-name> --previous

# 3. 进入容器调试
cubectl exec -it <pod-name> -- /bin/sh

# 4. 临时起一个调试 Pod
cubectl run debug --rm -it --image=busybox -- sh

扩展:生产环境必备监控:Prometheus(Grafana 看大盘) + EFK 日志收集。排查时优先看 Events 字段,K8s 会记录 Pod 生命周期中的所有事件。常用命令组合:kubectl get all -A 一眼看全集群资源。

14. K8s 多集群管理方案?

核心结论:Rancher 最成熟(一站式平台),Karmada 最标准(CNCF 项目),OCM 最轻量(IBM 开源)。

方案 特点 适用场景
Rancher 多集群统一 UI + RBAC + CI/CD 企业级平台
Karmada 资源模板 + 策略分发,多集群调度 多活/灾备
OCM IBM 开源,轻量级多集群注册 混合云
GitOps ArgoCD + 多集群 Application Git 驱动 
多集群架构:

┌─────────────────────────────────────────────┐
│              管理集群(Control Plane)          │
│  ┌─────────┐  ┌─────────┐  ┌─────────────┐  │
│  │ Rancher │  │ Karmada │  │   ArgoCD    │  │
│  └────┬────┘  └────┬────┘  └──────┬──────┘  │
└───────┼────────────┼──────────────┼─────────┘
        │            │              │
   ┌────┴────┐  ┌────┴────┐    ┌────┴────┐
   │ Cluster1 │  │ Cluster2│    │ Cluster3│
   │ (北京)   │  │ (上海)   │    │ (广州)   │
   └──────────┘  └──────────┘    └──────────┘

多集群场景:

  1. 多活架构:同一应用部署到多个集群,流量按地域就近访问
  2. 灾备切换:主集群挂了,流量切换到备用集群
  3. 多租户隔离:不同团队用不同集群,资源隔离

扩展:多集群的核心挑战是网络互通和数据同步。网络方案:Submariner(跨集群 L3 通信)、Istio 多集群网格。数据同步:Velero 备份恢复、etcd 跨集群同步。如果你的集群数 < 3,用 Rancher 管理就够了;超过 10 个集群建议 Karmada,它支持跨集群资源分发和调度策略。

15. K8s 中 Pod 启动失败怎么排查？

排查四步法：

# Step1: 查看 Pod 状态
kubectl get pod <name> -n <namespace>
# 关注: Pending / CrashLoopBackOff / ImagePullBackOff / Error

# Step2: 查看详细事件
kubectl describe pod <name> -n <namespace>
# 关键字段: Events → Last State / Reason / Message

# Step3: 查看日志
kubectl logs <name> -n <namespace> --previous  # 上一次运行的日志

# Step4: 进入 Pod 调试（临时）
kubectl debug <name> -it --image=busybox -- sh

常见失败原因：

状态 原因 解决
Pending 无可用节点 / PVC 未绑定 kubectl describe node，检查资源
CrashLoopBackOff 应用启动后崩溃 看日志，检查配置
ImagePullBackOff 镜像拉取失败 检查镜像地址、私有仓库认证
Init:OOMKilled Init 容器内存超限 调高 resources.limits.memory
Evicted 节点资源紧张被驱逐 扩容或清理节点

扩展：kubectl get events --sort-by=.lastTimestamp 查看集群所有事件；kubectl top pod 看资源消耗；生产环境用 OpenTelemetry 做分布式追踪。
