设计模式

1. 单例模式的实现方式?

单例实现对比:

1 双重检查锁(DCL,常用):
   volatile + 两次判空 + synchronized
   注意:volatile 必不可少(防止指令重排导致"半初始化"对象逸出)

2 静态内部类(优雅):
   利用 JVM 类加载机制--Holder 类在首次调用 getInstance() 时才加载
   天然线程安全 + 懒加载

3 枚举(最推荐):
   public enum Singleton { INSTANCE; }
   防反射攻击(newInstance 抛异常)、防序列化破坏、代码最简洁
   但无法继承(枚举不可被 extends)
方式 线程安全 懒加载 防反射 易用性
DCL ✓ ✓ ✗ 推荐
静态内部类 ✓ ✓ ✗ 推荐
枚举 ✓ ✗ ✓ 最推荐

扩展:Java 序列化会破坏单例——反序列化需写 readResolve() 返回单例。枚举天然防序列化破坏。

2. 工厂模式和抽象工厂的区别?

工厂方法 vs 抽象工厂:

工厂方法(Factory Method):
  一个工厂接口 → 多个具体工厂 → 每个工厂创建一种产品
  PhoneFactory → XiaomiFactory.createPhone() / HuaweiFactory.createPhone()
  扩展:新品牌(加一个工厂类),产品类型不变

抽象工厂(Abstract Factory):
  一个抽象工厂 → 多个具体工厂 → 每个工厂创建一系列产品
  DeviceFactory → XiaomiFactory.createPhone() + createWatch() + createEarphone()
  扩展:新品种(在工厂接口加方法),品牌数不变
对比 工厂方法 抽象工厂
产品数量 单一产品 产品族(一组关联产品)
扩展方式 加新工厂(横向) 加新产品(纵向)
适用 生产同类产品 生产配套产品

扩展:Spring 的 BeanFactory 是抽象工厂的体现——getBean() 返回不同类型的 Bean。

3. 代理模式?

代理模式结构:

Client → Proxy(代理) → RealSubject(真实对象)
              │
              ├─ 前置增强(鉴权、日志)
              ├─ 调用真实方法
              └─ 后置增强(清理、统计)

Spring AOP 就是代理模式的最佳实践

三种代理方式: - 静态代理:手写代理类,编译期确定。简单但代理多时代码膨胀 - JDK 动态代理:基于接口,Proxy.newProxyInstance()。目标类必须实现接口 - CGLIB 代理:基于继承,生成目标类的子类。不需要接口但不能代理 final 类/方法

JDK 代理 vs CGLIB 代理: - JDK 代理只能代理接口方法 → 代码清晰,但目标类必须有接口 - CGLIB 通过子类覆盖方法 → 不需要接口,但 final 方法不行 - Spring Boot 2.x 后默认 CGLIB(proxy-target-class=true)

扩展:代理模式控制访问,装饰器模式增强功能。两者类结构相似,区别在于意图。

4. 策略模式?

策略模式消除 if-else:

传统方式:
  if (type == "wechat") { 微信支付 }
  else if (type == "alipay") { 支付宝 }
  else if (type == "union") { 银联 }

策略模式:
  定义接口 PayStrategy { pay(order); }
  → WechatPay implements PayStrategy
  → Alipay implements PayStrategy
  → UnionPay implements PayStrategy
  使用时通过 Map/Spring 注入获取对应策略
  payStrategyMap.get(method).pay(order);

Spring 中的优雅实现: - 每个策略实现类用 @Service("wechatPay") 命名 - 用 Map<String, PayStrategy> strategyMap 自动注入所有实现 - 运行时 strategyMap.get(method).pay(order) 一行搞定

扩展:策略模式是外部选择算法(调用方决定),状态模式是内部根据状态自动切换(更智能)。策略常配合工厂模式使用。

5. 观察者模式?

观察者模式结构:

Subject(被观察者/事件源)
  ├── attach(Observer)    ← 注册观察者
  ├── detach(Observer)    ← 移除观察者
  └── notify()            ← 通知所有观察者

Observer(观察者)
  └── update(event)       ← 收到通知时更新

Spring 事件机制:
  ApplicationEvent → 事件
  @EventListener → 观察者
  ApplicationEventPublisher.publishEvent() → 发布通知

典型场景:订单支付成功 → 通知积分服务加分、通知短信服务发确认、通知物流服务发货。各个监听器互不感知,订单模块不用知道积分/短信/物流的存在。

扩展:Spring 事件默认同步,一个监听器慢会拖累整个调用链。加 @Async 异步执行。@TransactionalEventListener 在事务提交后才触发。

6. 常见反模式及设计原则?

常见反模式:
- 滥用单例:全局状态隐藏依赖,测试耦合,并发瓶颈
- 上帝类:一个类干了所有事(2000+ 行代码),改不动测不了
- 过度设计:为"以后可能"的需求提前加层,代码复杂但从未用到
- 循环依赖:A → B → C → A,改一发动全身
- 贫血模型:对象只有 getter/setter 没有行为,所有逻辑塞到 Service

SOLID 五大原则:

S - 单一职责:一个类只做一件事
O - 开闭原则:对扩展开放,对修改关闭(加新功能不碰老代码)
L - 里氏替换:子类能完全替换父类而不出错
I - 接口隔离:大接口拆小,不强迫实现不需要的方法
D - 依赖倒置:依赖抽象(接口),不依赖具体实现

扩展:KISS(Keep It Simple, Stupid)和 YAGNI(You Ain't Gonna Need It)比 SOLID 更基础--先保证代码够简单,再看是否需要设计模式。设计模式是"发现"的,不是"发明"的--是反复出现的解决方案,不是需要强行套用的模板。好的设计来自多次重构,不是一次画出来的。

7. 装饰器模式和代理模式的区别?

维度 装饰器模式 代理模式
目的 增强功能(加新能力) 控制访问(设门槛)
关注点 给对象"穿衣服" 给对象"安排秘书"
典型场景 Java IO(BufferedReader 包装 Reader) Spring AOP(事务、日志代理)
是否透明 调用方知道用的是装饰后的对象 调用方无感知,以为在调原对象 
装饰器模式:一层套一层,功能叠加

InputStream raw = new FileInputStream("data.txt");      // 原始:读文件
InputStream buffered = new BufferedInputStream(raw);    // 装饰:加缓冲
InputStream gzip = new GZIPInputStream(buffered);       // 装饰:加解压
// 每层装饰都增加一个功能

代理模式:访问控制和增强

UserService proxy = Proxy.newProxyInstance(...);  // 代理拦截调用
proxy.save(user);
    │
    ▼
  检查权限 → 记日志 → 开事务 → 调真正 save → 提交/回滚 → 关资源

扩展:Java IO 的"装饰器套娃"是装饰器模式最经典的应用--new BufferedReader(new InputStreamReader(new FileInputStream("a.txt"))) 把文件流 → 字符流 → 缓冲流层层包装。如果你觉得这种嵌套太深,Lombok 的 @Delegate 注解能帮你简化装饰器代码。

8. 模板方法模式是什么?在哪里看到过?

定义:定义一个算法的骨架,让子类实现具体步骤。就像作文模板--结构是固定的(开头、正文、结尾),内容每个学生自己填。

// 父类定义骨架(final 防止子类改顺序)
abstract class DataExporter {
    public final void export() {
        connect();       // 1 连接
        fetchData();     // 2 查数据 = 子类实现
        formatData();    // 3 格式化 = 子类实现
        writeFile();     // 4 写文件
        disconnect();    // 5 断开
    }
    abstract List<?> fetchData();   // 子类实现
    abstract String formatData();   // 子类实现
}

// 子类只填具体内容
class ExcelExporter extends DataExporter { ... }
class PdfExporter extends DataExporter { ... }

Spring 中的典型:JdbcTemplate(连接管理是骨架,SQL 是你填的)、RestTemplate、AbstractApplicationContext(refresh() 定义了容器初始化的 13 个步骤)。

扩展:模板方法和策略模式都是"行为参数化",区别在于--模板方法用继承(子类覆写),策略模式用组合(注入策略对象)。组合通常优于继承,所以现代 Java 中策略模式更受欢迎。

9. 适配器模式是什么?和代理模式、装饰器模式怎么区分?

就像出国转接头--中国的插头是扁的,欧洲的插座是圆的,需要一个"转换器"让它们兼容。

// 旧接口(被适配者)
interface OldPayment {
    void pay(String account, int amount);
}

// 新接口(目标)
interface NewPayment {
    boolean processPayment(PaymentRequest request);
}

// 适配器:让 OldPayment 能当 NewPayment 用
class PaymentAdapter implements NewPayment {
    private OldPayment oldPayment;

    public boolean processPayment(PaymentRequest request) {
        oldPayment.pay(request.getAccount(), request.getAmount());
        return true;
    }
}

三种"包装模式"一句话区分: - 适配器:接口不对,转换一下(插头转接头) - 代理:访问控制,中间把关(秘书) - 装饰器:功能增强,层层包装(穿衣服)

扩展:Spring 的 HandlerAdapter 是适配器模式的经典--不同类型的 Controller(@Controller、HttpRequestHandler、Servlet)通过不同的 Adapter 统一调 handle() 方法。Spring MVC 拿到 Handler 后先找对应的 Adapter,适配后再调用。

10. 建造者模式(Builder)解决了什么问题?

当一个对象有大量可选参数时,构造函数变成灾难:

// 不用 Builder:构造函数参数地狱
User user = new User("张三", null, null, "male", null, "Beijing", null, null, null, 25);

// 用 Builder:清晰优雅
User user = User.builder()
    .name("张三")
    .age(25)
    .gender("male")
    .city("Beijing")
    .build();
    // 只设了 4 个参数,其他用默认值

手写 Builder 模式:

class User {
    private String name;    private Integer age;
    private String email;   private String phone;

    private User(Builder builder) {
        this.name = builder.name;
        this.age = builder.age;
        this.email = builder.email;
        this.phone = builder.phone;
    }

    public static class Builder {
        private String name;       // 必需
        private Integer age;       // 可选
        private String email;      // 可选
        private String phone;      // 可选

        public Builder(String name) { this.name = name; }  // 必需的通过构造函数传
        public Builder age(Integer age) { this.age = age; return this; }
        public Builder email(String email) { this.email = email; return this; }
        public Builder phone(String phone) { this.phone = phone; return this; }
        public User build() { return new User(this); }
    }
}

扩展:Lombok 的 @Builder 注解可以自动生成 Builder 模式代码,省去手写。Builder 模式在构建复杂对象时特别好用--StringBuilder、HttpClient.Builder、OkHttpClient.Builder 都是典型。面试时如果让你写 Builder 模式,注意链式调用返回 this 和最终的 build() 方法。

11. Spring 框架中用了哪些设计模式?

设计模式 Spring 中的应用
单例模式 默认 Bean 作用域为 singleton
工厂模式 BeanFactory、ApplicationContext
代理模式 AOP(JDK/CGLIB 动态代理)
模板方法 JdbcTemplate、RestTemplate、AbstractApplicationContext
观察者模式 ApplicationEvent + @EventListener 事件机制
策略模式 ResourceLoader 根据前缀(classpath:/http:)选不同加载策略
适配器模式 HandlerAdapter 适配不同类型的 Controller
装饰器模式 BeanDefinitionDecorator、ServerHttpRequestDecorator
责任链模式 FilterChain、InterceptorChain

扩展:面试时"背出 Spring 用了哪些设计模式"不够,要能解释"为什么"。比如 AOP 用代理模式--因为要在方法前后加事务/日志,不能直接改源码;事件用观察者模式--因为发布方不想知道谁在监听,解耦。

12. 责任链模式是什么?在哪里用到?

就像请假审批流程:1 天假 → 主管批 → 3 天假 → 经理批 → 7 天假 → 总监批。请求沿链路传递,找到能处理的人为止。

Client → Handler A → Handler B → Handler C
            │            │            │
            │ 不处理     │ 不处理     │ 处理
            │ 传给 B     │ 传给 C     │ 返回
            ▼            ▼            ▼

// Servlet Filter 就是责任链的典型
@WebFilter("/api/*")
public class AuthFilter implements Filter {
    public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain) {
        if (checkAuth(req)) {
            chain.doFilter(req, resp);  // 通过 → 传给下一个
        } else {
            ((HttpServletResponse) resp).sendError(401);  // 不通过 → 终止
        }
    }
}

扩展:责任链和装饰器模式都是"链式处理",区别在于--责任链的每个节点可以终止传递(不再调下一个),装饰器的每层必须传递下去。Spring Security 的 SecurityFilterChain、Netty 的 ChannelPipeline、Sentinel 的 Slot Chain 都是责任链模式。

13. 解释开闭原则(Open/Closed Principle)?

对扩展开放对修改关闭。通过继承/组合扩展功能,不改已有代码。经典例子:策略模式实现支付系统扩展。SOLID 核心原则。

14. 适配器模式是什么?在哪里看到过?

适配器模式 = 电源转换插头。你去国外出差,插座口对不上--加个转换头,两头都能用了。你写代码时想让"圆口"的第三方库接到你的"方口"接口上,写个适配器类包一层就行。

适配器结构:

  Client(调用方)→ Target(你定义的接口)
                         ↑
                    Adapter(适配器,实现 Target,内部持有 Adaptee)
                         ↑
                    Adaptee(被适配者:第三方库 / 老系统)

三个角色: - Target(目标接口):你代码里想用的接口 - Adaptee(被适配者):已经存在但不能直接用的类(接口不兼容) - Adapter(适配器):实现 Target,内部包装 Adaptee,负责"翻译"调用

典型场景: 1. 老系统迁移:新系统定义了统一的支付接口 PayService,老的微信支付 SDK 接口完全不一样--写个 WechatPayAdapter 包一下老 SDK,对业务代码无感切换 2. 第三方库集成:项目用 Slf4j 日志门面,底层可以随便换 Log4j2 / Logback--Slf4j 本身就是适配器 3. Spring 中的体现:HandlerAdapter--DispatcherServlet 不关心 Controller 具体是什么类型(@RequestMapping 注解的、实现 Controller 接口的、Servlet 方式),通过适配器统一调用

场景:支付系统对接多个渠道

// 你的统一接口
interface PayService {
    void pay(Order order);
}

// 支付宝 SDK 的接口完全不同
class AlipaySDK {
    void createPayment(String orderId, BigDecimal amount, ...) { ... }
}

// 适配器:把 AlipaySDK 包装成 PayService
class AlipayAdapter implements PayService {
    private AlipaySDK sdk;

    public void pay(Order order) {
        sdk.createPayment(order.getId(), order.getAmount(), ...);
    }
}

// 使用时:所有渠道都调 PayService.pay(),内部转发给不同 SDK

扩展:适配器 vs 装饰器的区别(面试高频对比)--适配器是"换接口"(把 A 接口转成 B 接口),装饰器是"加功能"(不改接口,只是增强)。就像电源转换插头(适配器)和手机壳(装饰器)的区别。另一个容易混的是--适配器 vs 策略模式:适配器让不兼容的接口一起工作,策略模式是在多个兼容的算法中切换。

15. 什么是反模式?什么时候不该用设计模式?

反模式 = 看似解决了问题、实际引入了更大麻烦的错误设计。

常见 5 种反模式:

1 过度工程(Over-Engineering)
   症状:为"以后可能的需求"提前引入了大量抽象层
   后果:代码量膨胀 3 倍,改个配置要穿过 5 层抽象
   原则:YAGNI(You Ain't Gonna Need It)

2 单例滥用
   症状:全局状态满天飞 → 隐藏依赖、不可测试、并发瓶颈
   例:把 UserService 做成单例但塞了 request 级状态 → 数据串了

3 模式堆砌
   症状:10 个设计模式解决一个 CRUD,像教科书目录
   原则:简单问题用简单代码,模式是重构出来的不是设计出来的

4 贫血模型
   症状:对象只有 getter/setter,所有逻辑塞在 2000 行 Service 里
   后果:丧失 OOP 封装性

5 错误模式选择
   把装饰器当适配器用、用观察者模式替代简单 if-else → 绕远路

什么时候不该用设计模式?

1 业务简单、几乎不变 → 别用
   50 行的转换工具,直接写比套策略模式更清晰

2 还在探索阶段 → 先别用
   需求还在变,先跑通,稳定后再重构

3 模式的复杂度 > 问题本身的复杂度 → 别用
   3 个分支且一年才加一个 → 别套工厂模式

4 团队对模式不熟悉 → 慎重
   你用了但其他人看不懂 = 维护灾难

面试金句:"设计原则是内功,设计模式是招式。掌握了 SOLID(单一职责、开闭原则、里氏替换、接口隔离、依赖倒置),比背 23 种模式模板重要 10 倍。好的模式使用方式是--先写能用的简单代码 → 发现痛点 → 用模式重构,而非一开始就画 UML 类图。"

16. 设计模式在 Spring 源码中的实际应用？

Spring 框架本身就是设计模式的集大成者：

Spring 核心设计模式:
  单例模式     → Bean 默认单例
  工厂模式     → BeanFactory / ApplicationContext
  代理模式     → AOP（JDK DynamicProxy / CGLIB）
  模板方法模式  → JdbcTemplate、HibernateTemplate
  观察者模式    → ApplicationEvent + @EventListener
  策略模式     → TransactionManager（不同 DB 不同实现）
  装饰器模式    → BufferedInputStream 包装 FileInputStream
  责任链模式    → HandlerInterceptor / Filter
  建造者模式    → BeanDefinitionBuilder

代理模式实战（AOP）：

// Spring AOP 自动生成代理
@Transactional  // → 事务管理器（策略模式选择）
public void transfer(String from, String to, BigDecimal amount) {
    // Spring 生成代理：开启事务 → 执行方法 → 提交/回滚
}

模板方法模式（JdbcTemplate）：

// 定义骨架（模板方法）
jdbcTemplate.execute("INSERT INTO orders VALUES (...)", (ps) -> {
    ps.setString(1, order.getId());  // 变动的部分：子类实现
    ps.setBigDecimal(2, order.getAmount());
    return ps.executeUpdate();
});

扩展：Spring 的 @Async 也是代理模式（生成AsyncTaskExecutor的代理）；BeanFactory 用工厂模式 + 反射；ApplicationContext 是高级工厂，支持国际化、资源加载。
