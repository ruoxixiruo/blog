Elasticsearch

1. 什么是倒排索引?为什么 ES 比 MySQL 快?

正排索引(MySQL):
  文档1 → "Java 面试题详解"
  文档2 → "Spring Boot 入门"
  查"Java" → 必须扫所有文档 → O(n)

倒排索引(ES):
  "Java"    → [文档1, 文档5, 文档15]   ← 直接找到!
  "面试题"  → [文档1, 文档8, 文档20]
  "Spring"  → [文档2, 文档6]
  查"Java" → 直接拿到文档列表 → O(1)

就像书的关键词索引页--查"Java"直接看索引写着"第 3、7、15 页",瞬间定位。不用翻完整本书。

Elasticsearch 底层用 Lucene 实现倒排索引,核心数据结构包括: - Term Dictionary(词项字典):排序的词汇表,二分查找定位词项 - Posting List(倒排列表):每个词对应哪些文档的 ID 列表 - FST(有限状态转换器):把 Term Dictionary 压缩,前缀共享,省内存又加快查找

扩展:MySQL 的 LIKE '%关键词%' 无法利用 B+ 树索引(前缀模糊匹配),必须全表扫描。ES 不仅查得快,还支持分词("北京大学" → "北京"+"大学"+"北京大学")、相关性评分(TF-IDF/BM25)、高亮、聚合分析。但 ES 不适合做事务性写入(没有 ACID),通常和 MySQL 配合使用--MySQL 做主存储,ES 做搜索。

2. ES 集群有哪些节点角色?

ES 节点角色:

┌────────────┬─────────────────────────────────┐
│ Master     │ 集群大脑:创建/删除索引、分配分片│
│ (CEO)      │ 跟踪节点上下线、维护集群状态     │
├────────────┼─────────────────────────────────┤
│ Data       │ 数据工人:存储数据、执行 CRUD    │
│ (员工)     │ 占用最多资源(磁盘+内存+CPU)    │
├────────────┼─────────────────────────────────┤
│ Coordinating│ 前台:接收客户端请求             │
│ (协调节点)  │ 分发到各分片 → 汇总结果返回     │
├────────────┼─────────────────────────────────┤
│ Ingest     │ 预处理:数据写入前做格式转换     │
│            │ 如 grok 解析日志、geoip 转地理位置│
└────────────┴─────────────────────────────────┘

ES 7.x 后默认所有节点都是以上角色的组合(除非显式配置),小集群可以不分。大集群建议 Master 专用节点(只做管理,不存数据)和协调专用节点(转发汇总)。

扩展:Machine Learning 节点(付费功能)、Transform 节点、Remote Cluster Client 节点(跨集群搜索)是 ES 7.x+ 的新角色。node.roles 配置控制节点角色。Master 候选节点数建议为 3 或 5(奇数),只有候选节点才能参与 Master 选举。

3. 什么是分片和副本?

索引 = 主分片 × N + 副本 × M

假设 3 个主分片 + 1 个副本:

  Node1: P0 + R1
  Node2: P1 + R2
  Node3: P2 + R0

P=主分片(Primary),R=副本分片(Replica)
每个分片的数据分布在不同的节点上
对比 主分片(Primary Shard) 副本分片(Replica Shard)
作用 水平扩展(存储 + 读写吞吐) 高可用(容错) + 提升读吞吐
数量 创建后不可改 可动态调整
读写 处理读写 只处理读,写由主分片同步过来

黄金法则:单个分片 10~50GB 最佳(太大迁移慢,太小管理开销大)。副本至少 1 个(保证单节点挂了对服务无影响)。

扩展:写请求→协调节点→路由到主分片→主分片写入→同步到副本→确认返回。读请求可以走主分片或副本(负载均衡)。分片数量需要在"写入吞吐"和"查询聚合"之间平衡--分片越多写入越分散(好),但查询要汇总更多分片(慢)。

4. 如何避免脑裂?

脑裂(Split Brain)场景:

  3 个 Master 候选节点:M1 M2 M3
  网络故障 → M1 与 M2,M3 断开
  → M1 自己选为 Master(以为 M2,M3 挂了)
  → M2,M3 也选出一个 Master
  → 两个 Master 同时接受写入 → 数据冲突!

解决方案:discovery.zen.minimum_master_nodes = N/2 + 1(ES 7.x 之前)
         或 initial_master_nodes / discovery.seed_hosts(ES 7.x+ 自动管理)

  3 个节点 → 至少 2 票才能当选 Master
  M1 只有 1 票 → 不够 → 不会成为 Master ✓
  M2+M3 → 2 票 → 合法 Master ✓

建议:Master 候选节点设奇数个(3 或 5),N/2+1 保证任何网络分区只有一边能过半。

扩展:ES 7.x 后选举机制改进了--不再需要手动配置 minimum_master_nodes,通过 discovery.seed_hosts 配置候选节点列表即可。脑裂的一个常见原因是 GC 停顿--Master 长时间 GC 导致心跳超时,其他节点以为它挂了。给 Master 专用节点配足够内存可减少 GC 停顿。

5. ES 为什么是近实时搜索?

写入到可搜索的流程:

写入数据 → 写入内存 Buffer(不可搜索)
           ↓ 默认每 1 秒 refresh
        生成新 Segment(可搜索)
           ↓ Translog 记录每次操作
        数据真正安全(flush 到磁盘)

为什么叫"近实时"(Near Real-Time):
  默认 refresh_interval = 1s
  → 写入后最多等 1 秒才能搜到
  → 这就是"近"(快但不是即时)
操作 作用 默认频率 数据安全保障
refresh 内存→Segment(可搜索) 1s 可能丢 1s 数据
flush Segment→磁盘 + 清 Translog 30min 或 Translog 满 持久化
Translog 记录每次操作(WAL) 每次写入 宕机恢复的依据

扩展:refresh_interval 可以设为 -1(禁用自动刷新,批量导入时提升性能)。Translog 是 ES 的"redo log"--节点宕机后通过重放 Translog 恢复未 flush 的数据。ES 的 Segment 是不可变的(写入后不会被修改),更新的文档标记为 deleted,后续 merge 时真正删除。不可变性简化了并发控制和缓存。

6. query 和 filter 的区别?

对比 query filter
相关性评分 计算 _score 不算分,只判断 yes/no
缓存 不缓存(每次都算分) 缓存结果(filter cache)
性能 慢 快
适用 全文搜索、模糊匹配 精确过滤(状态/分类/日期) 
推荐用法:
GET /orders/_search
{
  "query": {
    "bool": {
      "must": { "match": { "product_name": "手机" } },   ← query,算相关性
      "filter": { "term": { "status": "paid" } }         ← filter,只过滤
    }
  }
}

经验法则:精确匹配用 filter(快),搜索打分用 query。filter 的缓存是自动的--ES 会缓存常用的 filter 结果。

扩展:constant_score 查询可以把 query 包装成 filter(不算分,统一给分 1.0)。bool 查询的 must、should、filter、must_not 四个子句可以灵活组合。ES 的 filter cache 在 Segment 级别(不是整个索引级别),Segment merge 时缓存失效。

7. 深分页怎么解决?

from+size 深分页问题:
  查 from=10000, size=10
  → 每个分片要查出 10010 条数据
  → 协调节点汇总 3 个分片 = 30030 条
  → 排序后丢弃前 9990 条,返回 10 条
  → 浪费了大量 IO、网络、内存!
  ES 默认限制 from+size ≤ 10000 (max_result_window)

两种替代方案:

方案 search_after scroll
原理 记住上页最后一条的 sort 值,下一页从它之后开始 生成一个数据快照游标,一路扫到底
适用 实时翻页、APP 列表 离线导出、全量数据迁移
是否实时 是(每次查最新数据) 否(快照那一刻的数据)
跳页 不支持(只能一页页翻) 不支持

扩展:max_result_window 可以调大但治标不治本(默认 10000)。APP 端的"无限下滑"用 search_after 最适合。scroll 会占用内存(维护快照),用完要 DELETE _search/scroll/{scroll_id} 清理。ES 7.x 后推荐用 pit(Point In Time)+ search_after 代替 scroll。

8. 集群健康状态怎么判断?

集群三色灯:

Green  🟢:所有主分片 + 副本都正常分配
  读写正常,最健康状态

Yellow 🟡:主分片全部正常,但部分副本没有分配
  读写正常(数据不丢),但副本缺失 = 少了高可用保障
  常见原因:节点数不够(比如单节点跑 ES,副本无处分配)
  处理:加节点 / 减少副本数 / 接受单节点风险

Red   🔴:部分主分片不可用
  数据不完整!部分数据读写都会失败
  紧急处理:恢复宕机节点 / 从快照恢复

排查步骤: 1. GET _cluster/health?level=indices → 看哪些索引不健康 2. GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason → 看未分配分片的原因 3. GET _cluster/allocation/explain → 解释某个分片为什么没有被分配

扩展:Yellow 在单节点集群中是正常的(副本无处分配),只要数据有备份就行。Red 是生产事故--_cluster/health 的 status 是 Red 时,对应的分片 GET/POST 操作都会报错。定期快照(Snapshot)是最后的数据保障--万一主分片全丢了还能从快照恢复。

9. ES 写入数据的完整流程?

1 文档写入 → 2 Memory Buffer → 3 refresh(默认1s) → 4 Segment(可搜索)
                         │
                         └──→ 5 Translog(持久化,防止数据丢失)
                                                    │
                        6 flush(默认30min) → 7 磁盘 Segment + 清空 Translog
概念 作用 默认间隔
refresh 将 Memory Buffer 的数据刷到 Segment,使文档可搜索 1 秒
translog 写入操作先记录到 translog(类似 MySQL binlog),断电后恢复数据 每次写入
flush 将 Segment 持久化到磁盘,清空 translog 30 分钟 
为什么"近实时"(NRT)?

  写入 → Memory Buffer(不可搜索)
         → refresh(1s) → Segment(可搜索) ← 这就是 1 秒延迟的来源
         → flush(30min) → 磁盘永久存储

  如果还没 flush 就断电 → translog 恢复

扩展:refresh_interval 可以设为 -1(关闭自动刷新)来加速大批量写入--等数据全写完了再手动 refresh。这就是为什么 ES 批量导入时速度能达到单条写入的几十倍。

10. term 和 match 的区别?

查询 行为 适用字段
term 不对查询词分词,精确匹配 keyword 类型(状态码、ID、标签)
match 先对查询词分词,再对每个词做匹配 text 类型(标题、正文) 
// term:不分词,"上海浦东" 作为一个完整词去匹配
// 适用于 keyword 字段
GET /index/_search
{
  "query": { "term": { "city": "上海浦东" } }
}

// match:把 "上海浦东" 分词为 ["上海", "浦东"],分别匹配
// 文档包含 "上海" 或 "浦东" 都能命中
GET /index/_search
{
  "query": { "match": { "description": "上海浦东" } }
}

扩展:如果你对 keyword 字段用 match 可能会查不到(keyword 不分词,match 分词后找不到匹配);如果对 text 字段用 term 也大概率查不到(因为 term 不分词,但 text 字段存储的是分词后的结果)。

11. ES 的 Mapping 是什么?dynamic mapping 的优缺点?

Mapping 定义了索引中字段的类型、是否分词、是否索引等。就像 MySQL 建表时的 CREATE TABLE 一样。

PUT /user
{
  "mappings": {
    "properties": {
      "id":     { "type": "long" },
      "name":   { "type": "keyword" },    // 不分词,精确匹配
      "bio":    { "type": "text" },       // 分词,全文搜索
      "age":    { "type": "integer" },
      "status": { "type": "keyword" }     // 精确匹配,聚合用
    }
  }
}
方式 做法 建议
dynamic: true(默认) 自动推断字段类型 快速开始,但可能猜错
dynamic: false 忽略未定义字段(不索引但存储) 数据只存不查
dynamic: strict 未定义字段直接报错 生产推荐,防止脏数据

扩展:dynamic mapping 最大的坑是把 ID 之类的字段猜测为 text 而非 keyword(如订单号 OD20240001 被分词就没意义了)。生产和测试索引最好使用显式 Mapping,或者至少把 String 类型的默认映射从 text 改为 keyword。

12. ES 删除/更新文档的底层原理?

ES 的 Segment 是不可变的(写入后不能改),所以删除和更新靠"标记":

  • 删除:在 .del 文件中标记该文档为"已删除"(逻辑删除),搜索时跳过
  • 更新:标记旧文档删除 + 写入新文档到新 Segment(不是原地更新!)
"更新"过程:

  旧 Segment: Doc1(id=1, name="张三")
                   │ 更新 name="张老三"
                   ▼
  .del 文件: [Doc1 标记删除]
  新 Segment: Doc2(id=1, name="张老三")

  搜索时:从 .del 知道 Doc1 已删 → 返回 Doc2

段合并(Segment Merge):后台自动把小 Segment 合并成大 Segment,同时真正删除被标记的文档。合并时 ES 会自动均衡 IO,不影响搜索。

扩展:如果大量删除后不做段合并,.del 文件越来越大,搜索性能下降。可以用 _forcemerge API 强制合并(如 POST /index/_forcemerge?max_num_segments=1),但生产环境不要在业务高峰期执行。

13. ES 的分词器(Analyzer)是什么?IK 分词器怎么选?

Analyzer(分析器) = Character Filter(字符过滤) + Tokenizer(分词) + Token Filter(词项过滤)。

输入:"The 2 QUICK Brown-Foxes"
  │
  ▼ Character Filter(字符过滤:去 HTML、替换字符)
  │
  ▼ Tokenizer(分词:拆成词项)
  │
  ▼ Token Filter(过滤:小写化、去停用词、词干提取)
  │
  ▼ 输出:["the", "2", "quick", "brown", "foxes"]

IK 分词器的两种模式:

模式 策略 示例 适用
ik_max_word 最细粒度,尽可能多分 "中华人民共和国" → ["中华人民共和国", "中华人民", "中华", "华人", "人民", "共和国"] 索引时(提高召回率)
ik_smart 最粗粒度,最少词数 "中华人民共和国" → ["中华人民共和国"] 搜索时(精准匹配)

扩展:推荐策略--索引时用 ik_max_word(尽量多分词),搜索时用 ik_smart(精准匹配)。IK 分词器还可以自定义词典(IKAnalyzer.cfg.xml),添加项目专有词汇(如公司名、产品名、黑话),这些词就不会被错误切分了。

14. ES 的 Refresh 和 Flush 有什么区别?

Refresh:buffer > OS Cache,文档可被搜索。Flush:OS Cache > 磁盘,清空 translog。批量写入时可临时关闭 refresh 提写入速度。

15. ES 如何实现海量数据的高效聚合分析?

核心思路:减少参与聚合的数据量 + 分层聚合 + 缓存优化。

优化策略:

1. 时间范围过滤 + 条件过滤
   GET /logs/_search
   {
     "query": {
       "bool": {
         "filter": [
           { "range": { "timestamp": { "gte": "now-7d" } } },  ← 先过滤
           { "term": { "level": "ERROR" } }
         ]
       }
     },
     "aggs": {
       "error_by_service": {
         "terms": { "field": "service", "size": 10 }
       }
     }
   }

2. 分层聚合:先粗粒度再细粒度
   aggs:
     地区聚合 → 每个地区内再聚合服务

3. 使用 composite 聚合做深度分页
   "aggs": {
     "my_buckets": {
       "composite": {
         "size": 100,
         "sources": [{ "date": { "date_histogram": { "field": "timestamp", "interval": "1d" } } }]
       }
     }
   }

性能对比:

优化手段 效果 适用场景
filter + aggs 过滤90%数据后再聚合 有明确查询条件
composite 支持深度分页聚合 结果集超10万
外部排序 降低内存占用 高基数聚合
预计算 直接查预聚合索引 固定维度统计

扩展:聚合默认不分页,返回 top N。如果结果集太大(百万级),使用 composite 聚合分批获取。高基数聚合(如 user_id)会导致内存暴涨,解决方案是使用 eager_global_ordinals:true 预加载全局序数,或者改用 rollup 索引预聚合。

16. ES 集群数据倾斜怎么解决?

现象:某些节点磁盘快满了,某些节点还很空;查询慢时发现热点数据集中在少数分片。

根因分析:

  1. 分片数量不均:早期创建的索引分片少,后期扩容节点多不均衡
  2. 数据分布不均:按时间分索引,新数据在少数节点
  3. 热点数据:查询集中在少数分片

解决方案:

1. 索引设计层面
   - 按时间分索引:logs-2024-01, logs-2024-02
   - 每个索引的分片数 = 节点数 × 单节点分片数
   - 设置 index.routing_partition_size 打散路由

2. 运维调整
   - PUT _cluster/settings {
       "persistent": {
         "cluster.routing.allocation.balance.threshold": 0.1
       }
     }
   - 手动移动分片:POST _cluster/reroute

3. 冷热分离架构
   - Hot 节点:SSD,存近期数据(7天)
   - Warm 节点:HDD,存历史数据
   - Curator 自动迁移冷数据

迁移命令示例:

POST _cluster/reroute
{
  "commands": [
    {
      "move": {
        "index": "logs-2024-01",
        "shard": 0,
        "from_node": "node-1",
        "to_node": "node-3"
      }
    }
  ]
}

扩展:生产环境建议每个节点分片数控制在 20 个以内(单个分片 10-50GB)。分片太多增加管理开销,太少影响并行度。使用 _cat/shards?v&h=index,shard,prirep,state,store,node&s=store:desc 排查磁盘占用最高的分片。

17. ES 写入性能瓶颈如何优化?

核心结论:批量写入 + 关闭刷新 + 增大缓冲区 + 异步刷盘 = 吞吐提升 10-50 倍。

优化配置:

1. 批量写入 bulk API
   POST _bulk
   { "index": { "_index": "logs", "_id": "1" } }
   { "message": "log content" }
   { "index": { "_index": "logs", "_id": "2" } }
   { "message": "another log" }

   批量大小:5-15MB 一批(别超过)_

2. 写入前关闭刷新
   PUT /logs/_settings
   { "refresh_interval": -1 }  ← 关闭!

3. 增大 translog 缓冲
   PUT /logs/_settings
   {
     "translog": {
       "flush_threshold_size": "512mb",  ← 默认 512mb
       "sync_interval": "5s"            ← 异步刷盘
     }
   }

4. 调整线程池
   thread_pool:
     write:
       size: 16        ← CPU 核数
       queue_size: 1000

性能对比(单节点 10 亿日志导入):

配置 耗时 吞吐
默认配置 8 小时 3500 docs/s
bulk + 关 refresh 25 分钟 67000 docs/s
+ 异步 translog 15 分钟 111000 docs/s

扩展:写入完成后记得恢复 refresh_interval 并手动调用 _forcemerge 合并段。如果源数据在 MySQL,建议用 Logstash 或 Canal 同步,别自己写代码轮询。大批量写入还要注意磁盘 IO 压力--SSD 是必须的,否则优化空间有限。

18. ES 查询DSL的执行流程与优化？

查询流程：

GET /products/_search
{
  "query": {
    "bool": {
      "must":   [{ "match": { "name": "手机" } }],
      "filter": [{ "range": { "price": { "lte": 3000 } } }]
    }
  }
}

执行流程:
  Query Phase:
    1. 协调节点接收请求
    2. 广播到所有分片（并行）
    3. 每个分片执行：评分（must）+ 过滤（filter缓存）
    4. 每个分片返回 top N 文档 ID

  Fetch Phase:
    5. 协调节点收集所有分片结果
    6. 合并排序，取 top 10
    7. 向目标分片请求完整文档
    8. 返回客户端

优化方向：

优化点 方法
减少分片数 冷数据合并分片（_forcemerge）
善用 filter filter 不评分，自动缓存
search_after 分页 深度分页用游标，不吃内存
source filtering "_source": ["name","price"] 只取必要字段
预热 warmup API 提前加载热点数据

扩展：7.x 后默认每分片 _primary，6.x 是 _primary|_replica；preference=_local 让查询优先读本地分片，减少网络跳数；写入优化用 bulk API + refresh_interval="30s"。
