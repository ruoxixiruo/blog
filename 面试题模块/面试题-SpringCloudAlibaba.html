Spring Cloud Alibaba & 微服务

1. 什么是微服务?优缺点?

单体 vs 微服务:

单体架构:
  [前端] → [一个大应用:用户+订单+商品+支付] → [一个DB]
  改一行代码 → 整个应用重新部署

微服务架构:
  [前端] → [网关]
            ├─ 用户服务 → [用户DB]
            ├─ 订单服务 → [订单DB]
            ├─ 商品服务 → [商品DB]
            └─ 支付服务 → [支付DB]
  改订单服务 → 只部署订单服务

优点:独立部署(改一个服务不用重启全部)、故障隔离(订单崩了不影响用户登录)、团队自治(Java/Go/Python 一个团队一种技术栈也行)、可扩展(订单压力大只扩订单服务)

缺点:分布式复杂性(网络不可靠、数据一致性难保证、事务跨服务)、运维成本高(监控/日志/链路追踪都要配套)、调试困难(一个请求跨 N 个服务)

扩展:团队 < 10 人、业务不复杂 → 单体更合适。Martin Fowler:"如果你做不好单体,也做不好微服务"--先写模块化单体,等扛不住了再拆。

2. Nacos 的三大核心能力?

能力 大白话说 技术说明
服务发现 微服务的通讯录,自动注册、自动找 服务注册、健康检查、负载均衡、服务元数据
配置管理 统一的遥控器,改配置不用重启 集中化配置管理、热更新、多环境隔离、变更推送
服务及元数据管理 服务标签、分组、版本管理 服务元数据管理、标签、DNS 域名

Nacos 相比 Eureka 的核心优势:Eureka 只是注册中心(且已停更),Nacos 注册+配置一体,一个组件干两件事。而且 Nacos 支持 AP/CP 切换--服务发现用 AP(可用性优先),配置管理用 CP(一致性优先)。

扩展:Nacos 2.x 通过 gRPC 长连接通信,不再需要 HTTP 心跳轮询。阿里双十一验证过超大规模场景。

2a. Nacos 的服务注册与发现流程?

服务提供者启动:
  → Nacos Client 发送 REST 请求注册实例
  → Nacos Server 存储实例到本地缓存(ConcurrentHashMap)
  → 异步同步到 MySQL(持久化实例)
  → 向订阅该服务的 Client 推送变更通知

服务消费者启动/调用:
  → Nacos Client 订阅服务
  → Nacos Server 返回当前所有健康实例列表
  → Nacos Client 本地缓存实例列表
  → 按负载均衡策略选择实例发起调用

服务变更(健康检查):
  → Nacos Server 定时检查实例心跳
  → 30s 无心跳 → 标记 unhealthy → 剔除
  → 推送变更通知给订阅者
  → 消费者刷新本地缓存

面试话术:"提供者启动时注册到 Nacos Server,消费者订阅服务获取实例列表并本地缓存。健康检查通过心跳机制--临时实例 30 秒无心跳剔除,永久实例由服务端主动探测。变更通过 gRPC 长连接实时推送给订阅者。"

2b. Nacos 的心跳机制?

实例类型 心跳方式 超时处理
临时实例(ephemeral=true) 客户端每 5 秒主动发送心跳 15s 未收到 → 标记 unhealthy,30s 未收到 → 剔除
永久实例(ephemeral=false) 服务端主动探测(TCP/HTTP) 不健康不剔除,仅标记

临时实例适合无状态服务(Pod/IP 漂移场景),永久实例适合有状态服务(数据库、缓存)。

2c. Nacos 2.x gRPC 通信原理?

Nacos 2.x 基于 gRPC 实现长连接:

1. Client 启动时:与 Server 建立 9848 端口的 gRPC 连接,建立 Session
2. 配置/服务变更时:Server 直接通过 gRPC Stream 推送,无需 Client 轮询
3. 优势:毫秒级推送(vs 1.x 的 30s 轮询)、服务端资源占用更低、支持双向通信
4. 降级机制:2.x Server 仍保留 HTTP 接口,1.x Client 可正常访问

Nacos 三个关键端口:8848(HTTP 控制台 + REST API)、9848(gRPC 客户端↔服务端通信,必须开放)、9849(服务端↔服务端 Raft 协议,集群内互通)。

2d. Nacos 的 Namespace 和 Group 的区别?

概念 作用 隔离级别
Namespace 环境隔离 最彻底(dev/test/prod)
Group 项目/模块分组 中等(DEFAULT_GROUP / 自定义)
Data ID 配置文件标识 细粒度(应用级别)

典型使用:Namespace: dev → Group: order-service → Data ID: order-service-dev.yaml

2e. Nacos 集群选主机制?

Nacos 使用 Raft 协议进行 Leader 选举: 1. 初始状态:所有节点为 Follower 2. 选举超时(150-300ms 随机)→ Follower 变为 Candidate,发起选举,给自己投票 3. 获得多数票的节点成为 Leader 4. Leader 发送心跳(AppendEntries)维持领导地位 5. 若 Leader 故障,其他节点重新选举

2f. Nacos vs Eureka vs Spring Cloud Config?

对比项 Nacos Eureka Spring Cloud Config
维护状态 阿里巴巴活跃维护 Netflix 已停更 Spring 官方
功能 注册中心 + 配置中心 仅注册中心 仅配置中心
一致性 CP+AP 可切换 仅 AP 依赖 Git
配置推送 gRPC 毫秒级 无 Git Webhook + Bus
界面 有 无 无
推荐度 新项目首选 已淘汰 需配套组件多

3. Nacos 的 AP 和 CP 如何切换?

AP vs CP 切换:

临时实例(ephemeral=true,默认) → AP 模式
  协议:Distro(阿里自研,最终一致性)
  特点:挂了也能继续提供发现服务(可能拿到旧数据)
  场景:服务注册(拿到旧实例比拿不到强)

持久实例(ephemeral=false) → CP 模式
  协议:Raft(强一致性)
  特点:网络发生分区时,少数派不可用,保证数据一致
  场景:配置管理(宁可不更新,不能拿到错误配置)

生产实践:服务注册用临时实例(AP),配置管理用持久实例(CP)。Nacos 一个集群可以同时支持两种实例。

扩展:Eureka 纯 AP(所有实例平等,无 Leader,挂了也能读本地缓存保障可用性)、Zookeeper 纯 CP(Leader 选举期间整个集群不可用)、Consul 默认 CP。选型建议:服务发现选 AP(可用性 > 一致性),配置中心选 CP(一致性 > 可用性)。

4. 微服务网关的作用?

网关 = 所有请求的"前台"

客户端 → [Gateway 网关] → 后端服务
              │
              ├─ 路由转发:/order/** → 订单服务,/user/** → 用户服务
              ├─ 统一认证:在网关验证 JWT,后端不用再验
              ├─ 限流熔断:QPS 超阈值 → 拒绝 / 排队
              ├─ 日志采集:记录每个请求的耗时、状态码
              ├─ 跨域处理:统一 CORS 配置,不用每个服务配
              └─ 协议转换:外部 HTTP → 内部 Dubbo/gRPC

就像公司前台--所有访客先过前台,前台登记、刷身份证、告诉你坐哪个电梯。你不需要认识每个部门的人。

扩展:Spring Cloud Gateway(基于 WebFlux,响应式,推荐) vs Zuul 1.x(Servlet 阻塞式,已淘汰) vs Zuul 2.x(Netty 异步,非 Spring 系)。Gateway 用 Route → Predicate(匹配条件)→ Filter(处理逻辑)的三段式设计。注意网关不能做太重--业务逻辑应该放后端,网关只做横切关注点。

5. Sentinel 的核心原理和流控方式?

Sentinel 核心是基于 Slot Chain(处理器链) 实现的,就像机场安检流水线:

请求 → NodeSelectorSlot → StatisticSlot → FlowSlot → DegradeSlot → SystemSlot → 业务逻辑

每个 Slot 各司其职:StatisticSlot 实时统计(滑动窗口,500ms 一个采样点)、FlowSlot 检查限流规则、DegradeSlot 检查熔断规则、SystemSlot 检查系统保护。任何一个 Slot 判断需要拦截,就抛出异常,后续业务不执行。

五种限流方式: 1. QPS 限流:每秒请求数限制--最常用 2. 并发线程数限流:同时执行线程数限制--控制并发深度 3. 热点参数限流:参数级别的细粒度限流--针对特定用户/商品 4. 系统自适应保护:CPU/Load/RT 自适应--全局保护 5. 集群流控:Token Server 统一管控集群总 QPS--多节点协同

Sentinel 使用滑动窗口算法(非固定窗口),解决了临界突变问题。相比 Hystrix 的关键优势:Hystrix 只支持并发线程数限流,Sentinel 支持 QPS 限流。

5a. Sentinel 熔断有哪些策略?

三种策略: 1. 慢调用比例熔断:响应时间 > 阈值的慢调用占比 > 设定值 → "服务太慢了,先停一下" 2. 异常比例熔断:异常请求占比 > 阈值 → "出错的太多了" 3. 异常数熔断:异常请求数量 > 阈值 → "连续出错"

熔断状态机:Closed(正常)→ 触发条件 → Open(熔断,直接拒绝)→ 等待时间窗 → Half-Open(放一个请求试探)→ 成功 → Closed / 失败 → Open。

面试亮点:minRequestAmount 是个巧妙的参数--窗口内请求太少时不触发熔断,避免冷启动误判。

5b. @SentinelResource 的 blockHandler 和 fallback 有什么区别?

参数 触发条件 异常类型 大白话
blockHandler Sentinel 限流/熔断触发 BlockException "门口保安拦住你了"
fallback 业务代码抛出异常 Throwable "你自己在业务里摔倒了"

blockHandler 处理流量控制(被"拦住"了),fallback 处理业务异常(业务逻辑自身出了 Bug)。两者是不同层面的保护。

5c. Sentinel 如何实现动态规则推送?

核心是 "写存分离"模式: 1. 外部存储(Nacos/Apollo/ZooKeeper)存储规则--真正的"数据库" 2. 客户端通过数据源监听规则变更(Watcher/Listener) 3. 规则变更时,客户端自动加载新规则--无需重启服务 4. Dashboard 修改规则 → 写入 Nacos → 客户端监听生效

一句话:Dashboard 只管"改",Nacos 负责"存",客户端负责"听"。

扩展:Sentinel 客户端无状态,不依赖 Dashboard(Dashboard 挂了不影响限流)。规则存 Nacos/Apollo,Sentinel 崩溃不影响业务。

7. CAP 定理?

CAP 定理:

C(Consistency):所有节点同一时刻看到的数据相同
A(Availability):每个请求都能收到响应(不管成功失败)
P(Partition Tolerance):网络分区时系统仍能工作

为什么只能三选二:
  网络出问题了(P 发生)→ 节点之间断了联系
  → 要么等它们恢复(放弃 A,选 CP)
  → 要么先响应用户(放弃 C,选 AP)

注册中心选型:
  Nacos:AP / CP 可切换(新项目首选)
  Eureka:AP(宁可拿到旧地址也不能拿不到地址列表)→ 已停更
  Zookeeper:CP(Leader 挂了选举期间整个不可用)→ 老项目在用
  Consul:CP(强一致,健康检查精确但性能低)

扩展:CAP 是"网络分区时"的取舍,不是常态。Paxos/Raft 在保证 P 的前提下兼顾 C 和 A。

8. 服务间通信方式?

三种通信方式对比:

同步 HTTP/REST(OpenFeign):
  适用:查询类接口,需要立即拿到结果
  优点:简单、通用、跨语言
  缺点:调用方等待,下游慢你也慢

同步 RPC(Dubbo/gRPC):
  适用:内部高性能服务间调用
  优点:序列化快、长连接、支持多种负载均衡
  缺点:耦合语言(Dubbo 是 Java 生态)

异步消息(RocketMQ/Kafka):
  适用:不需要立即结果的场景(下单→发短信)
  优点:解耦、削峰、最终一致
  缺点:增加复杂度,调试困难

扩展:gRPC 基于 Protobuf + HTTP/2,跨语言能力强,是云原生场景首选 RPC 方案。

9. 如何保证接口幂等性?

幂等 = 支付多次不会扣多次钱

场景:用户点了两次"提交订单"按钮
      或网关超时重试,后端实际执行了两次

方案1:数据库唯一索引
  INSERT INTO orders (order_id, ...)
  → 重复 order_id 直接报错(DupliateKeyException)
  最可靠,适合新建操作

方案2:Token 机制
  提交前先 GET /token(服务器发 Token)
  提交时带 Token → 服务器校验 Token → 删除 Token
  第二次提交 → Token 已不存在 → 拒绝

方案3:状态机
  UPDATE orders SET status='PAID' WHERE id=5 AND status='UNPAID'
  第二次执行 → status 已经不是 UNPAID → 影响行数为 0

方案4:乐观锁
  UPDATE orders SET ... version=version+1 WHERE id=5 AND version=3

扩展:MQ 消费幂等通常用消息表 + 唯一索引:INSERT INTO msg_consumed (msg_id) VALUES (?)。

12. 配置中心如何实现动态刷新?

Nacos 配置动态刷新流程:

1 修改 Nacos 配置 → Nacos 推送变更通知
2 收到通知 → 发布 RefreshEvent 事件
3 @RefreshScope 的 Bean → 懒加载代理被标记为"脏"
4 下次访问该 Bean → 代理销毁旧 Bean → 重新创建 → 新配置生效
5 不需要重启应用!

关键机制:@RefreshScope 本质是 @Scope("refresh") 的作用域代理--Bean 被代理包装,当收到 RefreshEvent 时,代理清空缓存,下次调用再重新创建。

扩展:@RefreshScope 是懒刷新。@ConfigurationProperties 天然支持刷新,无需额外加 @RefreshScope。

13. 负载均衡策略?

策略 原理 适用
轮询 一个个轮 通用
加权轮询 配置高的机器多分 机器配置不均
最小连接数 谁最闲给谁 长连接/耗时差异大
一致性哈希 同一用户固定到同一台 有状态/需要亲和性
随机 随便选 简单场景

Spring Cloud LoadBalancer(替代了 Ribbon)默认使用轮询。Dubbo 的加权随机更精细,可以根据预热时间(warmup)给刚启动的机器少分配流。

扩展:Ribbon 已进入维护模式,Spring Cloud 推荐 Spring Cloud LoadBalancer。Gateway 和微服务内部是两层负载均衡。

14. OpenFeign 的原理?

OpenFeign 工作原理:

@FeignClient(name = "user-service")
interface UserClient {
    @GetMapping("/user/{id}")
    User getUser(@PathVariable Long id);
}

底层流程:
1 Spring 扫描 @FeignClient 接口
2 为接口创建 JDK 动态代理
3 调用 getUser(1L) 时:
   → 代理拦截 → 解析注解(GET + /user/{id} + 参数)
   → 从负载均衡获取 user-service 的实例地址
   → 发送 HTTP 请求 → 解析响应 → 返回 User 对象

本质是动态代理--你调接口方法,代理在背后替你发 HTTP 请求、解析返回。集成了负载均衡(Spring Cloud LoadBalancer)和熔断(Sentinel)。

扩展:Feign 底层可换 OkHttp(连接池,性能好)。Spring Boot 3.x 下 @FeignClient 支持 fallback 降级。

15. 微服务链路追踪如何实现?

链路追踪原理:

用户请求 → 生成全局唯一的 TraceId
  ├─ 服务A(SpanId: A, ParentSpanId: null, TraceId: T001)
  │   └─ 调用服务B → HTTP Header 传 TraceId + SpanId
  ├─ 服务B(SpanId: B, ParentSpanId: A, TraceId: T001)
  │   └─ 调用服务C
  └─ 服务C(SpanId: C, ParentSpanId: B, TraceId: T001)

所有 Span 用同一个 TraceId,形成完整调用链
出问题时按 TraceId 串起所有日志 → 定位哪个环节出错

主流方案: - SkyWalking(推荐):Java Agent 自动埋点,零代码侵入。性能好,支持多种语言和中间件 - Sleuth + Zipkin:Spring 生态,轻量但功能有限(Sleuth 已进入维护模式,推荐迁移到 Micrometer Tracing) - Jaeger:CNCF 项目,兼容 OpenTracing 标准

扩展:Micrometer Tracing 是 Spring Cloud 新一代追踪方案(Spring Boot 3.x 推荐)。生产采样率一般设 10%-30%。

16. Sentinel 熔断降级规则有哪些类型?

三种策略: - 慢调用比例:响应时间超过阈值的比例超过设定值时熔断 - 异常比例:异常请求比例超过阈值时熔断 - 异常数:异常请求数量超过阈值时熔断

熔断状态机:Closed(正常)→ 触发条件 → Open(熔断,直接拒绝)→ 等待时间窗口到期 → Half-Open(放一个请求试探)→ 成功 → Closed / 失败 → Open。

17. Spring Cloud Alibaba 包含哪些组件?各自作用?

组件 功能 一句话概括
Nacos 注册中心 + 配置中心 服务的"通讯录"和"公告栏"
Sentinel 流量控制 + 熔断降级 交通管制中心
Seata 分布式事务 跨行转账协调器
Dubbo 高性能 RPC 框架 服务间高速公路
RocketMQ 分布式消息 异步快递系统
SchedulerX 分布式任务调度 定时工作分配器

Spring Cloud Alibaba 是 Netflix 停更后的替代方案--Nacos 替代 Eureka+Config、Sentinel 替代 Hystrix、Dubbo 替代 Feign+Ribbon、Seata 填补分布式事务空白。

18. Dubbo 和 Feign 的区别?如何选型?

对比项 Dubbo Feign
协议 Dubbo 协议(TCP)/ HTTP / gRPC HTTP/REST
性能 高(约 10 万 TPS) 中(约 2 万 TPS)
连接 长连接(Netty) 短连接
适用场景 内部高性能 RPC 对外 HTTP API
服务治理 完整(限流/路由/权重) 基础

选型建议:内部微服务调用优先 Dubbo(高性能、低延迟),对外暴露 API / 与前端交互使用 Feign(标准化 REST)。

19. RocketMQ 事务消息解决什么问题?

解决本地事务成功但消息发送失败的分布式一致性问题。

传统 MQ 问题:
  业务 DB 操作(成功)→ 发送 MQ 消息(失败)→ 下游收不到消息,数据不一致

RocketMQ 事务消息:
  1. TM 向 MQ 发送半消息(Half Message,消费者不可见)
  2. 执行本地事务
  3. 本地事务成功 → Commit → 消费者可见
     本地事务失败 → Rollback → 消费者不可见
  4. MQ Broker 定期回调 TM 检查事务状态(解决网络闪断)

20. 如何保证微服务架构的稳定性?

Spring Cloud Alibaba 全链路稳定性保障:

1. 流量控制(Sentinel):QPS 限流 + 并发限流 + 热点参数限流
2. 熔断降级(Sentinel / Dubbo 集群容错):慢调用/异常比例熔断 + 降级兜底
3. 隔离策略:Nacos 命名空间隔离 + 线程池隔离 + Dubbo 服务分组隔离
4. 超时控制:各层合理超时(Dubbo 默认 3000ms,Feign 默认 1000ms)
5. 幂等设计:消息消费幂等(去重表/唯一键)+ 接口幂等(Token/乐观锁)
6. 监控告警:Sentinel Dashboard + RocketMQ 堆积监控 + Nacos 健康检查 + ELK

核心思路:从限到熔、从拦到疏、从外到内--层层递进,不依赖单一防线。

21. Seata AT 模式的回滚日志是如何存储和恢复的？

Seata AT 模式通过 undolog（回滚日志） 实现自动补偿：

执行流程:
TC(Transaction Coordinator)
  ↓ 一阶段：注册全局事务
  ↓ 
TM(Transaction Manager) — 应用端
  ↓ 开启分支事务
  Branch1: UPDATE account SET bal=bal-100 WHERE id=1
    ↓ 记录前置镜像 (before_image): id=1, bal=原值
    ↓ 执行 SQL
    ↓ 记录后置镜像 (after_image): id=1, bal=新值
    ↓ 异步向 TC 注册分支，TC 写 undolog 到 db
  ↓ 二阶段（commit）：
    TC: 删除 undolog（全局事务结束）
  ↓ 二阶段（rollback）：
    TC: 读取 undolog 前后镜像
    逆 SQL: UPDATE account SET bal=原值 WHERE id=1

undolog 表结构（AT 模式）：

CREATE TABLE `undo_log` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `branch_id` bigint NOT NULL,
  `xid` varchar(100) NOT NULL,
  `context` varchar(128) NOT NULL,
  `rollback_info` longblob NOT NULL,  -- JSON 存储前后镜像
  `log_status` int NOT NULL,
  `log_created` datetime NOT NULL,
  `log_modified` datetime NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `ux_undo_log` (`xid`,`branch_id`)
);

扩展：undolog 和业务表在同一 DB，同一事务提交；性能优于 XA（因为是本地事务），但只能用于支持 ACID 的关系型 DB；TCC 模式不依赖 undolog，需自己实现补偿逻辑。
