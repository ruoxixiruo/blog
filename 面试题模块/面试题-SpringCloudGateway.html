Spring Cloud Gateway

Gateway 就像微服务体系的"前台小姐"--所有访客(请求)先过她,她负责查身份(认证)、指路(路由)、限流(排队)、看谁关门了换别家(熔断降级)。基于 WebFlux + Netty,异步非阻塞,性能远超 Zuul。

1. Spring Cloud Gateway 的核心组件和工作原理?

Gateway 就像一个智能快递分拣中心--来了包裹(请求),看标签(匹配路由),在传送带上处理(Filter 链),最后送达到目的地(下游服务)。

Spring Cloud Gateway 请求处理全流程:

┌─────────────────────────────────────────────────────────────┐
│                    客户端请求                                │
│              GET /api/users/123                              │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  1 Gateway Handler Mapping                                   │
│     遍历所有 Route,用 Predicate 匹配请求                      │
│     ┌─────────────────────────────────────────────────┐    │
│     │ Route 1: Path=/order/**    → 不匹配              │    │
│     │ Route 2: Path=/api/users/** → ✅ 匹配!找到第一个 │    │
│     │ Route 3: Path=/api/**      → 跳过(已找到)        │    │
│     └─────────────────────────────────────────────────┘    │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  2 组装该 Route 的 Filter 链                                  │
│     GlobalFilter 集合 + Route 专属的 GatewayFilter 集合       │
│     按 order 值统一排序                                       │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  3 执行 Pre Filter 链(order 小的先执行)                     │
│     · RateLimiter: 检查限流(order=1)                        │
│     · AuthFilter: 验证 JWT Token(order=2)                   │
│     · StripPrefix=1: 去掉 /api → /users/123(order=3)       │
│     · AddRequestHeader: 加 X-User-Id(order=4)              │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  4 代理请求到下游服务                                         │
│     lb://user-service → Nacos 获取实例 → 转发 /users/123      │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  5 执行 Post Filter 链(order 大的先执行,Pre 的逆序)        │
│     · LogFilter: 记录耗时 45ms(order=100)                   │
│     · AddResponseHeader: 加 X-Response-Time(order=99)      │
└──────────────────────────┬──────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                    返回响应给客户端                            │
└─────────────────────────────────────────────────────────────┘

核心三兄弟: - Route(路由):id + uri + predicates + filters,定义了一条请求转发规则 - Predicate(断言):Java 8 函数式接口,匹配请求的路径/方法/Header/参数等 - Filter(过滤器):分 GatewayFilter(路由级)和 GlobalFilter(全局),修改请求和响应

2. Spring Cloud Gateway 和 Zuul 的区别?

Gateway vs Zuul 并发模型对比:

  Zuul 1.x(同步阻塞 Servlet 模型):
┌────────────────────────────────────┐
│  请求 1 → 线程 1 → 阻塞等下游响应    │
│  请求 2 → 线程 2 → 阻塞等下游响应    │
│  请求 3 → 线程 3 → 阻塞等下游响应    │
│  ...                               │
│  请求 100 → 线程 100(线程池耗尽!)  │
│                                    │
│  问题: 1请求=1线程,线程大部分时间    │
│        在"等",浪费资源              │
│  性能: ~5K RPS                      │
└────────────────────────────────────┘

  Gateway(异步非阻塞 Netty 模型):
┌────────────────────────────────────┐
│  请求 1 ─┐                          │
│  请求 2 ─┤                          │
│  请求 3 ─┼→ 少量 EventLoop 线程     │
│  请求 4 ─┤   接收 → 异步发下游       │
│  请求 5 ─┤   下游响应 → 异步回写     │
│    ...  ─┘   线程永不阻塞           │
│                                    │
│  优势: 1个线程处理成千上万连接       │
│  性能: ~30K RPS(6倍于 Zuul 1.x)   │
└────────────────────────────────────┘
对比项 Gateway Zuul 1.x Zuul 2.x
I/O 模型 Netty 异步非阻塞 Servlet 同步阻塞 Netty 异步非阻塞
RPS ~30K ~5K ~15K
背压支持 ✅ Reactor ❌ ✅
维护状态 ✅ Spring 官方 ❌ 2018 停更 ⚠️ 社区维护
Spring 集成 ✅ 原生 ⚠️ 适配 ⚠️ 适配

面试话术:"Gateway 替代 Zuul 的核心原因是 I/O 模型升级--从 Servlet 同步阻塞变成 Netty 异步非阻塞。就像餐厅从'一桌配一个服务员'变成'一个服务员处理十桌',吞吐量提升 6 倍。再加上 Spring 生态原生集成和背压支持,新项目毫无疑问选 Gateway。"

3. GatewayFilter 和 GlobalFilter 的区别?

Filter 作用范围示意:

  GlobalFilter(全局,所有路由生效):
  ┌──────────────────────────────────────────────────┐
  │  Route /api/users/**  ─┐                         │
  │  Route /api/orders/** ─┼─ 全部经过 AuthFilter    │
  │  Route /api/pay/**    ─┘  全部经过 LogFilter     │
  │  Route /web/**        ─┘                         │
  └──────────────────────────────────────────────────┘

  GatewayFilter(路由级,仅指定路由生效):
  ┌──────────────────────────────────────────────────┐
  │  Route /api/users/** → StripPrefix=1 + AddHeader │
  │  Route /api/orders/** → RateLimiter 限流          │
  │  Route /api/pay/** → RateLimiter 更严格的限流     │
  │  Route /web/** → 无额外 Filter                    │
  └──────────────────────────────────────────────────┘
维度 GatewayFilter GlobalFilter
作用范围 单个路由(需在 YAML 中引用) 所有路由(全局生效)
注册方式 YAML filters 节点 @Component 自动注册
排序 和 GlobalFilter 混合按 order 排序 同左
典型场景 路径改写、添加请求头、路由级限流 认证、全局限流、日志、CORS

4. Gateway 的过滤器执行顺序?

Filter 执行顺序(关键!面试高频):

  Pre 阶段(请求方向):order 越小越先执行
  ┌──────────────────────────────────────────────────────────┐
  │  GlobalFilter-A (order=-1)                               │
  │    → GlobalFilter-B (order=0)                            │
  │      → GatewayFilter-C (order=1)                         │
  │        → GatewayFilter-D (order=5)                       │
  │          → 转发到下游服务 ...                              │
  └──────────────────────────────────────────────────────────┘

  Post 阶段(响应方向):order 越大越先执行(Pre 的逆序!)
  ┌──────────────────────────────────────────────────────────┐
  │  下游服务响应返回                                          │
  │    → GatewayFilter-D (order=5, Post 最先执行)             │
  │      → GatewayFilter-C (order=1)                         │
  │        → GlobalFilter-B (order=0)                        │
  │          → GlobalFilter-A (order=-1, Post 最后执行)       │
  └──────────────────────────────────────────────────────────┘

  记忆技巧: Pre 越小越靠前,Post 越大越靠前 -- 完美的对称结构

5. Gateway 如何实现限流?

三种方案选择:

  方案 1: Redis 令牌桶(内置,推荐起步使用)
  ┌──────────────────────────────────────────┐
  │  请求 → Redis Lua 脚本检查令牌            │
  │  有令牌 → 减 1,放行                     │
  │  无令牌 → 429 Too Many Requests         │
  │  适用: 单实例或分布式环境                  │
  │  配置: 5 行 YAML 搞定                    │
  └──────────────────────────────────────────┘

  方案 2: 自定义限流(灵活,适合特殊需求)
  ┌──────────────────────────────────────────┐
  │  @Component GlobalFilter                 │
  │  使用 Guava RateLimiter 或自己写算法      │
  │  适用: 单实例简单场景                     │
  │  注意: 分布式环境需配合外部存储            │
  └──────────────────────────────────────────┘

  方案 3: Sentinel 集成(最强,生产推荐)
  ┌──────────────────────────────────────────┐
  │  spring-cloud-alibaba-sentinel-gateway   │
  │  支持: QPS/并发/热点/系统自适应 全维度限流  │
  │  Dashboard 可视化管理                    │
  │  + 熔断降级一站式                        │
  │  适用: 中大型项目、需要 Dashboard 的团队   │
  └──────────────────────────────────────────┘

# 方案 1 配置示例
spring:
  cloud:
    gateway:
      routes:
        - id: rate-limited-route
          uri: lb://user-service
          predicates: [Path=/api/users/**]
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10   # 每秒 10 个令牌
                redis-rate-limiter.burstCapacity: 20    # 突发容量 20
  redis:
    host: localhost

  │  Nacos 配置中心            │
  │  存储路由配置 YAML          │
  └──────────┬───────────────┘
             │ 1 监听配置变更
             ▼
  ┌──────────────────────────┐
  │  Gateway 配置监听器        │
  │  NacosConfigListener      │
  └──────────┬───────────────┘
             │ 2 收到变更通知
             ▼
  ┌──────────────────────────┐
  │  RouteDefinitionWriter    │
  │  更新内存中的路由定义       │
  └──────────┬───────────────┘
             │ 3 发布事件
             ▼
  ┌──────────────────────────┐
  │  ApplicationEventPublisher│
  │  RefreshRoutesEvent       │
  └──────────┬───────────────┘
             │ 4 刷新缓存
             ▼

# 核心配置
spring:
  cloud:
    nacos:
      discovery:
        server-addr: nacos:8848   # 服务发现
      config:
        server-addr: nacos:8848   # 配置中心

    gateway:

        locator:

面试话术:"Gateway + Nacos 的组合拳--Nacos 存路由配置,Gateway 监听配置变更,通过 RouteDefinitionWriter 更新路由定义,再发布 RefreshRoutesEvent 刷新缓存。整个流程无需重启,毫秒级生效。这是生产环境动态路由的标准方案。"

8. Gateway 如何处理超时和熔断?

# 完整的超时 + 熔断配置
spring:
  cloud:
    gateway:
      httpclient:
        connect-timeout: 1000        # 连接超时 1 秒
        response-timeout: 5s         # 响应超时 5 秒
        pool:
          max-connections: 500       # 最大连接池
      routes:
        - id: protected-route
          uri: lb://user-service
          predicates: [Path=/api/users/**]
          filters:
            # 熔断配置
            - name: CircuitBreaker
              args:
                name: userServiceCB
                fallbackUri: forward:/fallback/user
            # 限流配置
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20

超时 + 熔断 + 限流 三者配合:超时防止线程阻塞 → 熔断防止雪崩 → 限流防止过载。网关层的"三层防护"。

9. Gateway 如何支持 WebSocket?

Gateway 通过内置的 WebSocketRoutingFilter 自动处理 WebSocket 升级。URI 使用 ws:// 或 wss://,支持 STOMP、SockJS 等子协议。配置几乎和普通路由一样,只是 URI 协议不同。

spring:
  cloud:
    gateway:
      routes:
        - id: websocket-route
          uri: ws://websocket-service:8080
          predicates:
            - Path=/ws/**

11. Gateway 如何实现灰度发布/金丝雀发布?

核心结论:利用 Gateway 的权重路由 + 自定义 Header/XFF,实现按比例/按用户/按标签的流量灰度。

# 按权重灰度:90% 流量走 v1,10% 走 v2
spring:
  cloud:
    gateway:
      routes:
        - id: user-service-gray
          uri: lb://user-service
          predicates:
            - Path=/api/users/**
          filters:
            - name: RewritePath
              args:
                regexp: /api/users/(?<segment>.*)
                replacement: /$\{segment}

# 更常见的方式:配合 Nacos 元数据路由
# v1 实例 metadata: version=v1
# v2 实例 metadata: version=v2
# Gateway 根据 header 或 cookie 决定路由到哪个版本

灰度策略:

灰度维度:
1. 按 Header(Claude-Gray: v2) → 适合测试人员
2. 按 Cookie(userId 在白名单) → 适合内部用户
3. 按权重(10%) → 适合渐进式发布
4. 按 IP 段 → 适合特定地区灰度

面试话术:"Gateway 做灰度发布是最合适的入口,因为所有流量都过它。配合 Nacos 的元数据和负载均衡,可以实现非常灵活的灰度策略。关键是灰度期间要能对比新旧版本的核心指标(错误率、延迟P99),确认 v2 没问题再全量。"

12. Gateway 的跨域(CORS)怎么配置?有哪些坑?

核心结论:Gateway 统一配置 CORS,微服务本身不再重复配置。

spring:
  cloud:
    gateway:
      globalcors:
        cors-configurations:
          '[/**]':
            allowed-origins: "https://www.example.com"
            allowed-methods: GET,POST,PUT,DELETE,OPTIONS
            allowed-headers: "*"
            allow-credentials: true
            max-age: 3600

踩坑点:

  1. allowed-origins 不能写 * 同时 allow-credentials: true--这是 CORS 协议硬性规定,写 * 浏览器会直接拒绝带 Cookie 的请求
  2. OPTIONS 预检请求不要带认证 Header--否则 OPTIONS 也走认证过滤器,预检失败 CORS 直接不通过
  3. max-age 合理设置--避免每次复杂请求都发 OPTIONS 预检
  4. 和 Nginx 不要重复配置 CORS--会导致 Access-Control-Allow-Origin 重复,浏览器报错
// 认证过滤器中跳过 OPTIONS 预检请求

public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    if (exchange.getRequest().getMethod() == HttpMethod.OPTIONS) {
        return chain.filter(exchange);  // OPTIONS 直接放行
    }

}

13. Gateway 如何实现请求日志追踪(TraceId 透传)?

核心结论:Gateway 生成 TraceId,通过 Header 透传给下游所有服务,实现全链路日志关联。

@Component
public class TraceFilter implements GlobalFilter, Ordered {
    private static final String TRACE_ID = "X-Trace-Id";

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String traceId = exchange.getRequest().getHeaders().getFirst(TRACE_ID);
        if (traceId == null) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        // 往下游透传 TraceId
        ServerHttpRequest request = exchange.getRequest().mutate()
            .header(TRACE_ID, traceId)
            .build();
        // 用 MDC 让日志框架自动带上 TraceId
        MDC.put("traceId", traceId);
        return chain.filter(exchange.mutate().request(request).build())
            .doFinally(s -> MDC.remove("traceId"));
    }

    @Override
    public int getOrder() { return Ordered.HIGHEST_PRECEDENCE; }
}

logback 配置自动输出 TraceId:

<pattern>%d{HH:mm:ss} [%X{traceId}] [%thread] %-5level %logger{36} - %msg%n</pattern>

面试话术:"全链路追踪的第一步是每个请求有唯一 ID。Gateway 作为流量入口,最适合生成和透传 TraceId。配合 MDC + logback,所有服务的日志都能自动带上 TraceId,排查问题时 grep 一下就能串起整个调用链。再接入 SkyWalking/ZipKin 就是完整的分布式追踪方案。"

21. Spring Cloud Gateway 如何实现全链路灰度？

Spring Cloud Gateway 通过 流量染色 + 标签路由 实现灰度发布：

# application.yml
spring:
  cloud:
    gateway:
      routes:
        - id: service-a
          uri: lb://service-a
          predicates:
            - Header=X-Target-Version=2.0    # Header 染色
            - Weight=service-a, 10           # 10% 流量走新版本
      default-filters:
        - AddRequestHeader=X-Gray-Tag, v1   # 默认 v1

# Nacos 配置动态路由
spring:
  cloud:
    nacos:
      discovery:
        server-addr: nacos:8848
        group: GRAY_GROUP  # 灰度服务单独分组

灰度路由策略：

Gateway 过滤器实现灰度：

@Component
public class GrayReleaseFilter implements GlobalFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String version = getTargetVersion(exchange);  // 从 Nacos 获取目标版本

        // 根据版本选择下游服务实例
        ServiceInstance instance = loadBalancer.choose(exchange, version);

        // 修改目标 URL
        String url = "http://" + instance.getHost() + ":" + instance.getPort();
        exchange.getAttributes().put("requestUri", url);

        return chain.filter(exchange);
    }
}
