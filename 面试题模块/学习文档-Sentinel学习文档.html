Sentinel 面试学习文档

Sentinel 是微服务的"商场安保系统"——限流 = 门口闸机，熔断 = 消防喷淋，降级 = 备用电源。

1. Sentinel 是干什么的？

1.1 白话理解

类比：你开了一家网红奶茶店。平时一天卖 200 杯，突然某个大V拍了探店视频，第二天门口排了 5000 人。这时候你需要：

  • 限流员站在门口："一次最多进 50 个人排队，后面的等等" —— QPS 限流
  • 制冰机坏了马上停止卖冰饮，不让顾客干等 —— 熔断降级
  • 排队堵死走廊时关闭部分点单窗口 —— 系统保护

Sentinel 就是阿里巴巴为微服务打造的这套"商场安保系统"，专门在流量洪峰、服务雪崩等极端情况下保护系统稳定性。

  • GitHub：https://github.com/alibaba/Sentinel
  • 起源：2012 年阿里内部诞生，每年双十一扛几十亿次调用，2018 年开源

1.2 解决什么痛点

微服务架构四大稳定性问题：

1. 流量激增（秒杀/突发流量）
   → 下游被压垮 → Sentinel：QPS 限流
   类比：地铁站节假日限流，分批放行

2. 服务雪崩（级联故障）
   → A → B 变慢 → A 线程池耗尽 → 链式崩溃
   → Sentinel：熔断降级
   类比：多米诺骨牌中间抽掉一张，别让它一路塌下去

3. 系统过载（CPU/内存打满）
   → Sentinel：系统自适应保护
   类比：电脑太烫自动降频，别烧主板

4. 慢调用拖垮服务
   → 某个外部接口变慢 → 连接池/线程池耗尽
   → Sentinel：慢调用比例熔断
   类比：一个慢的取件口堵了所有人，直接关掉这个口

1.3 核心特性速览

特性 说明 大白话
流量控制 QPS / 并发线程数 / 关联限流 控制"多少人同时进来"
熔断降级 慢调用比例 / 异常比例 / 异常数 某个出口坏了就关了，不浪费时间
热点限流 参数级别的细粒度限流 针对特定商品/用户单独限流
系统保护 CPU / 内存 / Load 自适应 整台机器快扛不住了，全局减速
网关限流 Spring Cloud Gateway / Zuul 集成 在"大门"就拦住
可视化 Dashboard 实时监控 + 动态规则 看得见的大屏监控
动态规则 Nacos / Apollo / ZooKeeper / Redis 改规则不用重启
开箱即用 注解 / 代码 / 配置多种接入 接进来就能用

2.4 滑动窗口统计

Sentinel 使用滑动窗口算法实时统计指标，解决固定窗口的"临界突变"问题——即流量恰好卡在窗口边界时的统计跳跃。

窗口配置：每秒 2 个采样窗口（500ms 一个）

单个窗口记录：
  pass      通过请求数
  block     被限流/熔断请求数
  exception 异常请求数
  rt        响应时间
  success   成功请求数

滑动窗口示例（1 秒）：
  [窗口1: 0-500ms]   [窗口2: 500-1000ms]
  pass:      50       pass:      52       → QPS = 102
  block:      3       block:      1       → 总限流 = 4
  exception:  0       exception:  1       → 异常率 = 1/102

多级统计：秒级（默认 1秒2窗口）→ 分钟级（60窗口）→ 小时级

3.2 限流维度

维度 含义 参数
QPS 每秒请求数限制——"每秒进多少人" FLOW_GRADE_QPS
并发线程数 同时处理中的线程数——"同时有多少人在处理" FLOW_GRADE_THREAD

3.3 限流策略

策略 关系 大白话
直接（DIRECT） 自身 限制自己的接口 QPS
关联（RELATE） 关联资源 "隔壁队伍太长了，我这队也限流"
链路（CHAIN） 入口链路 限制从特定入口进来的流量

3.4 流控效果

效果 大白话 适用场景
快速失败（Default） 超了就拒，毫不犹豫 通用场景
Warm Up（冷启动） 慢慢放开，别一开门就冲 秒杀/预热场景
匀速排队（Rate Limiter） 超了排队，不拒绝 削峰填谷

3.5 限流规则详解

// ========== 1. QPS 直接限流 ==========
FlowRule rule = new FlowRule("user-service")
    .setCount(100)                              // 阈值：100 QPS
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT)  // 快速失败
    .setStrategy(RuleConstant.STRATEGY_DIRECT)  // 直接限流
    .setLimitApp("default");                    // 限制来源（default=所有）

// ========== 2. 关联限流 ==========
// 当 order-service 的 QPS > 10 时，限流 user-service
FlowRule relatedRule = new FlowRule("user-service")
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(10)
    .setStrategy(RuleConstant.STRATEGY_RELATE)   // 关联限流
    .setRefResource("order-service");           // 关联资源

// ========== 3. 冷启动（Warm Up） ==========
// 预热 10 秒，从阈值 10% 逐渐提升到 100 QPS
FlowRule warmUpRule = new FlowRule("seckill-service")
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(100)
    .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP)
    .setWarmUpPeriodSec(10);  // 预热时间

// ========== 4. 匀速排队（削峰填谷） ==========
// 每 200ms 通过一个请求（QPS=5），超时 500ms
FlowRule rateLimitRule = new FlowRule("api-service")
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(5)
    .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER)
    .setMaxQueueingTimeMs(500);  // 最大排队等待时间

// ========== 5. 线程数限流 ==========
// 最大并发 50 个线程
FlowRule threadRule = new FlowRule("db-service")
    .setGrade(RuleConstant.FLOW_GRADE_THREAD)
    .setCount(50);

3.6 代码使用方式

// 方式1：SphU.entry()（手动埋点）
public String getUser(String userId) {
    Entry entry = null;
    try {
        entry = SphU.entry("getUser", EntryType.IN);
        // 业务逻辑
        return userService.getById(userId);
    } catch (BlockException e) {
        // 被限流/熔断
        return "系统繁忙，请稍后重试";
    } finally {
        if (entry != null) {
            entry.exit();
        }
    }
}

// 方式2：@SentinelResource 注解（推荐）
@SentinelResource(
    value = "getUser",
    blockHandler = "getUserBlockHandler",   // 限流/熔断处理
    fallback = "getUserFallback"             // 异常降级处理
)
public String getUser(String userId) {
    return userService.getById(userId);
}

// 限流处理方法（必须与原方法同参数 + BlockException）
public String getUserBlockHandler(String userId, BlockException ex) {
    return "请求过于频繁，请稍后重试";
}

// 异常降级处理方法（必须与原方法同参数 + Throwable）
public String getUserFallback(String userId, Throwable ex) {
    log.error("获取用户失败", ex);
    return "服务暂不可用";
}

4. 熔断降级（Degrade Rules）

4.1 什么是熔断

类比：自助餐厅的牛排区前面排了 30 个人都不动——你是继续等，还是换一个菜？熔断就是让你别等了，先去吃别的。Sentinel 会"暂停"这个窗口一段时间，再试探——好了就恢复，没好继续暂停。

4.2 三种熔断策略

策略 触发条件 大白话
慢调用比例 慢调用占比太高 "10个人里超过一半都等太久了，关窗口"
异常比例 报错占比太高 "10个人里一半都出错了，肯定有问题"
异常数 报错绝对数太高 "已经连续 10 个人出错了"

4.3 熔断状态机

           Sentinel 熔断状态机（三态流转）

                ┌──────────────┐
                │    CLOSED    │  正常状态：所有请求放行
                │  (正常通过)   │  持续统计：慢调用比例 / 异常比例 / 异常数
                └──────┬───────┘
                       │
          统计窗口内指标超过阈值？
          (如 慢调用比例 > 50%)
                       │
                       ▼
                ┌──────────────┐
                │     OPEN     │  熔断状态：所有请求直接拒绝
                │  (快速失败)   │  持续 timeWindow 秒（如 10s）
                └──────┬───────┘
                       │
             timeWindow 时间到
                       │
                       ▼
                ┌──────────────┐
                │  HALF-OPEN   │  半开状态：放行一个探测请求
                │ (试探性放行)  │
                └──────┬───────┘
                       │
            探测请求结果？
         ╱                             ╲
    成功                              失败
   ╱                                     ╲
  ▼                                       ▼
┌──────────┐                      ┌──────────┐
│  CLOSED  │                      │   OPEN   │
│ 恢复正常  │                      │ 重新熔断  │
└──────────┘                      └──────────┘

关键参数：
  minRequestAmount  —— 统计窗口最少请求数，避免冷启动误判
  statIntervalMs    —— 统计窗口时长（ms），默认 10000
  timeWindow        —— 熔断持续秒数，到期进入 Half-Open

4.4 熔断规则配置

// ========== 1. 慢调用比例熔断 ==========
// 响应时间 > 500ms 的请求 > 50% 且 窗口内请求数 > 5 → 熔断 10 秒
DegradeRule slowRule = new DegradeRule("payment-service")
    .setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType())
    .setCount(0.5)                    // 慢调用阈值（0.5 秒 = 500ms）
    .setSlowRatioThreshold(0.5)       // 慢调用比例阈值（50%）
    .setMinRequestAmount(5)           // 最小请求数（统计窗口内）
    .setStatIntervalMs(10000)        // 统计时间窗口（10 秒）
    .setTimeWindow(10);               // 熔断持续时间（10 秒）

// ========== 2. 异常比例熔断 ==========
// 异常比例 > 50% 且 窗口内请求数 > 5 → 熔断 10 秒
DegradeRule errorRatioRule = new DegradeRule("order-service")
    .setGrade(CircuitBreakerStrategy.ERROR_RATIO.getType())
    .setCount(0.5)                    // 异常比例阈值（50%）
    .setMinRequestAmount(5)
    .setStatIntervalMs(10000)
    .setTimeWindow(10);

// ========== 3. 异常数熔断 ==========
// 10 秒内异常数 > 10 → 熔断 60 秒
DegradeRule errorCountRule = new DegradeRule("third-party-api")
    .setGrade(CircuitBreakerStrategy.ERROR_COUNT.getType())
    .setCount(10)                     // 异常数阈值
    .setMinRequestAmount(5)
    .setStatIntervalMs(10000)
    .setTimeWindow(60);

// 加载规则
List<DegradeRule> rules = Arrays.asList(slowRule, errorRatioRule, errorCountRule);
DegradeRuleManager.loadRules(rules);

4.5 熔断参数详解

慢调用比例熔断：
  count: 响应时间阈值（秒）→ RT > count 即为慢调用
  slowRatioThreshold: 慢调用比例（0-1）→ 慢调用数/总请求数 > 此值触发
  minRequestAmount: 最小请求数 → 窗口内不足此值不触发（防冷启动误判）
  statIntervalMs: 统计窗口（ms）
  timeWindow: 熔断持续秒数 → 到期后进入 Half-Open

异常比例熔断：
  count: 异常比例阈值（0-1）→ 异常数/总请求数 > count 触发

异常数熔断：
  count: 异常数阈值 → 窗口内异常数 > count 触发

5. 热点参数限流

5.1 概念与示例

商城秒杀，普通商品每秒允许 1000 个请求，但"9.9 元的爆款手机"每秒只允许 10 个——因为大家都冲着这个来，不加限制直接被打穿。这就是热点参数限流：针对特定的"热门参数值"单独限流。

// ========== 热点参数限流 ==========
ParamFlowRule rule = new ParamFlowRule("queryOrder")
    .setCount(100)                      // 默认 QPS 阈值
    .setParamIdx(0)                      // 第 0 个参数
    .setGrade(RuleConstant.FLOW_GRADE_QPS);

// 特定参数值单独限流
ParamFlowItem hotItem = new ParamFlowItem()
    .setObject("specialUserId")          // 特定参数值
    .setClassType(String.class)
    .setCount(5);                        // 该参数值的 QPS 阈值（更严格）

rule.setParamFlowItemList(Arrays.asList(hotItem));

ParamFlowRuleManager.loadRules(Arrays.asList(rule));

// 使用
@SentinelResource(value = "queryOrder")
public Order queryOrder(@RequestParam String userId) {
    // specialUserId 的请求 QPS 限制为 5
    // 其他 userId 的请求 QPS 限制为 100
    return orderService.getByUserId(userId);
}

5.2 应用场景

适用场景：
  ✅ 秒杀活动（同一用户限制 QPS）
  ✅ 热点商品查询（同一商品 ID 限制 QPS）
  ✅ API Key 限流（同一 Key 限制调用次数）
  ✅ IP 限流（同一 IP 限制请求频率）

参数类型支持：int / long / double / String / List / Map / Set
高级用法：多参数联合限流、集合元素级别限流、集群热点限流（Token Server）

6. 系统保护

6.1 系统保护规则

前面都是保护"单个资源"的，系统保护是保护"整台机器"——相当于操作系统的自动降频保护：不管什么程序，机器扛不住了就统统减速。

保护维度 大白话 触发条件
Load Linux 系统负载 load1 > 阈值
CPU CPU 太烫了 CPU > 阈值（如 80%）
RT 整体响应太慢 RT > 阈值（秒）
线程数 并发的太多了 线程数 > 阈值
入口 QPS 全局 QPS 太高 QPS > 阈值

6.2 规则配置

// 系统保护规则（全局生效，保护整个系统）
SystemRule loadRule = new SystemRule()
    .setHighestSystemLoad(10.0)       // 系统负载 > 10 时触发
    .setAvgRt(1000)                  // 平均 RT > 1 秒时触发
    .setMaxThread(500)               // 最大线程数 > 500 时触发
    .setQps(10000)                   // 全局 QPS > 10000 时触发
    .setHighestCpuUsage(0.8);        // CPU 使用率 > 80% 时触发

SystemRuleManager.loadRules(Arrays.asList(loadRule));

6.3 自适应限流（BBR）

Sentinel 系统保护采用 BBR（Bottleneck Bandwidth and Round-trip time）算法：

核心思想：
  - 根据实时指标（CPU/RT/并发数）自适应调整限流阈值
  - 高负载自动限流，低负载自动放开，无需手动设定固定阈值

原理公式：
  max_concurrency = min_concurrency
    + (max_throughput - throughput) / (concurrency - min_concurrency)
    * min_concurrency

  → 并发数上升但吞吐量不升反降时，自动限流

                                │
                                ▼
                           更新本地规则
                                │
                                ▼
                           规则生效（无需重启）

spring:
  cloud:
    sentinel:
      scg:
        fallback:
          mode: response            # response / redirect
          response-status: 429     # HTTP 状态码
          response-body: '{"code":429,"msg":"请求过于频繁"}'

# 自定义 Gateway 限流回调
@Component
public class GatewayFallbackHandler implements GatewayCallbackManager.BlockRequestHandler {

    @Override
    public Mono<ServerResponse> handleRequest(ServerWebExchange exchange, Throwable ex) {
        Map<String, Object> response = new HashMap<>();
        response.put("code", 429);
        response.put("msg", "请求过于频繁，请稍后重试");
        response.put("path", exchange.getRequest().getPath().value());

        return ServerResponse.status(HttpStatus.TOO_MANY_REQUESTS)
            .contentType(MediaType.APPLICATION_JSON)
            .body(BodyInserters.fromValue(response));
    }
}

11. 实战案例

11.1 秒杀场景限流

// 秒杀场景：分布式限流 + 热点参数限流 + 熔断降级

@Service
public class SeckillService {

    // 1. 热点参数限流（同一用户 QPS=1）
    @SentinelResource(
        value = "seckill",
        blockHandler = "seckillBlockHandler"
    )
    public Result seckill(Long userId, Long productId) {
        // 2. Redis 分布式限流（原子操作）
        String key = "seckill:" + productId + ":" + userId;
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(key, "1", Duration.ofSeconds(1));
        if (Boolean.FALSE.equals(acquired)) {
            return Result.fail("购买过于频繁");
        }

        // 3. 业务逻辑（扣库存、创建订单）
        return doSeckill(userId, productId);
    }

    // 限流处理（Sentinel 热点限流触发）
    public Result seckillBlockHandler(Long userId, Long productId, BlockException ex) {
        return Result.fail("系统繁忙，请稍后重试");
    }
}

11.2 外部 API 调用熔断

// 外部 API 调用熔断降级
@Service
public class PaymentService {

    @SentinelResource(
        value = "call-payment-api",
        blockHandler = "callPaymentBlockHandler",
        fallback = "callPaymentFallback"
    )
    public PaymentResult callPayment(PaymentRequest request) {
        return restTemplate.postForObject(
            "https://payment-api.com/pay",
            request,
            PaymentResult.class
        );
    }

    // Sentinel 限流/熔断处理
    public PaymentResult callPaymentBlockHandler(PaymentRequest request, BlockException ex) {
        log.warn("支付接口被限流/熔断: {}", ex.getMessage());
        return PaymentResult.fallback("支付系统繁忙");
    }

    // 业务异常降级
    public PaymentResult callPaymentFallback(PaymentRequest request, Throwable ex) {
        log.error("支付接口调用失败", ex);
        return PaymentResult.fallback("支付失败，请稍后重试");
    }
}

12. 高频面试题

Q1：Sentinel 的核心原理？

Sentinel 核心是基于 Slot Chain（处理器链） 实现的责任链模式：

  1. NodeSelectorSlot：构建调用树，区分资源身份
  2. StatisticSlot：滑动窗口实时统计（每 500ms 一个采样点）
  3. FlowSlot：检查限流规则（QPS/线程数/热点）
  4. DegradeSlot：检查熔断规则（慢调用/异常比例/异常数）
  5. SystemSlot：系统保护（CPU/Load/RT）

任何一个 Slot 判定需要限流/熔断即抛异常，后续业务逻辑不执行。责任链模式是面试高频考点。

Q2：滑动窗口统计原理？

  • 每秒 2 个采样窗口（500ms 一个），每个窗口记录 pass/block/exception/rt/success
  • 支持多级统计（秒/分/小时）
  • 相比固定窗口解决了"临界突变问题"：固定窗口从 12:00:00 到 12:00:01 QPS=100，但 12:00:00.5 到 12:00:01.5 可能 QPS=200——因为流量集中在边界处。滑动窗口通过持续滑动消除了这个边界效应。

Q3：支持哪些限流方式？

五种限流，从粗到细：

  1. QPS 限流：每秒请求数——最常见
  2. 并发线程数限流：控制"并发深度"
  3. 热点参数限流：参数级别细粒度——针对特定用户或商品
  4. 系统自适应保护：CPU/Load/RT 自适应——全局保护
  5. 集群流控：Token Server 统一管控集群总 QPS

关键对比：Hystrix 只支持并发线程数限流，不支持 QPS 限流，这是质的区别。

Q4：熔断有哪些策略？

三种策略覆盖不同场景：

  1. 慢调用比例熔断：慢调用占比 > 阈值 → "服务太慢了"
  2. 异常比例熔断：异常占比 > 阈值 → "出错的太多了"
  3. 异常数熔断：异常数量 > 阈值 → "连续出错"

状态机：Closed → Open（全部拒绝，等待 timeWindow）→ Half-Open（放行一个探测）→ 成功则 Closed，失败则 Open。其中 minRequestAmount 避免冷启动误判——窗口内请求太少时不触发熔断。

Q5：如何实现动态规则推送？

核心是 "写存分离"模式：

  1. 外部存储（Nacos/Apollo/ZK）存储规则——真正的"数据库"
  2. 客户端通过数据源监听规则变更——就像订阅了一个频道
  3. 规则变更时自动加载新规则——无需重启服务（这是 Hystrix 做不到的）
  4. Dashboard 修改规则 → 写入 Nacos → 客户端监听生效

一句话：Dashboard 管"改"，Nacos 管"存"，客户端管"听"。

Q6：与 Hystrix 的区别？

（详见第 10 节对比表）

30 秒回答： - Sentinel 支持更多限流维度（QPS、热点参数、系统保护） - Sentinel 有可视化 Dashboard + 动态规则推送 - Hystrix 已停止维护，Sentinel 是主流替代方案

Q7：秒杀系统限流方案设计？

核心是多层防御，从外到内层层递进：

  1. 前端限流：按钮防抖、验证码——最外层拦截
  2. 网关限流（Sentinel Gateway）：全局 QPS 限流——守好大门
  3. Sentinel 热点限流：同一用户 QPS=1——防止黄牛/脚本
  4. Redis 分布式限流：原子操作保证全局一致——跨节点精准控制
  5. 消息队列削峰：RocketMQ 异步处理——不直接打 DB
  6. Sentinel 熔断降级：下游服务熔断保护——出问题不连累别人

设计理念：从外到内、从拦到疏、从限到降——体现系统设计的全局思维。

Q8：blockHandler 和 fallback 有什么区别？

参数 触发条件 异常类型 大白话
blockHandler Sentinel 限流/熔断触发 BlockException "门口保安拦住你了"
fallback 业务代码抛出异常 Throwable "你自己在业务里摔倒了"

blockHandler 处理流量控制（被"拦住"了），fallback 处理业务异常（业务逻辑自身出了 Bug）。

Q9：如何排查限流问题？

  1. Dashboard 实时监控面板查看 blockQPS——最直观
  2. 客户端日志：csp.sentinel.log.dir 目录下的日志——最详细
  3. Sentinel 自带日志格式：timestamp|resource|passQPS|blockQPS|...
  4. BlockException 异常处理中打印详细信息——自定义化处理

Q10：如何实现高可用？

Sentinel 的设计哲学是 "客户端不依赖服务端"：

  1. 客户端高可用：SDK 无状态，不依赖 Dashboard——Dashboard 挂了也不影响限流
  2. 规则高可用：规则存储在 Nacos/Apollo，Sentinel 崩溃不影响业务
  3. 集群流控高可用：Token Server 支持集群部署，单点故障有备选
  4. Dashboard 高可用：可部署多个实例

总结：Sentinel 是"弱依赖"组件，它挂了不会让业务也挂，这正是生产级中间件的设计标准。

学习建议：Sentinel 面试核心围绕三个关键词——流量控制（QPS/线程/热点）、熔断降级（慢调用/异常比例/状态机）、动态规则（Nacos 持久化/Dashboard）。建议先理解 Slot Chain 的执行原理（责任链模式），再深入限流和熔断的各种策略，最后掌握与 Spring Cloud Gateway 的集成和动态规则持久化。必会组合：Sentinel + Nacos + Gateway 三位一体，这是 Spring Cloud Alibaba 体系中最常见的面试组合。

与面试岗位的关联：Sentinel 主要出现在微服务/中间件/架构方向的后端面试中，常与以下知识点联合考察：Spring Cloud Alibaba 全家桶、Spring Cloud Gateway（网关限流）、Nacos（规则持久化）、分布式限流方案设计、秒杀系统设计等。
