Netty

1. Netty 是什么?为什么用?

Netty 是 Java 高性能网络通信框架。Dubbo、RocketMQ、Elasticsearch 的底层网络通信都在用它。

核心原因:Java 原生 NIO API 太难用、坑太多(epoll 空轮询 bug、ByteBuffer 不可变、API 复杂)。Netty 把 NIO 封装好了,提供简单 API + 高性能 + 安全稳定。

         应用层
    ┌──────┼──────┐
    │ Dubbo│ RocketMQ│ ES │  ← 各种中间件
    └──────┼──────┘
           │
    ┌──────▼──────┐
    │    Netty     │  ← 统一的网络通信层
    └──────┬──────┘
           │
    ┌──────▼──────┐
    │ Java NIO/Epoll│  ← 操作系统级 IO
    └─────────────┘

扩展:Netty 的广泛应用证明了一个道理--好的基础设施比好的应用更值钱。你不需要自己写高性能网络层,直接用 Netty 就行。Spring WebFlux、gRPC Java 版也基于 Netty--它已经是 Java 生态网络通信的事实标准。

2. Netty 的线程模型?

Boss Group + Worker Group:

  • Boss 线程(通常 1 个):负责接收客户端连接
  • Worker 线程(CPU 核数 × 2):负责读写 IO 和处理业务

每个线程绑定一个 Selector,能管多个 Channel。

客户端连接 ──▶ BossGroup (1线程)
                    │ 接收连接
                    ▼
              WorkerGroup (N线程)
              ┌───┬───┬───┐
              │W1 │W2 │W3 │  ← 每个线程管多个 Channel
              └───┴───┴───┘
                轮询 IO 事件
                    │
                    ▼
              Pipeline 链式处理
              (编码 → 业务 → 解码)

扩展:Boss 线程只有 1 个够吗?对于大多数场景够了--一个线程管理几千个连接的建立绰绰有余。如果真有海量连接(百万级),可以配多个 Boss 线程,每个 Boss 监听不同端口。真正的工作瓶颈在 Worker 线程--它既要读数据又要做业务处理,所以按 CPU 核数配。

3. Netty 为什么快?

  1. NIO 多路复用(epoll):单线程处理多连接,不用为每个连接开一个线程
  2. 零拷贝:DirectBuffer 减少内存拷贝(直接操作堆外内存,跳过堆内复制);文件传输用 sendfile(内核态直接到网卡)
  3. 内存池:复用 ByteBuf,减少 GC 压力
  4. 无锁化:每个 Channel 绑定单个线程,串行处理无需锁
  5. 对象池:ChannelHandler 等可复用,减少对象创建
传统 IO(多次拷贝):          零拷贝 sendfile:
磁盘 → 内核缓存 → 用户态 → 内核缓存 → 网卡    磁盘 → 内核缓存 → 网卡
      (拷贝1)    (拷贝2)   (拷贝3)   (拷贝4)         (DMA)    (DMA)
                                                  零次 CPU 拷贝!

扩展:DirectBuffer 虽然快,但分配和回收成本比堆内存高--所以 Netty 用了池化来复用。另外 DirectBuffer 不在 GC 管辖范围,如果忘了释放会导致堆外内存泄漏--Netty 的 ByteBuf 用引用计数来管理生命周期,release() 减到 0 自动回收。

4. Netty 和 Tomcat 的区别?

维度 Netty Tomcat
定位 通用网络通信框架 Web 应用容器
协议 自定义协议(TCP/UDP) 主要 HTTP
IO 模型 原生 NIO/Epoll 早期 BIO,新版支持 NIO
场景 RPC、IM、网关底层 Web 应用部署

简单的说:Tomcat 是"开箱即用的 Web 服务器",Netty 是"造通信系统用的乐高积木"。

扩展:Spring Boot 默认内嵌 Tomcat,但可以换成 Netty(spring-boot-starter-webflux 默认用 Netty)。如果只做 HTTP Web 应用,Tomcat 够用;如果要自研网关、IM、RPC 框架,用 Netty。

5. Netty 的零拷贝是怎么实现的?

零拷贝 = 快递员不需要把每件货卸到仓库再搬上车,直接从 A 车搬到 B 车--数据不经过用户态拷贝到用户缓冲区,全程在内核态完成。

Netty 的零拷贝是组合拳:

1. CompositeByteBuf(组合缓冲区)

   Header Buffer(请求头)+ Body Buffer(请求体)
         ↓ 不需要拷贝
   CompositeByteBuf(逻辑上是一个整体)
   = 零拷贝合并多个 ByteBuf

2. wrap / slice(包装/切片)

   原始 ByteBuf [H][E][L][L][O]
     slice(1,3) →  [E][L][L](共享同一块内存!)

3. FileRegion(文件传输)

   磁盘 → DMA → 内核缓冲区 → DMA → 网卡
         (全程不经过用户态,不用 CPU 搬运)

4. 池化内存(PooledByteBufAllocator)
   = 对象复用而非每次 new,减少 GC 压力

和操作系统零拷贝的区别:OS 零拷贝(sendfile)是系统调用层面的优化,Netty 的 CompositeByteBuf 是 JVM 层面的优化--两者互补。Netty 用 FileRegion 封装了 transferTo()(底层是 sendfile),把文件直接写...

扩展:Netty 4.1+ 的 EpollSocketChannel 在 Linux 上直接走 epoll,配合 SO_REUSEPORT 可以实现多线程绑定同一端口,进一步提升吞吐。但 Windows 上只能用 NIO(Selector),所以生产部署务必用 Linux。

6. Netty 的心跳和断线重连怎么实现?

心跳 = 定期给对方发"我还在"。如果对方几次没回应,就判对方断了,执行重连或清理。

心跳机制:

  Client                        Server
    │                              │
    │──── PING ──────────────────→ │  (客户端发心跳)
    │←─── PONG ───────────────────│  (服务端回应)
    │                              │
    │  ... 5 秒一次 ...            │
    │                              │
    │──── PING ──→ X  ⚡(超时)    │
    │  ... 3 次没回 ...            │
    │                              │
    │  判断断连 → 执行重连逻辑      │

Netty 心跳实现(IdleStateHandler):

// 服务端:5 秒没读到客户端数据 → 认为空闲 → 发心跳 → 30 秒还没数据 → 断开
ch.pipeline().addLast(new IdleStateHandler(30, 0, 0, TimeUnit.SECONDS));

// 客户端:5 秒没写数据 → 主动发 PING
ch.pipeline().addLast(new IdleStateHandler(0, 5, 0, TimeUnit.SECONDS));

断线重连(ChannelFutureListener):

public void connect() {
    bootstrap.connect(host, port).addListener((ChannelFutureListener) future -> {
        if (!future.isSuccess()) {
            // 断线后延迟重连
            future.channel().eventLoop().schedule(this::connect, 5, TimeUnit.SECONDS);
        }
    });
}

扩展:生产上心跳间隔别设太短--1 秒一次心跳 × 10 万连接 = 每秒 10 万次网络 IO,服务器撑不住。一般 30~60 秒一次足够。另外 IdleStateHandler 判断的是"没读写"而非"连接断没断"--TCP 半开连接可能还在但对方已经挂了,要靠心跳这种应用层探测来发现。

7. Netty 的 ChannelPipeline 是怎么工作的?

ChannelPipeline = 一条双向流水线。入站数据从 Head 流向 Tail,出站数据从 Tail 流向 Head。每个 Handler 是一道工序。

入站(读数据):

  [Head] → [帧解码器] → [协议解析] → [业务Handler] → [Tail]
               ↑              ↑              ↑
           将字节流按         把字节转为        处理业务逻辑
           长度拆成帧          Java对象

出站(写数据):

  [Tail] → [业务Handler] → [协议编码] → [帧编码] → [Head]
               ↑              ↑            ↑
           业务返回对象       对象→字节    加上长度头

核心规则:

  • InboundHandler(入站处理器):按添加顺序执行,数据从 Head → Tail
  • OutboundHandler(出站处理器):按添加的逆序执行,数据从 Tail → Head
  • ctx.fireChannelRead(msg):传给下一个 InboundHandler(忘调 = 数据丢了)
  • ctx.write(msg):从当前 Handler 往前找 OutboundHandler 开始写出站
ch.pipeline()
    .addLast(new LengthFieldBasedFrameDecoder(...))  // Inbound 1: 拆帧
    .addLast(new ProtobufDecoder(...))               // Inbound 2: 解码
    .addLast(new ProtobufEncoder())                  // Outbound 1: 编码
    .addLast(new LengthFieldPrepender(2))            // Outbound 2: 加帧头
    .addLast(new BusinessHandler());                 // Inbound 3: 业务

扩展:ChannelPipeline 的设计本质上是责任链模式 + 链表。每个 Channel 有独立的 Pipeline(线程安全,因为一个 Channel 绑定一个 EventLoop 线程)。注意:不要在 Pipeline 里做耗时操作(如 IO、复杂计算)--会阻塞整个 EventLoop,影响该线程上所有 Channel。耗时操作请丢进业务线程池。

8. Netty 如何解决拆包/粘包?

四种解码器:FixedLengthFrameDecoder、LineBasedFrameDecoder、DelimiterBasedFrameDecoder、LengthFieldBasedFrameDecoder(最常用)。

9. Netty 的 ByteBuf 为什么比 Java NIO ByteBuffer 更好?

核心结论:ByteBuf 支持池化+零拷贝+读写分离指针+引用计数管理,性能和易用性都碾压 ByteBuffer。

ByteBuffer 致命缺陷:

1. 写入后 flip() 才能读,读完后 compact() 才能写 ← 操作繁琐
2. 固定长度,不够了得创建新的 ← 内存浪费
3. 没有池化,频繁 GC ← 性能瓶颈

ByteBuf 改进:

       读指针(readerIndex)    写指针(writerIndex)
              ↓                    ↓
┌─────────────────────────────────────────────┐
│  已读区  │   可读区   │   可写区    │  可扩容  │
│ (discard) │ (readable) │ (writable) │(动态扩容)│
└─────────────────────────────────────────────┘

- 读写指针分离,不需要 flip
- 支持动态扩容(写满自动扩容)
- 支持池化(PooledByteBufAllocator)
- 引用计数自动管理内存释放

ByteBuf 三种类型:

类型 分配方式 适用场景
Heap ByteBuf 堆内存,GC 管理 普通业务
Direct ByteBuf 堆外内存,零拷贝 高性能网络 IO
Composite ByteBuf 逻辑组合,无拷贝 多 Buffer 合并

引用计数使用示例:

ByteBuf buf = ByteBufAllocator.DEFAULT.buffer(1024);
buf.retain();  // 引用计数 +1
buf.release(); // 引用计数 -1,减到 0 自动回收

// 错误:忘记 release → 内存泄漏
ByteBuf buf = ...;
process(buf);
// 忘了 release! 堆外内存永远不会被 GC 回收

扩展:Netty 用内存池解决 DirectBuffer 分配慢的问题--预先分配大块内存,切分成小块复用。PooledByteBufAllocator 比非池化性能高 5 倍以上。调试内存泄漏可以用 ResourceLeakDetector。生产上务必检查:如果日志中出现 LEAK: ByteBuf.release() was not called before it's garbage-collected,说明有 ByteBuf 没释放。

10. Netty 如何实现异步回调?

核心结论:ChannelFuture + GenericFutureListener = 异步非阻塞,比传统 Future.get() 更高效。

传统 Future 问题:

Future<String> future = executor.submit(() -> doRequest());
String result = future.get();  // 阻塞等待! ← 线程空转

Netty ChannelFuture:

ChannelFuture future = channel.writeAndFlush(msg);
future.addListener((ChannelFutureListener) f -> {
    if (f.isSuccess()) {
        System.out.println("发送成功");
    } else {
        System.out.println("发送失败: " + f.cause());
    }
});
// 不阻塞! 继续干别的事 ← 异步回调

异步回调链:

// 链式异步调用
bootstrap.connect(host, port)
    .addListener(f -> {
        if (f.isSuccess()) {
            System.out.println("连接成功");
            // 连接成功后发送数据
            Channel ch = ((ChannelFuture) f).channel();
            ch.writeAndFlush(msg)
                .addListener(f2 -> {
                    if (f2.isSuccess()) {
                        System.out.println("发送成功");
                    }
                });
        } else {
            System.out.println("连接失败,5秒后重试");
            Thread.sleep(5000);
            bootstrap.connect(host, port);  // 断线重连
        }
    });

同步 vs 异步对比:

方式 线程利用率 适用场景
sync() 低(阻塞等待) 简单测试
addListener() 高(回调通知) 高并发生产

扩展:Netty 的 Promise 是可写的 Future,既支持设置结果又支持异步回调。Dubbo 的异步调用就是基于 Netty ChannelFuture 实现的。注意:回调逻辑不要做耗时操作,否则阻塞 EventLoop 线程,影响整个 Selector 上所有 Channel 的处理。

11. Netty 如何处理半包和粘包问题?

核心结论:TCP 是流式协议,需要应用层定义消息边界--长度字段、分隔符、固定长度均可。

TCP 粘包/拆包本质:

发送方:  消息1(16B) | 消息2(32B) | 消息3(8B)
                           │
            TCP 缓冲区(可能合并发送)
                           ▼
接收方读取到的可能情况:

粘包:  消息1+消息2(48B) ← 两个包粘在一起
拆包:  消息1前半(10B) | 消息1后半+消息2(38B) ← 一个包被拆开

四种解决方案:

方案 解码器 适用场景 缺点
固定长度 FixedLengthFrameDecoder 定长协议 浪费带宽
换行分隔 LineBasedFrameDecoder 文本协议(如 Redis) 消息不能含换行
自定义分隔符 DelimiterBasedFrameDecoder 特殊分隔符 同上
长度字段 LengthFieldBasedFrameDecoder 二进制协议(最通用) 复杂度高

LengthFieldBasedFrameDecoder 示例:

消息格式:
┌───────────┬─────────────┬─────────────┐
│ 长度(4B)  │  版本(2B)   │   数据(NB)  │
│ length    │   version   │    body     │
└───────────┴─────────────┴─────────────┘

解码器配置:
new LengthFieldBasedFrameDecoder(
    1024,   // maxFrameLength: 最大帧长度
    0,      // lengthFieldOffset: 长度字段偏移
    4,      // lengthFieldLength: 长度字段占 4 字节
    -2,     // lengthAdjustment: 长度值不含版本和数据,需调整
    4       // initialBytesToStrip: 解码后去掉长度字段
);

扩展:自定义协议通常用长度字段方案,因为灵活且不浪费带宽。大多数 RPC 框架(如 Dubbo、gRPC)都用长度字段。调试时可以用 Wireshark 抓包看 TCP 流的实际分段情况,理解粘包拆包的真相。

12. Netty ByteBuf 为什么要设计成池化？

ByteBuf 是 Netty 的数据容器，池化解决了两大问题：

直接申请 ByteBuf 的问题：
  - 每次分配都调用系统 malloc()
  - GC 回收时需要 C free()
  - 频繁分配/释放造成内存碎片
  - 高并发下 malloc 成为性能瓶颈

池化（PooledByteBufAllocator）的解决方案：
  - 预分配内存池，按大小分组（16B~16MB）
  - 申请时从池中取，释放时归还池（不真的释放）
  - 减少 90%+ 的 malloc/free 调用

内存分配算法（Slab 分配）：

Chunk（16MB大块）分为多个 Page（默认8KB）：

Tiny 池: 16B, 32B, 48B, ..., 496B（每16B递增）→ Page 内按序分配
Small 池: 512B, 1KB, 2KB, 4KB           → Page 内分配
Normal 池: 8KB, 16KB, 32KB...            → 多页组合
Huge 池: > 16MB                           → 非池化，每次直接分配

PooledByteBuf vs Unpooled：

// UnpooledHeapByteBuf（默认）：堆内存，有 GC 开销
// UnpooledDirectByteBuf：直接内存（堆外），无 GC，但申请慢
// PooledHeapByteBuf（推荐）：池化堆内存，综合最优
// PooledDirectByteBuf：池化直接内存，高性能网络框架首选

// Netty 默认使用 PooledDirectByteBuf
// 零拷贝场景（文件传输）用 PooledHeapByteBuf + CompositeByteBuf

扩展：System.bytebuf.pool.size.threshold 控制池大小；io.netty.leakDetection.level=PARANOID 检测内存泄漏；Netty 4.x 全面池化，3.x 是非池化（这是 3→4 性能提升的关键）。
