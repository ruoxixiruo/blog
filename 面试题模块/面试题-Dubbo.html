Dubbo & RPC

1. 什么是 RPC?完整流程是怎样的?

RPC(远程过程调用)让你调用远程服务像调用本地方法一样自然,网络细节全隐藏。关键是本地代理(Stub)--它假装是远程服务,实际上在背后做了序列化、网络调用这些脏活。

Client 端                           Server 端

UserService.getUser(id)
    │
    ▼
┌──────────┐                    ┌──────────┐
│ 代理 Stub │  ──序列化──▶     │ 骨架 Skeleton│
│ (假装本地) │    网络传输       │ (反射调用)   │
└──────────┘  ◀──序列化返回──  └──────────┘
                                     │
                              真实 UserService.getUser(id)

完整流程:客户端调本地代理 → 序列化方法名和参数 → 网络发送 → 服务端反序列化 → 反射调用真实方法 → 返回结果 → 序列化返回 → 客户端代理反序列化拿到结果。

扩展:RPC 和 HTTP 接口有什么区别?RPC 调的是方法(面向行为),HTTP 调的是资源(面向数据)。RPC 更快(自定义协议,节约带宽/序列化开销),但 HTTP 更通用(跨语言/跨平台)。Dubbo 3 引入了 Triple 协议(基于 gRPC),兼具 RPC 的高性能和 HTTP 的通用性。

2. Dubbo 整体架构?

四大角色:

角色 作用 类比
Provider 服务提供者,启动时注册到注册中心 餐厅(提供服务)
Consumer 服务消费者,启动时订阅所需服务 食客(消费服务)
Registry 注册中心(Nacos/ZK),存服务地址,推送变更 大众点评(查哪家好吃)
Monitor 监控中心,统计调用次数和耗时 摄像头(监控一切) 
Provider ──注册──▶ Registry ◀──订阅── Consumer
   │                                      │
   └──────────── 直接调用 ────────────────┘
              (已拿到地址,不经过 Registry)

注册中心挂了影响吗?不影响已有连接(Consumer 本地缓存了地址),但新注册和订阅会失败。就像你手机里已经存了餐厅的地址--大众点评挂了不影响你去已经知道的餐厅。

扩展:Dubbo 3 引入应用级服务发现--以前是接口级(一个服务有多少个接口就注册多少次),现在是应用级(一个应用注册一次),注册数据量大幅下降,支持更大规模集群。这是 Dubbo 3 最重要的架构升级之一。

3. Dubbo 负载均衡策略?

策略 原理 场景
Random(默认) 按权重随机 大多数业务
RoundRobin 平滑加权轮询 服务性能一致
LeastActive 选最闲的(活跃请求最少) 服务耗时差异大
ConsistentHash 同参数请求固定到一台 有状态服务
ShortestResponse 选预估响应最快的 2.7+,实时优化 
LeastActive 示例:三台机器

Provider A:3 个请求在处理中(忙)
Provider B:1 个请求在处理中(闲) ← 新请求优先发给它
Provider C:5 个请求在处理中(很忙)

扩展:ConsistentHash(一致性哈希)不只是负载均衡,它能做有状态路由--如果某台机器上有用户缓存,让同一个用户的请求总打到这台机器,缓存命中率高得多。Dubbo 的一致性哈希默认 160 个虚拟节点,防止节点增减时数据倾斜。

4. Dubbo 集群容错策略?

策略 行为 场景
Failover(默认) 失败自动换一台重试(默认 2 次) 幂等读操作
Failfast 快速失败,只调一次 非幂等写(新增订单)
Failsafe 异常直接忽略 不重要操作(审计日志)
Failback 失败后定时重试 最终一致性场景
Forking 并行调多台,任一成功返回 实时性要求高(牺牲资源换速度)

扩展:最容易踩的坑--对非幂等操作用 Failover。比如创建订单,如果超时了 Dubbo 自动换一台重试,结果订单创建了两份。所以写操作要用 Failfast,或者在业务层做好幂等。

5. Dubbo 序列化协议怎么选?

协议 性能 跨语言
Hessian2(默认) 适中 有限
Protobuf 高 支持
Kryo 最高 不支持(Java only)
JSON 低 支持

性能排序:Kryo > Protobuf > Hessian2 > JSON。

选型决策:

Java to Java? → Kryo(高性能首选)
跨语言?      → Protobuf(生态好)
想看内容调试?→ JSON(可读性最好)
默认够用?    → Hessian2(Dubbo 原生支持,零配置)

扩展:Protobuf 为什么比 JSON 快很多?因为它是二进制格式,字段名不传(用数字代替),整数用 varint 压缩(小整数只占 1 字节)。JSON 传 {"userId":123} 要 15 字节,Protobuf 可能只需要 3 字节。但 Protobuf 需要定义 .proto 文件和编译步骤,多了些开发成本。

6. RPC 和 HTTP 的区别?什么时候用 RPC?

RPC = 打电话(直接叫对方做事,效率优先),HTTP = 寄邮件(格式规范,跨平台兼容)。

维度 RPC HTTP
协议 自定义(Dubbo/Hessian/gRPC) 标准 HTTP/1.1 或 HTTP/2
序列化 二进制(Protobuf/Kryo),体积小 JSON/XML,可读但体积大
语义 方法调用语义(orderService.create()) 资源语义(POST /orders)
跨语言 看协议(gRPC 支持,Dubbo 偏 Java) 天然跨语言
性能 高(长连接 + 二进制 + 非阻塞 IO) 较低(短连接 + 文本解析开销)
调试 需要专用工具 浏览器/curl 就能调

选型决策:

微服务内部调用 → RPC(性能高,调用语义清晰)
对外 API / 跨平台 → HTTP(通用性强,生态好)
移动端 → HTTP(防火墙友好,开发工具成熟)
实时通信(IM/游戏)→ 自研 RPC / WebSocket

一句话:对内用 RPC,对外用 HTTP。但趋势是融合--gRPC 用 HTTP/2 + Protobuf,兼具两者优势。

扩展:Feign 声明式调用是 RPC 和 HTTP 的混合体--写起来像 RPC(接口 + 注解),底层走 HTTP + JSON。Dubbo 3.0 支持 Triple 协议(基于 HTTP/2),开始从纯 RPC 框架向云原生演进。选型时还要考虑网关兼容性:Istio 能路由 HTTP/TCP,但对 Dubbo 私有协议需要额外适配。

7. Dubbo 服务暴露流程是怎样的?

Dubbo 服务暴露 = 餐馆开业:准备菜单(接口信息)→ 在美食平台登记(注册到注册中心)→ 对外营业(监听端口)。

服务启动流程:

  Spring 容器启动
      ↓
  ServiceBean 扫描 @DubboService
      ↓
  1. 构建 URL(协议、IP、端口、接口名)
      ↓
  2. 启动 Netty Server(监听端口)
      ↓
  3. 注册到注册中心(Nacos / ZK)
      ↓
  注册中心保存:接口名 → ip:port 映射
      ↓
  服务可用 ✅

关键细节:

  • 本地暴露(injvm 协议):JVM 内的 Service 和 Reference 直接调用,不走网络
  • 远程暴露:创建 Netty Server + 注册到注册中心
  • 两个端口:Dubbo 协议监听一个端口(如 20880),QOS 端口(22222)用于运维命令

扩展:Dubbo 3.x 引入了应用级服务发现(Application-level Service Discovery)--不再以接口粒度注册,而是以应用粒度注册。注册中心的数据量从接口数 × 实例数 降到 应用数 × 实例数,极大减轻 ZK/Nacos 的压力。但需要元数据中心(如 Nacos)存放接口→应用的映射。

8. Dubbo 的服务降级怎么配?

服务降级 = 商店停电了,门口挂个牌子"今日歇业",比让顾客进去发现没人理好得多。

降级触发场景:
  Provider 挂了 → 返回 mock 数据 / 空结果
  下游响应太慢 → 超时后降级
  主动降级(大促/压测)→ 关闭非核心服务

配置方式(Dubbo Admin 或代码):

# dubbo 配置
dubbo:
  consumer:
    mock: true  # 服务调用失败时返回 mock 值
    # 精确控制
    mock: "return null"           # 返回 null
    mock: "return {\"id\":0}"     # 返回指定 JSON
    mock: "throw com.xxx.Exception" # 抛出异常
    mock: "com.example.MockService" # 指定 Mock 类

Mock 类写法:

@Service
public class OrderServiceMock implements OrderService {
    @Override
    public OrderDTO getOrder(Long id) {
        // 降级逻辑:返回缓存的数据或空对象
        return OrderDTO.builder().id(id).status("未知(降级)").build();
    }
}

扩展:Dubbo 的服务降级和 Sentinel 的降级是两回事--Dubbo 的降级是 RPC 层面的"调用失败兜底",Sentinel 的降级是流量控制层面的"保护下游不被冲垮"(熔断)。Dubbo 2.7+ 原生集成了 Sentinel,可以同时做 RPC 降级和流量防护。大促场景的标准做法是:Sentinel 在前做流量控制,Dubbo Mock 在后做调用兜底。

9. Dubbo SPI 和 Java SPI 的区别?

Dubbo SPI 按需加载,配置文件 META-INF/dubbo/,支持 IoC/AOP 和 Key 适配。Java SPI 一次性加载所有实现。

10. Dubbo 服务调用超时怎么处理?

核心结论:优先业务幂等,超时后根据场景选择重试(Failover)或快速失败(Failfast)。

超时场景分析:

1. 查询类操作(幂等)
   → 使用 Failover,自动重试其他节点
   → 默认策略,超时 1s,重试 2 次

2. 写入类操作(非幂等)
   → 使用 Failfast,快速失败
   → 业务层处理重试(带唯一键防重)

3. 重要操作(必须成功)
   → 失败后进入异步重试队列
   → 定时任务补偿 + 告警

配置示例:

// 服务端设置超时(提供者优先)
@DubboService(timeout = 3000)
public class OrderServiceImpl implements OrderService {
    // ...
}

// 消费端指定超时策略
@DubboReference(
    timeout = 5000,
    retries = 2,              // 重试次数
    cluster = "failover"      // 或 "failfast"
)
private OrderService orderService;

// 非幂等操作用 failfast
@DubboReference(
    timeout = 5000,
    cluster = "failfast"      // 不重试
)
private PaymentService paymentService;

扩展:Dubbo 超时判定的关键点:客户端超时 ≠ 服务端超时。客户端超时直接返回异常,服务端可能还在执行。所以超时后要考虑请求是否已到达服务端、是否已生效。最佳实践:服务端配置比客户端稍长,避免服务端还在执行就被客户端掐断。

11. Dubbo 3.0 有哪些重要新特性?

核心结论:应用级服务发现 + Triple 协议 + 云原生适配 = 面向下一代的 RPC 框架。

特性 说明 解决的问题
应用级服务发现 从接口级改为应用级注册 注册中心压力大(百万接口→万应用)
Triple 协议 基于 gRPC + HTTP/2 跨语言、流式通信、与云原生兼容
统一路由规则 统一流控、路由、降级规则 配置分散、规则冲突
服务网格支持 Sidecar 模式兼容 无侵入式治理
GraalVM 支持 原生镜像编译 启动慢、内存占用高 
Dubbo 2.x vs 3.x 注册模型:

Dubbo 2.x (接口级):
  /dubbo
    /com.example.UserService
      /providers → [ip:port, ip:port, ...]
      /consumers → [...]
    /com.example.OrderService
      /providers → [...]
    /com.example.PaymentService
      /providers → [...]

  问题:100 个服务 × 1000 个实例 = 注册中心存 10 万条数据!

Dubbo 3.x (应用级):
  /services
    /app-order → [ip:port, ip:port, ...]
    /app-user  → [ip:port, ip:port, ...]

  元数据(接口→应用映射)存在元数据中心,注册中心压力降 90%!

Triple 协议优势:

// 传统 Dubbo 协议:二进制,仅 Java
public interface UserService {
    User getUser(Long id);
}

// Triple 协议:支持流式通信
public interface UserService {
    // 一元 RPC
    User getUser(Long id);

    // 服务端流(返回 Stream)
    Stream<User> listUsers(StreamRequest request);

    // 双向流
    Stream<User> chat(Stream<Message> messages);
}

扩展:Dubbo 3.x 的迁移路径:如果已有 Dubbo 2.x 项目,先升级到 3.x,双注册模式(同时注册到接口级和应用级),逐步迁移消费者。新项目直接用 3.x 应用级服务发现即可。Triple 协议对 Go/Python 等语言友好,是 Dubbo 走向云原生、跨语言的关键一步。

12. Dubbo 3.0 的三重注册/发现机制？

Dubbo 3.0 引入 应用级服务发现，彻底解决兼容性：

Dubbo 2.x 服务发现:
  接口级：/dubbo/com.example.UserService/providers/
  → 注册中心存储量大，K8s 环境下全量订阅开销大

Dubbo 3.0 服务发现:
  应用级：/dubbo/apps/com.example.UserService/providers/
  → 注册量减少 90%，K8s 友好

三重注册机制：

# dubbo.properties
dubbo.registry.address=poj://localhost:2181
# 三种注册方式（可同时配置）：

# 1. Zookeeper 注册中心（传统方式）
dubbo.registry.protocol=zookeeper

# 2. Nacos 注册中心（国内主流）
dubbo.registry.protocol=nacos
dubbo.registry.address=nacos://localhost:8848

# 3. Consul（云原生）
dubbo.registry.protocol=consul
dubbo.registry.address=consul://localhost:8500

推荐配置（生产级）：

dubbo:
  application:
    name: order-service
  protocol:
    name: dubbo
    port: 20880
  registry:
    address: nacos://nacos:8848
    group: prod
    use-as-metadata-service: true  # 元数据只注册一份
  provider:
    timeout: 3000
    retries: 0
  consumer:
    timeout: 3000
    check: false  # 启动时不检查依赖

扩展：Dubbo 3.0 的 Triple 协议兼容 gRPC，HTTP/2；服务治理（限流/熔断/权重）通过 dubbo-mesh 对接 Istio；QOS 端口（22222）提供运行时运维接口。
