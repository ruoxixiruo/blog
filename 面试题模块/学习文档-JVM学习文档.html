JVM 面试学习文档

📅 整理日期：2026-06-27 | 🎯 目标：系统掌握 JVM 内存模型、垃圾回收、类加载机制与面试高频考点

1. JVM 概述

1.1 JVM 是什么

JVM（Java Virtual Machine）是 Java 跨平台的基石——编译后的字节码（.class）不直接运行在操作系统上，而是运行在 JVM 中。主要职责：加载字节码、管理内存、执行代码。

核心特点：一次编写，到处运行（Write Once, Run Anywhere）。不同平台有不同 JVM 实现（HotSpot / OpenJ9 / GraalVM），但字节码是通用的。

面试话术：JVM 本质是一个规范的实现，它将 Java 字节码解释/编译为机器码。JVM 的核心价值在于内存自动管理（GC）和跨平台抽象。面试 JVM 的核心三个考点：内存布局、垃圾回收、类加载。

1.2 JVM 架构总览

+-------------------------------------------------------------+
|                    JVM 架构                                   |
+-------------------------------------------------------------+
|                                                              |
|  +-----------+  +----------+  +----------+  +------------+  |
|  | 类加载器   |  | 运行时   |  | 执行引擎  |  | 本地接口   |  |
|  | 子系统     |  | 数据区   |  |           |  | (JNI)     |  |
|  |           |  | (内存)   |  | 解释器    |  |            |  |
|  | Bootstrap |  +----------+  | JIT 编译器|  | 本地方法库 |  |
|  | Extension |                | GC       |  |            |  |
|  | AppClass  |                |          |  |            |  |
|  +-----------+                +----------+  +------------+  |
|                                                              |
+-------------------------------------------------------------+

JVM 启动流程:
  1. 加载配置（查找 JVM 实现）
  2. 创建 JVM 实例（分配堆/栈等内存）
  3. Bootstrap ClassLoader 加载核心类（rt.jar）
  4. 运行 main() 方法
  5. 执行字节码（解释执行 + JIT 编译热点代码）
  6. GC 自动回收垃圾
  7. 所有非守护线程退出 → JVM 关闭

1.3 运行时数据区

+------------------------------------------------------+
|               运行时数据区 (Runtime Data Area)           |
+------------------------------------------------------+
|                                                       |
|  +------------------+  +----------------------------+ |
|  | 线程私有          |  | 线程共享                    | |
|  |                  |  |                            | |
|  | 程序计数器 (PC)   |  | 堆 (Heap)                 | |
|  |                  |  |  (存所有对象)               | |
|  | JVM 栈 (VM Stack)|  |                            | |
|  |  (方法调用栈)     |  | 方法区 (Method Area)       | |
|  |                  |  |  (类信息/常量/静态变量)     | |
|  | 本地方法栈        |  |                            | |
|  |  (Native)        |  | 运行时常量池 (Runtime CP)   | |
|  +------------------+  +----------------------------+ |
|                                                       |
+-------------------------------------------------------+

线程私有区域: 随线程创建/销毁，自动管理
线程共享区域: GC 主要活动区域，需要调优

2. 内存区域详解

2.1 堆（Heap）

堆是 GC 管理的主要区域（GC Heap），也是面试最常问的区域。所有对象实例和数组都在堆上分配。

堆内存结构（分代模型，HotSpot）：

  +--------------------+--------------------+--------------+
  |     新生代 (Young)   |     老年代 (Old)    |   元空间     |
  |                    |                     | (Metaspace) |
  | +--+---+---------+ |  大对象/长期存活对象  | 类元数据    |
  | |E|S0 |   S1    | |                     |            |
  | |d|   |         | |                     |  (本地内存)  |
  | |e|   |         | |                     |            |
  | |n|   |         | |                     |            |
  | +--+---+---------+ |                     |            |
  |    8:1:1 (默认比例) |                     |            |
  +--------------------+--------------------+--------------+

分代比例（默认）:
  - 新生代 : 老年代 = 1 : 2（-Xmn 可调整）
  - Eden : S0 : S1 = 8 : 1 : 1

对象分配流程:
  new 对象 → Eden 区
    → Minor GC 后存活 → 进入 S0
    → 下一次 Minor GC → S0 存活移入 S1（年龄+1）
    → 年龄达到阈值（默认 15）→ 进入老年代
    → 大对象直接进入老年代（-XX:PretenureSizeThreshold）

2.2 栈（VM Stack）

每个线程私有，存储栈帧。每调用一个方法就创建一个栈帧入栈，方法结束出栈。

栈帧结构:

  +----------------------------+
  | 局部变量表 (Local Variable) |
  |   - this (实例方法第0位)    |
  |   - 方法参数               |
  |   - 局部变量               |
  +----------------------------+
  | 操作数栈 (Operand Stack)   |
  |   - 字节码指令的操作数      |
  +----------------------------+
  | 动态链接 (Dynamic Linking) |
  |   - 符号引用 → 直接引用     |
  +----------------------------+
  | 方法返回地址               |
  |   - 正常/异常返回地址       |
  +----------------------------+

栈大小:
  -Xss 默认 1MB（Linux x64）
  方法调用层级太深 → StackOverflowError

2.3 方法区（Method Area）

版本 实现 存储内容
JDK 7 永久代（PermGen） 类信息、常量池、静态变量
JDK 8+ 元空间（Metaspace） 类元数据（字符常量/静态变量移到堆）

关键变化：JDK 8 移除永久代，改为元空间（本地内存，默认无上限）。字符串常量池和静态变量移到堆中。

2.4 程序计数器

线程私有，记录当前线程执行的字节码行号。唯一在 JVM 规范中没有 OOM 的区域。

  • Java 方法：记录字节码指令地址
  • Native 方法：计数器值为空（Undefined）

2.5 本地方法栈

为 JNI（Java Native Interface）调用的本地方法（C/C++）服务。HotSpot 中与 VM Stack 合并实现。

3. 对象存活判定

3.1 可达性分析算法

JVM 使用可达性分析（Reachability Analysis）判断对象是否存活，而非引用计数。

引用计数（Java 不用）:
  对象 A 引用 B → B.count++
  对象 B 引用 A → A.count++
  外部不再引用 A、B → 但 count 不为 0 → 内存泄漏！

可达性分析（Java 用）:
  从 GC Roots 出发，遍历引用链
  能到达的 → 存活
  不能到达的 → 垃圾，回收

  GC Roots ---> Object A ---> Object B
       |              |
       |              +---> Object C (存活)
       |
       +---> Object D ---> Object E (存活)

       Object F (没有引用链 → 回收)
       Object G (没有引用链 → 回收)

3.2 GC Roots

可以作为 GC Roots 的对象：

┌─────────────────────────────────────────────┐
│ 1. 虚拟机栈（栈帧本地变量表）引用的对象       │
│    当前正在执行的方法中的局部变量             │
│ 2. 方法区中静态属性引用的对象                 │
│    static 字段引用的对象                     │
│ 3. 方法区中常量引用的对象                     │
│    字符串常量池、final 常量                   │
│ 4. JNI（本地方法栈）引用的对象               │
│ 5. 活跃线程（Thread 对象）                   │
│ 6. 被 synchronized 持有的对象（锁对象）      │
└─────────────────────────────────────────────┘

3.3 引用类型

引用类型 回收时机 使用场景
强引用 永不回收（OOM 也不收） new Object() 普通对象
软引用 内存不足时回收 缓存（图片/数据）：SoftReference
弱引用 下一次 GC 即回收 WeakHashMap / ThreadLocal
虚引用 任何时候都可能回收 对象回收追踪（DirectByteBuffer 清理）

4. 垃圾回收算法

4.1 标记-清除（Mark-Sweep）

标记-清除流程:

  [存活对象]  [垃圾]  [存活对象]  [垃圾]
       ↓         ↓         ↓         ↓
  第一步: 标记 (从 GC Roots 出发标记所有存活对象)
       ↓         ↓         ↓         ↓
  第二步: 清除 (直接回收所有未标记的对象)

  优点: 简单
  缺点: ① 产生内存碎片 ② 分配大对象时可能提前触发 GC

4.2 标记-复制（Mark-Copy）

标记-复制（新生代使用的算法）:

  +-----------+     +-----------+     +-----------+
  |  Eden+S0  |     |   垃圾     |     |           |
  | (分配/使用) | --→ | (回收)    |     |  S1 (空)  |
  |    ↓      |     |    ↓      |     |    ↓      |
  |  存活对象  | --→ | 复制到 S1 |     |  存活对象  |
  +-----------+     +----+------+     +-----------+
                          |
                     Eden + S0 = 空

  每次回收时: Eden + S0 中存活对象复制到 S1
  然后清空 Eden 和 S0
  最后交换 S0 和 S1 的引用

  优点: 无碎片，效率高
  缺点: 有一块区域始终空闲（浪费 10%，S1 空着）

4.3 标记-整理（Mark-Compact）

标记-整理（老年代使用的算法）:

  第一步: 标记存活对象
  +---+---+---+---+---+---+---+---+---+---+
  | L | G | L | L | G | G | L | G | G | L |
  +---+---+---+---+---+---+---+---+---+---+
              ↓
  第二步: 整理（向一端移动存活对象）
  +---+---+---+---+---+-------------------+
  | L | L | L | L | L |   剩余空闲空间    |
  +---+---+---+---+---+-------------------+
              ↓
  第三步: 清除边界外的所有空间

  优点: 无碎片、内存利用率高
  缺点: 移动对象需要 STW，效率比复制低

4.4 分代收集理论

HotSpot 基于弱分代假设设计：绝大多数对象朝生夕死（很快变成垃圾）；熬过多次 GC 的对象趋向于长期存活。

  • 新生代：标记-复制（效率高，因为存活对象少）
  • 老年代：标记-整理（避免碎片，因为存活对象多）

5. 垃圾收集器

5.1 Serial 收集器

  • 单线程 GC，GC 时 STW（Stop The World）
  • 简单高效，适合单核 CPU、客户端模式
  • -XX:+UseSerialGC

5.2 Parallel 收集器

  • 多线程 GC，关注吞吐量（CPU 利用效率）
  • JDK 8 默认收集器
  • -XX:+UseParallelGC / -XX:+UseParallelOldGC
  • -XX:ParallelGCThreads=N 指定 GC 线程数
  • -XX:MaxGCPauseMillis=200 设置最大停顿时间

5.3 CMS 收集器

Concurrent Mark Sweep：追求最短停顿时间。

CMS 的 7 个阶段:

  1. 初始标记 (STW)        — 标记 GC Roots 直接引用的对象（很快）
  2. 并发标记              — 从 GC Roots 出发遍历引用链（与用户线程并发）
  3. 并发预清理            — 处理并发标记期间变化的引用
  4. 重新标记 (STW)        — 修正并发标记期间变动的引用（比初始标记大但可控）
  5. 并发清除              — 清除垃圾（与用户线程并发）
  6. 并发重置              — 重置数据结构

  优点: 并发，停顿短
  缺点:
    - 产生内存碎片（标记-清除算法）
    - 占用 CPU 资源（与业务线程争抢）
    - 无法处理浮动垃圾，可能发生 Concurrent Mode Failure
      → 退化为 Serial Old（串行 Full GC，超长停顿）
    - JDK 9 标记为废弃，JDK 14 移除

5.4 G1 收集器

Garbage-First：分区的、可预测停顿的收集器。JDK 9+ 默认收集器。

G1 核心设计:

  +---------------------------------------------------+
  |  堆被划分为 2048 个 Region（每个 1~32MB）           |
  |                                                     |
  |  +----+----+----+----+----+----+----+----+----+   |
  |  | E  | E  | O  | O  | S  | E  | O  | H  | E  |   |
  |  +----+----+----+----+----+----+----+----+----+   |
  |  | E  | O  | O  | E  | E  | S  | O  | E  | H  |   |
  |  +----+----+----+----+----+----+----+----+----+   |
  |  | E  | O  | E  | E  | O  | E  | O  | O  | E  |   |
  |  +----+----+----+----+----+----+----+----+----+   |
  |                                                     |
  |  E = Eden（新生代）  O = Old（老年代）               |
  |  S = Survivor       H = Humongous（大对象区）        |
  +-----------------------------------------------------+

  特点:
    - 不再有物理分代，每个 Region 动态决定角色
    - 每次只回收部分 Region（Garbage-First 优先回收垃圾最多的区域）
    - 通过 Remembered Set（RSet）避免全堆扫描
    - 可设置预期停顿时间: -XX:MaxGCPauseMillis=200

  G1 回收过程:
    Young GC: 暂停所有用户线程，并行复制 Eden 中的存活对象到 Survivor/Old
    Mixed GC: 回收部分 Old Region（选垃圾最多的几个）
      → 初始标记(STW) → 并发标记 → 重新标记(STW) → 筛选回收(STW)

  G1 vs CMS:
    - G1 停顿可预测（设置目标），CMS 停顿不稳定
    - G1 无碎片（标记-整理），CMS 有碎片（标记-清除）
    - G1 适合大堆（6G+），CMS 适合中小堆

5.5 ZGC 收集器

JDK 11 引入的低延迟收集器，停顿时间 < 1ms，与堆大小无关。

ZGC 核心原理:

  1. 染色指针 (Colored Pointers):
     在 64 位指针的高位存储元数据（Finalizable/Remapped/Marked0/Marked1）
     无需额外数据结构，直接从指针判断对象状态

  2. 读屏障 (Load Barrier):
     对象访问时检查指针状态
     如果对象正在重定位，读屏障自动修正指针
     用户线程无需停顿

  3. 并发整理:
     ZGC 所有阶段（标记、转移、重映射）都是并发的
     只有 GC Roots 扫描需要 STW（非常短）

  性能:
    - 停顿 < 1ms（JDK 16+ 已稳定）
    - 最大堆可达 4TB（64 位指针）
    - 吞吐量略低于 G1（约低 5%~15%）

  适用场景:
    低延迟要求高的系统（交易系统、实时服务）

5.6 收集器对比总结

收集器 GC 算法 优势 缺点 适用场景
Serial 复制 + 整理 简单高效 STW 时间长 单核、客户端
Parallel 复制 + 整理 吞吐量高 STW 时间较长 批处理、科学计算
CMS 标记-清除 低停顿并发 碎片、CPU 争抢、已废弃 已不推荐
G1 Region 化复制 停顿可预测、大堆友好 小堆性能略低 服务端（JDK 9+ 默认）
ZGC 染色指针+并发 < 1ms 停顿、超大堆 吞吐量略低、JDK 较新 低延迟系统

6. 类加载机制

6.1 类加载生命周期

类加载 7 个阶段:

  加载 ─→ 验证 ─→ 准备 ─→ 解析 ─→ 初始化 ─→ 使用 ─→ 卸载
  (解析可以在初始化之后开始，支持动态绑定)

  1. 加载:
     - 通过全限定名获取 class 字节流
     - 将静态存储结构转化为方法区运行时数据结构
     - 在堆中生成一个 Class 对象作为入口

  2. 验证:
     - 文件格式验证（魔数 0xCAFEBABE）
     - 元数据验证（语义检查）
     - 字节码验证（数据流/控制流分析）
     - 符号引用验证（类是否存在）

  3. 准备:
     - 为静态变量分配内存，赋零值
     - static int x = 10 → 此时 x = 0
     - final static 常量直接赋值（编译期确定）

  4. 解析:
     - 符号引用 → 直接引用（内存地址）
     - 类的符号引用、字段、方法、接口方法

  5. 初始化:
     - 执行 <clinit> 方法（静态变量赋值 + 静态代码块）
     - 由 JVM 保证线程安全（只有一个线程执行 <clinit>）

  触发类初始化的 6 种情况（主动引用）:
    - new/putstatic/getstatic/invokestatic
    - 反射调用
    - 子类初始化触发父类初始化
    - main 方法的启动类
    - MethodHandle 调用
    - Java 8 Lambda 表达式

6.2 双亲委派模型

                    ┌──────────────────────┐
                    │ Bootstrap ClassLoader│
                    │  (启动类加载器)        │
                    │  加载 rt.jar / core   │
                    │  C++ 实现，无父类     │
                    └─────┬────────────────┘
                          │
                    ┌─────v────────────────┐
                    │ Extension ClassLoader│
                    │  (扩展类加载器)        │
                    │  加载 jre/lib/ext    │
                    │  Java 实现           │
                    └─────┬────────────────┘
                          │
                    ┌─────v────────────────┐
                    │ App ClassLoader     │
                    │  (应用类加载器)        │
                    │  加载 classpath 上的类│
                    │  用户代码的默认加载器   │
                    └──────────────────────┘

  工作流程:
    加载一个类时，先委托给父类加载器
    父类加载不了（抛出 ClassNotFoundException）时，自己尝试加载

  好处:
    - 安全性：核心类（java.lang.String）由 Bootstrap 加载
      → 自定义同名类无法替换核心类，防止核心 API 被篡改
    - 避免重复加载：父类加载过的子类不再重复加载

6.3 双亲委派被打破的场景

场景 原因 解决方案
JDBC SPI DriverManager 由 Bootstrap 加载，但 MySQL 驱动在 classpath 上 线程上下文类加载器（TCCL）
Tomcat 多个 WebApp 需要隔离：同一个类不同版本 自定义 WebAppClassLoader，优先加载自己 war 包内的类
热部署 / OSGi 动态加载/替换类 自定义类加载器实现模块化和版本管理
Java 模块化（JPMS） JDK 9 模块化 模块化边界检查替代部分双亲委派

7. JVM 调优

7.1 常用 JVM 参数

参数 说明 示例
-Xms 初始堆大小 -Xms4g
-Xmx 最大堆大小 -Xmx4g（建议 -Xms = -Xmx）
-Xmn 新生代大小 -Xmn1g
-Xss 线程栈大小 -Xss512k
-XX:MetaspaceSize 元空间初始大小 -XX:MetaspaceSize=256m
-XX:+UseG1GC 使用 G1 收集器 JDK 9+ 默认
-XX:MaxGCPauseMillis 最大 GC 停顿目标 -XX:MaxGCPauseMillis=200
-XX:+HeapDumpOnOutOfMemoryError OOM 时自动 dump 必备参数
-XX:HeapDumpPath dump 文件路径 -XX:HeapDumpPath=/tmp/dump.hprof
-XX:+PrintGCDetails 打印 GC 日志 JDK 8

7.2 常见 OOM 场景

OOM 类型 原因 排查方向

8. JVM 性能优化

8.1 逃逸分析

通过分析对象的作用域是否逃逸出方法/线程，JVM 可以做如下优化：

  • 栈上分配：对象不逃逸时，直接在栈上分配（随方法结束自动销毁，减少 GC 压力）
  • 标量替换：将对象拆解为基本类型，直接在栈上分配字段
  • 锁消除：确定不会有竞争时，去掉 synchronized

JDK 8 默认开启逃逸分析（-XX:+DoEscapeAnalysis），但这并非严格保证栈上分配——HotSpot 实际通过标量替换实现类似效果。

8.2 TLAB

Thread Local Allocation Buffer：每个线程在 Eden 区分配一块私有的缓冲区，避免多线程竞争分配指针。默认开启（-XX:+UseTLAB），线程优先在 TLAB 中分配对象，TLAB 用完再竞争 Eden 区。

8.3 SafePoint

JVM 进行 GC 时必须等待所有线程到达 SafePoint（安全点），才能获取线程的准确执行状态。SafePoint 的位置：

  • 循环末尾
  • 方法返回前
  • 可能抛异常的位置
  • 刚完成的对象分配

长时间运行无 SafePoint 的代码（如空循环）会导致 GC 无法执行 → 表现为"长时间停顿"或 STW 卡住。

9. 高频面试题

Q1：JVM 运行时数据区有哪些？

线程私有：程序计数器（唯一无 OOM 的区域）、VM Stack（栈帧：局部变量表/操作数栈/动态链接/返回地址）、本地方法栈。线程共享：堆（对象实例，GC 主战场）、方法区（JDK 8+ 为元空间，存类元数据/常量池）。

Q2：哪些对象可以作为 GC Roots？

六个来源：① 栈帧局部变量引用的对象 ② 静态属性引用的对象 ③ 常量引用的对象 ④ JNI 引用的对象 ⑤ 活跃线程对象 ⑥ synchronized 锁对象。

Q3：如何判断对象已死？

JVM 用可达性分析（不用引用计数，因为无法解决循环引用）。从 GC Roots 出发遍历引用链，不可达的对象就是垃圾。对象还可能通过 finalize() 自救一次（但不推荐用，已弃用）。

Q4：新生代为什么分 Eden 和 Survivor？

为了避免内存碎片。如果没有 Survivor，Eden GC 后存活对象直接进老年代（老年代很快就被撑满导致 Full GC）。用复制算法（Eden + S0 → S1），新生代 GC 时只需要复制少量存活对象，效率高且无碎片。默认 Eden:S0:S1 = 8:1:1。

Q5：什么时候发生 Full GC？

Full GC 触发条件:
  1. 老年代空间不足（晋升对象太多）
  2. Metaspace / PermGen 空间不足
  3. System.gc() 显式调用（建议但非强制）
  4. CMS Concurrent Mode Failure（CMS 清理跟不上垃圾产生速度）
  5. Young GC 晋升时老年代剩余空间小于晋升对象大小（担保失败或 HandlePromotionFailure）

Q6：CMS 和 G1 的区别？

对比项 CMS G1
堆结构 物理分代（连续新生代/老年代） 逻辑分代（2048 个 Region 动态分配角色）
算法 标记-清除（有碎片） 标记-整理（Region 内复制，无碎片）
停顿 不稳定，可能较长 可预测，设 MaxGCPauseMillis
回收范围 老年代（配合 Parallel Young GC） 每次选垃圾最多的部分 Region 回收
JDK 状态 JDK 9 废弃，JDK 14 移除 JDK 9+ 默认收集器

Q7：G1 和 ZGC 的区别？

G1 追求停顿可预测（~200ms），适合通用服务端场景。ZGC 追求超低延迟（< 1ms），适合延迟敏感场景。ZGC 的停顿与堆大小无关（染色指针 + 读屏障），但吞吐量略低于 G1。G1 适合 4~64G 堆，ZGC 更适合 64G+ 超大堆。

Q8：类加载的过程？

5 个阶段（后 3 个有交叉）：加载（找 class 文件）→ 验证（检查格式/语义/字节码）→ 准备（给 static 变量分配零值）→ 解析（符号引用→直接引用）→ 初始化（执行 <clinit>，真正赋值）。

Q9：双亲委派模型及打破场景？

模型：类加载器收到加载请求时，先委托给父加载器加载，父加载器加载不了才自己加载。保证核心类安全（java.lang.String 由 Bootstrap 加载，不会被篡改）。
打破场景：JDBC SPI（TCCL）、Tomcat WebApp 隔离、OSGi 模块化、热部署。

Q10：CPU 飙高 / OOM 怎么排查？

CPU 飙高排查:
  1. top -H -p <pid> 找到占用 CPU 最高的线程
  2. printf "%x\n" <tid> 转十六进制
  3. jstack <pid> | grep -A 30 <nid> 查看线程栈
  4. 定位到具体代码行

OOM 排查:
  1. 启动参数加 -XX:+HeapDumpOnOutOfMemoryError
  2. OOM 时自动生成 .hprof dump 文件
  3. 用 MAT 或 JProfiler 打开 dump
  4. 查看 GC Roots 路径 → 找到泄漏对象
  5. 常见泄漏: 过期引用未清、ThreadLocal 泄露、连接未关闭

学习建议：JVM 面试三个核心方向：① 内存结构（运行时数据区、GC Roots、引用类型）② 垃圾回收（算法/收集器演化路线 Serial→Parallel→CMS→G1→ZGC）③ 类加载（加载过程、双亲委派）。最常问的是 G1 和 ZGC 的对比，以及 OOM 排查实践。建议用 JMC/VisualVM 连接本地运行的应用，实时观察堆内存和 GC 行为。
