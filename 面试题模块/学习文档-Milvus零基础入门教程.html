Milvus 从入门到精通

本文档从零开始系统讲解 Milvus 向量数据库，适合后端开发者、AI 应用开发者、以及想系统掌握向量检索技术的工程师。从基础概念讲到生产部署，类比丰富，代码可运行。

一、Milvus 基础概念

1.1 向量数据库是什么

传统数据库（MySQL、PostgreSQL）擅长"精确匹配"——你找 WHERE name='张三'，它精确返回。但在 AI 时代，我们经常需要找"和某个东西最像的 N 个东西"：

  • 找和"怎么退钱"语义最像的文档片段
  • 找和这张图片最像的商品图
  • 找和这个用户兴趣最像的其他用户

这就是向量检索。先把数据用 AI 模型转成"向量"（一串浮点数），再比较向量之间的距离。距离越近，语义越相似。

🎯 类比——地图坐标
北京 (116.4, 39.9) 和天津 (117.2, 39.1) 在地图上离得近。
向量也一样——"猫"和"狗"的向量离得近（都是宠物），"猫"和"汽车"的向量离得远。
只不过向量不是 2 维坐标，而是 128~7680 维的"语义坐标"。

能力 普通数据库（关系库） 向量数据库（Milvus）
核心查询 精确匹配、范围过滤 近似最近邻（ANN）
数据类型 数字、字符串、日期、JSON 向量（浮点数数组）+ 标量字段
索引 B-tree, GIN, GiST HNSW, IVF, DiskANN
适用场景 事务、报表、用户数据 语义搜索、推荐、RAG

Milvus 是什么？

Milvus 是开源的向量数据库，由 Zilliz 开发（2023 年捐给 Linux Foundation）。它专为向量检索设计，支持：

  • 万亿级向量的近似最近邻检索
  • 多种索引类型（HNSW、IVF、DiskANN 等）
  • 混合检索（向量 + 标量过滤）
  • 分布式集群部署
  • 多语言 SDK（Python、Java、Go、Node.js）

对比同类产品：

产品 定位 开源 分布式
Milvus 专业向量数据库 ✅ Apache 2.0 ✅
Pinecone 托管向量数据库 ❌ ✅
Weaviate 向量+对象数据库 ✅ BSD ✅
Qdrant 向量数据库 ✅ Apache 2.0 ✅
Chroma 轻量向量数据库 ✅ Apache 2.0 ❌

1.2 Milvus 核心概念

🔹 Collection（集合）

类似关系数据库的表。一个 Collection 包含：

  • 向量字段：存向量的地方（每个 Collection 至少一个）
  • 标量字段：存普通数据的字段（id、文本、标签等）
  • Schema：定义字段名、类型、维度
🎯 类比：Collection = Excel 表格，向量字段 = 一个特殊列存坐标，标量字段 = 其他普通列

🔹 Entity（实体）

Collection 里的一行数据。一个 Entity 包含：一个向量 + 若干标量字段。

{
    "id": 1,
    "vector": [0.12, 0.45, 0.78, ...],
    "text": "退款政策说明",
    "author": "张三"
}

🔹 Index（索引）

Milvus 的核心——没有索引，检索就是"全库暴力遍历"，几百万条要算几百万次距离，根本跑不动。索引是专门为加速 ANN 检索而建的数据结构。

建索引 ≈ 给数据重新组织一下，让"找最近邻"这件事能从 O(N) 降到 O(log N) 甚至 O(1)。

🎯 类比——新华字典的偏旁部首索引：没索引 → 一页页翻（O(N)）；有索引 → 先查偏旁部首，定位到某一页（O(log N)）

🔹 Partition（分区）

把一个 Collection 按某个字段的值拆成多个物理分区。查询时可以指定只查某个分区，缩小搜索范围。

🔹 Sharding（分片）

数据水平切分到多个节点。Milvus 自动处理，开发者无感。

🔹 ANN vs KNN

类型 全称 准确度 速度 说明
KNN K 最近邻（精确） 100% 慢 全库遍历，保证找到精确的 Top-K
ANN 近似最近邻 99%+ 快 100x 牺牲一点点精度换极速，实际够用

Milvus 默认用 ANN。没人会在生产环境用 KNN（太慢）。

1.3 Milvus 架构概览

Milvus 采用存算分离架构，核心组件：

┌─────────────────────────────────────────────────────────┐
│                    SDK / API Layer                       │
│           (Python, Java, Go, Node.js, REST)              │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────┐
│                    Proxy (无状态网关)                     │
│       请求路由、鉴权、结果聚合、请求/响应编解码              │
└────────┬──────────────┬──────────────┬──────────────────┘
         │              │              │
         ▼              ▼              ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  Coordinator │ │  Data Node   │ │  Query Node   │
│  集群管理     │ │ 数据持久化    │ │ 向量检索执行   │
│  DDL/DML     │ │ 增量/批量写入 │ │ 索引加载+查询  │
└──────────────┘ └──────────────┘ └──────────────┘
         │              │              │
         └──────────────┼──────────────┘
                        ▼
               ┌────────────────┐
               │  Object Store   │  ← 数据最终存对象存储 (MinIO/S3/GCS)
               └────────────────┘
                        │
               ┌────────────────┐
               │    Meta Store   │  ← 元数据 schema/索引状态 (etcd)
               └────────────────┘

核心组件说明：

组件 职责 类比
Proxy 网关层，接收请求、分发到 Query Node 餐厅前台
Coordinator 管理集群状态、处理 DDL（建表/删表） 餐厅经理
Data Node 数据写入、持久化到对象存储 后厨切菜师傅
Query Node 加载索引、执行向量检索 跑堂的上菜
Object Store 存实际数据（向量+标量） 仓库
Meta Store 存元数据（etcd） 菜单本

与 Elasticsearch 架构的关键区别：

  • ES 写入实时搜索可见；Milvus 数据写入先到 Data Node 落盘，查询时 Query Node 加载才能搜到——最终一致性
  • ES 存算一体；Milvus 存算分离——Query Node 和 Data Node 独立扩缩
  • Milvus 依赖对象存储（MinIO/S3）做主要存储，不是本地磁盘

2.2 创建第一个 Collection

from pymilvus import (
    Collection, CollectionSchema, DataType, FieldSchema,
    connections, utility
)

connections.connect(host="localhost", port="19530")

fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True, auto_id=False),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=128),
    FieldSchema(name="title", dtype=DataType.VARCHAR, max_length=256),
    FieldSchema(name="category", dtype=DataType.VARCHAR, max_length=64),
]

schema = CollectionSchema(fields=fields, description="我的第一个集合", enable_dynamic_field=False)

collection_name = "book_demo"
collection = Collection(name=collection_name, schema=schema)

index_params = {
    "metric_type": "COSINE",
    "index_type": "HNSW",
    "params": {"M": 8, "efConstruction": 200}
}
collection.create_index(field_name="embedding", index_params=index_params)

print(f"Collection '{collection_name}' 创建成功")

关键参数： dim=128 向量维度；metric_type="COSINE" 余弦相似度；index_type="HNSW" 通用索引。

2.3 插入与检索

插入数据

import random

entities = [
    [i for i in range(100)],
    [[random.random() for _ in range(128)] for _ in range(100)],
    [f"文档标题_{i}" for i in range(100)],
    [random.choice(["技术", "金融", "医疗"]) for _ in range(100)],

collection.insert(entities)
print(f"插入了 {collection.num_entities} 条数据")

执行向量检索

collection.load()

query_vector = [[random.random() for _ in range(128)]]

search_params = {"metric_type": "COSINE", "params": {"ef": 64}}
results = collection.search(
    data=query_vector, anns_field="embedding",
    param=search_params, limit=5,

for hits in results:

              f"标题: {hit.entity.get('title')}")

results = collection.search(

    expr="category == '技术'",

)

精确查询（按主键查）

result = collection.query(

三、索引详解

索引是 Milvus 的灵魂。选对了索引，毫秒级检索几百万向量；选错了，查一次卡几分钟。

3.1 索引类型概览

索引类型 内存占用 检索速度 召回率 适合场景
FLAT 高 极慢 O(N) 100% 精确 数据量很小（<1万）
IVF_FLAT 中 快 高 百万级，精度优先
IVF_SQ8 低（1/4） 快 中 百万级，内存受限
IVF_PQ 极低（1/8~1/16） 中等 中低 十亿级，极致省内存
HNSW 高 极快 高 绝大多数场景，千万级以下
DiskANN 低（主要在磁盘） 较快 高 十亿级，内存不够放 HNSW

3.2 HNSW 详解

HNSW = Hierarchical Navigable Small World（分层可导航小世界图）

当前最流行、最通用的 ANN 索引。本质是构建一个多层图结构：

层级1 (最顶层): ●──●──●         ← 稀疏连接，"高速通道"
                 │  │  │
层级2:          ●──●──●──●      ← 中间层
                 │  │  │  │
层级3 (底层):   ●──●──●──●──●   ← 密集连接，精确近邻

🎯 类比——地铁换乘
你在北京从"回龙观"到"亦庄"：
- 高层（层级1）= 快线：先坐 13 号线（粗粒度跳到附近区域）
- 底层（层级3）= 支线：到了望京，换 15 号线慢慢找具体站（细粒度精确定位）
HNSW 搜索就是从高层快速逼近目标区域，再到底层精确定位。

核心参数：

参数 作用 默认值 调大 调小
M 每节点最大连接数 8 召回率↑ 内存↑ 召回率↓ 内存↓
efConstruction 建索引搜索广度 200 索引质量↑ 建索引慢↑ 索引质量↓ 建索引快↓
ef 检索搜索广度 64 召回率↑ 检索慢↑ 召回率↓ 检索快↓

参数调优经验：

# 精度优先（召回率 99%+）
index_params = {"index_type": "HNSW", "params": {"M": 16, "efConstruction": 500}}
search_params = {"params": {"ef": 200}}

# 速度优先（延迟 < 10ms）
index_params = {"index_type": "HNSW", "params": {"M": 4, "efConstruction": 80}}
search_params = {"params": {"ef": 32}}

# 默认平衡
index_params = {"index_type": "HNSW", "params": {"M": 8, "efConstruction": 200}}
search_params = {"params": {"ef": 64}}

3.3 IVF 系列

IVF = Inverted File（倒排文件）

核心思路：把向量空间聚类成 K 个桶。检索时，只搜离查询向量最近的 N 个桶，而不是全库。

全库 100 万条向量 → 聚类成 100 个桶（nlist=100）
查询时：
1. 找到离查询向量最近的 5 个桶（nprobe=5）
2. 只在这 5 个桶里遍历（约 5 万条）
3. 从 5 万条中找 Top-K
🎯 类比——图书馆找书：没索引 = 一排一排走过所有书架；IVF = 先把书按类别分到 100 个书架，你只搜计算机那个书架

IVF 三个变种：

变种 存储方式 内存节省 精度损失
IVF_FLAT 完整 float32 无 无
IVF_SQ8 int8 量化 4x 约 1-2%
IVF_PQ 乘积量化 8~16x 约 2-5%

核心参数：

参数 说明 经验值
nlist 聚类桶的数量 sqrt(N)
nprobe 检索时搜几个桶（查询参数） 通常 8~32 
index_params = {"metric_type": "COSINE", "index_type": "IVF_FLAT", "params": {"nlist": 256}}
collection.create_index("embedding", index_params)

search_params = {"metric_type": "COSINE", "params": {"nprobe": 16}}
results = collection.search(query_vectors, "embedding", search_params, limit=10)

3.4 量化索引 PQ/SQ

当向量数据太大、内存放不下时，需要量化——把向量"压缩"一下，牺牲一点精度换内存。

SQ8（标量量化）： float32 → int8，每维从 4 字节 → 1 字节，省 4 倍内存。

PQ（乘积量化）： 把向量分段，每段单独压缩成码本，能省 8~16 倍。

🎯 类比——模糊照片：原图 10MB → JPEG 1MB。肉眼看着差不多（精度略降），但省了 90% 空间。

3.5 DiskANN

DiskANN = 基于磁盘的 ANN 索引。当数据量大到内存装不下（>1000 万条、>100GB），DiskANN 把图结构和大部分数据放磁盘，只用少量内存做缓存。

维度 HNSW DiskANN
数据存储 全在内存 主要在 SSD
1000 万条 768 维 约 30GB 内存 约 3GB 内存
检索延迟 1~5ms 5~20ms 
index_params = {"metric_type": "COSINE", "index_type": "DISKANN", "params": {}}

3.6 如何选择索引

决策树：

数据量 < 1万？
├── 是 → FLAT（精确查找）
└── 否 → 内存够放所有向量？
         ├── 是 → HNSW（通用首选，千万级以下随便用）
         └── 否 → 可以接受多大内存？
                  ├── 4x 压缩 → IVF_SQ8
                  ├── 16x 压缩 → IVF_PQ
                  └── 磁盘都可以 → DiskANN
场景 首推
新手、通用、千万级以下 HNSW（M=8, efConstruction=200, ef=64）
精度要求极高（99%+） HNSW（M=16, efConstruction=500, ef=200）
内存受限（百万级） IVF_SQ8（nlist=sqrt(N), nprobe=16）
十亿级、磁盘充足 DiskANN

四、高级功能

4.1 混合搜索（Hybrid Search）

Milvus 2.4+ 支持在一个 Collection 里建多个向量字段，做"多路向量召回 + RRF 融合"。

fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True),
    FieldSchema(name="text_emb", dtype=DataType.FLOAT_VECTOR, dim=768),
    FieldSchema(name="image_emb", dtype=DataType.FLOAT_VECTOR, dim=512),
    FieldSchema(name="content", dtype=DataType.VARCHAR, max_length=1024),
]

collection.create_index("text_emb",  {"index_type": "HNSW", "params": {"M": 8, "efConstruction": 200}})
collection.create_index("image_emb", {"index_type": "HNSW", "params": {"M": 8, "efConstruction": 200}})

from pymilvus import RRFRanker

hybrid_results = collection.hybrid_search(
    reqs=[
        collection.search(data=[text_query_vec], anns_field="text_emb",
                          param={"metric_type": "COSINE", "params": {"ef": 64}}, limit=10),
        collection.search(data=[image_query_vec], anns_field="image_emb",
                          param={"metric_type": "COSINE", "params": {"ef": 64}}, limit=10),
    ],
    ranker=RRFRanker(k=60), limit=5
)

4.2 标量过滤

expr = "category == '技术'"
expr = "category in ['技术', '金融']"
expr = "price >= 100 && price <= 500"
expr = "title like '%退款%'"            # Milvus 2.3+
expr = "(category == '技术' && score > 0.8) || author == '张三'"

⚠️ 标量过滤发生在向量检索之内，不是先过滤再搜向量。Milvus 在 ANN 遍历时"边走边过滤"。

4.3 Partition 与 Sharding

# 创建分区
collection.create_partition(partition_name="tech_docs")
collection.insert(data, partition_name="tech_docs")

# 只查询某个分区
results = collection.search(
    data=query_vectors, anns_field="embedding",
    param=search_params, limit=10,
    partition_names=["tech_docs"]
)

# 创建时指定分片数
collection = Collection(name="my_collection", schema=schema, shards_num=4)

什么时候用 Partition？

  • 数据有明显的"分组"属性（租户、语言、年份）
  • 查询总是带着该属性过滤
  • 需要按组物理删除数据

五、性能优化

5.1 索引参数调优

HNSW 参数调优路线图：

1. 先试探 M=8, efConstruction=200, ef=64
2. 召回率不够 → 增大 ef（64→128→200），还不够就增大 M（8→16）
3. 延迟太高 → 减小 ef（64→32）或减小 M（8→4）
4. 建索引太慢 → 减小 efConstruction（200→100）

IVF 参数调优：

nlist = sqrt(N)    100 万条 → nlist=1000
nprobe 从 8 开始，越大越准越慢

5.2 查询优化策略

1. 批量查询合并网络开销

# ❌ 100 次查询 = 100 次网络往返
for i in range(100):
    result = collection.search([single_query], ...)

# ✅ 1 次查询 = 1 次网络往返
results = collection.search(batch_100_queries, ...)

2. 合理设置 limit（Top-10 一般够用）
3. 用 Partition 缩小搜索范围
4. 不用时释放内存：collection.release()

5.3 资源规划

HNSW 内存 ≈ dim × N × 4（float32）× 1.2（图结构）

举例：100 万条 × 768 维 ≈ 3.7 GB
      1000 万条        ≈ 37 GB  → 该考虑 DiskANN 或 IVF_PQ
组件 建议配置
Milvus Standalone 8C 16GB
etcd 2C 4GB
MinIO 4C 8GB

七、面试题

Q1：向量数据库和普通数据库有什么区别？

A：普通数据库做精确查找（WHERE name='张三'），用 B-tree 索引；向量数据库做近似查找（"给我最近的 N 个向量"），用 HNSW/IVF 等 ANN 索引。

Q2：HNSW 的原理是什么？

A：分层小世界图，上层稀疏连接（高速通道），下层密集连接（精确近邻）。检索时从上层快速逼近，再到底层精确定位。时间复杂度 O(log N)。

Q3：怎么选索引类型？

A：千万级以下 HNSW，内存受限用 IVF_SQ8，十亿级用 DiskANN 或 IVF_PQ，<1万用 FLAT。

Q4：Milvus 的存算分离架构？

A：Proxy（网关）、Query Node（计算）、Data Node（存储）独立部署。数据存对象存储，计算节点按需加载。好处是独立扩缩、成本低。

Q5：怎么保证召回率？

A：索引参数（ef/nprobe），混合检索（向量+BM25），Cross-Encoder 精排。

Q6：Milvus 的数据最终一致性？

A：写入→Data Node 落盘→Index Node 建索引→Query Node 加载才能搜到，不是实时可见。

Q7：怎么估内存？

A：HNSW ≈ dim × N × 4 × 1.2。100 万条 768 维 ≈ 3.7 GB。

Q8：标量过滤是"先搜再滤"还是"边搜边滤"？

A：边搜边滤——ANN 遍历时检查条件，不满足的直接跳过。

Q9：Milvus 和 ES 架构的关键区别？

A：ES 写入实时可见、存算一体；Milvus 最终一致性、存算分离、依赖对象存储。

Q10：RRF 融合的原理？

A：Reciprocal Rank Fusion，把多路召回结果按排名融合，只看名次不看绝对分数。公式：score = Σ 1/(k + rank_i)，k 通常取 60。

掌握 Milvus，就掌握了 AI 时代最核心的向量搜索基础设施。
