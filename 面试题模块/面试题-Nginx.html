Nginx

1. 正向代理和反向代理的区别?

正向代理(替客户端办事):
  [你的电脑] → [代理服务器] → [Google]
    ↑ 被隐藏     ↑ 对外暴露
  场景:VPN、翻墙、公司内网访问外网

反向代理(替服务端办事):
  [用户浏览器] → [Nginx] → [Tomcat1, Tomcat2, Tomcat3]
                  ↑ 对外暴露    ↑ 被隐藏
  场景:网站入口、负载均衡、API 网关

一句话:正向代理是客户端的"马甲"(代理客户端,服务端不知道真正的客户端),反向代理是服务器的"门面"(代理服务器,客户端不知道真正的服务器,只看到一个域名)。

扩展:Nginx 作为反向代理时,常用 proxy_set_header X-Real-IP $remote_addr 和 X-Forwarded-For 把真实客户端 IP 传给后端,否则后端只能看到 Nginx 的 IP。VPN 是典型的正向代理--你的流量经过了 VPN 服务器,目标网站只能看到 VPN 的 IP。

2. 为什么 Tomcat 前面要放 Nginx？

四大作用： 1. 动静分离：Nginx 处理静态资源（epoll + sendfile），动态请求转发 Tomcat 2. 负载均衡：流量分到多台 Tomcat 3. 安全：隐藏后端真实 IP 和端口 4. SSL 卸载：HTTPS 在 Nginx 完成，后端只需 HTTP

扩展：Nginx 还可做限流、缓存、请求改写、跨域处理。

3. 负载均衡策略有哪些？

策略 规则 适用
轮询（默认） 一个一个轮 服务器配置相同
加权轮询 按权重 服务器配置不均
ip_hash 同 IP 固定 需要 Session 保持
least_conn 连接数少优先 请求耗时差异大

选型：服务器差不多→轮询；有强有弱→加权；需登录保持→ip_hash（或 Redis 共享 Session）。

扩展：ip_hash 前面有代理时全打到一台，可用 hash $remote_addr。

4. Nginx 怎么实现高并发？

核心：Master-Worker 多进程 + 异步非阻塞 + epoll。

  1. Master-Worker 模型：Master 管理，Worker（CPU核数）独立处理请求
  2. 异步非阻塞：epoll 监听，有事件才处理，不阻塞
  3. 高效内存管理：连接/请求内存池

对比 Tomcat（一个请求一个线程）：10000 连接 → 10000 线程 → 大量上下文切换；Nginx → 4 个 Worker → epoll 事件驱动。

扩展：worker_processes auto 设 CPU 核数，worker_connections 10240 设最大连接。sendfile on 零拷贝，gzip on 压缩。

5. location 的匹配规则?

location 匹配优先级(从高到低):

1 = /exact    → 精确匹配,命中直接停(最高优先级)
2 ^~ /prefix/ → 前缀匹配,命中后不再继续匹配正则
3 ~ \.php$    → 正则匹配(区分大小写)
4 ~* \.PNG$   → 正则匹配(不区分大小写)
5 /           → 通用前缀匹配(最低优先级)

注意:多个正则按配置文件中出现的顺序匹配,第一个中的为准
      普通前缀匹配选最长的那个

示例配置:
location = /login { ... }         ← 只匹配 /login
location ^~ /static/ { ... }      ← 匹配 /static/ 开头的所有
location ~ \.php$ { ... }         ← 匹配 .php 结尾
location / { ... }                ← 兜底

扩展:alias 和 root 的区别常被混淆--root /var/www; 会把完整 URI 拼接到路径后,alias /var/www/; 只替换匹配的部分。例如 location /images/ { root /data; } → /images/1.jpg 映射到 /data/images/1.jpg;而 alias /data/images/; → /images/1.jpg 映射到 /data/images/1.jpg。

6. Nginx 如何实现限流?

限流 = 游乐场门口检票。漏桶算法:均匀放行,像检票员按固定节奏一个个放人--人来了太多就排队(burst),排不下就拒之门外(503)。令牌桶算法:门口放一桶令牌,来一个人拿一个令牌才能进,没令牌就等着--允许短暂爆发(桶里有库存时一次放很多人),但长期限速不变。

# 1 基于 IP 的请求速率限制(漏桶算法)
limit_req_zone $binary_remote_addr zone=req_limit:10m rate=10r/s;

server {
    location /api/ {
        limit_req zone=req_limit burst=20 nodelay;
        # burst=20: 桶容量,允许 20 个突发请求排队
        # nodelay: 突发请求立即处理(不排队),用令牌桶替代漏桶
    }
}

# 2 并发连接数限制
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

server {
    location /download/ {
        limit_conn conn_limit 5;    # 每个 IP 最多 5 个并发连接
        limit_rate 100k;            # 每个连接限速 100KB/s
    }
}

rate=10r/s + burst=20 效果:

  请求速率                       时间
    20个↓   ↓稳定 10个/s
  ████████▄▄▄▄▄▄▄▄▄▄▄▄▄
  └─burst─┘ └── 限速通行 ──┘
  前 20 个排队(或nodelay直接过)

扩展:漏桶(没有 nodelay)严格按照固定速率处理--超过 rate 的请求排队,桶(burst)满了就 503。加上 nodelay 后相当于令牌桶--突发请求立即通过,但通过后会控制后续速率。接口限流推荐用漏桶 + nodelay(容忍突发但控制均值)。

7. Nginx 的 500/502/503/504 错误码分别什么意思?

状态码 含义 常见原因
500 Nginx 自身内部错误 配置语法错误、rewrite 死循环
502 上游服务返回无效响应 后端服务挂了/没启动
503 服务暂时不可用 后端全挂了、连接数打满、限流
504 上游超时 后端响应太慢,超过 proxy_read_timeout 
排查决策树:

  Nginx 返回 502?
    ├── 后端进程在跑吗? → ps aux | grep java
    ├── 端口在监听吗? → ss -tunlp | grep :8080
    └── 防火墙挡了吗? → telnet localhost 8080

  Nginx 返回 504?
    ├── 后端接口是否慢? → 查 APM/日志
    ├── proxy_read_timeout 是否太短? → 默认 60s
    └── 是否大量慢 SQL 阻塞? → 查数据库

扩展:500 和 502/503/504 有本质区别--500 是 Nginx 自己的问题,502/503/504 是上游(后端)的问题。error_log 中会记录上游连接失败的具体原因,配置 proxy_intercept_errors on 可以让 Nginx 拦截后端的错误页并统一展示友好页面。

8. Nginx 如何实现动静分离?

        用户请求
           │
      ┌────▼────┐
      │  Nginx   │
      └────┬────┘
           │
    ┌──────┼──────┐
    │             │
 静态文件     动态请求
 (.html/.css   (/api/*)
  /.js/.png)
    │             │
    ▼             ▼
  Nginx自己     Tomcat/Django
  直接返回      (处理业务逻辑)

server {
    # 静态文件:Nginx 直接返回
    location /static/ {
        root /var/www;
        expires 7d;           # 浏览器缓存 7 天
        add_header Cache-Control "public, immutable";
    }

    # 动态请求:代理到后端
    location /api/ {
        proxy_pass http://backend;
    }
}

扩展:expires 指令设置浏览器缓存时间--静态资源通常设 7~30 天。改版时文件名加 hash(如 app.a3f2bc.js)来破坏缓存,而不是缩短 expires。CDN 本质上就是"分布式动静分离"--把静态资源分散到全球节点。

9. Nginx 如何配置 HTTPS?

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;

    # 只用 TLS 1.2 和 1.3(TLS 1.0/1.1 已不安全)
    ssl_protocols TLSv1.2 TLSv1.3;

    # 推荐加密套件
    ssl_ciphers ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers on;

    # 启用 HSTS(强制 HTTPS)
    add_header Strict-Transport-Security "max-age=63072000" always;
}

扩展:80 端口只做重定向:return 301 https://$host$request_uri;。Let's Encrypt 提供免费的 SSL 证书,搭配 certbot 可以自动续期。SSL 握手有一定开销,生产环境建议开启 ssl_session_cache shared:SSL:10m(10MB 缓存),减少重复握手。

10. Nginx 如何处理 WebSocket 转发?

配置 proxy_http_version 1.1、proxy_set_header Upgrade $http_upgrade、Connection Upgrade。需设 proxy_read_timeout 防断开。

11. Nginx 如何实现灰度发布？

灰度发布的四种 Nginx 实现方式：

# 方式1: 基于 IP 段（简单粗暴）
geo $backend {
    default       backend_v1;
    10.0.0.0/8   backend_v2;   # 内网IP走新版本
}

# 方式2: 基于 Cookie（用户维度）
map $cookie_version $backend {
    ~^2\.0    backend_v2;
    default   backend_v1;
}

# 方式3: 基于 Header（测试环境）
set $backend backend_v1;
if ($http_x_app_version = "2.0") {
    set $backend backend_v2;
}

# 方式4: 基于权重（流量比例）
upstream backend_v1 {
    server 10.0.1.1:80 weight=90;
}
upstream backend_v2 {
    server 10.0.1.2:80 weight=10;
}

生产级推荐：用 OpenResty + Lua 做更灵活的灰度（基于用户 ID、AB实验平台）：

-- openresty/lua 灰度示例
local version = ngx.header["X-User-Version"]
if version == "2.0" then
    ngx.var.target = "backend_v2"
else
    ngx.var.target = "backend_v1"
end

扩展：金丝雀发布（Canary Release）通常先切 5% 流量，观察 24h 无异常后逐步扩大；Istio + K8s 的灰度比 Nginx 更精细（基于请求内容、百分比、可观测性联动）。
