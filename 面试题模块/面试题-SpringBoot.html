Spring Boot

1. Spring Boot 的自动配置原理?

自动配置工作流程:

@SpringBootApplication
  └─ @EnableAutoConfiguration
       └─ @Import(AutoConfigurationImportSelector.class)
            └─ 读取 spring.factories / .imports 文件
                 └─ 找到所有 XxxAutoConfiguration 类
                      └─ @Conditional 条件判断
                           ├─ @ConditionalOnClass:依赖包存在吗?
                           ├─ @ConditionalOnMissingBean:用户自己配了吗?
                           └─ @ConditionalOnProperty:配置文件满足条件吗?
                                └─ 条件都满足 → 自动创建 Bean

你引入一个 Starter(如 mybatis-spring-boot-starter),这个 Starter 带了一个 AutoConfiguration 类。Spring Boot 启动时扫到它,检查条件满足后自动创建所有需要的 Bean。

扩展:Spring Boot 3.0+ 用 META-INF/spring/xxx.imports 替代 spring.factories,排错设 debug: true 查看自动配置生效情况。

2. @Component、@Service、@Repository、@Controller 的区别?

四个注解功能几乎一样--都是把类交给 Spring 管理(注册为 Bean)。区别在于语义分层:

@Controller  ← 控制层,处理 HTTP 请求(Spring MVC)
  @Service   ← 业务层,写业务逻辑
    @Repository  ← 数据层,操作数据库(额外提供异常翻译)
      @Component  ← 通用组件,不属于以上三层的用这个

@Repository 的独特能力:它多了一个"异常翻译"--把数据库特有的异常(如 MySQL 的 SQLException、Hibernate 的 HibernateException)翻译成 Spring 统一的 DataAccessException。

扩展:四者都间接标注 @Component,@ComponentScan 都能扫到。@Indexed 注解(Spring 5+)可在编译时生成候选 Bean 索引,加速启动扫描。

3. Spring 的依赖注入方式?

三种注入方式对比:

1 构造器注入(⭐ 官方推荐)
   private final UserService userService;
   public UserController(UserService userService) {
       this.userService = userService;
   }
   优点:依赖不可变(final)、不依赖容器(测试时直接 new)、编译期检查

2 Setter 注入
   @Autowired
   public void setUserService(UserService userService) { ... }
   优点:可选依赖、可动态改
   缺点:依赖可变,可能 NPE

3 字段注入
   @Autowired
   private UserService userService;  // 简洁但不推荐
   缺点:不能 final、测试必须启动容器、隐藏了依赖

为什么推荐构造器注入: - 测试时直接 new UserController(mockUserService),不用启动 Spring - final 保证了不可变性,不会出现"先创建对象后补依赖"的状态不一致 - 依赖一目了然--构造器参数太多说明类设计有问题(单一职责)

扩展:Lombok @RequiredArgsConstructor 可自动生成构造器;Spring 4.3+ 单构造器可省略 @Autowired;可选依赖用 Optional 参数。

4. Spring AOP 的原理?

AOP 动态代理流程:

客户端 → 代理对象(Proxy)
            │
            ├─ Before Advice(前置通知)
            ├─ 调用真实方法 target.method()
            ├─ AfterReturning / AfterThrowing
            └─ After Advice(后置通知)

客户端访问的不是真实对象,是代理对象
代理在调用前后偷偷加上了切面逻辑

AOP 让你在不改源码的情况下给方法"加切面"。Spring 内部大量用 AOP: - @Transactional:代理在方法前开启事务,成功提交,异常回滚 - @Cacheable:代理在方法前检查缓存,命中直接返回 - @Async:代理把方法提交到线程池异步执行

两种代理: - JDK 动态代理:基于接口,目标类必须实现接口。Proxy.newProxyInstance() - CGLIB 代理:基于继承,生成目标类的子类。Spring Boot 2.x 后默认用 CGLIB

扩展:this.method() 不走代理(this 是真实对象)。AspectJ 编译期织入无需代理,但需额外编译插件。默认只拦截 public 方法。

5. Spring 事务的传播行为和隔离级别?

传播行为(常用 3 种):

REQUIRED(默认):
  方法B 调用 方法C
  B 有事务 → C 加入 B 的事务(一起提交/回滚)
  B 没有 → C 自己新建事务

REQUIRES_NEW:
  B 有事务 → C 另起一个新事务,B 的事务被挂起
  C 提交/回滚 与 B 无关

NESTED:
  B 有事务 → C 创建嵌套事务(设置 savepoint)
  C 回滚 → 只回滚到 savepoint,B 不受影响
  B 回滚 → C 也回滚
行为 一句话 类比
REQUIRED 有就加入,没就新建 "搭顺风车"
REQUIRES_NEW 总是另起炉灶 "我开我的,你管你的"
NESTED 嵌套分支 "在正本上标记一页,撕掉这页不影响正本"

扩展:NESTED 依赖 savepoint 实现。REQUIRES_NEW/NESTED 需连接池足够大(挂起事务占连接)。

6. @Transactional 失效场景?

@Transactional 失效 6 大场景:

1 同类方法调用(最常见!)
   public void methodA() {
       this.methodB();  // ← this 不是代理对象!
   }
   @Transactional
   public void methodB() { ... }  // 事务不生效!

2 非 public 方法
   @Transactional
   private void doSomething() { ... }  // 代理只能拦截 public

3 异常被自己吞了
   @Transactional
   public void save() {
       try { db.save(); }
       catch (Exception e) { log.error(e); }  // 不回滚!
   }

4 抛出 checked 异常
   @Transactional
   public void save() throws IOException {  // 默认不回滚 IOException
   }

5 数据库引擎不支持事务
   MyISAM 引擎 → 事务压根不支持

6 多线程
   新线程不在当前事务上下文中 → 事务不传播

解决同类调用:注入自己(@Autowired private XxxService self;)后调用 self.methodB(),或将方法拆分到不同类。

扩展:事务默认只回滚 RuntimeException/Error。Checked 异常回滚用 rollbackFor = Exception.class。@Transactional 放接口上只有 JDK 代理生效(CGLIB 需在实现类)。

7. Bean 的生命周期?

Bean 生命周期全流程:

1 实例化(构造器/new)      → 空壳对象,属性是 null
2 属性注入(@Autowired)    → 填充依赖
3 BeanNameAware / BeanFactoryAware → 拿到自己的 ID 和 BeanFactory
4 BeanPostProcessor#postProcessBeforeInitialization
5 @PostConstruct 方法       → 初始化回调(最常用)
6 InitializingBean#afterPropertiesSet
7 BeanPostProcessor#postProcessAfterInitialization → 可能返回代理对象
8 Bean 就绪!放入单例池

销毁流程:
9 @PreDestroy 方法
10 DisposableBean#destroy
11 自定义 destroy-method

关键扩展点(面试重点):

  • @PostConstruct:最常用的初始化钩子(第5步)
  • BeanPostProcessor:Spring 最核心的后置处理器,AOP、事务、@Autowired 等所有"魔法"都靠它(第47步)
  • Aware 接口族:让 Bean 获取容器资源(第3步)

扩展:BeanFactoryPostProcessor 在实例化前执行(修改 BeanDefinition),BeanPostProcessor 在实例化后执行(修改 Bean 实例)。@Configuration 通过 ConfigurationClassPostProcessor 处理。

8. Spring 的循环依赖如何解决?

循环依赖场景:
  A 依赖 B,B 依赖 A → 死循环!先创建谁?

三级缓存(DefaultSingletonBeanRegistry):

┌─────────────┬──────────────────────┬─────────────────┐
│ singletonObjects  │ earlySingletonObjects │ singletonFactories │
│   一级缓存        │     二级缓存          │    三级缓存       │
│ 成品 Bean         │  半成品 Bean(引用)   │ 半成品的工厂函数   │
│ (完全初始化好的)   │ (实例化了但属性未注入) │ (能创建代理)       │
└─────────────┴──────────────────────┴─────────────────┘

解决流程:

1 创建 A → 实例化(空壳)→ 把 A 的工厂放入三级缓存
2 注入 A 的属性 → 发现需要 B → 去创建 B
3 创建 B → 实例化 → 注入 B 的属性 → 发现需要 A
4 从三级缓存取 A 的工厂 → 调用工厂拿到 A 的引用(可能是代理!)
5 A 的引用放入二级缓存 → 注入给 B → B 完成
6 回到 A,B 已就绪 → 注入 B → A 完成
7 把 A 放入一级缓存,清除二三级

为什么是三级不是二级:三级缓存存的不是对象本身,而是能生成代理对象的工厂。如果 A 需要 AOP 代理,B 拿到的 A 必须是代理过的引用。三级缓存的工厂函数在"谁需要 A 就给谁生成合适的引用"。

构造器注入的循环依赖:❌ 解决不了。因为构造器执行时对象还没实例化完,无法提前暴露引用。

扩展:Spring 只能解决单例循环依赖,prototype 直接抛异常。根本解法是重新设计避免循环,@Lazy 可缓解。

9. @Configuration 和 @Component 的区别?

区别演示:

@Configuration
class AppConfig {
    @Bean A a() { return new A(); }
    @Bean B b() { return new B(a()); }  // ← a() 是代理调用,返回单例!
}
→ a() 和 b() 获取到的是同一个 A 实例 ✓

@Component
class AppConfig {
    @Bean A a() { return new A(); }
    @Bean B b() { return new B(a()); }  // ← a() 是普通方法调用
}
→ a() 和 b() 获取到的是两个不同的 A ✗(不符合预期)

原理:@Configuration 类被 CGLIB 代理增强了--每次 @Bean 方法调用时,代理先检查容器里是否已经有这个 Bean,有就直接返回,没有才真正调方法创建。所以多次调用同一个 @Bean 方法返回的是同一个单例实例。

@Component(包括 @Service、@Repository)中的 @Bean 方法不走代理,是普通的 Java 方法调用。

扩展:Spring 5.2+ 支持 @Configuration(proxyBeanMethods = false) 关闭 CGLIB 代理提升启动速度,适合无方法间调用的纯配置类。

10. Starter 是什么?如何自定义?

Starter 结构:

my-starter(空 jar,只做依赖管理)
  ├─ my-starter-autoconfigure(自动配置模块)
  │   ├─ XxxAutoConfiguration.java
  │   ├─ XxxProperties.java        ← 配置属性绑定
  │   └─ META-INF/spring/...AutoConfiguration.imports
  └─ (其他依赖)

引入 starter 后:
  1 依赖自动引入(不需要再手动加相关 jar)
  2 自动配置生效(条件满足就创建默认 Bean)
  3 用户可以在 application.yml 中覆盖默认配置

Starter 是一组打包好的依赖 + 自动配置 + 默认参数。比如你引入 mybatis-spring-boot-starter,MyBatis 的所有依赖、SqlSessionFactory 的创建、Mapper 扫描都自动搞定。

自定义步骤:

  1. 创建 Properties 类(@ConfigurationProperties)定义外部化配置项
  2. 创建 AutoConfiguration 类(@AutoConfiguration),用 @Conditional 控制条件
  3. 在 META-INF/spring/xxx.AutoConfiguration.imports 中注册配置类
  4. 创建 Starter 模块引入 autoconfigure 模块

扩展:命名规范--官方 Starter 叫 spring-boot-starter-xxx,第三方叫 xxx-spring-boot-starter(如 mybatis-spring-boot-starter)。Spring Boot 3.0 后 @AutoConfiguration 替代了旧的 @Configuration + spring.factories 组合。@EnableConfigurationProperties 可以激活 Properties 类并绑定配置。

11. Bean 的作用域有哪些?

作用域 生命周期 用途
singleton(默认) 整个 IoC 容器中只有一个实例 无状态 Bean(Service、Controller)
prototype 每次 getBean() 返回新实例 有状态 Bean(如每个请求独立的上下文)
request 每个 HTTP 请求一个实例 Web 应用中请求级别的数据
session 每个 HTTP 会话一个实例 用户登录信息
application ServletContext 级别 全局 Web 上下文 
特别注意 prototype:
@Service
@Scope("prototype")
class PrototypeBean { ... }

单例 Bean 注入了 Prototype 的 Bean → Prototype 只创建一次!
因为单例 Bean 只在初始化时注入一次依赖
解决:用 @Lookup 方法注入或注入 ObjectFactory

扩展:@RefreshScope 可在不重启应用的情况下刷新配置。WebSocket 场景还有 websocket 作用域。

12. @Conditional 系列注解的作用?

常用 @Conditional 注解:

@ConditionalOnClass(xxx.class)        ← 类路径有这个类吗?
@ConditionalOnMissingClass            ← 类路径没有这个类吗?
@ConditionalOnBean(xxx.class)         ← 容器里有这个 Bean 吗?
@ConditionalOnMissingBean             ← 容器里没有吗?
@ConditionalOnProperty("my.config")   ← 配置文件里有这个配置吗?
@ConditionalOnExpression("...")       ← SpEL 表达式满足吗?
@ConditionalOnWebApplication          ← 是 Web 应用吗?
@ConditionalOnJava(...)               ← Java 版本对吗?

原理:每个 @Conditional 注解对应一个 Condition 接口的实现类,matches() 返回 true 才创建 Bean。Spring Boot 的自动配置就是靠这些注解实现"按需配置"的--有 Redis 就配 Redis,有 MyBatis 就配 MyBat...

实战例子:你引入了 spring-boot-starter-data-redis → classpath 有 RedisTemplate.class → RedisAutoConfiguration 上的 `@ConditionalOnClass(RedisTemplate.cl...

扩展:自定义 Condition 实现 matches(ConditionContext, AnnotatedTypeMetadata)。排错设 logging.level.org.springframework.boot.autoconfigure=DEBUG。

13. Spring Boot 如何实现多环境配置?

多环境配置文件:

application.yml              ← 公共配置(所有环境共享)
application-dev.yml          ← 开发环境
application-test.yml         ← 测试环境
application-prod.yml         ← 生产环境

激活方式(优先级从高到低):
1 命令行:--spring.profiles.active=prod
2 JVM 参数:-Dspring.profiles.active=prod
3 环境变量:SPRING_PROFILES_ACTIVE=prod
4 application.yml:spring.profiles.active: prod

配置合并:公共配置 + 环境专属配置合并生效,环境专属配置覆盖公共配置的同名项。

@Profile 注解:让 Bean 只在指定环境创建--@Profile("dev") 只在 dev 环境下生效。

扩展:2.4+ 支持 YAML 多文档(--- 分隔)。优先级:命令行 > JNDI > 环境变量 > application-{profile}.yml > application.yml > @PropertySource。

14. @Value 和 @ConfigurationProperties 的区别?

对比:

@Value("${app.url}")
private String url;              ← 一个个绑,多了很烦

@Value("#{2 * 3}")
private int num;                 ← 支持 SpEL 表达式(@ConfProps 不支持)

@ConfigurationProperties(prefix = "app")
class AppProperties {            ← 批量绑定,类型安全,支持校验
    private String url;          ← 属性名自动匹配 app.url
    private int timeout;         ← 松散绑定:app.timeout / app.time-out 都可以
    @NotNull private String name;← JSR-303 校验
}
对比 @Value @ConfigurationProperties
批量绑定 一个个写 一次绑一组
松散绑定 不支持 支持(kebab/camel/snake)
校验 不支持 支持 JSR-303
SpEL 支持 不支持
适用 少量配置项 一组相关配置

扩展:需配合 @EnableConfigurationProperties 或 @ConfigurationPropertiesScan(Spring Boot 3.x 推荐)。spring-boot-configuration-processor 可在 yml 中获得属性提示。

15. Spring Boot 内置 Tomcat 的调优?

Tomcat 线程模型(BIO → NIO):

请求 → Acceptor 线程(接收连接)
  → NIO Poller 线程(检测哪些连接有数据)
  → Worker 线程(执行业务逻辑)

调优核心:Worker 线程池
参数 默认值 建议
server.tomcat.max-threads 200 最大工作线程数
server.tomcat.min-spare-threads 10 空闲时保留的最小线程
server.tomcat.max-connections 8192 最大连接数(BIO 默认不同)
server.tomcat.accept-count 100 等待队列(满了拒绝连接)
server.tomcat.connection-timeout 60s 连接超时

核心参数的含义: 1. 请求进来 → 工作线程有空闲 → 直接处理 2. 工作线程全忙(已达 max-threads)→ 请求排队(accept-count) 3. 队列也满了 → 拒绝新连接 4. 连接空闲超过 connection-timeout → 关闭连接

调优口诀:IO 密集型设 CPU 核数 * 2 或更高,CPU 密集型接近 CPU 核数。持续观察 server.tomcat.threads.busy 指标,长期接近 max 就扩。

扩展:3.x 默认 Tomcat 10(Jakarta EE 9),可换 Undertow/Jetty。Undertow 高并发下吞吐量更优。max-keep-alive-requests 防止连接霸占。

16. Spring Boot 如何实现异步方法调用?

@EnableAsync + @Async 注解。默认 SimpleAsyncTaskExecutor,建议自定义 ThreadPoolTaskExecutor 设置 corePoolSize、maxPoolSize、queueCapacity。

17. @Transactional 失效的 10 种场景?

@Transactional 失效的本质原因只有一句话:事务是通过 AOP 代理实现的,如果调用没经过代理对象,事务就不生效。就像门禁系统--只有从大门走才检查权限,翻窗进去的不检查。

10 种失效场景(按出现频率排序):

1 非 public 方法
   原因:Spring AOP 默认只代理 public 方法
   @Transactional
   private void save() { ... }  ← 事务不生效!

2 同类方法自调用(最常见!)
   @Transactional
   public void save() { this.doInsert(); }  ← 走 this,绕过了代理

   @Transactional  ← 这行不生效!
   public void doInsert() { ... }

   原因:this 是原始对象,不是代理对象。就像自己叫自己干活,不会重新过门禁
   解决:注入自己(@Autowired self)、或拆到另一个 Service

3 异常被 try-catch 吞掉了
   @Transactional
   public void save() {
       try {
           db.insert();  // 抛异常
       } catch (Exception e) {
           log.error("出错了", e);  // 吞掉异常,Spring 感知不到!
       }
   }
   原因:Spring 只在抛出未捕获异常时才回滚,捕获了就不回滚
   解决:catch 里手动 throw,或 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()

4 rollbackFor 没配对(检查型异常不回滚)
   @Transactional  ← 默认只回滚 RuntimeException 和 Error
   public void save() throws IOException { ... }
   → IOException 是 checked 异常,不回滚!
   解决:@Transactional(rollbackFor = Exception.class)

5 数据库引擎不支持事务
   MyISAM 不支持事务,InnoDB 才支持。表引擎不对,事务白配

6 多数据源 / 多线程
   事务绑定在当前线程的 Connection 上,多数据源各管各的事务
   new Thread(() -> save()).start();  ← 新线程,不在原事务中

7 @Transactional 用在非 Spring Bean 的方法上
   只有 Spring 管理的 Bean 才会被 AOP 代理
   new UserService().save();  ← 手动 new 的,没有代理

8 传播机制配错
   @Transactional(propagation = Propagation.NEVER)  ← 要求没有事务
   @Transactional(propagation = Propagation.NOT_SUPPORTED)  ← 挂起当前事务

9 final 类 / final 方法
   CGLIB 代理通过继承生成子类,final 类/方法无法被继承 → 无法代理
   Spring Boot 默认用 CGLIB,所以加了 final 事务就没了

10 事务方法被嵌套调用,内层传播级别为 REQUIRES_NEW 但外层的异常在内层之后
   内层事务已提交,外层回滚时内层已经提交了 → 数据不一致

快速排查口诀:先看数据库引擎对不对,再看是不是 public,再看有没有 try-catch 吃异常,最后看是不是同类自调用。这四种覆盖了 90% 的问题。

扩展:事务基于 AOP + ThreadLocal--Connection 绑定到当前线程,timeout 默认 -1(永不超时),长事务可能导致连接池耗尽。

18. Spring Boot 3.x 迁移要注意什么?GraalVM 原生镜像的原理?

Spring Boot 2.x → 3.x 迁移核心变化:

1 Jakarta EE 替代 Java EE
   所有 javax.* → jakarta.*
   影响:Servlet、JPA、Validation、Mail 等全部改包名
   背景:Oracle 保留 javax 商标,Java EE 移交 Eclipse 基金会

2 JDK 17 基线
   不再支持 Java 8/11
   JDK 17 新特性:Record、Sealed Class、Pattern Matching、Text Block

3 自动配置 SPI 变化
   2.x:META-INF/spring.factories(扫所有 jar,性能差)
   3.x:META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

4 虚拟线程支持(3.2+)
   spring.threads.virtual.enabled=true
   Tomcat/Jetty 请求处理自动切换为虚拟线程

5 AOT 编译支持
   构建时预编译,减少启动时的 JIT 编译负担
   即使在 JVM 模式下也能获得 30%-50% 启动加速

6 可观测性改进
   内置 Micrometer Tracing(替代 Sleuth)
   健康检查 / 指标 / 追踪 统一到 spring-boot-actuator

GraalVM 原生镜像(Native Image):

Native Image 是什么?
  把 Java 字节码 AOT 编译成操作系统原生可执行文件(不依赖 JVM)

效果对比:
  启动速度:3 秒 → 50 毫秒(60 倍加速)
  内存占用:500MB → 50MB(90% 降低)
  部署体积:jar 50MB → 可执行文件 80MB(一个文件直接跑)
  峰值吞吐:降低 10%-20%(因为缺少 JIT C2 编译器的运行时优化)

原理(关键前提--封闭世界假设):
  AOT 编译器在构建时分析所有可达的代码路径
  运行时不会再加载新类 → 反射、动态代理、资源加载必须"事先声明"
  通过 RuntimeHints API 告诉 GraalVM 哪些类被反射

适用场景判断:

场景 适合 Native Image? 原因
Serverless / FaaS ✅ 完美 冷启动从秒级→毫秒级
K8s 弹性伸缩 ✅ 很好 新 Pod 秒级就绪
CLI 工具 ✅ 很好 用户感受不到启动延迟
传统 Web 应用 ⚠️ 看情况 反射多的应用适配成本高
开发环境 ❌ 不适合 改了代码重新编译要 10 分钟
大量动态代理的应用 ❌ 困难 动态代理难以静态分析 
# Maven 构建原生镜像
mvn -Pnative spring-boot:build-image

# 或直接用 GraalVM 编译
mvn -Pnative native:compile -DskipTests

常见坑: - 反射的类必须声明(@RegisterReflectionForBinding) - CGLIB 动态代理不支持 Native,改用 JDK 动态代理 - 资源文件要显式配置(resources-config.json) - 构建时间很长(大项目 3-10 分钟),需 CI/CD 配合

扩展:面试策略:诚实说"现有项目因反射依赖暂未迁移,新项目 Serverless 已用 Native Image",展示工程判断力。

19. Spring MVC 的请求处理流程?

HTTP 请求 → Filter 链 → DispatcherServlet
  → HandlerMapping 找到 Controller
  → HandlerAdapter 执行 Controller(经过 Interceptor)
  → ViewResolver 解析视图
  → 渲染响应 → Filter 链 → 返回
组件 作用
DispatcherServlet 前端控制器,统一调度
HandlerMapping 根据 URL 找到对应的 Handler
HandlerAdapter 执行 Handler,适配不同类型 Controller
ViewResolver 根据视图名找到模板文件

20. @Controller 和 @RestController 的区别?

  • @Controller:返回视图名(String),配合 @ResponseBody 返回数据
  • @RestController = @Controller + @ResponseBody,默认返回 JSON

21. Spring Boot 如何做参数校验?

1 DTO 加校验注解:@NotBlank @Size @Email @Min @Max
2 Controller 加 @Valid:校验通过才执行业务逻辑
3 @RestControllerAdvice 全局处理 MethodArgumentNotValidException
   → 提取 field errors → 返回统一格式错误提示

22. Spring Security 的认证流程?

请求 → SecurityFilterChain
  → UsernamePasswordAuthenticationFilter(提取用户名密码)
  → AuthenticationManager → AuthenticationProvider
    → UserDetailsService.loadUserByUsername()(查数据库)
    → PasswordEncoder.matches()(验证密码)
  → SecurityContextHolder 保存认证信息

核心组件:UserDetailsService(加载用户数据)、PasswordEncoder(密码加密+验证)、SecurityContextHolder(持有当前用户认证信息)。

23. JWT 在 Spring Boot 中的实现流程?

登录 → 验证用户名密码 → JwtService.generateToken(user)
  → 返回 access_token(30min)+ refresh_token(7天)
后续请求 → Authorization: Bearer <token>
  → JwtAuthenticationFilter 拦截 → 验证签名+过期
  → 提取用户信息 → SecurityContextHolder
access_token 过期 → 用 refresh_token 换新

24. Spring Boot 如何做缓存?

@EnableCaching  // 启用缓存
@Cacheable("users")    // 先查缓存,没有才执行方法
@CachePut("users")     // 更新缓存
@CacheEvict("users")   // 删除缓存

缓存实现切换:spring.cache.type=redis 或不设置用 Caffeine/Simple。

25. Spring Boot 如何实现定时任务?

@EnableScheduling
@Scheduled(cron = "0 0 2 * * *")     // 每天凌晨2点
@Scheduled(fixedRate = 5000)          // 每5秒
@Scheduled(fixedDelay = 3000)         // 上次结束后3秒

Cron:秒 分 时 日 月 周。分布式场景配合 @SchedulerLock(ShedLock)保证只执行一次。

26. Spring Boot Actuator 有哪些实用端点?

端点 用途
/actuator/health K8s liveness/readiness probe
/actuator/metrics 接入 Prometheus + Grafana
/actuator/beans 查看所有注册的 Bean
/actuator/env 环境变量和配置

27. Spring Boot 的启动流程?

main() → SpringApplication.run()
  → createApplicationContext() → 创建容器
  → prepareEnvironment() → 加载配置
  → refreshContext() → 刷新容器(核心)
      ↓ 准备上下文 → BeanFactoryPostProcessor → 注册Bean后置处理器
      ↓ initMessageSource → onRefresh(创建内嵌Tomcat)
      ↓ finishBeanFactoryInitialization(实例化所有单例Bean)
  → callRunners() → 执行 ApplicationRunner / CommandLineRunner

28. 如何定位 Spring Boot 应用的性能瓶颈?

排查层级(从上到下逐步缩小范围):
  1 Actuator + Micrometer → 接 Prometheus,找"哪个接口慢"
  2 慢查询日志 + EXPLAIN → 找"哪条 SQL 慢"
  3 @Timed + Arthas trace → 找"哪个方法慢"
  4 jstat -gcutil + jstack → 找"是不是 GC 或锁的问题"
  5 链路追踪 + Redis SLOWLOG → 找"是不是下游或缓存慢"

29. Spring Boot 2.7 升 3.0 做了哪些重大变更？

Spring Boot 3.0 基于 Spring Framework 6.0，最低要求 JDK 17，核心变更：

1. Jakarta EE 9+（命名空间从 javax.* 迁移到 jakarta.*）
   - 包名全改：javax.servlet → jakarta.servlet
   - 影响：第三方库必须兼容 jakarta

2. GraalVM 原生镜像支持
   - Spring Native 可将 Spring Boot 打包成原生可执行文件
   - 启动时间从秒级 → 毫秒级
   - 内存减少 60-80%

3. Spring Framework 6.0 变更
   - @RequiresSpring → 无替代，直接用 @Component
   - BeanFactory 替代大部分 ApplicationContextAware
   - PathPatternParser 替代 AntPathMatcher（性能 6 倍提升）

迁移步骤：

<!-- 1. JDK 17+ -->
<!-- 2. 升级 Spring Boot 2.7 → 3.0 -->
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.2.0</version>
</parent>
<!-- 3. 依赖升级 -->
<dependency>
    <groupId>jakarta.persistence</groupId>
    <artifactId>jakarta.persistence-api</artifactId>
</dependency>

扩展：3.0 大版本升级跨度大，建议分步走（2.7 → 3.0 小版本逐步升级）；Jakarta EE 迁移用 jakarta_namespace_migration_plugin。
