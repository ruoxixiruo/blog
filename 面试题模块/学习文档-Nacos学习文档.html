1. Nacos 概述

比喻理解

微服务之间需要互相调用，但不知道对方的 IP 和端口。Nacos 充当中央通讯录（服务发现）+ 统一遥控器（配置管理）：服务启动时自动注册，配置变更一键推送全部生效。

正式定义

Nacos（Dynamic Naming and Configuration Service）是阿里巴巴开源的动态服务发现、配置管理和服务管理平台。

  • 定位：微服务架构中的基础设施
  • 官方文档：https://nacos.io/zh-cn/index.html
  • GitHub：https://github.com/alibaba/nacos
  • 版本：1.x（HTTP/1.1 轮询）、2.x（gRPC 长连接推送）

三大核心能力

能力说明技术实现
服务发现微服务通讯录，自动注册/查找注册、健康检查、负载均衡、元数据
配置管理统一遥控器，热更新不重启集中配置、热更新、多环境隔离、变更推送
服务及元数据管理标签、分组、版本管理元数据、标签、DNS 域名

2. 配置管理 -- 热更新原理

核心流程

传统方式：改文件 --> 打包 --> 重启 --> 上线。Nacos：控制台修改 --> 发布 --> gRPC 实时推送 --> 全部服务实例热更新，无需重启。

2.1 配置管理模型

Namespace（命名空间）--> Group（配置分组）--> Data ID（配置文件）
  • Namespace：默认 public，多环境隔离
  • Group：默认 DEFAULT_GROUP，多项目/多模块分组
  • Data ID：${prefix}-${profile}.${file-extension}

2.2 Data ID 命名规范

# 格式: ${prefix}-${spring.profile.active}.${file-extension}
# prefix 默认取 spring.application.name

# 示例（spring.application.name=demo-app）：
# dev   --> demo-app-dev.yaml
# test  --> demo-app-test.yaml
# prod  --> demo-app-prod.yaml
# 无后缀 --> demo-app.yaml（共享配置）

2.3 配置发布示例

# Data ID: demo-app-dev.yaml / Group: DEFAULT_GROUP / Namespace: dev

spring:
  application:
    name: demo-app
  datasource:
    url: jdbc:mysql://localhost:3306/demo
    username: root
    password: ${DB_PASSWORD}  # 支持占位符

app:
  max-connections: 100
  timeout: 3000
  feature-flags:
    enable-new-search: true

2.4 配置变更推送原理（面试高频）

配置发布流程：
  Nacos Console 修改配置
    --> 写入 MySQL (持久化)
    --> 查找所有订阅此 Data ID 的 Client 长连接
    --> gRPC Push 变更通知 (Nacos 2.x, 毫秒级)
      或 HTTP 轮询等待 (Nacos 1.x, 最多 30s)
    --> Client 收到通知
    --> 触发 @NacosConfigurationProperties / @NacosValue 刷新
    --> 应用内存中配置立即生效，无需重启

推送方式对比：
  Push (gRPC 2.x): Server 主动推，毫秒级延迟，连接复用
  Pull (HTTP 1.x): Client 定时轮询，最多 30s 延迟，消耗带宽

2.5 配置隔离层级

# 三层隔离（由粗到细）：
# Namespace 隔离：完全物理隔离，不同 namespace 互不可见
# Group 隔离：   逻辑分组，同 namespace 下按业务/模块划分
# Data ID 隔离： 应用级别，每个应用独立的配置文件

2.6 配置监听与热更新

// 方式1：@ConfigurationProperties（推荐，自动同步）
@Data
@ConfigurationProperties(prefix = "app")
@Component
public class AppConfig {
    private int maxConnections;
    private int timeout;
    private Map<String, Boolean> featureFlags;
}

// 方式2：@NacosValue + 手动监听
public class MyConfig {
    @NacosValue(value = "${app.timeout:3000}", autoRefreshed = true)
    private int timeout;

    @NacosConfigurationProperties.DataListener(changedKeys = "app.max-connections")
    public void onMaxConnectionsChanged(String newValue) {
        System.out.println("max-connections 变更: " + newValue);
    }
}

3. 服务发现 -- 注册、心跳、负载均衡

核心流程

Provider 启动时向 Nacos 注册（IP + 端口 + 元数据），Consumer 从 Nacos 订阅服务获取实例列表并本地缓存。Provider 定期发心跳，30s 无心跳则被剔除，Consumer 通过 gRPC 实时收到变更通知。

3.1 服务注册与发现模型

Namespace --> Cluster（机房/可用区）--> Service（服务名）--> Instance（实例 1..N）

3.2 服务注册内容

NacosClient.registerInstance(serviceName, instance);

Instance {
    instanceId: "192.168.1.100:8080",  // 实例唯一ID
    ip: "192.168.1.100",
    port: 8080,
    serviceName: "order-service",
    weight: 1.0,                         // 权重
    healthy: true,                       // 健康状态
    enabled: true,                      // 是否启用
    ephemeral: true,                     // true=临时实例 false=永久实例
    clusterName: "DEFAULT",              // 所属集群
    namespaceId: "public",
    metadata: {                          // 自定义元数据
        version: "v1",
        region: "shanghai"
    }
}

3.3 服务发现方式

方式说明
DNS-F 模式服务名解析为 IP:Port，类 DNS
HTTP API调用 Nacos Open API 获取实例列表
Nacos SDKJava/Go SDK 直接调用

3.4 负载均衡策略

# 配合 Ribbon 或 Spring Cloud LoadBalancer 使用：
# 1. 权重随机（默认）-- 同权重随机选
# 2. 加权响应时间    -- 根据平均响应时间动态分配权重
# 3. 最少活跃调用    -- 选当前活跃连接数最少的实例
# 4. 一致性哈希     -- 相同参数路由到同一实例

3.5 健康检查机制

+------------------------------------------------------------------+
|                         Nacos Health Check                        |
|                                                                   |
|  TEMP Instance (ephemeral=true) -- 无状态服务 (推荐)              |
|    Client --heartbeat(5s)--> Server                               |
|    No heartbeat > 15s --> UNHEALTHY                              |
|    No heartbeat > 30s --> REMOVE from registry                  |
|    Push change notification to all subscribers                    |
|                                                                   |
|  PERSIST Instance (ephemeral=false) -- 有状态服务                 |
|    Server --TCP/HTTP probe--> Instance                            |
|    Unhealthy: mark only, do NOT remove                            |
|    Suitable for DB, cache, etc.                                   |
+------------------------------------------------------------------+
# 临时实例心跳配置
nacos:
  naming:
    heart:
      beat-interval: 5000     # 心跳间隔（ms）
      expire-time: 15000      # 过期时间（ms）

Nacos 2.x 通过 Cluster 分组实现机房就近访问，配合 Istio 等网格感知拓扑。

6. Nacos Sync -- 跨机房同步

概述

多机房部署时，各机房 Nacos 通过 Nacos Sync 双向同步服务实例和配置，实现异地多活。

6.1 典型场景

  • 双活架构：两机房各自 Nacos，Sync 双向同步
  • 迁移场景：自建 Nacos 迁移到阿里云 MSE Nacos
  • 多云同步：私有云 + 公有云实例同步

6.2 同步架构

  +---------------------+    Nacos Sync    +---------------------+
  |   Nacos Cluster A    |<===============>|   Nacos Cluster B    |
  |   (上海机房)          |    双向同步      |   (北京机房)          |
  |   Service-A (50%)    |                  |   Service-A (50%)    |
  +---------------------+                  +---------------------+

6.3 同步配置

nacos:
  sync:
    task-interval: 1000   # 同步间隔（ms）
    retry-times: 3        # 重试次数
    timeout: 5000         # 超时时间（ms）

7. Nacos 2.x 新特性

核心变化

从 HTTP 短连接轮询（最多 30s 延迟）升级为 gRPC 长连接推送（毫秒级延迟），吞吐量提升 10 倍。

7.1 1.x vs 2.x 对比

特性Nacos 1.xNacos 2.x
通信协议HTTP/1.1gRPC（长连接）
变更推送轮询（Poll）推送（Push）
端口1 个（8848）3 个（8848+9848+9849）
吞吐量~1,000 TPS~10,000+ TPS
服务端处理同步阻塞异步非阻塞
连接模型短连接长连接（Session 保持）

7.2 端口说明

端口用途必须开放
8848HTTP 控制台 + REST API是
9848gRPC Client <--> Server是（否则长连接失败）
9849gRPC Server <--> Server（Raft）是（集群内互通）

7.3 推送优势对比

1.x 轮询：Client(每30s) --poll--> Server --> 全量返回 --> 高延迟 + 高带宽
2.x 推送：Client --gRPC connect--> Server --> 变更即 Push --> 毫秒级 + 低带宽

7.4 兼容性

  • Nacos 2.x Server 兼容 1.x Client（HTTP 降级）
  • Nacos 2.x Client 可连 1.x Server（自动降级 HTTP）
  • 配置和服务数据格式完全兼容

9. 配置持久化

概述

开发用 Derby（嵌入式，零配置），生产用 MySQL 共享存储，集群节点共享同一份数据。

9.1 持久化方案对比

数据库适用规模优点缺点
Derby单节点零配置，开箱即用不支持多节点共享
MySQL中小规模（~1000 实例）社区成熟，运维方便需维护主从
PostgreSQL中大规模支持 JSON 类型配置稍复杂
Oracle企业大规模高可靠商业授权

9.2 配置表结构

CREATE TABLE config_info (
    id             BIGINT NOT NULL AUTO_INCREMENT,
    data_id        VARCHAR(255) NOT NULL,
    group_id       VARCHAR(128) DEFAULT '',
    content        LONGTEXT NOT NULL,
    md5            VARCHAR(32) DEFAULT NULL,
    gmt_create     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

10.3 CAP 定理与 Nacos AP/CP 切换

CAP 定理：分布式系统无法同时满足 Consistency（一致性）、Availability（可用性）、Partition tolerance（分区容错性）。Nacos 通过双协议支持 AP 和 CP 两种模式。

+------------------------------------------------------------------+
|                    Nacos AP/CP Mode Switching                     |
+------------------------------------------------------------------+
|                                                                   |
|  +-----------------------------+    +-----------------------------+|
|  |      AP Mode (Distro)       |    |      CP Mode (Raft)         ||
|  |  Default for Naming Service |    |  Default for Config Service ||
|  +-----------------------------+    +-----------------------------+|
|  |                             |    |                             ||
|  | Write Flow:                 |    | Write Flow:                 ||
|  |  Any node accepts write     |    |  Only Leader accepts        ||
|  |  Async replicate to peers   |    |  Replicate to majority      ||
|  |  Return success instantly   |    |  Confirm quorum then ack    ||
|  |                             |    |                             ||
|  | Read Flow:                  |    | Read Flow:                  ||
|  |  Read from local cache      |    |  Read from Leader           ||
|  |  (may be stale briefly)     |    |  (strongly consistent)      ||
|  |                             |    |                             ||
|  | Partition Behavior:         |    | Partition Behavior:         ||
|  |  Each partition works       |    |  Minority partition         ||
|  |  independently              |    |  cannot serve writes        ||
|  |                             |    |                             ||
|  +-----------------------------+    +-----------------------------+|
|                                                                   |
|  Switching (2.x):                                                 |
|    nacos.core.protocol.raft.data.type=file                        |
|    nacos.core.protocol.raft.minimum.commit.index=1                |
+------------------------------------------------------------------+

Usage Guidance:
  AP (Distro) --> Service Registration (availability matters most)
  CP (Raft)   --> Configuration Management (consistency matters most)
# Nacos 2.x 切换为 CP 模式配置
nacos.core.protocol.raft.data.type=file
nacos.core.protocol.raft.minimum.commit.index=1

12. 高频面试题

Q1：Nacos 的服务注册与发现流程？

Provider 启动:
  --> Client 发送 REST 注册实例到 Server
  --> Server 存入 ConcurrentHashMap 缓存 + 异步写 MySQL
  --> 向订阅此服务的 Consumer 推送变更通知

Consumer 启动:
  --> Client 订阅服务
  --> Server 返回所有健康实例列表
  --> Client 本地缓存 + 负载均衡选择实例发起调用

健康检查:
  --> 临时实例每 5s 心跳，30s 无心跳剔除
  --> 永久实例 Server 主动 TCP/HTTP 探测，只标记不剔除
  --> 变更通过 gRPC 长连接实时推送

面试话术："Provider 启动注册实例，Consumer 订阅获取实例列表并本地缓存。临时实例心跳 30s 超时剔除，永久实例服务端探测只标记。变更通过 gRPC 长连接实时推送。"

Q2：Nacos 如何保证配置中心的数据一致性？

  • CP 模式（Raft）：Leader 接收写请求，复制到多数 Follower 确认后返回。分区时少数派不可写入。用于配置管理。
  • AP 模式（Distro）：任意节点独立处理写请求，异步同步。分区时各节点独立工作。用于服务注册。

配置中心默认 CP，通过 Raft 选主保证一致性。

Q3：Nacos 和 Eureka 的区别？

对比项NacosEureka
维护状态阿里活跃维护Netflix 停维
功能配置中心 + 注册中心仅注册中心
一致性CP+AP 可切换仅 AP
健康检查TCP/HTTP/MySQL/自定义客户端心跳
界面有无
配置管理原生支持需配合 Config

Eureka 2.x 已停维，生产推荐 Nacos。

Q4：Nacos 的心跳机制？

临时实例 (ephemeral=true, 推荐):
  Client --每5s--> Server 心跳
  15s 无心跳 --> UNHEALTHY
  30s 无心跳 --> 从注册表移除
  适用：无状态服务（Pod/IP 漂移）

永久实例 (ephemeral=false):
  Server --TCP/HTTP--> Instance 主动探测
  不健康仅标记，不移除
  适用：有状态服务（DB/Cache）

Q5：Nacos 如何实现配置热更新？

配置发布 --> Server 写入 DB
         --> 查找订阅此配置的 Client gRPC 连接
         --> Push 变更通知 (毫秒级)
         --> Client 回调 @NacosConfigurationProperties 监听器
         --> Bean 自动刷新，无需重启

Q6：Nacos 2.x gRPC 通信原理？

1. Client 启动 --> 与 Server:9848 建立 gRPC 长连接 --> 建立 Session
2. 配置/服务变更 --> Server 通过 gRPC Stream 实时 Push
3. 优势：毫秒级延迟（vs 1.x 30s 轮询）、低资源占用、双向通信
4. 降级：2.x Server 保留 HTTP 接口，兼容 1.x Client

Q7：Namespace 和 Group 的区别？

概念作用隔离级别
Namespace环境隔离最彻底（dev/test/prod 完全隔离）
Group项目/模块分组中等（DEFAULT_GROUP / 自定义）
Data ID配置文件标识细粒度（应用级别）
 
# 典型分层
Namespace: dev
  Group: order-service
    Data ID: order-service-dev.yaml
  Group: payment-service
    Data ID: payment-service-dev.yaml
  Group: common
    Data ID: redis-dev.yaml（共享）
    Data ID: mysql-dev.yaml（共享）

Q8：Nacos 权限控制？

2.x 支持 RBAC：用户 --> 角色（admin/developer/guest）--> 权限。

nacos.core.auth.enabled=true
spring.cloud.nacos.username=developer
spring.cloud.nacos.password=xxxxxx

Q9：Nacos 集群选主机制？

使用 Raft 协议：所有节点初始为 Follower --> 选举超时随机 150-300ms --> Candidate 发起投票 --> 获多数票者成为 Leader --> Leader 定期发送心跳维持地位 --> Leader 故障则新一轮选举。

Q14：Nacos 如何防止配置误删？

  1. 配置备份：控制台手动导出
  2. 历史版本：每次变更生成快照，支持回滚
  3. 软删除：del_flag = 1，非物理删除
  4. 审计日志：记录所有变更操作
  5. 权限控制：仅管理员可修改生产配置
  6. 回收站（2.x）：支持配置恢复

Q15：Distro 协议原理？

Nacos 自研的 AP 协议（最终一致性）：

1. 写：任意节点接收 --> 异步同步其他节点 --> 本地立即返回成功
2. 读：本地直接读（无需跨节点），可能短暂不一致
3. 数据分片：节点按哈希分片，只负责部分数据
4. 适用：服务注册（AP 足够，强一致性非必须）
