并发编程

1. 进程、线程、协程的区别?

进程 vs 线程 vs 协程:

┌────────────┬──────────┬──────────┬──────────────┐
│            │ 进程     │ 线程     │ 协程         │
├────────────┼──────────┼──────────┼──────────────┤
│ 资源       │ 独立内存  │ 共享堆   │ 共享线程     │
│ 切换开销   │ 大(ms)   │ 中(μs)  │ 极小(ns)     │
│ 调度者     │ OS       │ OS      │ 用户态/程序   │
│ 比喻       │ 独立工厂  │ 工厂工人 │ 一个工人多工位│
└────────────┴──────────┴──────────┴──────────────┘
  • 进程:操作系统分配资源的最小单位。每个进程有独立的内存空间(虚拟地址空间),进程间通信靠 IPC(管道、共享内存、Socket)。切换需要切换页表等,开销最大的
  • 线程:CPU 调度的最小单位。同一进程的线程共享堆和方法区,各有自己的栈和程序计数器。切换只需切换寄存器和栈,比进程快。但线程是 OS 调度的,仍涉及内核态切换
  • 协程:用户态的"轻量级线程"。完全在用户态调度,不经过 OS,切换只保存少量寄存器。一个线程可以跑成千上万个协程。Go 的 goroutine、Python 的 asyncio、Java 21 的虚拟线程都是协程的变体

选型:CPU 密集型(计算任务)→ 多进程/多线程;IO 密集型(网络、文件)→ 协程最划算。

扩展:Java 21 的虚拟线程(Virtual Threads,Project Loom)本质就是 JVM 层面的协程--虚拟线程阻塞时,底层平台线程(载体线程)会被释放去执行其他虚拟线程,不会浪费 OS 线程。几万个虚拟线程只用几个平台线程调度,IO 密集场景性能超越传统线程池。但 CPU 密集场景不适合虚拟线程--计算不会触发卸载。

2. 线程的生命周期?

Java 线程 6 状态转换图:

    NEW(新建)
     │ start()
     ▼
    RUNNABLE(就绪 + 运行中)
     │          │         │
     │ 获取锁失败│wait()    │sleep()
     ▼          ▼         ▼
  BLOCKED   WAITING   TIMED_WAITING
     │    (无限等待)   (限时等待)
     │          │         │
     │  获取锁  │notify   │时间到
     │          │         │
     └──────────┴─────────┘
              │
              ▼
         TERMINATED(终止)
  • NEW:new Thread() 但还没 start()--线程对象创建了但还没真正跑起来
  • RUNNABLE:就绪(等 CPU 时间片)或正在运行中。Java 不区分"就绪"和"运行",统称 RUNNABLE
  • BLOCKED:等待获取锁(synchronized),锁被其他线程持有。拿到锁后回到 RUNNABLE
  • WAITING:无限等待,等 notify()/notifyAll() 唤醒。如 Object.wait()、Thread.join()
  • TIMED_WAITING:限时等待,时间到了自动醒。如 Thread.sleep(ms)、Object.wait(ms)
  • TERMINATED:run() 执行完毕或未捕获异常退出

扩展:Thread.getState() 可以获取当前状态。BLOCKED 和 WAITING 的区别常考--BLOCKED 是"被动"等待(等别人释放锁),WAITING 是"主动"等待(自己调了 wait/join,等另一个线程来叫)。jstack 可以看到所有线程的状态,排查死锁时重点关注 BLOCKED 状态的线程。

3. synchronized 和 ReentrantLock 的区别?

对比维度 synchronized ReentrantLock
实现 JVM 内置关键字 Java API(AQS 框架)
释放 自动(退出代码块/异常) 必须手动 unlock(finally)
可中断 不支持,死等 lockInterruptibly() 可被中断
超时获取 不支持 tryLock(timeout) 拿不到就走
公平性 非公平 可选公平/非公平
条件变量 wait/notify(单条件队列) Condition(多条件队列)
性能 JDK 6+ 优化后差不多 差不多 
选择建议:
简单场景 → synchronized(省心,不担心忘 unlock)
需要中断/超时 → ReentrantLock
需要多条件协作 → ReentrantLock + Condition
需要公平锁 → ReentrantLock(true)

扩展:ReentrantLock 的 Condition 可以实现精确唤醒--比如生产者消费者中,生产者只唤醒消费者,消费者只唤醒生产者,而不是把所有人叫醒(notifyAll)。synchronized 只有一个等待队列,notifyAll 唤醒所有等待线程,效率低。此外 ReentrantLock 支持 isHeldByCurrentThread() 和 getHoldCount(),可以检查锁的持有状态,这对调试很有用。

4. 什么是 CAS?ABA 问题怎么解决?

CAS(Compare And Swap)原理:

do {
  1 读取内存当前值 E
  2 计算新值 V = E + 1
  3 CAS(内存地址, E, V):如果内存值 == E,则改为 V;否则什么都不做
} while (!CAS成功);  // 失败了重试

CPU 指令级:CMPXCHG(x86),一条原子指令

CAS 就像排队办理业务--你拿到的号是 5,走到窗口前看看现在几号:是 5 就办,不是就说明有人插队了,重新看号再等。

ABA 问题:值从 A → B → A,CAS 只看最终值还是 A,以为没变过,实际中间被改过两次。就像你离开座位一分钟,回来水杯还在原位--但可能被你同事拿去喝了口水又放了回来。

解决:加版本号(AtomicStampedReference),每次修改版本号 +1。不只是比较值,还比较版本号。JDK 还提供了 AtomicMarkableReference(只关心"有没有被改过"而不关心改了几次)。

扩展:CAS 是 JUC(java.util.concurrent)的基石--AtomicInteger、ConcurrentHashMap、ReentrantLock 的底层都用 CAS。但 CAS 有"自旋开销"--高并发下 CAS 频繁失败导致线程一直空转(忙等)。JDK 8 的 LongAdder 对此做了优化--将单一变量拆成多个 Cell,并发更新分散到不同 Cell,最后 sum 汇总,减少了 CAS 碰撞。

5. AQS 原理?

AQS(AbstractQueuedSynchronizer)结构:

  volatile int state          ← 锁状态(0=空闲,1=被占用,>1=重入次数)
  CLH 双向队列(FIFO)         ← 等待线程排队
  ┌───┐   ┌───┐   ┌───┐
  │头 │←→ │B  │←→ │C  │←→ tail
  │节点│   │   │   │   │
  └───┘   └───┘   └───┘

获取锁流程:
  tryAcquire(1) → CAS 尝试改 state
    ├── 成功:当前线程持有锁,继续执行
    └── 失败:线程打包成 Node,CAS 入队尾部
              → 自旋检查:我是第一个排队的人吗?
                → 是:再尝试获取锁
                → 否:park() 挂起,等前驱叫醒

AQS 是 JUC 包的核心骨架。你只需要重写 tryAcquire/tryRelease(独占模式)或 tryAcquireShared/tryReleaseShared(共享模式),排队和唤醒由 AQS 帮你搞定。

基于 AQS 的常见实现: - ReentrantLock:独占锁,state 表示重入次数 - CountDownLatch:共享模式,state 是计数器 - Semaphore:共享模式,state 是许可数 - ReadWriteLock:state 高 16 位是读锁计数,低 16 位是写锁计数

扩展:CLH 队列为什么用双向链表而不是单向?因为需要从队尾唤醒下一个节点(后继)--当前节点释放锁后,通过 next 指针找到下一个等待者并 unpark。队头节点(持有锁的线程)释放时触发队头的后继被唤醒。AQS 中 Condition 的等待队列是单独的单向链表,当 signal 时节点从 Condition 队列转移到 CLH 主队列。

6. wait() 和 sleep() 的区别?

wait() sleep()
所属 Object 的方法 Thread 的静态方法
锁释放 会释放锁 不释放锁
唤醒 notify/notifyAll 时间到自动醒 / interrupt
调用前提 必须在 synchronized 块里 随便调
用途 线程间通信协作 线程暂停等待

核心区别图解:

sleep(抱着锁睡):
  线程A: synchronized(lock) { sleep(5000); }
  线程B: synchronized(lock) { ... }  ← 等 5 秒!锁被占着

wait(让出锁):
  线程A: synchronized(lock) { wait(); }
  → 释放锁,B 可以拿到锁执行
  → B 调 notify() 后 A 重新抢锁

sleep 是"我想休息一会,但我的东西不给你用"--不释放锁。wait 是"我先不干活了,东西你用"--释放锁,等别人叫我再干。

最佳实践:永远用 while 而不是 if 来包裹 wait() 的条件判断--防止虚假唤醒(线程被意外唤醒但条件不满足)。

synchronized (lock) {
    while (condition_not_met) {  // while 不是 if!
        lock.wait();
    }
}

扩展:wait() 和 notify() 必须在 synchronized 中调用,否则抛 IllegalMonitorStateException。因为 JVM 需要知道是"哪个对象上的等待队列"--只有持有该对象的监视器锁才能操作它的等待队列。Condition.await() 是 Lock 体系下 wait 的等价物,同样需要先获取锁。

7. 线程池的核心参数(7 个)?

线程池任务调度流程(ThreadPoolExecutor):

新任务到来
  │
  ├─ 当前线程数 < corePoolSize?
  │   是 → 新建线程执行(即使有空闲线程)
  │   否 ↓
  ├─ 队列未满?
  │   是 → 任务入队等待
  │   否 ↓
  ├─ 当前线程数 < maximumPoolSize?
  │   是 → 新建线程执行
  │   否 ↓
  └─ 执行拒绝策略

7 个参数: - corePoolSize:常驻核心线程数。即使空闲也保留(除非设了 allowCoreThreadTimeOut) - maximumPoolSize:最大线程数上限 - keepAliveTime:超过核心线程数的多余线程,空闲多久后销毁 - unit:keepAliveTime 的时间单位 - workQueue:排队队列。三种常见选择: - SynchronousQueue:不存储,直接提交(适合任务数可控,要求快速响应) - LinkedBlockingQueue(无界):无限排队(核心线程忙就先排着,永远不会到 max)⚠️ 容易 OOM - ArrayBlockingQueue(有界):有上限的排队 - threadFactory:线程工厂,给线程起有意义的名字(排查问题时救命) - rejectedExecutionHandler:队列满且线程数达 max 时的处理

扩展:生产上不要用 Executors.newFixedThreadPool() 和 newCachedThreadPool()--《阿里巴巴 Java 开发手册》指出,前者用无界 LinkedBlockingQueue 可能 OOM,后者用 SynchronousQueue + Integer.MAX_VALUE max 可能创建无限线程。请直接用 new ThreadPoolExecutor(...)。IO 密集任务的核心线程数可以设 CPU 核数 * 2 或更多,CPU 密集任务设 CPU 核数 + 1。

8. 拒绝策略有哪几种?

策略 行为 通俗解释 适用
AbortPolicy(默认) 抛 RejectedExecutionException "满了!不干了!报错!" 需要感知拒绝的场景
CallerRunsPolicy 提交任务的线程自己执行 "你送来的,你自己做" 利用调用线程做缓冲
DiscardPolicy 静默丢弃新任务 "假装没看见" 允许丢任务的场景
DiscardOldestPolicy 丢弃队列里最老的任务 "对不起等最久的走人" 新任务优先于旧任务

CallerRunsPolicy 的两个作用:

  1. 让提交任务的线程(通常是主线程或关键线程)亲自执行,相当于天然限流--调用方执行时无法提交更多任务
  2. 不会丢任务,任务只是被"延后"执行了

什么时候自定义:记录日志、写入持久化队列(MQ/数据库)、发送告警通知。比如 Dubbo 的自定义策略--把拒绝的任务写到日志并打印 dump 信息便于排查。

扩展:ThreadPoolExecutor 的 beforeExecute 和 afterExecute 钩子方法可以用来监控任务执行(记录耗时、异常通知等)。结合 getPoolSize()、getActiveCount()、getQueue().size() 可以做线程池监控大盘,实时查看线程池健康度。

9. CountDownLatch 和 CyclicBarrier 的区别?

CountDownLatch(减法计数器,一次性):
  主线程: latch.await() → 等着...
  线程A/B/C: 做完各自的事 → latch.countDown()
  计数器归零 → 主线程醒来继续
  场景:等其他线程都做完再继续
  比喻:保安等所有运动员冲过终点才收工

CyclicBarrier(加法计数器,可复用):
  线程A/B/C: 各自跑到 barrier.await() → 互相等
  所有线程到齐 → 屏障打开,大家一起继续
  场景:所有线程准备好再同时出发
  比喻:几个朋友约好同时出发旅行,人到齐了再走
对比 CountDownLatch CyclicBarrier
计数方向 减(N→0) 加(0→N)
可重用 不可(用一次) 可(reset 重新用)
触发规则 一个/多个线程等别的线程 所有线程互相等
回调 没有 支持 barrierAction(人到齐后执行)
比喻 保安等冲线 朋友等出发

扩展:Phaser(JDK 7+)是两者增强版--动态增减参与线程数、多阶段协调。CyclicBarrier reset 时若还有线程在等待,会抛 BrokenBarrierException。

10. ThreadLocal 应用场景?

ThreadLocal 经典三场景:

1 数据库连接管理
  每个线程绑定自己的 Connection,事务操作互不干扰
  Spring 的 TransactionSynchronizationManager 就用的 ThreadLocal

2 用户上下文传递
  拦截器从 Token 解析用户信息 → 存入 ThreadLocal
  → Controller/Service/Dao 链路上任何位置都能取到
  不用把 userId 从 Controller 一路传到 Dao!

3 SimpleDateFormat 线程安全
  SimpleDateFormat 线程不安全 → 每个线程一个实例
  或直接用 DateTimeFormatter(线程安全,不用 ThreadLocal 也行)

为什么不用全局变量:Web 服务器是线程池模式,多个请求复用同一个线程。全局变量在请求间会串,ThreadLocal 天然隔离。

使用链路:拦截器 set 用户信息 → 业务代码 get → 请求结束时 remove(防泄漏!)

扩展:ThreadLocal 不解决共享变量安全问题--只是复制隔离。父线程值不传子线程,线程池用 InheritableThreadLocal 也有复用问题,推荐阿里 TransmittableThreadLocal。

11. Semaphore 的原理和应用?

Semaphore 原理:

  Semaphore sem = new Semaphore(5);  // 5 个许可

  线程调用 acquire():
    有许可 → 许可 -1,线程通过
    没有许可 → 阻塞,等别人 release()

  线程调用 release():
    许可 +1,唤醒一个等待线程

核心能力:控制最多允许多少个线程同时访问某个资源。就像停车场只有 10 个车位--满了后来的车就得在门口等。

经典场景:

  • 限流:接口 QPS 控制,最多允许 N 个线程同时处理
  • 数据库连接池:限制并发连接数(acquire() 拿连接,release() 还连接)
  • 秒杀系统:控制进入下单环节的并发数,超过的直接拒绝

Semaphore 可以一次性获取/释放多个许可:acquire(3) 拿 3 个,release(3) 还 3 个。这在分页下载等场景有用。

扩展:Semaphore(permits, true) 公平模式(等待最久先拿),默认非公平。Semaphore 管并发数量,CountDownLatch 等全员完成。

12. ReadWriteLock 的读写锁机制?

读写锁规则:

┌──────┬───────┬───────┐
│      │ 读锁  │ 写锁  │
├──────┼───────┼───────┤
│ 读锁 │ ✓共享 │ ✗互斥 │
│ 写锁 │ ✗互斥 │ ✗互斥 │
└──────┴───────┴───────┘

场景:
  线程A 持有读锁 → 线程B 可以同时持有读锁(共享)
  线程A 持有读锁 → 线程C 不能获取写锁(互斥,防止读到脏数据)
  线程A 持有写锁 → 其他所有人都不能获取任何锁

锁降级(写锁 → 读锁,允许):

// 先写后读,保证数据一致性
writeLock.lock();
  updateData();           // 写操作
  readLock.lock();        // 先拿读锁
writeLock.unlock();        // 再释放写锁 ← 降级为读锁
  readData();             // 此时仍持有读锁,看到的是自己刚写的数据
readLock.unlock();

锁升级(读锁 → 写锁,不允许/会死锁):持有读锁时直接获取写锁会死锁,因为写锁要等所有读锁释放,而你持有读锁没释放。

扩展:StampedLock(JDK 8+)是读写锁升级版,支持乐观读(读完验证stamp)。不可重入,非 ReadWriteLock 实现。读多写少用乐观读,写锁可能饿死(非公平模式)。

13. CompletableFuture 的作用?

CompletableFuture 核心方法:

1 创建异步任务
   supplyAsync(() -> 查订单)      ← 有返回值
   runAsync(() -> 发通知)          ← 无返回值

2 结果转换
   .thenApply(order -> 计算金额)   ← 同步转换
   .thenCompose(order -> 异步查物流) ← 异步串联(拍平)

3 组合多个任务
   .thenCombine(查库存, (订单, 库存) -> 合并结果)  ← 两者都完成
   .applyToEither(备选方案, result -> result)    ← 谁先返回用谁

4 异常处理
   .exceptionally(ex -> 兜底值)     ← 异常时返回默认值
   .handle((result, ex) -> ...)     ← 正常和异常都走这里

以前用 Future 只能 get() 阻塞拿结果。CompletableFuture 可以像流水线一样链式编排:"查订单 → 算金额 → 查库存 → 合并结果",每一步不阻塞。

thenApply vs thenCompose: - thenApply:同步转换,A 的结果变成 B(A → B) - thenCompose:异步串联,A 的结果作为 B 的输入(A → CompletableFuture<B>),不会套两层 CompletableFuture<CompletableFuture<B>>

扩展:默认用 ForkJoinPool.commonPool()(CPU-1 线程),生产建议传自定义线程池。JDK 9+:orTimeout()、completeOnTimeout()、copy()、allOf()、anyOf()。

14. Fork/Join 框架的原理?

Fork/Join 工作流程:

大任务: 算 1+2+...+10000
  │ fork: 拆分成子任务
  ├─ 子任务1: 算 1+...+2500     → 线程A 执行
  ├─ 子任务2: 算 2501+...+5000   → 线程B 执行
  ├─ 子任务3: 算 5001+...+7500   → 线程C 执行
  └─ 子任务4: 算 7501+...+10000  → 线程D 执行
  │ join: 汇总结果
  └─ 合并 = 结果1 + 结果2 + 结果3 + 结果4

核心组件: - ForkJoinPool:线程池,每个线程维护一个双端队列(deque) - RecursiveTask<T>:有返回值的任务 - RecursiveAction:无返回值的任务

工作窃取算法:线程先干完自己的任务 → 看到别人队列里还有很多 → 从别人队列的尾部偷一个任务来干,不会重复。这样避免了忙的线程忙死、闲的线程闲死。

扩展:并行流底层用公共 ForkJoinPool(CPU-1 线程),多并行流共享可能互相阻塞,可自定义隔离。invoke() 同步等结果,submit()+get() 异步。JDK 8 Arrays.parallelSort() 基于 Fork/Join。

15. 什么是伪共享?如何避免?

伪共享(False Sharing)原理:

CPU 缓存行 = 64 字节(x86)

线程A 频繁写变量 X → X 所在的整个缓存行失效
线程B 频繁读变量 Y → 虽然 Y 没变,但和 X 在同一行 → 缓存行失效 → 线程B 得重新从主存加载 → 性能大幅下降!

就像两个室友各住一间,但共用一面墙--这边装修咚咚敲,那边也不得安宁。两人做的事完全不同,但物理上被绑在了一起。

如何避免:

  1. 填充法(JDK 8 之前):
public volatile long value;
private long p1, p2, p3, p4, p5, p6, p7; // 填充到 64 字节

在变量前后填充无用的 long,让目标变量独占一个缓存行

  1. @Contended 注解(JDK 8+):JVM 自动填充,需加 -XX:-RestrictContended 开启

  2. 用数组分散:AtomicLongArray 中不同元素大概率在不同缓存行

扩展:ConcurrentHashMap CounterCell、Thread 字段用 @Contended 填充。Disruptor 高频写场景最明显。普通业务代码很少遇到,过度优化没必要。

16. 什么是 Happens-Before 原则?

JMM 核心规则,判断操作可见性和有序性。 - 程序次序:同一线程前面操作 happens-before 后面 - 锁规则:unlock happens-before 后一个 lock - volatile 规则:volatile 写 happens-before volatile 读 - 传递性

17. ThreadPoolExecutor 的 7 个参数怎么配?

线程池就像一个外包团队:核心员工(corePoolSize)一直在岗,忙不过来了就招临时工(maxPoolSize - corePoolSize),任务堆在任务池(workQueue),临时工闲着就裁掉(keepAliveTime),任务池满了还来人就拒绝(handler)。

线程池工作流程(execute 一个任务时):

新任务来了
    │
    ▼
核心线程有空? ──是──▶ 核心线程执行
    │
   否
    │
    ▼
队列满了? ──否──▶ 扔队列排队
    │
   是
    │
    ▼
线程数 < maxPoolSize?──是──▶ 新建临时线程执行
    │
   否
    │
    ▼
走拒绝策略 ❌

7 个参数详解:

new ThreadPoolExecutor(
    corePoolSize,      // 1 核心线程数:平时在岗的最少线程
    maxPoolSize,       // 2 最大线程数:最忙时能扩展到多少
    keepAliveTime,     // 3 空闲存活时间:临时线程闲多久后回收
    unit,              // 4 时间单位
    workQueue,         // 5 任务队列:任务排队的队伍
    threadFactory,     // 6 线程工厂:怎么创建线程(起名字用)
    handler            // 7 拒绝策略:队列满了怎么办
);

1 corePoolSize(核心线程数):一直活着的线程(除非 allowCoreThreadTimeOut=true)。就像公司的正式员工。 - CPU 密集型(计算任务为主):CPU 核数 + 1(太少浪费 CPU,太多上下文切换) - IO 密集型(网络/数据库操作多):CPU 核数 × 2 或更高(CPU 大部分时间在等 IO)

2 maxPoolSize(最大线程数):能开到的最多线程数。核心线程 + 临时线程的总上限。

3 keepAliveTime(空闲存活时间):临时线程没活干时,等多长时间被回收。

4 时间单位:TimeUnit.SECONDS / TimeUnit.MILLISECONDS 等。

5 workQueue(任务队列):核心线程满了,新任务先排队。三种常见选择:

队列类型 特点 场景
SynchronousQueue 不存任务,直接交给线程。没有线程就新建(上限 maxPoolSize) 任务少但需要快速响应
LinkedBlockingQueue(无界) 无限排队(Integer.MAX_VALUE)。核心线程满了全进队列,maxPoolSize 失效! 任务稳定可预测
ArrayBlockingQueue(有界) 有界排队,满了才创建新线程 生产推荐

⚠️ 最容易踩的坑:用 Executors.newFixedThreadPool(n) 底层是 LinkedBlockingQueue(无界队列),任务永远进不了拒绝策略--堆着堆着 OOM 了!

6 threadFactory(线程工厂):给线程起名字。生产上必须自定义--出问题查 jstack 时看到 order-pool-1 比看到 pool-1-thread-1 有用一万倍。

7 handler(拒绝策略):

策略 行为 场景
AbortPolicy(默认) 抛异常 必须感知过载
CallerRunsPolicy 让提交任务的线程自己执行 推荐,自然降速
DiscardPolicy 直接丢弃(不通知) 不重要的任务
DiscardOldestPolicy 丢弃最老的,插队 需要最新数据 
// 生产推荐配置示例
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    Runtime.getRuntime().availableProcessors(),  // core = CPU 核数
    Runtime.getRuntime().availableProcessors() * 2,  // max = 2 倍核数
    60L, TimeUnit.SECONDS,            // 临时线程 60s 不用就回收
    new ArrayBlockingQueue<>(200),    // 有界队列,防 OOM
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 满了自己跑,自然降速
);

扩展:Executors 4 个工厂方法均不推荐生产直接用(无界队列/无限线程 OOM 风险)。一律 new ThreadPoolExecutor(...) 显式设参。beforeExecute/afterExecute 钩子可记录任务耗时。

18. CompletableFuture 怎么编排异步任务?

CompletableFuture 是 Java 8 引入的异步任务编排器。它解决了两个问题:1 回调地狱(嵌套回调越叠越深);2 多异步任务的依赖关系(A 完成才能 B,C 和 D 并行等 A 的结果)。

核心 API 速查:

创建异步任务:
  supplyAsync(() -> result)     → 有返回值
  runAsync(() -> {})            → 无返回值

转换/消费(任务完成后的回调):
  thenApply(result → newResult)     → 转换结果(T → U)
  thenAccept(result → {})           → 消费结果(无返回值)
  thenRun(() → {})                  → 不关心结果,只要完成了就执行

组合:
  thenCompose(result → future)      → 扁平化(避免 Future<Future<T>>)
  thenCombine(otherFuture, bifunc)   → 合并两个独立 Future 的结果

异常处理:
  exceptionally(ex → fallback)       → 异常时返回兜底值
  handle((result, ex) → {...})       → 无论成败都处理(类似 finally)

等待所有/任一:
  allOf(f1, f2, f3)                 → 所有完成
  anyOf(f1, f2, f3)                 → 任意一个完成

实际编排示例:

// 场景:查用户 → 同时查订单和算积分 → 合并推荐 → 返回

CompletableFuture<User> userFuture =
    CompletableFuture.supplyAsync(() -> userService.getUser(userId));

CompletableFuture<Recommendation> result = userFuture
    .thenApply(user -> {
        // 并行获取订单和积分
        CompletableFuture<List<Order>> orders =
            CompletableFuture.supplyAsync(() -> orderService.getOrders(user.getId()));
        CompletableFuture<Integer> points =
            CompletableFuture.supplyAsync(() -> pointService.getPoints(user.getId()));
        // 等待两个都完成 → 合并推荐
        return orders.thenCombine(points,
            (ol, pt) -> recommendService.recommend(user, ol, pt));
    })
    .thenCompose(f -> f)           // 扁平化 Future<Future<T>>
    .orTimeout(3, TimeUnit.SECONDS)  // Java 9+:3 秒超时
    .exceptionally(ex -> RecommendService.defaultRecommend());  // 降级

// allOf 收集所有结果(常见坑:allOf 返回 Void,要手动 collect)
List<CompletableFuture<String>> futures = ids.stream()
    .map(id -> CompletableFuture.supplyAsync(() -> fetch(id)))
    .toList();
CompletableFuture<List<String>> allResults =
    CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
        .thenApply(v -> futures.stream()
            .map(CompletableFuture::join)
            .toList());

面试高频对比:

thenApply vs thenCompose:
  thenApply:  T → U(类似 map)
  thenCompose: T → CompletableFuture<U>(类似 flatMap)
  关键:thenCompose 避免嵌套的 CompletableFuture<CompletableFuture<T>>

supplyAsync 的线程池:
  默认用 ForkJoinPool.commonPool()(不适合阻塞 IO 任务)
  生产上必须传自定义线程池!supplyAsync(task, executor)

handle vs exceptionally:
  handle: 成功和失败都执行(类似 try+catch+finally)
  exceptionally: 只在异常时执行

扩展:Java 21 虚拟线程可替代线程池做 IO 密集任务。StructuredTaskScope(Java 21+)结构化并发--fork 多子任务、自动等待、一个失败全取消,比 CompletableFuture 更安全。

19. CompletableFuture 如何实现异步编排？

CompletableFuture 是 Java 8 的异步编程核心，比 Future 更强大：

// 场景：查询用户信息 → 查用户画像 → 查推荐列表
CompletableFuture<User> userFuture = CompletableFuture
    .supplyAsync(() -> userService.getUser(userId));  // 异步查用户

CompletableFuture<UserProfile> profileFuture = userFuture
    .thenCompose(user ->  // 串行依赖
        CompletableFuture.supplyAsync(() -> profileService.get(user.getId())));

CompletableFuture<List<Recommend>> recommendFuture = userFuture
    .thenCombine(profileFuture, (user, profile) ->  // 并行合并
        recommendService.getRecommend(user, profile));

// 最终结果
List<Recommend> result = recommendFuture.join();

常用组合方法：

方法 含义
thenApply 异步结果转换
thenCompose 扁平化（链式依赖）
thenCombine 两个异步任务并行，合并结果
thenAccept 消费结果，无返回值
exceptionally 异常处理兜底
allOf/anyOf 等待所有/任一完成

扩展：默认用 ForkJoinPool.commonPool()（并行度 = CPU 核数 - 1）；需要自定义线程池时用 supplyAsync(supplier, executor)；大量异步 IO 用自定义 ExecutorService 避免公共池耗尽。
