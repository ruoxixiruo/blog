分布式事务

1. 四种方案一句话区分

方案 一句话 一致性级别
2PC/XA 强一致的提交协议,协调者两阶段提交 强一致
TCC 业务级两阶段:Try 预留 → Confirm 确认 / Cancel 取消 最终一致
Seata AT 自动补偿框架,依赖 undo log 回滚 最终一致
Saga 长事务补偿,先执行再补偿,最终一致 最终一致 
一致性光谱:

强一致 ◀──────────────────────────────▶ 最终一致
  │                                      │
 2PC/XA        TCC        Seata AT      Saga
 (锁到完成)   (预留后确认)  (自动补偿)   (事后补救)
  │                                      │
 性能差 ←─────────────────────────────▶ 性能好

扩展:为什么 2PC 在实际业务中很少直接用?因为它的锁定时间长--第一阶段锁住资源,第二阶段才释放。如果协调者挂了,锁一直不释放,其他事务全卡住。这就是为什么阿里搞出了 Seata--不用数据库锁,用 undo log 做补偿。

2. TCC 的三个阶段?

  • Try:预留/冻结资源(占坑)。比如冻结 100 元,钱还在但不可用
  • Confirm:确认提交,真正生效(转正)。比如真正扣款 100 元
  • Cancel:释放资源,撤销预留(退坑)。比如解冻 100 元
Try:冻结 100 元(余额 500 → 可用 400,冻结 100)
     │
     ├── 所有 Try 成功 → Confirm:真正扣 100(余额 400 → 余额 400,冻结 0)
     │
     └── 有 Try 失败 → Cancel:解冻(余额 400 → 可用 500,冻结 0)

核心理念:不是在数据库层面回滚,而是在业务层做"补偿操作"。就像电商退款--不是把数据库时间倒流,而是创建一个退款单把钱退回去。

扩展:TCC 对企业级业务非常实用,但它的代价是每个接口都要写三套逻辑(Try/Confirm/Cancel),代码量大。所以 TCC 适合核心链路(支付、库存),不那么重要的场景用 AT 或 Saga 就够了。

3. TCC 的三个难点?

  • 幂等:Confirm/Cancel 可能被重复调用(网络超时重试),结果必须一致。比如重复解冻不能变成"倒贴钱"。

  • 空回滚:Cancel 被调了但 Try 根本没执行(Try 请求超时,协调者直接发 Cancel)。需要识别并安全处理--别"解冻一个根本没冻结的余额"。

  • 悬挂:Cancel 先到执行了,后到的 Try 不能再把资源占住--否则资源被永久冻结。

正常流程:Try → Confirm/Cancel

空回滚:Try (超时) → 协调者直接发 Cancel → Cancel 到了但 Try 没执行过

悬挂:   Try (超时) → Cancel 先到执行了 → Try 后到(不能执行)

解决:状态机表 + 唯一键 + 防悬挂机制。

扩展:防悬挂的实现--Try 执行时检查有没有 Cancel 记录,如果有说明已经被取消了,拒绝执行。这些状态记录通常放在一张事务日志表中,用全局事务 ID 做主键。

4. Seata 的 TC、TM、RM 是什么?

  • TM(事务管理器):事务发起者,负责开启和结束全局事务。比如下单服务说"我开始一个分布式事务了"
  • RM(资源管理器):管理分支事务,执行本地数据库操作。比如订单库、库存库各自管自己的操作
  • TC(事务协调者):记录全局和分支事务状态,协调提交/回滚。是整个事务的"裁判"
TM(下单服务)
 │ 开启全局事务
 │
 ├──▶ RM(订单库):插入订单 ──▶ TC 记录:分支1 成功
 │
 └──▶ RM(库存库):扣库存   ──▶ TC 记录:分支2 成功
                                     │
                       全部成功 → Commit / 有失败 → Rollback

扩展:TC 通常独立部署(Seata Server),它就是一个协调中心。TM 和 RM 都在你的微服务里--加个 @GlobalTransactional 注解,Seata 自动帮你做 TM/RM 的事情。

5. Seata AT 模式原理?

一阶段:拦截 SQL → 记录 before image(改前数据)和 after image(改后数据)→ 注册分支事务 二阶段:提交 → 异步删 undo log;回滚 → 按 undo log 反向补偿恢复数据

一阶段:执行 SQL + 记录 undo log

UPDATE account SET money = 400 WHERE id = 1
        │
        ▼
  before image: {id:1, money:500}   ← 记下改前
  after image:  {id:1, money:400}   ← 记下改后
        │
        ▼
  二阶段提交:删 undo log(异步清理)
  二阶段回滚:逆向 SQL → {id:1, money:500}(恢复原值)

优点:业务侵入低,加个注解就行。局限:依赖 JDBC,复杂 SQL 不太适用。

扩展:AT 模式和数据库 undo log 的思路一样,区别在于 AT 是在应用层做 undo log(拦截 SQL 自动生成补偿 SQL),而不是依赖数据库的 undo 表空间。因为应用层的 undo log,所以跨库也能用--这是 AT 模式最聪明的地方。

6. Seata 四种模式怎么选?

  • 标准 CRUD → AT(低成本首选,加注解就行)
  • 有明确预留语义(冻结/扣减)→ TCC(业务控制力最强)
  • 长流程、允许中间状态 → Saga(无长锁,性能好)
  • 资源方原生支持 XA → XA(强一致,数据库帮你做)
选型决策树:

  能加注解就行? ──是──▶ AT (90% 场景)
      │ 否
      ▼
  需要强一致? ──是──▶ XA
      │ 否
      ▼
  长流程(>10步)? ──是──▶ Saga
      │ 否
      ▼
  有冻结/预留语义? ──是──▶ TCC

扩展:TCC 和 AT 的选择不是非此即彼,很多公司混着用--核心资金链路用 TCC(性能好、控制力强),普通 CRUD 用 AT(省心)。Seata 支持一个全局事务里不同分支用不同模式。

7. Saga 和 TCC 区别?

  • TCC:先预留再确认(资源锁持有短,隔离性强)--像"先交定金再付全款"
  • Saga:先执行再补偿(无长锁,中间状态会暴露,最终一致)--像"先发货不满意再退货"
TCC:Try(冻结) → Confirm(转正)
     锁住资源 → 释放锁
     中间状态不可见(资源被冻结)

Saga:执行1 → 执行2 → 执行3
     没有锁,每步都真实执行
     中间状态可见(别人能查到未完成的数据)
     失败时:补偿3 → 补偿2 → 补偿1(倒序回滚)

扩展:Saga 最适合长流程场景--比如机票+酒店+租车的旅行预订,整个过程可能几分钟甚至几小时。用 TCC 锁资源这么久不现实。Saga 每步提交后就释放,失败时靠补偿往回修--就像旅行中取消订单要一步步退还。

8. 分布式事务什么时候不该用?

异步通知、日志、统计这些能容忍延迟和补偿的,不要用分布式事务。能拆成"先落核心数据 + 异步修正"的就别搞长事务。

判断流程:

跨服务数据一致性需求
    │
    ├── 能异步搞定? → 用消息队列 + 本地消息表
    │   例:下单后发短信通知 → 失败重试即可
    │
    ├── 能事后对账/补偿? → 不要用分布式事务
    │   例:对账文件 T+1 对平
    │
    └── 必须实时一致? → 才考虑分布式事务
        例:扣款 + 出账 → TCC

扩展:业界共识--能用最终一致性解决的,别上强一致性。强一致的成本(性能、复杂度、可用性牺牲)远高于最终一致。很多业务看着像需要强一致,换个思路(异步补偿 + 对账)就能用最终一致解决。

9. 什么是 BASE 理论?

Basically Available 基本可用、Soft State 软状态、Eventually Consistent 最终一致性。BASE + ACID 混合:支付用 ACID,非关键用 BASE。

10. Seata 四大模式(AT / TCC / SAGA / XA)怎么选?

Seata 是阿里开源的分布式事务框架,提供了四种模式来应对不同场景。核心架构是 TC(事务协调器)+ TM(事务管理器)+ RM(资源管理器) 三角色协作。

AT 模式(默认,最常用):

核心是自动生成 undo log--Seata 代理数据源,拦截业务 SQL,自动记录修改前后的数据(前后镜像)。一阶段提交本地事务,二阶段 TC 决定全提交或全回滚。

AT 模式两阶段:
一阶段:执行业务 SQL → 记录前后镜像到 undo_log → 提交本地事务
二阶段(全部成功):异步删除 undo_log
二阶段(有失败):根据 before image 逆向 SQL 恢复数据

优点:对业务零侵入,改造成本极低
缺点:有全局锁,高并发有瓶颈;默认读未提交

TCC 模式(性能最强,开发成本最高):

业务代码自己实现 Try / Confirm / Cancel 三个方法。Try 预留资源、Confirm 确认执行业务、Cancel 释放资源。

Try:    冻结余额(可用余额-100,冻结金额+100)
Confirm:扣除冻结金额(冻结金额-100)
Cancel: 解冻余额(冻结金额-100,可用余额+100)

优点:无全局锁,性能最高,不依赖数据库
缺点:代码侵入性高,需处理空回滚、悬挂、幂等三大难题

SAGA 模式(长事务):

将长事务拆成一系列本地短事务,每个短事务有对应的补偿操作。失败时反向执行补偿。

正向:下单 → 扣库存 → 扣余额 → 发券
              ❌ 失败
补偿:← 恢复库存 ← 取消订单

四大模式全景对比:

维度 AT TCC SAGA XA
一致性 最终一致 最终一致 最终一致 强一致
代码侵入 无 高 中高 无
性能 中 高 高 低
事务长度 短 短 长 短
适用场景 标准CRUD 高并发+有预留语义 长流程+多服务 必须强一致

选型决策树:

能接受最终一致?
├── 是 → 标准 CRUD + 关系型数据库?
│   ├── 是 → AT 模式(最省事)
│   └── 否 → 高并发 + 可投入开发成本?
│       ├── 是 → TCC 模式(最高性能)
│       └── 否 → 长流程?→ SAGA
└── 否 → 必须强一致 → XA(牺牲性能)

扩展:AT 模式的"全局锁"是它最大的性能瓶颈--多个事务操作同一行数据时,即使一阶段已提交,二阶段完成前其他事务也必须等全局锁。热点数据场景(如秒杀扣库存)建议改用 TCC 或 Redis 原子操作 + MQ 异步。另外,TCC 的空回滚问题(Cancel 先于 Try 到达)和悬挂问题(Cancel 执行后 Try 才到)是面试高频追问--Seata 的 TCC Fence 机制通过 tcc_fence_log 表记录状态来解决。

11. Seata 的 AT、TCC、Saga 模式横向对比？

维度 AT 模式 TCC 模式 Saga 模式
侵入性 低（自动补偿） 高（需写 try/confirm/cancel） 中（需写状态机）
性能 高（本地事务） 高（无全局锁） 高
一致性 准强一致（弱 XA） 强一致 最终一致
适用场景 对一致性要求高 高并发 + 独立系统 长流程 + 异步补偿
锁粒度 全局行锁 无全局锁 无全局锁
依赖 支持 ACID 的 DB 无（应用自己保证） 无
回滚可靠性 高（undolog） 低（try 失败则回滚） 中（状态机驱动）

AT vs TCC 选择： - 有现成 DB，不愿改业务代码 → AT - 高并发、分布式系统、无共享 DB → TCC - 超长链路（10+ 节点）、可接受最终一致 → Saga

TCC 示例（库存服务）：

@LocalTCC
public interface StockTccService {
    @TwoPhaseBusinessAction(name="deduct", commitMethod = "confirm", rollbackMethod = "cancel")
    boolean tryDeduct(@BusinessActionContextParameter(paramName="id") Long id, int count);

    boolean confirm(BusinessActionContext ctx);
    boolean cancel(BusinessActionContext ctx);
}

扩展：AT 模式实际上是 2PC 的变体（一阶段预提交 + 二阶段异步确认）；Seata 的 GlobalTransactionalInterceptor 负责所有分布式事务的发起；跨服务 + 强一致场景优先选 AT，允许延迟选 Saga。
