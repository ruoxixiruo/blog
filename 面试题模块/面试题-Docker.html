Docker

1. 镜像、容器、仓库的区别?

镜像(Image) → 容器(Container) → 仓库(Registry)

镜像     容器      仓库
安装包   运行程序   应用商店
.iso    进程       Docker Hub
不可变   可写层     存储/分发
  • 镜像:只读模板,包含运行环境 + 代码。就像操作系统的 ISO 文件--你自己不改它,拿来装就行。分层存储,每层只读
  • 容器:镜像跑起来的实例,在镜像只读层上加了可写层。就像用 ISO 装好了系统,你可以在里面装软件、改文件。容器停了,可写层还在(docker start 恢复);容器删了,可写层消失
  • 仓库:存镜像的地方。Docker Hub(公有)、Harbor(私有)、阿里云容器镜像服务。docker pull/push 的对象

扩展:多个镜像共享基础层(如 10 个 Java 应用都基于 openjdk:17)。生产数据用 Volume 挂载。

2. Dockerfile 常用指令?

Dockerfile 核心指令:

FROM openjdk:17-slim           ← 基础镜像(越精简越好)
WORKDIR /app                   ← 工作目录
COPY target/*.jar app.jar      ← 复制文件(推荐 COPY,简单透明)
RUN apt-get update && apt-get install -y curl  ← 构建时执行
ENV JAVA_OPTS="-Xms512m -Xmx512m"             ← 环境变量
EXPOSE 8080                    ← 声明端口(文档作用,不实际映射)
ENTRYPOINT ["java", "-jar", "app.jar"]  ← 固定入口
CMD ["--server.port=8080"]     ← 默认参数
指令 作用 注意
FROM 基础镜像 尽量用 alpine/slim
COPY 复制文件 比 ADD 更透明
ADD 复制 + 自动解压 不需要解压就别用
RUN 构建时执行 多条用 && 合并减层
CMD 默认启动命令 运行时可覆盖
ENTRYPOINT 固定入口 不会被覆盖

扩展:.dockerignore 减小构建上下文。不常变的放前面(先 COPY 依赖再 COPY 源码),频繁改的放后面,充分利用层缓存。

3. CMD 和 ENTRYPOINT 的区别?

组合关系:

1 只有 CMD:
  CMD ["java", "-jar", "app.jar"]
  docker run myimage → 执行 java -jar app.jar
  docker run myimage /bin/bash → 覆盖 CMD,执行 /bin/bash

2 只有 ENTRYPOINT:
  ENTRYPOINT ["java", "-jar", "app.jar"]
  docker run myimage → 执行 java -jar app.jar
  docker run myimage /bin/bash → 执行 java -jar app.jar /bin/bash(当参数加在后面!)

3 ENTRYPOINT + CMD(最佳实践):
  ENTRYPOINT ["java", "-jar", "app.jar"]
  CMD ["--server.port=8080"]
  docker run myimage → java -jar app.jar --server.port=8080
  docker run myimage --server.port=9090 → java -jar app.jar --server.port=9090

最佳实践:ENTRYPOINT 设主程序(不能被覆盖),CMD 设默认参数(可以被 docker run 后面参数覆盖)。就像 ENTRYPOINT 是"做什么菜",CMD 是"默认放多少盐"--你可以改放盐的量。

扩展:Shell 格式启动 /bin/sh -c,信号传递有问题。Exec 格式 PID 1 是程序本身,能正常接收 docker stop 的 SIGTERM。

4. 如何减小 Docker 镜像体积?

镜像瘦身三板斧:

1 选对基础镜像(最省事):
   openjdk:17         → ~470MB
   openjdk:17-slim    → ~200MB
   openjdk:17-alpine  → ~180MB
   distroless-java    → ~120MB(连 shell 都没有,最安全)

2 多阶段构建(最有效):
   # 第一阶段:用大镜像编译
   FROM maven:3.8-openjdk-17 AS builder
   COPY src /app/src
   RUN mvn package -DskipTests

   # 第二阶段:只复制编译产物到精简镜像
   FROM openjdk:17-slim
   COPY --from=builder /app/target/*.jar app.jar
   ENTRYPOINT ["java", "-jar", "app.jar"]

   最终镜像只有 JRE + jar,没有 Maven/GCC 这些构建工具!

3 合并 RUN 命令减少层:
   RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*
   三条合成一条 → 少两层

扩展:Distroless 镜像连 shell 都没有,攻击面最小。docker history <image> 可定位肥胖层。

5. Docker Compose 是什么?

Docker Compose 一个文件搞定多容器:

version: '3.8'
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root
    volumes:
      - mysql_data:/var/lib/mysql
  app:
    build: .
    ports:
      - "8080:8080"
    depends_on:
      - mysql
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/mydb

docker-compose up -d    → 后台启动所有服务(自动创建网络)
docker-compose down     → 停止并删除容器
docker-compose logs -f  → 看所有服务日志

Compose 让多容器应用一键启动--不用手动挨个 docker run、不用手动创建网络。特别适合本地开发和集成测试。

扩展:depends_on 只保证启动顺序,不保证 MySQL 就绪。healthcheck + condition: service_healthy 可确保依赖服务完全就绪。

6. Docker 网络模式有哪些?

四种网络模式:

┌─────────────────────────────────────────────────────┐
│ bridge(默认):独立网络栈 + NAT 出外网              │
│   [容器A: 172.17.0.2] [容器B: 172.17.0.3]          │
│   └── docker0 网桥 ──→ 宿主机 NAT ──→ 外网          │
│   容器间通过 IP 互通,外部通过端口映射访问           │
├─────────────────────────────────────────────────────┤
│ host:直接用宿主机网络                               │
│   容器和宿主机共享 IP,端口直接暴露                  │
│   性能最好(无 NAT),但有端口冲突风险               │
├─────────────────────────────────────────────────────┤
│ none:无网络                                         │
│   完全隔离,适合不需要网络的批处理任务               │
├─────────────────────────────────────────────────────┤
│ container:共享另一个容器的网络栈                    │
│   容器A 和容器B 共享 localhost,适合紧密耦合的服务   │
└─────────────────────────────────────────────────────┘

扩展:自定义网络中容器可通过容器名 DNS 解析。Overlay 用于跨主机 Swarm,Macvlan 用于传统应用迁移。

7. 什么是写时复制(Copy-on-Write)?

写时复制(Copy-on-Write):

镜像(只读层):
  [Layer 4: 应用代码]        ← 最上层
  [Layer 3: JDK]
  [Layer 2: apt 包]
  [Layer 1: Ubuntu 基础]     ← 底层

容器(加可写层):
  [Container 可写层]         ← 容器自己的修改
  [Layer 4: 应用代码]        ← 共享,不改
  ...

修改 Layer 3 的文件时:
1 把文件从 Layer 3 复制到 Container 可写层
2 在可写层修改
3 Layer 3 原文件不变(其他容器还能用)

好处:多个容器共用同一套只读层(如 10 个容器都基于 openjdk:17,基础 JDK 只存一份)。每个容器只存自己的修改量,省磁盘空间。启动快--只创建空的可写层就行。

扩展:Docker 默认用 Overlay2 存储驱动。容器删掉后数据丢失--持久化数据用 Volume 挂载。

8. COPY 和 ADD 的区别?

指令 功能 使用建议
COPY 从宿主机复制文件/目录到镜像 首选,简单透明
ADD COPY + 自动解压 tar + 支持远程 URL 有坑,谨慎使用 
# 推荐:用 COPY
COPY target/app.jar /app/app.jar

# ADD 的特殊行为(有坑):
ADD archive.tar.gz /app/     # 自动解压 tar.gz(有时你不想解压!)
ADD https://example.com/file /app/  # 能从 URL 下载(但不会清理缓存)

扩展:Docker 官方推荐优先使用 COPY。需要下载文件时,用 RUN curl/wget 替代 ADD URL,可控制缓存和清理。

9. Docker Volume 的三种类型和区别?

类型 存储位置 特点
Volume /var/lib/docker/volumes/(Docker 管理) 推荐,Docker 完全管理,跨平台,可共享
Bind Mount 宿主机任意路径 灵活但依赖目录结构,开发环境常用
tmpfs 内存 临时数据,容器停止即消失 
Volume(推荐):                Bind Mount(开发用):      tmpfs(临时):

Docker 管理区域                宿主机 ←→ 容器              仅内存
/var/lib/docker                 /home/user/                /tmpfs
    │                              │                         │
    └── data/ ──▶ 容器              └── code/ ──▶ 容器          └── 容器内临时数据
    可共享、备份                   开发时热更新               速快、重启即丢

扩展:生产用 Volume,开发用 Bind Mount(代码改后容器内立即生效)。docker volume prune 清理未用 Volume。

10. Docker 如何限制容器资源?

# 内存限制
docker run -m 512m --memory-swap 1g nginx
# -m: 物理内存上限
# --memory-swap: 物理+交换空间上限(-1=无限制)

# CPU 限制
docker run --cpus 1.5 nginx        # 最多用 1.5 个 CPU 核心
docker run --cpuset-cpus 0-2 nginx # 绑定到 CPU 0,1,2

# 进程数限制
docker run --pids-limit 100 nginx  # 最多 100 个进程

扩展:生产环境必须给每个容器设 -m 和 --cpus。docker stats 可实时看每个容器的 CPU/内存/网络/磁盘 IO。

11. Docker、containerd、runc 三者的关系?

Docker(最高层)→ containerd(中层)→ runc(底层)
                                            │
                                     创建容器进程(OCI 标准)
组件 作用
Docker 面向用户的 CLI + API(docker build、docker run、镜像管理)
containerd 容器生命周期管理(拉镜像、创建/启动/停止容器、管理存储和网络)
runc OCI 标准容器运行时,真正创建和运行容器进程

扩展:K8s 1.24 移除了 Dockershim,直接通过 CRI 接口调 containerd。更轻量--K8s 只需要 containerd 就够了。

12. Docker 容器退出码的含义?

退出码 含义
0 正常退出(成功)
1 应用错误(程序自己 exit 1)
137 被 SIGKILL 杀死(通常是 OOM:dmesg \| grep -i oom 确认)
143 收到 SIGTERM,优雅退出 
排查流程:
  docker ps -a 看到容器 Exited(137)
       │
       ▼
  Exit 137 = 128 + 9(SIGKILL)
       │
       ▼
  大概率 OOM → 检查内存限制是否太小 → 调大 -m 或排查内存泄漏

扩展:退出码 137 = 128 + 9(SIGKILL),通常是 OOM。docker inspect 的 State.OOMKilled 字段可确认。

13. Docker 镜像构建缓存机制是怎样的?

Docker 镜像是分层存储的,每一层对应 Dockerfile 的一条指令。构建时,Docker 会检查当前指令和上下文是否跟上次一样--一样就用缓存,不一样就重建(且后续所有层全部失效)。

缓存工作原理:

Dockerfile 逐行构建:

FROM python:3.11          ← 第 1 层
COPY requirements.txt .   ← 第 2 层(如果文件没变 → 缓存命中 ✅)
RUN pip install -r ...    ← 第 3 层(如果上一层命中且命令没变 → 缓存命中 ✅)
COPY . .                  ← 第 4 层(源码经常变 → 缓存失效 ❌)
RUN python setup.py       ← 第 5 层(上一层失效 → 这一层也跟着失效 ❌)

核心规则:某层缓存失效后,后续所有层全部失效--就像链条断了一节,后面全断。

优化技巧(面试必答):

# ❌ 差:COPY . . 在最前面,每次改代码都重建所有依赖
FROM python:3.11
COPY . .
RUN pip install -r requirements.txt   # 代码一改,这层也重跑

# ✅ 好:先单独 COPY 依赖文件,再 COPY 源码
FROM python:3.11
COPY requirements.txt .          # 依赖文件很少变 → 缓存命中
RUN pip install -r requirements.txt   # 很长的一步,能用缓存省很多时间
COPY . .                         # 最后才 COPY 常变的源码

缓存为什么不命中? - COPY/ADD 的文件内容变了(最常见) - RUN 的命令字符串变了(即使逻辑一样) - 上一层没命中(级联失效) - 用了 --no-cache 参数 - 构建上下文中有 .dockerignore 未排除的大文件变化

扩展:BuildKit --mount=type=cache 可跨构建共享依赖缓存。多阶段构建减小镜像体积--构建依赖在第一阶段,最终镜像只 COPY 编译产物。

14. Docker Swarm 和 Kubernetes 选哪个？

Docker Swarm：Docker 原生，部署极简，5 分钟上手：

# 初始化集群
docker swarm init
# 发布服务
docker stack deploy -c docker-compose.yml myapp

K8s vs Swarm 核心对比：

维度 Docker Swarm Kubernetes
学习曲线 低（1天） 高（2-4周）
功能 基础 完整云原生生态
生产认可度 轻量场景 事实标准
扩缩容 replicas: 3 HPA 自动弹性
服务发现 DNS 自动 Ingress + Service
社区/生态 一般 极其丰富

选型建议： - 小团队、快速验证 → Docker Swarm - 生产级、长期运维 → Kubernetes（自建 or EKS/GKE/ACK） - 中大型企业 → K3s（轻量 K8s，单节点也能跑）

扩展：Docker Compose 本地开发，docker stack 生产部署（Swarm）；生产用 K8s 时，Argo CD/GitOps 是推荐部署方式。
