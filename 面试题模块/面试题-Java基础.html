Java

1. JDK、JRE、JVM 的区别?

JDK(最大)
├── JRE
│   ├── JVM(核心引擎)
│   └── 核心类库(rt.jar / java.base)
├── javac(编译器)
├── javadoc(文档工具)
├── jdb(调试器)
└── 其他开发工具
  • JVM(Java 虚拟机):执行字节码的引擎。把 .class 文件翻译成机器码跑起来。相当于"灶台"--只管加热
  • JRE(运行环境):JVM + 核心类库(如 java.lang、java.util)。跑 Java 程序需要的最小环境。相当于"灶台+锅碗瓢盆"--能做饭了
  • JDK(开发工具包):JRE + 编译器(javac)+ 调试工具(jdb)+ 文档工具(javadoc)。写 Java 程序需要的。相当于"完整厨房"--能买菜、切菜、做饭

包含关系:JDK ⊃ JRE ⊃ JVM。用户电脑只需装 JRE(或直接用 jlink 打包的最小运行时),开发者需要 JDK。

扩展:JDK 11 后 Oracle 不再提供单独的 JRE--运行时由 jlink 按需构建。JDK 9 引入模块化(JPMS),把原本庞大臃肿的 rt.jar 拆成了精细的模块,程序可以只打包需要的模块。另外,GraalVM 作为新的"多语言虚拟机",可以跑 Java、Python、JavaScript 等,还能做 AOT 编译成原生镜像。

2. == 和 equals() 的区别?

==    (引用比较):两个指针是否指向同一块内存地址
equals(值比较)  :两个对象的内容是否相同

堆内存:
  [String "hello" @0x100] ← a 指向这里
  [String "hello" @0x200] ← b 指向这里
  a == b        → false(地址不同)
  a.equals(b)   → true(内容相同)
  • ==:基本类型比值,引用类型比内存地址(是不是同一个对象)。就像比"是不是住在同一个房子里"
  • equals():Object 默认也是比地址(和 == 一样),但 String、Integer 等重写了,比的是值。就像比"两个人名字是不是一样"
String a = new String("hello");
String b = new String("hello");
a == b       // false,两个不同的对象
a.equals(b)  // true,内容一样

扩展:字符串常量池的存在让情况更复杂--String s1 = "hello"; String s2 = "hello"; s1 == s2 是 true,因为两个变量指向常量池中同一个对象。Integer 也有缓存池(-128 到 127),在这个范围内 == 也可能返回 true。面试时经常拿这些"反直觉"的情况考察对底层机制的理解。

3. hashCode() 和 equals() 的关系?

HashMap 查找流程:
key → hashCode() → 定位桶(bucket) → equals() 精确匹配

如果只重写 equals 没重写 hashCode:
  obj1.equals(obj2) == true
  obj1.hashCode()  != obj2.hashCode()
  → HashMap 把它们放到不同的桶 → 找不到!

铁律:equals 相等的两个对象,hashCode 必须相等。反过来不一定(哈希碰撞--不同的对象可以有相同的 hashCode)。

为什么?HashMap/HashSet 先通过 hashCode 快速定位到桶(就像快递先看收件小区),再用 equals 精确判断(再核实门牌号)。如果你重写了 equals 但没重写 hashCode,两个逻辑相等的对象可能被放到不同的桶里--HashMap 就找不到正确的值了。

结论:重写 equals 必须同时重写 hashCode。Lombok 的 @EqualsAndHashCode 和 IDEA 的 Generate 功能都能自动保证这个一致性。

扩展:好的 hashCode 实现能减少哈希碰撞→提升 HashMap 性能。常见做法是用质数 31 作为乘数--31 * result + field.hashCode()。因为 31 是质数且 JVM 可以将 31 * i 优化为 (i << 5) - i(位运算更快)。String 的 hashCode 就用这个算法:s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]。

4. String、StringBuilder、StringBuffer 的区别?

类型 可变性 线程安全 性能 场景
String 不可变 天然安全 拼接时慢(创建新对象) 少量拼接、常量、Map 的 key
StringBuilder 可变 不安全 最快 单线程频繁拼接
StringBuffer 可变 安全(synchronized) 较慢 多线程拼接 
String 拼接陷阱:
String s = "";
for (int i = 0; i < 10000; i++) {
    s += i;  // 每次循环都 new String()!10000 个临时对象
}

用 StringBuilder:
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10000; i++) {
    sb.append(i);  // 同一块内存追加,无临时对象
}

String 不可变因为底层是 final byte[](JDK 9+,之前是 char[])--一旦创建不能改。好处:哈希值可以被缓存(HashMap 的 key 首选 String)、线程安全、字符串常量池可以共享相同值。

扩展:JDK 9 将 char[] 改为 byte,因为大多数拉丁字符只需 1 字节。JDK 9+ 的字符串拼接底层自动优化为 invokedynamic + StringConcatFactory,简单拼接不比 StringBuilder 差。但循环中拼接编译器无法优化,仍要用 StringBuilder。另外 StringJoiner 和 String.join() 在拼接分隔符时比手动追加更简洁。

5. ArrayList 和 LinkedList 的区别?

ArrayList(底层数组 Object[]):
  [A][B][C][D][_]  ← 连续内存
  get(2) → O(1) 直接 C = elementData[2]
  add(1, X) → O(n) 要把 BCD 往右移一格

LinkedList(底层双向链表):
  head ⇄ [A|prev|next] ⇄ [B|prev|next] ⇄ [C|prev|next] ⇄ tail
  get(2) → O(n) 从 head 走两步才找到 B
  add(1, X) → O(1) 改前后两个指针就行(但找位置要 O(n))
操作 ArrayList LinkedList
随机 get O(1) O(n)
尾部 add O(1) 均摊 O(1)
中间 add/remove O(n)(移动元素) O(1)(改指针,但找位置 O(n))
内存占用 紧凑(连续) 多两个指针

实际建议:90% 的场景用 ArrayList--连续内存对 CPU 缓存友好,链表指针跳转会造成 cache miss。LinkedList 只在频繁头/尾部插入且不需要随机访问时考虑(但此时 ArrayDeque 更合适)。

扩展:ArrayList 默认容量 10,满了按 1.5 倍扩容(oldCapacity + oldCapacity >> 1)。扩容会用 Arrays.copyOf() 复制整个数组,所以如果能预估大小,用 new ArrayList<>(n) 指定初始容量减少扩容次数。Vector 是老牌的线程安全 List(synchronized 所有方法),已被 CopyOnWriteArrayList 和 Collections.synchronizedList() 替代。

6. HashMap 的原理(1.8)?

HashMap = 一个超大号抽屉柜。每个抽屉(桶)编了号(哈希值定位),一个抽屉里可能塞多个文件(哈希碰撞→链表),东西太多时抽屉升级成文件夹分类(→红黑树)。

HashMap 数据结构(JDK 1.8):

bucket:   [0]   [1]   [2]   [3]   ...   [15]
            |     |           |
          链表  红黑树        null
          A→B   C
               / \
              D   E

put 流程:

key.hashCode() → 扰动处理(高16位 ^ 低16位)→ 与 (n-1) 取模定位桶
  → 桶为空:直接放
  → 桶有数据(哈希碰撞):
     → 链表节点 < 8:追加到链表末尾
     → 链表节点 ≥ 8 且数组长度 < 64:扩容
     → 链表节点 ≥ 8 且数组长度 ≥ 64:链表转红黑树
  → key 相同:覆盖旧值

关键参数:

  • 默认容量 16,负载因子 0.75--当元素数 > 16 × 0.75 = 12 时触发扩容
  • 扩容时容量 ×2,每个桶的节点要么在原位置,要么移到原位置 + 原容量
  • 容量必须是 2 的幂--这样 hash & (n-1) 等价于 hash % n,位运算更快
  • 链表转红黑树阈值 = 8(泊松分布下概率约千万分之一),红黑树退化为链表阈值 = 6

扩展:JDK 1.7 的 HashMap 存在"死循环"问题--扩容时头插法会导致链表成环(多线程并发时)。1.8 改为尾插法修复了这个问题,所以面试时常说"1.7 HashMap 线程不安全是因为死循环,1.8 是因为数据覆盖"。(n-1) & hash 比 % 快是因为位运算只用 1 个 CPU 周期,取模要几十个周期。hash 值扰动(高 16 位异或低 16 位)是为了让高位也参与低位运算,因为大多数场景下容量不大的 HashMap 只用低位。

高级追问--HashMap 设计决策的"为什么":

为什么容量必须是 2 的幂? hash & (n-1) 等价于 hash % n 只在 n 是 2 的幂时成立。如果容量不是 2 的幂,低位会有槽永远用不上,分布严重不均。扩容时 2 倍扩容还有一个好处:元素要么在原来位置,要么在原位置+原容量(只需判断 hash 新增的那一位是 0 还是 1),迁移成本低。

为什么负载因子是 0.75? 空间和时间的权衡:设低了(如 0.5)-空间利用率低但冲突少;设高了(如 1.0)-空间利用率高但冲突多、查询退化。0.75 是 JDK 团队在大量测试后选的甜点值,也是泊松分布计算的基准参数。

为什么树化阈值是 8? 基于泊松分布:负载因子 0.75 时,链表长度 ≥8 的概率约千万分之六。也就是说正常情况下几乎不会树化--树化是一个"极端情况的兜底",不是常规路径。退化阈值设为 6(不等 8)是为了留一个缓冲,防止在 7-8 之间反复树化和退化。

7. ConcurrentHashMap 如何保证线程安全?

JDK 1.7(Segment 分段锁):
┌─────────────────────────────┐
│ Segment[0]  Segment[1]      │
│  ┌─┬─┬─┐     ┌─┬─┬─┐       │
│  │a│b│c│     │d│e│f│       │
│  └─┴─┴─┘     └─┴─┴─┘       │
│  锁住整个   锁住整个        │ ← 并发度 = Segment 数量(默认 16)
│  Segment    Segment         │
└─────────────────────────────┘

JDK 1.8(CAS + synchronized 锁桶头节点):
┌─────────────────────────────┐
│ [0]  [1]  [2]  [3]  ...     │
│  ↓    ↓    ↓    ↓           │
│ CAS  syn  null CAS          │ ← 只锁冲突的那个桶
└─────────────────────────────┘

1.7(分段锁):整个 Map 分成 16 个 Segment,每个 Segment 内一把锁。16 个线程分别操作不同 Segment 时互不阻塞。但并发度被局限在 16,且粒度还是偏粗。

1.8 改进--CAS + synchronized: - put 操作:桶为空 → CAS 尝试设置(无锁);桶有数据 → 只对桶头节点加 synchronized(最小粒度) - get 操作:完全不加锁(Node 的 val 和 next 都是 volatile,保证可见性) - 扩容:多线程可以协作扩容(transfer 方法给每个线程分配迁移区间),效率大幅提升

就像 1.7 是锁整个楼层(同一楼层的人都要等),1.8 是锁每个房间的门--只有同一个房间的人需要排队。

扩展:ConcurrentHashMap 不允许 null 的 key 和 value(HashMap 允许),因为多线程下 get(null) 无法区分"key 不存在"和"value 就是 null"。size() 方法在 1.8 中不再锁整个 map 而是通过 baseCount + CounterCell 数组累加各线程的计数,精度比 1.7 稍低但性能好很多。computeIfAbsent 方法在 ConcurrentHashMap 中是原子的,可以安全地做"不存在则计算并放入"。

8. synchronized 锁升级过程?

锁升级路径(单向,不可降级):

无锁 ──→ 偏向锁 ──→ 轻量级锁 ──→ 重量级锁
 无竞争   同一线程  少量竞争   激烈竞争
        反复进入  CAS 自旋   进入阻塞队列
                        ↓
                   自旋失败/竞争加剧

偏向锁:第一个线程进来时,锁上贴个"专属于线程 A"的标签(Mark Word 记录线程 ID)。以后线程 A 再来,看到是自己的标签--直接进,什么都不用做。就像你的专属停车位--看到名字直接停。

轻量级锁:其他线程也来抢时,偏向锁升级。线程 B 通过 CAS 尝试在 Mark Word 中设置 Lock Record 指针。没抢到的自旋等待(循环尝试,不阻塞)。适合锁持有时间短的场景--自旋的 CPU 开销 < 线程阻塞/唤醒的开销。

重量级锁:自旋了一定次数还是拿不到锁 → 升级为重量级锁。线程进入 OS 级别的互斥量(Mutex),进内核态排队阻塞。CPU 开销转嫁给了 OS 调度。适合锁持有时间长或竞争激烈的场景。

扩展:JDK 15 默认禁用了偏向锁(因为在高竞争场景下偏向锁撤销的开销可能大于收益),JDK 21 中偏向锁已被标记为废弃。锁消除(JIT 发现不可能有竞争,直接去掉锁)和锁粗化(合并相邻的加锁/解锁)也是 JIT 对 synchronized 的重要优化。JDK 21 的虚拟线程(Virtual Threads)可以极大降低重量级锁阻塞的代价--虚拟线程阻塞不占用 OS 线程。

9. volatile 的作用?

volatile 的两大能力:

1 可见性:
  线程A:flag = true;  → 立刻刷到主内存
  线程B:读 flag  → 直接从主内存读(不用工作内存的缓存)
  保证:A 的修改 B 立刻能看到

2 禁止指令重排:
  写 volatile 之前的操作不能排到后面
  读 volatile 之后的操作不能排到前面
  (内存屏障保证)

不保证原子性--i++ 看起来一步,实际是"读→改→写"三步:

线程A 读 i=0 → 线程B 读 i=0 → A 写 i=1 → B 写 i=1
  结果 i=1,应该是 2!volatile 管不了这件事

使用 volatile 的经典场景:

  • 状态标记:private volatile boolean running = true;
  • DCL 单例中的 instance(防止指令重排导致的"半初始化"对象逸出)
  • 读多写少的计数器不要求严格精确时

扩展:DCL(Double-Checked Locking)单例中 instance 必须用 volatile,因为 new Singleton() 不是原子的--它分三步:分配内存 → 初始化对象 → 赋值给引用。不加 volatile,JIT 可能把"初始化"和"赋值"重排,导致其他线程拿到一个未初始化的对象。synchronized 也能保证可见性(退出同步块时刷主内存),但 volatile 比 synchronized 轻量得多(只是内存屏障,无锁)。

10. ThreadLocal 原理及内存泄漏问题?

ThreadLocal 内部结构:

Thread-1                     Thread-2
  ThreadLocalMap               ThreadLocalMap
    key(弱引用) → TL对象        key(弱引用) → TL对象
    value → 用户数据            value → 用户数据
    key(弱引用) → TL对象2
    value → 用户数据2

每个线程都有一个 ThreadLocalMap
每个 ThreadLocal 对象是 Map 的 key

原理:每个线程内部维护一个 ThreadLocalMap,key 是 ThreadLocal 对象的弱引用,value 是你存的值。这样不同线程访问同一个 ThreadLocal 对象的 get() 时,实际上是从自己线程的 Map 里取值--天然线程隔离。

内存泄漏原因:

ThreadLocal 对象(外部强引用被置 null)
  → GC 回收 ThreadLocal 对象(因为是弱引用 key)
  → 但 value 还在 ThreadLocalMap 中(强引用)
  → 线程池线程长期不销毁 → value 永远不被回收 → 内存泄漏

解决:用完一定要调 remove()。就像用完储物柜要清空--key(号码牌)还了,东西(value)还占着柜子。

扩展:JDK 8 的 ThreadLocal 已经在 get/set/remove 时会顺便清理 key 为 null 的 Entry(惰性清理),但没有调 remove 的话清理不完全。InheritableThreadLocal 可以让子线程继承父线程的值(fork-join 场景),但不支持线程池(线程复用导致继承失效)。阿里 TransmittableThreadLocal(TTL)解决了线程池场景下的上下文传递问题,已被 Spring Cloud 和 Dubbo 采用。

11. JVM 内存模型?

JVM 运行时数据区域:

┌─────────────────────────────────────────┐
│              堆 (Heap)                   │ ← 所有线程共享,GC 主战场
│  ┌────┬────┬────────────┐               │
│  │Eden│ S0 │ S1 │ Old Gen│               │
│  └────┴────┴────────────┘               │
├─────────────────────────────────────────┤
│          元空间 (Metaspace)              │ ← 方法区的实现,存类元信息
│     直接内存 (Direct Memory)             │ ← NIO 使用的堆外内存
├──────────┬──────────┬───────────────────┤
│ 虚拟机栈  │ 本地方法栈│  程序计数器        │ ← 线程私有
│ (Java调用)│(native)  │  (当前字节码行号)   │
└──────────┴──────────┴───────────────────┘
  • 堆:对象和数组的实例存放区,GC 主要发生地。分新生代(Eden + 两个 Survivor)和老年代
  • 方法区/元空间:存储类信息、常量、静态变量、JIT 编译的代码。JDK 8 后从堆内永久代(PermGen)移到本地内存(Metaspace),不再容易 OOM
  • 虚拟机栈:每个线程私有。每个方法调用时创建一个栈帧(存局部变量表、操作数栈、方法返回地址)
  • 本地方法栈:类似虚拟机栈,但服务于 native 方法
  • 程序计数器:记录当前线程执行到哪条字节码指令,是 JVM 中唯一不会 OOM 的区域

扩展:JDK 8 将永久代替换为元空间的主要原因是--永久代大小固定(-XX:MaxPermSize),类加载多了容易 OOM: PermGen。元空间使用本地内存,默认无上限(受限于物理内存),并且字符串常量池也从永久代移到了堆中。直接内存(DirectByteBuffer)不受 GC 管理,适合大块数据长期驻留的场景(如 Netty 的网络缓冲区),但需要手动释放。

12. 垃圾回收算法?

四种 GC 算法对比:

标记-清除(Mark-Sweep):
  [A][ ][B][ ][C][ ][D][ ]  → 碎片化,大对象可能放不下

标记-整理(Mark-Compact):
  [A][B][C][D][ ][ ][ ][ ]  → 无碎片,但整理慢(STW 长)

复制(Copying):
  内存分两块,只用一半:
  Eden + S0 → 活对象复制到 S1,Eden+S0 清空
  快,无碎片,但浪费一半空间

分代收集(Generational):
  新生代 → 复制(对象朝生夕死,98% 活不过一轮)
  老年代 → 标记-整理 或 标记-清除
算法 怎么做 优点 缺点
标记-清除 标记活对象 → 清除死的 简单 碎片化
标记-整理 标记活对象 → 移到一端 无碎片 STW 长
复制 活的复制到另一区 无碎片,快 浪费一半空间
分代收集 新老分别用复制/整理 各取所长 复杂度高

为什么新生代用复制:新生代中 98% 的对象"朝生夕死",每次 GC 只有少量存活。复制少量活对象到 Survivor 区就行,很高效。只需要 10% 的保留空间(两个 Survivor 区),不算浪费。

为什么老年代用标记-整理:老年代中的对象存活率高、存活时间长。如果用复制,一半空间浪费太大。所以用标记-清除(CMS)或标记-整理(Serial/Parallel Old)。

扩展:复制算法中的 Survivor 为什么是两个(S0 和 S1)而不是一个?因为每次 GC 后 Eden + 其中一个 Survivor 的存活对象要复制到另一个 Survivor,两个 Survivor 交替使用,始终保持一个为空。如果 Survivor 不够放,存活对象直接进入老年代(分配担保机制)。大对象(超过 -XX:PretenureSizeThreshold)也会直接进老年代。

13. CMS 和 G1 的区别?

CMS(Concurrent Mark Sweep):
  老年代用,标记-清除
  目标:最短停顿时间
  问题:碎片化 + 浮动垃圾
  JDK 14 已废弃

G1(Garbage First):
  整堆划分为等大小的 Region
  优先回收垃圾最多的 Region
  目标:可预测的停顿时间(-XX:MaxGCPauseMillis)
  JDK 9+ 默认收集器
对比维度 CMS G1
堆结构 连续新生代 + 连续老年代 多 Region(逻辑分代)
回收策略 只回收老年代 选垃圾最多的 Region 回收
碎片 标记-清除有碎片 复制整理,无碎片
停顿预测 不可预测 可设目标值
适用堆大小 小到中(< 4G) 中到大(> 4G)
JDK 状态 14+ 废弃 9+ 默认,推荐

CMS 的问题:标记-清除产生碎片,老年代没有连续空间分配大对象时,触发 Full GC(Serial Old 做标记-整理,单线程,STW 很长)。另外并发清理时用户线程还在运行会产生新的垃圾(浮动垃圾),可能在下一次 GC 前触发 Concurrent Mode Failure。

G1 如何解决:将堆分成大小相等的 Region(1-32MB),每次只回收一部分垃圾最多的 Region(而不是整个老年代),控制每次停顿时间。Region 之间用 Remembered Set(记忆集)记录跨 Region 引用,避免扫描全堆。

扩展:ZGC(JDK 11 实验,15+ 生产可用)和 Shenandoah(JDK 12+)是新一代低延迟收集器,目标是把 STW 控制在 10ms 以内,且停顿时间不随堆大小增加。ZGC 使用着色指针和读屏障,Shenandoah 使用 Brooks 指针和转发指针。JDK 21 的 Generational ZGC 把 ZGC 改成了分代模式,性能进一步提升。未来 CMS 和 Parallel Old 都会逐步退役。

14. Java 8 新特性有哪些?

Java 8 核心特性一览:

Lambda      → (a, b) -> a + b        匿名函数的简洁写法
Stream      → filter/map/reduce      函数式处理集合,声明式编程
Optional    → Optional.ofNullable()  消灭 NPE 的容器
接口增强     → default / static       接口可以有方法体了
新时间 API   → LocalDate/LocalTime   不可变、线程安全、API 清晰
CompletableFuture → 异步编排         回调地狱的终结者
方法引用     → String::length         Lambda 的简化写法

重点解读:

  • Lambda 表达式:(参数) -> { 方法体 },本质是函数式接口(只有一个抽象方法的接口)的匿名实现。让代码从"怎么做"变成"要什么"
  • Stream API:list.stream().filter(x -> x > 10).map(String::valueOf).collect(toList())--链式声明式处理,内部迭代 + 惰性求值
  • Optional:包装可能为 null 的值,强制你处理空值情况。optional.map().orElse() 替代层层 if-null 判断
  • 新日期时间 API(java.time):Date 和 Calendar 终于可以扔了--不可变、线程安全、API 直观(LocalDate.now().plusDays(7))
  • CompletableFuture:supplyAsync().thenApply().thenAccept() 链式编排异步任务,摆脱回调嵌套

扩展:Stream 的惰性求值--中间操作(filter/map)不立即执行,只在终端操作(collect/forEach/count)触发时才上一条龙处理。默认方法解决了接口演化问题--给 Collection 加 stream() 方法而不用逼所有实现类都改。JDK 8 中还引入了 Base64 工具类、ConcurrentHashMap 重写等大量改进。

15. 异常体系中 checked 和 unchecked 的区别?

Java 异常体系:

Throwable
├── Error(不应捕获)
│   └── OutOfMemoryError, StackOverflowError
└── Exception
    ├── RuntimeException(unchecked,不强制处理)
    │   └── NullPointerException, IllegalArgumentException
    └── 其他 Exception(checked,编译器强制处理)
        └── IOException, SQLException, ClassNotFoundException
对比 Checked Unchecked(RuntimeException)
编译检查 必须 try-catch 或 throws 不强制
典型场景 外部系统异常(IO、网络) 编程错误(空指针、越界)
设计意图 "这个错误你应该预见到" "这是你代码写得不对"
举例 FileNotFoundException NullPointerException

设计哲学:可预测的外部异常(文件不存在、网络断开)强制你处理--因为你无法控制外部环境。程序逻辑错误(空指针、数组越界)不强制--你的代码不该写出这种 bug,如果写了就让程序崩溃,而不是悄悄吞掉。

扩展:Spring 框架倾向于使用 RuntimeException(提倡 unchecked 异常),认为 checked 异常增加了代码噪音且很多场景无法从异常中恢复。@Transactional 默认只在 RuntimeException 和 Error 时回滚,checked 异常不自动回滚(需要 rollbackFor 指定)。另外 finally 块中的 return 会吞掉 try 中的异常,这是经典的坑。

16. 反射的原理及应用场景?

反射工作流程:

类加载 → JVM 在方法区创建 Class 对象(包含类的所有元信息)
  → 通过 Class.forName() / obj.getClass() / 类名.class 获取 Class 对象
  → 获取 Field / Method / Constructor
  → 调用 method.invoke(obj, args) 或 field.set(obj, value)

反射让程序在运行时获取类的所有信息并操作它--就像有了一个类的"X 光片",能在运行时看穿里面的每个字段、每个方法。

经典应用场景: - Spring 依赖注入:@Autowired 时通过反射设置字段值 - JDK 动态代理:Proxy 类用反射调用目标方法 - JDBC 驱动加载:Class.forName("com.mysql.cj.jdbc.Driver") 加载驱动类(JDK 4+ 后 SPI 自动加载) - JSON 序列化:Jackson/Gson 用反射读写对象字段 - 单元测试:JUnit 通过反射调用 @Test 方法

代价:性能比直接调用慢(需要安全检查、包装/拆箱、方法查找),破坏了封装性(setAccessible(true) 可以访问 private 成员)。

扩展:setAccessible(true) 的性能开销较大,建议在初始化时缓存 Method/Field 对象避免重复查找。JDK 17+ 中反射访问被模块化系统限制更严格(强封装),但 --add-opens JVM 参数可以开放。MethodHandle(JDK 7+)和 VarHandle(JDK 9+)是反射的替代方案,性能接近直接调用。Lambda 表达式底层用 invokedynamic + LambdaMetafactory,不依赖反射。

17. 泛型中的 <? extends T> 和 <? super T> 的区别?

PECS 原则:Producer Extends, Consumer Super

List<? extends Number>:生产者,你从里面拿东西
  → 只能读(get 返回 Number),不能写(add 不知道具体类型)
  → 可以接受 List<Integer>、List<Double> 等

List<? super Integer>:消费者,你往里面放东西
  → 能写(可以 add Integer),读只能拿到 Object
  → 可以接受 List<Integer>、List<Number>、List<Object>
通配符 读(get) 写(add) 适用
? extends T T 类型 不能写 生产者
? super T Object T 及其子类 消费者
无通配符 <T> T T 读写都有

经典例子:

// 把 src 的元素复制到 dest
// src 是生产者(只读),dest 是消费者(只写)
void copy(List<? extends T> src, List<? super T> dest) {
    for (T item : src) {
        dest.add(item);
    }
}

不能写的原因:List<? extends Number> 可能是 List<Integer> 也可能是 List<Double>,你往里面 add 3.14 如果它实际是 List<Integer> 就炸了。(类型安全)

扩展:Java 泛型是"编译期擦除"--编译后 List<Integer> 和 List<String> 都是 List,泛型信息只在编译时存在。所以不能 instanceof List<Integer>、不能 new T()、不能创建泛型数组。? extends 和 ? super 是编译期的类型约束,运行时不区分。Kotlin 的泛型更清晰--in = ? super(消费者),out = ? extends(生产者),且支持声明处型变。

18. Java 的类加载机制?

双亲委派模型:

Bootstrap ClassLoader(最顶层)
  ↑ 加载 <JAVA_HOME>/lib,核心类 rt.jar / java.base
Extension ClassLoader
  ↑ 加载 <JAVA_HOME>/lib/ext
Application ClassLoader(最底层)
  ↑ 加载 classpath 下的类

加载流程(自底向上询问,自顶向下加载):
  1 AppClassLoader 收到请求
  2 先问 ExtClassLoader:你能加载吗?
  3 ExtClassLoader 再问 Bootstrap:你能加载吗?
  4 Bootstrap 加载不到 → ExtClassLoader 也加载不到 → AppClassLoader 自己加载

好处:

  1. 避免重复加载:父加载器已经加载过这个类,子加载器就不用再加载(同一个命名空间只用一份)
  2. 保护核心类安全:你写一个 java.lang.String 想替换 JDK 的核心 String--Bootstrap ClassLoader 说"我已经加载过了",你的冒牌货不会被加载,防止核心库被注入恶意代码

打破双亲委派:某些场景需要打破:

  • Tomcat:每个 Web 应用有自己的 WebAppClassLoader,隔离不同应用的类和 jar
  • SPI(JDBC 驱动):ServiceLoader 的线程上下文类加载器让 Bootstrap 类能加载应用级的实现类
  • OSGi:网状加载,模块间精确控制类可见性

扩展:JDK 9 模块化后,类加载从三层变为--Bootstrap(java.base 等核心模块)、Platform(替代 ExtClassLoader 加载 java.se 等)、App。模块化将 ExtClassLoader 改名为 PlatformClassLoader,且引入模块描述符(module-info.java)控制包的导出和依赖。自定义类加载器只需重写 findClass()(遵循双亲委派)或重写 loadClass()(打破双亲委派)。

19. Java 中 try-with-resources 的原理?

try-with-resources 是 Java 7 引入的语法糖--让你不用手动在 finally 里关资源,编译器帮你生成了关闭代码。

传统写法 vs try-with-resources:

// 传统写法:手动关资源,又臭又长
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("file.txt"));
    String line = br.readLine();
} catch (IOException e) {
    e.printStackTrace();
} finally {
    if (br != null) {
        try {
            br.close();  // close() 也可能抛异常!
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

// try-with-resources:一行括号搞定
try (BufferedReader br = new BufferedReader(new FileReader("file.txt"))) {
    String line = br.readLine();
}  // br.close() 自动调用

底层原理:

编译后,javac 把 try-with-resources 展开成 try-finally 结构。关键点:所有实现了 AutoCloseable(或 Closeable)的对象都可以放 try() 括号里。

Suppressed 异常(核心考点):

如果业务代码和 close() 都抛异常,怎么办?传统写法中 finally 抛的异常会覆盖 try 里的异常--你最想知道的那个业务异常就丢了!try-with-resources 用 suppressed 异常 机制解决了这个问题:

try (BadResource r = new BadResource()) {
    r.doSomething();  // 抛异常 A(业务异常)
    // r.close() 也抛异常 B(关闭异常)
}
// 最终抛出异常 A,异常 B 作为 suppressed 附加在 A 上
// 通过 ex.getSuppressed() 能拿到异常 B

多个资源:声明顺序打开,相反顺序关闭(类似栈--后进先出)。

try (A a = new A(); B b = new B(); C c = new C()) {
    // 使用 a, b, c
}
// 关闭顺序:c.close() → b.close() → a.close()

扩展:Java 9 改进了 try-with-resources--可以在 try 外面声明资源变量,只要变量是"effectively final"就行。这样代码更清晰:BufferedReader br = new BufferedReader(...); try (br) { ... }。另外,连接池的 Connection(如 HikariCP)的 close() 不是真关闭连接,而是归还连接池--所以放 try() 里没问题。

20. 接口和抽象类的区别?

用一句话区分:接口=行为合同(你能做什么),抽象类=基因继承(你是什么)。就像鸟和飞机都会飞(接口 Flyable),但鸟是动物、飞机是机器(抽象类不同)。

对比维度 接口(Interface) 抽象类(Abstract Class)
继承方式 多实现,一个类可实现多个接口 单继承,一个类只能继承一个抽象类
方法 Java 8 前只有抽象方法;8 后支持 default/static 可以有抽象方法,也可以有具体实现
变量 只能是 public static final 常量 可以有各种修饰符的成员变量
构造器 没有 有(给子类调用的)
设计目的 定义"能做什么"(has-a 关系、行为规范) 代码复用 + 模板设计(is-a 关系)
实例化 不能 不能 
// 接口:定义行为规范
interface Flyable {
    int MAX_HEIGHT = 1000;       // 隐式 public static final
    void fly();                   // 隐式 public abstract

    default void land() {         // Java 8+:默认实现,子类可覆盖
        System.out.println("降落");
    }
}

// 抽象类:包含部分实现 + 模板方法
abstract class Bird {
    String name;
    Bird(String name) { this.name = name; }  // 构造器给子类用

    abstract void sing();                      // 子类必须实现
    void eat() { System.out.println(name + "吃东西"); }  // 子类直接继承
}

// 类可实现多个接口,但只能继承一个抽象类
class Eagle extends Bird implements Flyable { ... }

选型决策:

用接口当:不同类共享行为但无继承关系
  例:鸟、飞机、超人 都实现 Flyable
  例:String、Integer 都实现 Comparable

用抽象类当:多个类有共同属性和部分相同实现
  例:所有动物都有 name 属性 + eat() 方法,但 sing() 各自不同
  例:模板方法模式--流程骨架在抽象类,细节在子类

扩展:为什么 Java 8 要给接口加 default 方法?为了向后兼容--比如 Java 8 在 Collection 接口中加了 stream() 默认方法,如果这是抽象方法,所有 Collection 的实现类(包括你自定义的)全要改代码。default 方法给了老接口"进化"的能力。另外接口可以多继承(一个接口 extends 多个父接口),这是抽象类做不到的。

21. 什么是泛型擦除?有什么影响?

泛型擦除 = 安检只在进门时检查,进来后都一样。编译时 List<String> 和 List<Integer> 是不同的(编译器会检查),但编译后字节码里都是 List(类型信息被擦除了)。这样做的目的是兼容老版本 Java(Java 5 之前没有泛型)。

// 编译前
List<String> list = new ArrayList<>();
list.add("Hello");
String s = list.get(0);      // 不需要强转

// 编译后(泛型被擦除,等价于):
List list = new ArrayList();  // 原始类型
list.add("Hello");
String s = (String) list.get(0); // 编译器自动插入强转

泛型擦除带来的 5 个限制:

1 运行时无法获取泛型类型
   list.getClass() 返回 ArrayList,不是 ArrayList<String>
   if (obj instanceof List<String>)  ← 编译报错!

2 不能用基本类型做泛型参数
   List<int> ← 编译报错,只能 List<Integer>
   原因:擦除后 int 不能当 Object

3 方法签名冲突(桥方法)
   class Parent<T> { void set(T t) {} }
   class Child extends Parent<String> {
       void set(String s) {}  // 编译器生成桥方法 void set(Object o) 保证多态
   }

4 不能创建泛型数组
   T[] arr = new T[10];  ← 编译报错
   List<String>[] arr = new List<String>[10];  ← 编译报错

5 静态方法不能用类的泛型参数
   class Box<T> {
       static T value;  ← 编译报错!(静态方法属于类,不依赖实例,T 无法确定)
   }

通配符(PECS 原则):

// 上界通配符 - Producer(生产者,只读不写)
List<? extends Number> nums;  // 能接受 List<Integer>/List<Double>
Number n = nums.get(0);       // ✅ 读出来一定是 Number
nums.add(1);                  // ❌ 编译报错!不知道具体是什么类型

// 下界通配符 - Consumer(消费者,只写不读)
List<? super Integer> list;   // 能接受 List<Integer>/List<Number>/List<Object>
list.add(1);                  // ✅ 写 Integer 一定安全
Integer i = list.get(0);      // ❌ 编译报错!不知道取出来是什么

PECS 记忆法:Producer Extends, Consumer Super。如果一个集合只往外取数据(生产者),用 ? extends T;如果只往里放数据(消费者),用 ? super T。

扩展:Java 为什么不用 C# 的"真泛型"(运行时保留类型信息)?因为 Java 选择的是迁移兼容性--老代码不加修改就能在 Java 5 上运行。C# 2.0 直接改了 CLR(运行时),老代码需要重新编译。这是两种哲学:Java 选了兼容、C# 选了完整性。现在 Java 也在通过 Valhalla 项目探索在运行时保留部分泛型信息。

22. Java 21 虚拟线程(Virtual Thread)的原理?和传统线程有什么区别?

虚拟线程 = JVM 管理的轻量级线程(Project Loom)。传统 Java 线程是 OS 线程的 1:1 映射,虚拟线程是 M:N 映射--多个虚拟线程运行在少量载体线程(Carrier Thread)上。

// 创建虚拟线程(Java 21+)
Thread vThread = Thread.ofVirtual().start(() -> {
    System.out.println("Hello Virtual Thread");
});

// 虚拟线程池:1 万个任务只占用少量平台线程!
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> Thread.sleep(1000));
    }
}

核心原理:虚拟线程阻塞时(如 Thread.sleep()、Socket.read())会从载体线程卸载,载体线程可以去执行其他虚拟线程。阻塞结束后,虚拟线程重新挂载到载体线程继续执行。由 JVM 自动管理,不需要程序员干预。

对比 传统线程 虚拟线程
调度者 OS 内核 JVM
栈空间 默认 1MB(可调) 动态增长,在堆上
阻塞时 载体线程被占用 载体线程释放
适合场景 CPU 密集 IO 密集

扩展:虚拟线程里不能用 synchronized(会 pin 住载体线程),要用 ReentrantLock。CPU 密集任务不适合虚拟线程--计算不会触发卸载。

23. Java 的 Record 类是什么?解决了什么问题?

Record = 不可变数据载体的语法糖。当你需要一个纯数据类(只有字段 + 访问器,没有业务逻辑),Record 一行搞定。

// 传统写法:一堆样板代码
class User {
    private final String name;
    private final int age;
    User(String name, int age) { this.name = name; this.age = age; }
    String getName() { return name; }
    int getAge() { return age; }
    // 还要重写 equals/hashCode/toString...
}

// Record 写法:编译器自动生成构造器、访问器、equals、hashCode、toString
record User(String name, int age) {}

Record 的规则: - 所有字段隐式 final(不可变) - 不能声明实例字段(只能有 static 字段) - 类是 final 的(不能被继承) - 可以实现接口,但不能继承其他类

和 Lombok @Data 的区别:@Data 生成可变类(有 setter),Record 是不可变类(无 setter)。@Data 可以继承其他类,Record 不能。

扩展:Record 适合做 DTO、模式匹配配合(Java 17+ instanceof 模式匹配)、Map.entry(k, v) 的返回类型就是 Record。

24. 强引用、软引用、弱引用、虚引用有什么区别?使用场景?

强引用 (Strong Reference)
  Object o = new Object();
  → GC 永不回收(只要引用还在)
  → 场景:普通对象引用

软引用 (Soft Reference)
  SoftReference<Object> ref = new SoftReference<>(obj);
  → 内存不够时(OOM 前)才回收
  → 场景:内存敏感缓存(如图片缓存)

弱引用 (Weak Reference)
  WeakReference<Object> ref = new WeakReference<>(obj);
  → 下次 GC 必回收(不管内存够不够)
  → 场景:WeakHashMap、ThreadLocal(见下文)

虚引用 (Phantom Reference)
  PhantomReference<Object> ref = new PhantomReference<>(obj, queue);
  → get() 永远返回 null,只能配合 ReferenceQueue 在对象被回收时收到通知
  → 场景:管理堆外内存(DirectByteBuffer 的 Cleaner)

ThreadLocal 为什么用弱引用(高频追问):

// ThreadLocalMap 的 Entry 设计
Entry extends WeakReference<ThreadLocal<?>> { Object value; }
// key(ThreadLocal)是弱引用,value 是强引用

如果 key 是强引用:线程池场景,线程长期运行,ThreadLocalMap 持有 ThreadLocal 的强引用,即使外部 threadLocal = null,ThreadLocal 也无法被回收 → 内存泄漏!用弱引用后,threadLocal = null 时,下次 GC 会回收 ThreadLocal(Entry.key = null),后续 ThreadLocalMap 会清理这些 Entry。

扩展:用完 ThreadLocal 必须调用 remove()!弱引用只能保证 ThreadLocal 被回收,但 value 还是强引用,不 remove 还是会内存泄漏。

25. JDK 17 ZGC 有哪些改进？

ZGC（Z Garbage Collector）是低延迟 GC，目标是 < 1ms 停顿：

ZGC 核心设计:
  - 染色指针(Colored Pointers)：在对象头64位中染色标记
  - 读屏障(Load Barrier)：读取对象时检查染色位
  - 并发标记+重定位：GC 时和应用线程并发执行
  - 分代 ZGC(JDK 21)：引入年轻代/老年代，减少 GC 开销

JDK 17 改进： - 卸载不使用的类（-XX:+ClassUnloading 默认开启） - 增强 NUMA 支持（多插槽服务器的本地内存访问优化） - 兆字节级堆支持（−Xms512m −Xmx8T）

JDK 21 里程碑：分代 ZGC（Generational ZGC）正式发布，GC 次数大幅减少，吞吐量比 ZGC 提升 10-20%。

扩展：−XX:+UseZGC −Xmx4g 启用；ZGC 的 STW 停顿始终 < 1ms，与堆大小无关；CMS、G1 的停顿随堆增大而增大；延迟敏感服务（金融报价、游戏服务器）首选 ZGC。
