第一章：LangChain 概述

1.1 什么是 LangChain

LangChain 是一个用于构建基于大语言模型（LLM）应用的开发框架，旨在帮助开发者更高效地集成、管理和增强大语言模型的能力，构建端到端的应用程序。

LangChain 提供了一套模块化工具和接口，支持从简单的文本生成到复杂的多步骤推理任务。它已成为大模型开发工程师的标配工具。

1.2 核心价值

LangChain 的核心价值在于简化 LLM 应用程序生命周期的每个阶段：

需求分析 → 模型选择 → Prompt 工程 → 工具集成
  ↓
Agent 构建 → 记忆管理 → 监控调试 → 部署上线

1.3 生态组成

LangChain 生态主要由以下部分组成：

组件 作用
LangChain Core 核心抽象和基类，定义组件接口
LangChain Community 第三方集成（各种 API、数据库、工具）
LangGraph 用于构建有状态、多actor应用的框架（Agent 底层依赖）
LangSmith 调试、监控和评估平台

1.4 LangChain 版本差异

LangChain 从 0.x 到 1.x 经历了重大重构：

  • 0.x：碎片化设计，每种场景有独立的 API（如 create_react_agent、create_json_agent）
  • 1.x：统一 API，通过 create_agent() 一个入口创建所有类型的 Agent，底层由 LangGraph 图结构驱动

补充实战示例

检查运行环境与最小可运行示例（LangChain 1.2.12）：

import langchain
print("LangChain 版本:", langchain.__version__)  # 1.2.12

from langchain.chat_models import init_chat_model
model = init_chat_model("qwen-plus", model_provider="openai")
print(model.invoke("用一句话介绍 LangChain 是什么").content)

安装指定版本：

pip install langchain==1.2.12 langchain-openai langchain-community langchain-core

1.5 为什么需要 LangChain（动机与设计理念）

LangChain 的诞生源于一个根本矛盾：单一大语言模型能力很强，但无法独立构成实用的生产级 AI 应用。

  • 从传统应用到智能体时代：传统软件由人写死逻辑；智能体时代则让 LLM 充当「推理引擎」，自主规划并调用外部资源。
  • 单一 LLM 的三大局限：
    1. 知识滞后——训练数据有截止日期，无法获取实时信息；
    2. 知识缺失与幻觉——遇到训练集未覆盖的领域会编造答案；
    3. 无法行动——本身不能直接查数据库、调 API、读写文件。
  • 结论：要构建真正实用的 AI 应用，必须把 LLM 与外部工具、数据源、记忆机制有机结合——这正是 LangChain 的设计理念，其名称即来自 Lang（语言模型）+ Chain（链式连接），体现「链接模型与各种计算/数据资源」的核心思想。

1.6 LangChain 框架的定位：LLM 与应用间的「中间层」

LangChain 位于大模型与上层应用之间，作为统一的中间层：

  • 统一调用各类大模型（屏蔽 OpenAI / Anthropic / Ollama 等接口差异）；
  • 管理提示词与上下文；
  • 集成外部工具与数据源，快速搭建具备推理与行动能力的智能体。

其核心定位可归纳为三点：

  1. 打通大模型与外部资源：统一接口对接数据库、检索引擎、API、文件系统等；
  2. 封装底层复杂逻辑：抽象工具调用、记忆等能力，降低智能体开发难度；
  3. 支撑多智能体协作：依托 LangGraph 等生态，从单智能体拓展到工业级多智能体系统。

一句话定位：LangChain 是整个生态的「操作系统内核」，是所有上层能力的基础。

1.7 LangChain 的六大典型应用场景

主文档后续章节会深入 RAG、Agent 等，但概述章应先给出应用场景全景：

  1. 检索增强生成（RAG）——解决知识滞后与幻觉，检索外部知识库并向量化后让模型基于最新资料回答。
  2. Agent 智能体构建——将模型作为推理引擎，自主规划并动态调用外部工具（订票、查报告、写 SQL）完成复杂任务。
  3. 对话系统与聊天机器人——通过记忆管理系统解决多轮对话「记忆流失」，结合私有数据提供专业服务。
  4. 多模态应用开发——融合图像识别、语音转文字，让模型具备处理音视频与图片的综合推理能力。
  5. 自动化写作与格式化生成——配合提示词模板与输出解析器，自动产出规范报告、合同、邮件。
  6. 数据连接与结构化处理——从 PDF / Excel 提取关键信息，或实现自然语言与 SQL 的自动转换。

1.9 v0.3「版本碎钞机」之痛 与 v1.2 的范式转变

主文档仅一句话提及 0.x→1.x 重构，课件则有丰富的对比维度，值得补全：

  • v0.3 的痛点：因 API 变动频繁被戏称「版本碎钞机」；团队将原有链和智能体标记为弃用，而 GPT-4 普及后 Function Calling、结构化输出、系统提示词成为模型原生能力，开发者觉得再用 LangChain 封装「多此一举」，导致大规模流失。
  • v1.2 的里程碑：2025.10.20 发布 v1.0.0 与 LangGraph v1.0.0，官方首次明确 API 稳定保证——承诺 2.0 前无破坏性变更；同期完成 1.2 亿美元融资，估值超 12 亿美元。

1.10 LangChain v1.2 的核心模块组成（四包分工）

主文档 1.3 生态表格未提及 langchain-classic，且未解释各包职责，补全如下：

  • langchain-core：官方推荐的核心 API，如 Runnable、BaseMessage 等基础抽象。
  • langchain-classic：把冗余或已不推荐的经典 API（如 0.x 常用、1.x 移除的 API）迁入此处，保持主包轻量。
  • langchain-community：第三方集成（如 langchain-openai、langchain-anthropic 等合作伙伴包），按需安装、避免臃肿。
  • langgraph：深度整合 LangGraph 1.0，协调多个 Chain / Agent / Tool 完成复杂任务，支持循环调用，是 LangChain 的图形化增强版。

学习策略：不要试图学完所有 API，把它当「工具箱」——搞懂核心逻辑与核心模块，用到什么再查什么。

1.11 LangChain 家族「四大支柱」：从框架到智能体生态

截至 2025.11，LangChain 已从独立框架成长为覆盖智能体全生命周期的技术生态，由四大核心支柱构成：

支柱 定位 角色层
LangChain 智能体开发基石，提供模型调用、工具/中间件集成、Agent 构建 基础能力层
LangGraph 复杂工作流的编排引擎 运行时编排层
Deep Agent 智能体的执行框架（Agent Harness） 智能体抽象层
LangSmith 可视化监控与测试平台 监控与评估层

四者共同构成「从技术验证到生产部署、从单体智能到复杂协作」的项目闭环。

1.12 Deep Agent：智能体执行框架（Agent Harness）

这是主文档完全缺失的新组件。Deep Agent 被定位为 Agent Harness（智能体执行框架），构建于 LangChain 与 LangGraph 之上，让开发者无需从零构建控制逻辑即可获得深度能力。

核心能力：

  • 显式规划：自主生成、执行并动态调整多步任务计划；
  • 虚拟文件系统：为智能体提供结构化的中间结果与知识存储；
  • 子智能体：支持任务在多个智能体间分解与协作；
  • 长期记忆：结合 LangGraph 状态存储，实现跨对话经验积累；
  • 可扩展中间件：允许嵌入安全审计、性能监控或自定义业务逻辑。

1.13 三大框架的关系：能力抽象层 vs 执行编排层 vs 执行框架

课件强调三者不是竞争关系，而是可叠加的三层，复杂项目完全可以同时用到：

  • LangChain = 能力抽象层（LLM / Tool / Message 标准化）——负责「有什么能力」；
  • LangGraph = 执行与编排层（状态机 / 工作流 / 多 Agent 系统）——负责「怎么跑」；
  • Deep Agent = 执行框架——在二者之上赋予 Agent 更强的自主规划与协作能力。

官方口诀：「快速起步用 LangChain，复杂控制用 LangGraph，二者并行协同；再用 Deep Agents 赋予 Agent 更强的自主能力」——这才是完整的 LangChain 生态玩法。

2.6 模型调用方法

LangChain 提供了多种调用方式，适用于不同场景：

方法 模式 说明 典型场景
invoke() 同步阻塞 一次性返回完整结果 简单问答、批处理
stream() 流式输出 实时逐 token 返回 聊天机器人、长文本生成
batch() 批量并行 多条请求并行处理 文档摘要、批量问答
ainvoke() 异步非阻塞 不等待即可继续执行 高并发 Web 应用
astream() 异步流式 异步+流式组合 实时交互应用
abatch() 异步批量 异步+批量组合 大规模数据处理

invoke() — 同步调用

最基本的方式，程序等待模型完全生成响应后一次性返回：

response = model.invoke("翻译成英文：你好世界")
print(response.content)  # Hello World

stream() — 流式输出

实时返回每个生成的 token，避免等待时间长时的"假死"体验：

for chunk in model.stream("写一首七言律诗"):
    print(chunk.text, end="", flush=True)

batch() — 批量处理

一次性发送多条独立请求，模型并行处理：

questions = [
    "你好，你是谁？",
    "2 + 3 * 5 = ?",
    "中国首都在哪里？"
]

responses = model.batch(questions)
for r in responses:
    print(r.content)

性能对比：批量调用 vs 循环 invoke，批量可节省约 50% 时间。

ainvoke() — 异步调用

不阻塞主线程，在等待 API 响应时可以执行其他任务：

import asyncio

async def demo():
    print("发起异步调用...")
    task = asyncio.create_task(model.ainvoke("用一句话解释AI"))

    # 并行执行其他任务
    for i in range(3):
        await asyncio.sleep(1)
        print(f"执行其他任务 {i+1}...")

    response = await task
    print(f"AI回复: {response.content}")

asyncio.run(demo())

3.1 为什么需要消息系统

大模型本身是无状态的（Stateless），不维护会话历史。每次调用都是独立的。

为了让模型理解对话上下文，需要在每次请求时手动传入历史消息列表。消息系统正是负责这件事的核心组件。

3.2 消息类型

LangChain 提供了四种核心消息类型：

角色 字典格式 对象格式 作用 示例
System {"role": "system", ...} SystemMessage(...) 设定 AI 行为规则和角色 "你是一个专业的数学老师"
User {"role": "user", ...} HumanMessage(...) 用户输入 "什么是微积分？"
Assistant {"role": "assistant", ...} AIMessage(...) AI 历史回复 "微积分是研究变化的数学分支..."
Tool {"role": "tool", ...} ToolMessage(...) 工具执行结果 {"content": "北京晴天", "tool_call_id": "call_123"}

3.3 消息格式对比

字典格式（推荐生产使用，JSON 兼容）：

messages = [
    {"role": "system", "content": "你是一个专业的Python导师"},
    {"role": "user", "content": "什么是装饰器？"},
    {"role": "assistant", "content": "装饰器是一种设计模式..."},
    {"role": "user", "content": "能给个例子吗？"}
]

response = model.invoke(messages)

对象格式（适合大型项目，IDE 类型检查友好）：

from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

messages = [
    SystemMessage(content="你是一个专业的Python导师"),
    HumanMessage(content="什么是装饰器？"),
    AIMessage(content="装饰器是一种设计模式..."),
    HumanMessage(content="能给个例子吗？")
]

response = model.invoke(messages)

3.4 多轮对话的关键：传递历史

不传历史 = 失忆：

# 第一次对话
messages1 = [HumanMessage("你好，我叫小明")]
response1 = model.invoke(messages1)  # AI: 你好，小明！

# 第二次对话（不传历史）
messages2 = [HumanMessage("我叫什么名字？")]
response2 = model.invoke(messages2)  # AI: 我不知道你的名字

# 原因：两次调用是完全独立的，模型不记得第一次对话

传历史 = 记住上下文：

# 在 messages 中追加历史
conversation = [
    SystemMessage("你是一个友好的AI助手"),
    HumanMessage("你好，我叫小明"),
]
response = model.invoke(conversation)

# 追加 AI 回复
conversation.append(AIMessage(content=response.content))

# 追加下一个问题
conversation.append(HumanMessage("我叫什么名字？"))

# 再次调用
response = model.invoke(conversation)  # AI: 你叫小明

3.5 LangChain Expression Language (LCEL)

LCEL 是 LangChain 的管道表达式，将组件像管道一样链接在一起：

from langchain_core.output_parsers import StrOutputParser

# 使用管道符 `|` 将 model 和 parser 连接
chain = model | StrOutputParser()

# 调用链
result = chain.invoke("你好")
# 等价于: model.invoke("你好") → StrOutputParser().invoke(result)

LCEL 的优势：

  • 声明式：直观表达数据处理流程
  • 统一接口：所有 Runnable 对象都可以用 .invoke() / .stream() / .batch() 调用
  • 内置优化：批量、流式、异步自动处理

补充实战示例

系统 / 用户 / 助手多角色拼接多轮对话：

from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

msgs = [
    SystemMessage("你是一位严谨的英语翻译"),
    HumanMessage("把『今天天气真好』译成英文"),
    AIMessage("The weather is really nice today."),
    HumanMessage("换成更口语的说法"),
]
print(model.invoke(msgs).content)

3.6 ToolMessage 的完整用法

ToolMessage 用于将工具执行结果返回给模型，关键参数：

  • content：工具返回的内容（必填）
  • tool_call_id：工具调用唯一 ID，必须与 AIMessage 中 tool_calls 的 id 匹配
  • name：工具名称（可选）
from langchain_core.messages import AIMessage, ToolMessage, HumanMessage
from langchain.chat_models import init_chat_model

model = init_chat_model("qwen-plus", model_provider="openai")

# 模拟 AI 消息（包含工具调用）
ai_message = AIMessage(
    content="",
    tool_calls=[{
        "name": "get_weather",
        "args": {"city": "北京"},
        "id": "call_00_abc123"  # 工具调用ID
    }]
)

# 工具返回消息（tool_call_id 必须匹配）
tool_message = ToolMessage(
    content="北京今天晴天，温度15°C",
    tool_call_id="call_00_abc123",  # 与上面的 id 一致
    name="get_weather"
)

messages = [
    HumanMessage(content="北京天气如何？"),
    ai_message,
    tool_message
]

response = model.invoke(messages)
print(response.content)  # 基于工具结果生成最终回答

JSON 字典格式写法：

tool_message = {
    "role": "tool",
    "content": "北京天气晴朗",
    "tool_call_id": "call_00_abc123"
}

3.7 AIMessage 的完整字段说明

AIMessage 包含多个重要属性：

1. content：模型输出的原始文本

2. tool_calls：工具调用信息列表（当模型决定调用工具时）

response = model_with_tools.invoke("北京天气如何？")

if response.tool_calls:
    for call in response.tool_calls:
        print(f"工具名: {call['name']}")      # get_weather

        print(f"调用ID: {call['id']}")        # call_xxx
        print(f"类型: {call['type']}")        # tool_call

3. response_metadata：模型响应的元数据

print(metadata['model_name'])      # gpt-4o-mini
print(metadata['finish_reason'])   # stop
print(metadata['token_usage'])     # Token消耗详情

4. usage_metadata：Token 使用量（简化版）

usage = response.usage_metadata
print(f"输入tokens: {usage['input_tokens']}")
print(f"输出tokens: {usage['output_tokens']}")
print(f"总计: {usage['total_tokens']}")

完整示例：

from langchain.chat_models import init_chat_model

3.9 content_blocks：LangChain 1.2 统一多模态数据结构

content_blocks 是 LangChain 1.2 引入的跨模型标准化多模态数据结构，用于统一处理文本、图片、音频、视频等内容。

核心优势：

  • 一套代码兼容 OpenAI、Anthropic、Gemini 等不同供应商
  • 统一的输入输出格式，无需针对不同模型写适配代码

输入格式化（多模态内容）：

from langchain.messages import HumanMessage
from langchain.chat_models import init_chat_model
import base64

model = init_chat_model("qwen-plus", model_provider="openai")

def encode_image(img_path):
    with open(img_path, "rb") as f:
        return base64.b64encode(f.read()).decode()

base64_image = encode_image("photo.png")

# 使用 content_blocks（推荐）
response = model.invoke([
    HumanMessage(
        content_blocks=[
            {"type": "text", "text": "这张图里有什么？"},
            {
                "type": "image",
                "base64": base64_image,
                "mime_type": "image/png"
            }
        ]
    )
])
print(response.content)

输出格式化（统一解析不同模型的响应）：

对于 DeepSeek 等输出包含"思考内容"的模型，content_blocks 可统一提取：

model = init_chat_model(
    model="deepseek:deepseek-r1",
    extra_body={"thinking": {"type": "enabled"}}
)

response = model.invoke("你好")

# 使用 content_blocks 统一解析
for block in response.content_blocks:
    if block["type"] == "reasoning":
        print(f"思考过程: {block['reasoning']}")
    elif block["type"] == "text":
        print(f"最终回答: {block['text']}")

支持的内容块类型：

type 说明 字段示例
text 文本内容 {"type": "text", "text": "你好"}
image 图片 {"type": "image", "base64": "...", "mime_type": "image/png"}
audio 音频 {"type": "audio", "base64": "...", "mime_type": "audio/mp3"}
video 视频 {"type": "video", "base64": "...", "mime_type": "video/mp4"}
tool_call 工具调用 自动包含在 AIMessage 中
reasoning 思维链 DeepSeek R1 等推理模型的思考过程

注意：content_blocks 是懒加载的，调用时才解析。

4.7 ChatPromptTemplate 三种调用方法的区别

方法 返回类型 用途
invoke(vars) ChatPromptValue 直接传给模型（推荐）
format(vars) str 生成可读字符串（调试用）
format_messages(vars) list[BaseMessage] 获取消息列表对象 
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是{role}"),
    ("human", "{question}")
])

# 方式1：invoke() 返回 ChatPromptValue（可直接传给模型）
result1 = prompt.invoke({"role": "翻译", "question": "你好"})
print(type(result1))  # <class 'ChatPromptValue'>
# 直接传模型：model.invoke(result1)

# 方式2：format() 返回字符串
result2 = prompt.format(role="翻译", question="你好")
print(type(result2))  # <class 'str'>
print(result2)
# System: 你是翻译
# Human: 你好

# 方式3：format_messages() 返回消息列表
result3 = prompt.format_messages(role="翻译", question="你好")
print(type(result3))  # <class 'list'>
print(result3[0])     # SystemMessage(content='你是翻译')

4.9 对话历史管理实战函数

当对话历史过长时，需要裁剪以节省 Token：

def keep_recent_messages(messages, max_pairs=3):
    """
    保留最近的 N 轮对话
    
    参数:
        messages: 消息列表
        max_pairs: 保留的对话轮数（每轮 = user + assistant）
    
    返回:
        裁剪后的消息列表（保留 system + 最近对话）
    """
    # 分离 system 消息和对话消息
    system_msgs = [m for m in messages if m.get("role") == "system"]
    conversation_msgs = [m for m in messages if m.get("role") != "system"]
    
    # 只保留最近 N 轮（每轮2条消息）
    recent_msgs = conversation_msgs[-(max_pairs * 2):]
    
    # 返回：system + 最近对话
    return system_msgs + recent_msgs

# 使用示例
conversation = [
    {"role": "system", "content": "你是Python导师"}
]

# 模拟多轮对话...
conversation.append({"role": "user", "content": "什么是列表？"})
conversation.append({"role": "assistant", "content": "列表是..."})
conversation.append({"role": "user", "content": "列表和元组区别？"})
conversation.append({"role": "assistant", "content": "元组不可变..."})
conversation.append({"role": "user", "content": "什么是字典？"})
conversation.append({"role": "assistant", "content": "字典是键值对..."})

print(f"原始消息数: {len(conversation)}")  # 7条

# 裁剪为最近2轮
optimized = keep_recent_messages(conversation, max_pairs=2)
print(f"优化后消息数: {len(optimized)}")  # 5条（1个system + 2轮×2条）

第五章：LCEL 与 Runnable 接口进阶

5.1 什么是 Runnable

LangChain 中所有组件都实现了统一的 Runnable 接口，这意味着它们都支持 invoke / batch / stream / ainvoke / astream / abatch 六种调用方式。只要组件实现了 Runnable，就能用管道符 | 自由组合。

from langchain_core.runnables import RunnableLambda, RunnablePassthrough

# 任何函数都能包成 Runnable
double = RunnableLambda(lambda x: x * 2)
print(double.invoke(3))  # 6

5.2 RunnablePassthrough（透传）

把输入原样传给下一步，常用于「在链中保留原始变量」：

from langchain_core.runnables import RunnablePassthrough

# prompt 需要 {question} 和 {context} 两个变量
# 用 Passthrough 把 question 原样传递，context 由检索器注入
retrieval_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)

answer = retrieval_chain.invoke("什么是 LangChain？")

5.3 RunnableParallel（并行分支）

用字典语法一次性并行执行多个分支，最后汇集成一个字典：

from langchain_core.runnables import RunnableParallel

parallel = RunnableParallel({
    "poem": poem_chain,        # 生成诗歌
    "summary": summary_chain,  # 生成摘要
})

result = parallel.invoke("春天")
print(result["poem"])
print(result["summary"])

5.4 RunnableLambda（包装函数）

把任意 Python 函数接入链中，做格式转换、清洗等：

import json
from langchain_core.runnables import RunnableLambda

# 把模型输出解析为 JSON
parse_json = RunnableLambda(lambda text: json.loads(text))

chain = model | StrOutputParser() | parse_json

5.5 RunnableBranch（条件路由）

根据条件把输入路由到不同子链（类似 if/else）：

from langchain_core.runnables import RunnableBranch

branch = RunnableBranch(
    (lambda x: "代码" in x, code_chain),      # 条件1成立走 code_chain
    (lambda x: "翻译" in x, translate_chain), # 条件2成立走 translate_chain
    default_chain,                             # 兜底
)

result = branch.invoke("帮我翻译这段话")

5.6 综合示例：检索增强问答链

from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_template(
    "根据上下文回答：\n{context}\n\n问题：{question}"
)

rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)

# 一次 invoke 完成：检索 → 拼提示词 → 调模型 → 解析
print(rag_chain.invoke("LangChain 的核心价值是什么？"))

5.7 流式输出

任意 Runnable 链都能 .stream()，逐块拿到结果：

第七章：LangSmith 的使用

7.1 什么是 LangSmith

LangSmith 是 LangChain 生态中专门用于 LLM 应用调试、监控、评估和管理 的平台。

7.2 核心功能

功能 作用
Tracing（追踪） 记录每次 LLM 调用的详细信息，包括 Prompt、响应、Token 消耗、每个节点耗时
Monitoring（监控） 查看 Token 消耗趋势、QPS、错误率、平均延迟
Datasets & Experiments 管理测试数据集，运行 Prompt/模型版本对比实验
Evaluators（评估器） 配置基于规则或 LLM 的自动打分（答案相关性、幻觉检测）
Annotation Queues 人工反馈与数据清洗，高质量标注数据用于微调
Playground 网页端交互界面，无需代码即可测试 Prompt

7.2.1 LangSmith 功能全景（三大类）

LangSmith 的能力可归为三大类：

  • 核心应用与开发：Tracing（追踪）、Monitoring（监控）、Datasets & Experiments（数据集与实验）、Evaluators（评估器）、Annotation Queues（标注队列）
  • 提示词与调试工具：Prompts（提示词版本管理，类似“提示词版 GitHub”，支持 v1/v2 与团队协作）、Playground（网页演练场）、Studio（与 LangGraph 深度集成的可视化调试，可在节点间“暂停”并手动修改状态后再继续）、Context Hub（存放可复用的全局上下文/公共模板）
  • 部署与沙盒：Deployments（基于 LangGraph Cloud 一键部署为生产 API，处理并发/队列/持久化）、Sandboxes（轻量在线沙盒，安全试运行 Agent）

进阶建议：入门阶段重点关注 Tracing（观察调用细节）和 Playground（快速调优提示词）；当应用变复杂（多 Agent 协同、复杂 RAG）时，再引入 Datasets 做量化评估、用 Studio 做可视化调试。

第八章：回调系统 Callbacks

8.1 回调的作用

Callbacks 是 LangChain 的事件钩子机制，让你在不改动链代码的前提下，监听「模型开始/结束」「链开始/结束」「token 生成」等事件，实现日志、计费、流式 UI 更新等需求。

8.2 自定义回调处理器

继承 BaseCallbackHandler，重写感兴趣的事件方法：

from langchain_core.callbacks import BaseCallbackHandler

class MyLogger(BaseCallbackHandler):
    def on_llm_start(self, serialized, prompts, **kwargs):
        print(f"[LLM开始] 提示词: {prompts[0][:50]}...")

    def on_llm_end(self, response, **kwargs):
        print(f"[LLM结束] token数: {response.llm_output['token_usage']}")

    def on_llm_new_token(self, token, **kwargs):
        print(token, end="", flush=True)  # 实时打印每个 token

# 调用时传入 callbacks
chain = prompt | model | StrOutputParser()
chain.invoke("讲个笑话", config={"callbacks": [MyLogger()]})

8.3 常用回调事件

事件方法 触发时机
on_llm_start 模型调用前
on_llm_new_token 每生成一个 token（流式）
on_llm_end 模型返回后
on_chain_start / on_chain_end 链开始 / 结束
on_tool_start / on_tool_end 工具调用前 / 后
on_retriever_start / on_retriever_end 检索前 / 后

8.4 与 LangSmith 的关系

LangSmith（第七章）底层正是通过 Callback 实现追踪的。两者可并存：

第九章：Tools 工具调用

9.1 为什么需要工具

仅有生成文本的能力，大模型只能"纸上谈兵"。工具让大模型能够与外部世界交互，从而执行搜索、计算、调用 API、读写文件等操作，让 AI 从"认识世界"走向"改变世界"。

9.2 工具的定义

在 LangChain 中，工具是明确定义了输入输出的可调用函数（即函数调用/Function Calling）。

使用 @tool 装饰器（推荐）

from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """获取指定城市的天气信息
    
    参数:
        city: 城市名称，如"北京"、"上海"
    
    返回:
        天气信息字符串
    """
    # 实际实现中这里会调用天气API
    return f"{city}晴天，温度15°C"

# 直接调用工具
result = get_weather.invoke({"city": "北京"})
print(result)  # 北京晴天，温度15°C

注意：@tool 装饰器会从函数的 docstring（文档字符串）中自动提取工具描述，这是 AI 理解工具用途的关键。

9.3 将工具绑定到模型

这是让 AI 自己决定是否调用工具 的核心步骤：

# 将工具绑定到模型
model_with_tools = model.bind_tools([get_weather])

# 提问（AI 会判断是否需要调用工具）
response = model_with_tools.invoke("北京今天天气如何？")

# 检查是否有工具调用
if response.tool_calls:
    print("AI 想调用工具：", response.tool_calls)
    # 输出示例：
    # [{'name': 'get_weather', 'args': {'city': '北京'}, 'id': 'call_xxx', 'type': 'tool_call'}]
else:
    print("AI 直接回答：", response.content)

9.4 完整工具调用流程

大模型决定调用工具后，需要开发者手动执行工具并将结果传回模型：

用户提问 → 模型判断需调用工具 → 返回 ToolCall
    ↓
开发者执行工具 → 生成 ToolMessage
    ↓
将 ToolMessage 传回模型 → 模型生成最终回答

from langchain.messages import HumanMessage, ToolMessage

# 第一步：用户提问，模型生成工具调用请求
response = model_with_tools.invoke([HumanMessage("今天北京天气如何")])

# 第二步：从响应中提取工具调用信息
tool_calls = response.tool_calls
for tool_call in tool_calls:
    if tool_call["name"] == "get_weather":
        # 执行工具（@tool 修饰的函数可自动生成 ToolMessage）
        tool_result = get_weather.invoke(tool_call)
        print(type(tool_result))  # <class 'ToolMessage'>
        
        # 第三步：将工具结果追加到消息列表
        messages.append(tool_result)

# 第四步：将完整消息传回模型，生成最终回答
final_response = model_with_tools.invoke(messages)
print(final_response.content)  # 北京今天是晴天☀，是个好天气！

9.5 不使用 @tool 时的手写版

如果函数没有 @tool 修饰，需要手动拼接 ToolMessage：

from langchain.messages import HumanMessage, ToolMessage

@tool 装饰器参数详解

9.9 description 参数

# @tool 优先级：description 参数 > docstring 第一行
@tool(description="根据城市名称查询当日天气的工具")
def get_weather(city: str):
    """天气查询工具"""   # 会被忽略
    return f"{city}晴"

9.10 parse_docstring=True（推荐开启）

默认 @tool 将整个 docstring 视为 description；开启后会自动解析 Google 风格 docstring，将 Args: 中的参数说明填充到各参数的 description 字段：

from langchain_core.tools import tool

@tool(parse_docstring=True)
def get_weather(city: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """
    获取当日天气，可选择是否同时查询未来五日天气预报

    Args:
        city: 城市
        units: 气温单位，可选：celsius-摄氏度，fahrenheit-华氏度
        include_forecast: 是否包含未来五日的天气预报
    """
    temp = 22 if units == "celsius" else 72
    result = f'{city}当天气温: {temp}°'
    if include_forecast:
        result += "\n未来五天都是晴天"
    return result

# 生成的工具描述中，每个参数都有独立的 description
# 不开 parse_docstring 时，所有 Args 内容都堆在同一个 description 里

9.11 name_or_callable 参数

# 方式1：显式命名
@tool(name_or_callable="getWeather")
def get_weather(city: str):

# 方式2：简写

args_schema 参数：Pydantic 模型与 JSON Schema

当工具参数较复杂（需要枚举值、范围限制、验证逻辑）时，使用 args_schema 提供精确的参数模式。

9.12 方式一：Pydantic 模型

from pydantic import BaseModel, Field
from typing import Literal
from langchain_core.tools import tool

class WeatherInput(BaseModel):
    city: str = Field(default="北京", description="城市名称")
    unit: Literal["celsius", "fahrenheit"] = Field(
        default="celsius",
        description="气温单位"
    )
    include_forecast: bool = Field(
        default=False,
        description="是否包含未来五日天气预报"
    )

@tool(args_schema=WeatherInput)
def get_weather(city: str, unit: str = "celsius", include_forecast: bool = False) -> str:
    """获取当日天气"""
    temp = 22 if unit == "celsius" else 72
    result = f'{city}当天气温: {temp}°'
    if include_forecast:
        result += "\n未来五天都是晴天"
    return result

# 使用 Pydantic 模型后：
# - Literal 类型参数会生成 'enum' 字段，限制 AI 只能传枚举值
# - Field 的 description 会成为参数的 description
# - Field 的 default 决定是否必填（无 default → required）

9.13 方式二：JSON Schema 字典

适合参数结构需运行时动态生成的场景：

from langchain_core.tools import tool

weather_schema = {
    "type": "object",
    "properties": {
        "location": {"type": "string"},
        "units": {"type": "string"},
        "include_forecast": {"type": "boolean"}
    },
    "required": ["location", "units", "include_forecast"]
}

@tool(args_schema=weather_schema)
def get_weather(city: str, unit: str = "celsius", include_forecast: bool = False) -> str:
    """获取当日天气"""
    return f"{city}当天气温 22°"

注意： JSON Schema 方式下，函数签名中的参数名（如 city）与 schema 中的 key（如 location）可以不一致 —— schema 中的名称才是 AI 看到的参数名。

bind_tools 的 tool_choice 参数：强制使用工具

tool_choice 控制模型是否必须调用工具，取值如下：

值 含义 示例
"none" 绝不调用工具 即使问天气，模型也不调用
"auto" 默认值，模型自主决定 问天气则调用，问"你好"则不调用
"required" 必须调用工具 即使问"你好"，模型也会调用天气工具
"any" 等价于 required 同上
"工具名" 强制调用特定工具 无论问什么，都调用指定工具 
# 强制不使用工具（模型会拒绝调用）
model_with_tools = model.bind_tools([get_weather], tool_choice="none")
response = model_with_tools.invoke([HumanMessage("北京天气如何")])
# 模型返回纯文本："我无法直接获取实时天气数据"

# 强制使用工具（即使不需要也会调用）
model_with_tools = model.bind_tools([get_weather], tool_choice="required")
response = model_with_tools.invoke([HumanMessage("你好啊")])
# 模型仍返回 ToolCall，参数为默认值 city="北京"

# 强制调用特定工具
model_with_tools = model.bind_tools(
    [get_weather_v1, get_weather_v2],
    tool_choice="get_weather_v2"   # 指定调用哪个
)

大模型每次推理只调用一轮工具，当一个问题需要调用多个工具时，需开发者管理循环：

from langchain_core.tools import tool

@tool(parse_docstring=True)
def get_stock_price(company: str, timeframe: str = "today") -> str:
    """获取指定公司的股票价格信息

    Args:
        company: 公司名称
        timeframe: 时间范围（today/week/month）
    """
    return f"{company} {timeframe}价格: 185.20美元"

@tool(parse_docstring=True)
def search_news(company: str) -> str:
    """搜索指定公司的财经新闻

    Args:
        company: 公司名称
    """
    return f"{company}最近发布了新产品"

model_with_tools = model.bind_tools([get_stock_price, search_news])
messages = [HumanMessage("苹果公司今天的股价是多少？最近有什么新闻？")]

# while 循环：模型每次返回后检查 tool_calls，无工具调用则退出
while True:
    response = model_with_tools.invoke(messages)
    messages.append(response)

    if not response.tool_calls:
        break  # 没有工具调用，退出循环

    for tool_call in response.tool_calls:
        if tool_call["name"] == "get_stock_price":
            tool_result = get_stock_price.invoke(tool_call)
        elif tool_call["name"] == "search_news":
            tool_result = search_news.invoke(tool_call)
        else:
            raise Exception(f"不存在的工具: {tool_call['name']}")
        messages.append(tool_result)

for msg in messages:
    msg.pretty_print()

工具异常处理与重试机制

9.14 三层防护

第1层：工具内部处理

@tool
def safe_divide(a: float, b: float) -> str:
    """
    除法计算

    Args:
        a: 被除数
        b: 除数
    """
    try:
        if b == 0:
            return "错误：除数不能为零"
        result = a / b
        return f"{a} / {b} = {result}"
    except Exception as e:
        return f"计算错误：{e}"

第2层：Agent 级重试（通过 prompt）

agent = create_agent(
    model=model,
    tools=[...],
    system_prompt="如果工具失败，尝试使用其他方法解决问题。"
)

第3层：调用级重试（使用 @retry）

from tenacity import retry, stop_after_attempt

@retry(stop=stop_after_attempt(3))
def call_agent(question):
    """最多尝试 3 次（第1次正常调用 + 2次重试），3次都失败才抛出异常"""
    return agent.invoke({"messages": [{"role": "user", "content": question}]})

9.15 工具返回值建议：返回字符串

LangChain 强烈建议工具返回 str 而非 dict，避免大模型受到 Unicode 编码干扰：

import json

# ✅ 好：返回字符串
@tool
def get_user_info(user_id: str) -> str:
    user = {"id": user_id, "name": "张三"}
    return json.dumps(user, ensure_ascii=False)  # '{"id": "123", "name": "张三"}'

# ❌ 不好：返回字典
@tool
def get_user_info(user_id: str) -> dict:
    return {"id": user_id, "name": "张三"}
    # 强制转字符串时中文可能变成 \u5f20\u4e09，干扰大模型

工具的最佳实践

  1. 清晰的 docstring：使用 Google 风格，完整描述工具用途和每个参数。docstring 是 AI 理解工具用途的关键依据。

  2. 功能单一：每个工具只做一件事，不要把多个功能塞进一个工具。

  3. 参数类型完整：所有参数都要有类型注解，否则 convert_to_openai_tool 无法生成正确的参数类型信息。

  4. 善用 parse_docstring=True：开启后 Google 风格 docstring 的 Args: 内容会自动填充到各参数的 description 字段，效果比 Pydantic Field 更简洁。

  5. 同步 vs 异步选择：

    • 同步工具 @tool：适合 CPU 密集型、简单场景
    • 异步工具 @tool + async def：适合 IO 密集型（API 调用、数据库操作）
# 同步
@tool
def sync_tool(x: str) -> str:
    return process(x)

# 异步（async def）
@tool
async def async_tool(x: str) -> str:
    return await async_api_call(x)

第十章：结构化输出

10.1 为什么需要结构化输出

默认情况下，模型返回的是纯文本。如果你要把模型结果接入程序（写入数据库、调用 API、做条件判断），纯文本需要额外的正则或 json.loads 解析，既不稳健又容易出错：模型可能输出 "json ... " 包裹、前后带说明文字、字段名大小写不一致等。

with_structured_output 让模型直接返回结构化对象（Pydantic 对象、字典等），无需手动解析。对比：

方式 做法 问题
传统方式 让模型输出 JSON 文本，再用 json.loads 解析 格式不稳定，解析易失败
结构化输出 把结构定义交给 with_structured_output，模型直接返回对象 稳定、类型安全、自动校验

其底层原理是：LangChain 把你的结构定义转成 JSON Schema 注入系统提示词，并以强约束方式要求模型遵守输出格式，返回后自动解析并（在 Pydantic 模式下）做类型校验。

10.2 四种支持的数据结构

LangChain 1.x 的 with_structured_output 支持四种结构定义方式：

  1. Pydantic 模型（最常用、最健壮，支持类型校验）
  2. TypedDict（轻量，适合不想引入 Pydantic 校验的场景）
  3. JSON Schema 字典（第三方 / 无 Pydantic 依赖时）
  4. @dataclass（已有 dataclass 代码复用）

10.3 Pydantic 模式（最常用）

① 基本用法

from pydantic import BaseModel

# 定义期望的输出结构
class Person(BaseModel):
    name: str
    age: int
    gender: str = "未知"        # 可选字段，有默认值
    skills: list[str]           # 列表类型

# 绑定结构化输出
model_with_structure = model.with_structured_output(Person)

# 调用
result = model_with_structure.invoke(
    "张三，男，30岁，拥有8年编程开发经验，熟悉Python和Java"
)

# 直接访问属性，无需解析
print(result.name)        # 张三
print(result.age)         # 30
print(result.gender)      # 男
print(result.skills)      # ['Python', 'Java']

② 可选字段与默认值（Optional / 默认值）

from typing import Optional
from pydantic import BaseModel

class Person(BaseModel):
    name: str
    age: int
    gender: str = "未知"            # 给默认值
    address: Optional[str] = None   # 允许缺失，缺失时为 None

③ 枚举 / 字面值约束（Literal）

把取值限定为固定集合，避免模型自由发挥：

from typing import Literal
from pydantic import BaseModel

class Person(BaseModel):
    name: str
    age: int
    gender: Literal["男", "女", "未知"] = "未知"

④ 列表提取（list[...]）

class Person(BaseModel):
    name: str
    skills: list[str]          # 自动抽取多个技能
    previous_companies: list[str]

⑤ 嵌套结构（建议 ≤ 3 层）

支持子模型嵌套，但层级过深会增加模型出错概率，实践建议不超过 3 层：

from typing import Optional
from pydantic import BaseModel

class Address(BaseModel):
    city: str
    district: Optional[str] = None

class Employee(BaseModel):
    name: str
    age: int
    address: Address                 # 嵌套子结构
    previous_companies: list[str]

model = model.with_structured_output(Employee)
result = model.invoke("李四，28岁，家住北京朝阳区，曾在阿里和腾讯工作")
print(result.model_dump())

⑥ 字段校验约束（Field）

用 Field 加约束，模型返回不符合约束时 Pydantic 会抛 ValidationError：

from pydantic import BaseModel, Field

class Person(BaseModel):
    name: str = Field(min_length=1, max_length=10)   # 字符串长度约束
    age: int = Field(ge=0, le=120)                    # 数值范围约束（>=0, <=120）

class Point(BaseModel):
    x: float = Field(gt=0)    # 大于 0
    y: float = Field(lt=0)    # 小于 0

补充实战示例 —— 嵌套提取联系人信息：

from pydantic import BaseModel
from typing import List

class Contact(BaseModel):
    name: str
    emails: List[str]

extractor = model.with_structured_output(Contact)
c = extractor.invoke("王五的邮箱是 wang@a.com 和 w@b.com")
print(c.name, c.emails)   # 王五 ['wang@a.com', 'w@b.com']

10.4 TypedDict 模式

不想引入 Pydantic 校验时，可用 TypedDict。用 Annotated[..., "描述"] 给字段加说明，描述用 ... 占位表示"沿用类型本身说明"：

from typing import TypedDict, Annotated, List

class Person(TypedDict):
    name: str
    age: Annotated[int, "用户年龄（岁）"]
    skills: Annotated[List[str], "掌握的技能列表"]

model_with_structure = model.with_structured_output(Person)
result = model_with_structure.invoke("张三，30岁，会Python和Java")
print(result["name"], result["age"], result["skills"])

注意：TypedDict 模式只做解析、不做类型校验。若模型返回了错误类型（如 age 返回字符串），不会抛异常，可能得到脏数据。

10.5 JSON Schema 模式

直接传一个 JSON Schema 字典，适合无法使用 Pydantic / TypedDict 的第三方场景。需指定 method="json_schema"：

json_schema = {
    "title": "joke",                          # 结构名称
    "description": "Joke to tell user.",      # 结构用途说明
    "type": "object",
    "properties": {                           # 字段定义
        "setup": {
            "type": "string",
            "description": "The setup of the joke",
        },
        "punchline": {
            "type": "string",
            "description": "The punchline to the joke",
        },
    },
    "required": ["setup", "punchline"],       # 必填字段
}

structured_llm = model.with_structured_output(
    json_schema,
    method="json_schema",
    name="joke",
    description="Joke to tell user.",
)
structured_llm.invoke("讲个程序员笑话")

JSON Schema 关键字说明：

  • title / description：结构与字段的人类可读描述，帮助模型理解
  • type：字段类型（string / integer / number / array / object 等）
  • properties：各字段的 schema
  • required：必填字段列表

10.6 @dataclass 模式

已有 @dataclass 定义的类时，可直接复用：

from dataclasses import dataclass

@dataclass
class Joke:
    setup: str
    punchline: str

structured_llm = model.with_structured_output(Joke)
structured_llm.invoke("讲个程序员笑话")

10.7 工作原理图解（四步）

定义结构               协议转换                  模型交互                      自动解析与校验
(Pydantic /            LangChain 调用            JSON Schema 注入系统提示词，  解析 JSON ->
 TypedDict /           model_json_schema()       以 strict grammar sampling     构造对象
 JSON Schema /  ───▶   转为 JSON Schema   ───▶    强约束输出格式        ───▶   （Pydantic 模式
 @dataclass)                                                  │                    还会做类型校验）
                                                            ▼
                                                  模型严格按 schema 返回 JSON
  1. 定义结构：你用 Pydantic / TypedDict / JSON Schema / @dataclass 描述期望结构；
  2. 协议转换：LangChain 调用 model_json_schema() 把结构定义转成 JSON Schema；
  3. 模型交互：JSON Schema 作为格式约束注入系统提示词，并通过 strict=True 的语法采样（grammar sampling）强约束模型输出；
  4. 自动解析与校验：把模型返回的 JSON 解析并构造为对象（Pydantic / dataclass 模式还会做类型校验）。

10.8 返回原始响应（include_raw=True）

有时你想拿到"原始响应"以便排查解析问题，可加 include_raw=True，返回字典包含三部分：

structured_llm = model.with_structured_output(Person, include_raw=True)
result = structured_llm.invoke("张三，30岁，熟悉Python")

print(result["raw"])            # 原始 AIMessage 对象
print(result["parsed"])         # 解析后的 Person 对象（解析失败时为 None）
print(result["parsing_error"])  # 解析异常对象（成功时为 None）

10.9 四种模式对比与选型建议

模式 类型校验 适用场景
Pydantic ✅ 校验不符抛 ValidationError 生产首选，需健壮性、约束与默认值
TypedDict ❌ 仅解析不校验 轻量场景，不想引入 Pydantic
JSON Schema ❌ 仅解析不校验 第三方 / 不能写类的环境
@dataclass ⚠️ 经 pydantic 时校验 已有 dataclass 代码复用

关键区别：只有 Pydantic（及经 pydantic 包裹的 dataclass）模式会在字段类型不符时抛异常；TypedDict 与 JSON Schema 模式只做解析、不校验，可能静默返回脏数据。生产环境优先选 Pydantic。

10.10 传统方式：输出解析器（了解即可，不推荐）

早期 LangChain 用"输出解析器"把格式指令拼进提示词，需要手动在模板里放 {format_instructions} 占位符，且解析不稳定：

from langchain_core.output_parsers import JsonOutputParser
from langchain_core.prompts import ChatPromptTemplate

parser = JsonOutputParser(pydantic_object=Person)
prompt = ChatPromptTemplate.from_messages([
    ("system", "输出 JSON：\n{format_instructions}"),
    ("human", "{query}"),
]).partial(format_instructions=parser.get_format_instructions())

chain = prompt | model | parser
chain.invoke({"query": "张三，30岁，熟悉Python"})

如今更推荐直接用 with_structured_output，无需手动拼接 format_instructions，且由模型侧强约束格式，稳定性更高。

第十一章：多模态输入

11.1 为什么支持多模态

现代大模型（GPT-4o、Qwen-VL、Gemini 等）可接受图片、音频作为输入。LangChain 通过消息的 content 支持多模态内容块。

11.2 图片输入

把图片转为 base64 或传 URL，封装为 image_url 内容块：

import base64

def img_to_data_url(path: str) -> str:
    with open(path, "rb") as f:
        b64 = base64.b64encode(f.read()).decode()
    return f"data:image/jpeg;base64,{b64}"

message = {
    "role": "user",
    "content": [
        {"type": "text", "text": "这张图里有什么？"},
        {"type": "image_url", "image_url": {"url": img_to_data_url("cat.jpg")}},
    ],
}
response = model.invoke([message])
print(response.content)

11.3 多图与图文混合

content 是列表，可放多张图 + 多段文字：

message = {
    "role": "user",
    "content": [
        {"type": "text", "text": "对比这两张图的异同"},
        {"type": "image_url", "image_url": {"url": url1}},
        {"type": "image_url", "image_url": {"url": url2}},
    ],
}

11.4 音频输入

部分模型支持音频 URL（需模型本身支持）：

message = {
    "role": "user",
    "content": [
        {"type": "input_audio", "input_audio": {
            "data": base64.b64encode(open("speech.mp3","rb").read()).decode(),
            "format": "mp3",
        }},
    ],
}

11.5 多模态注意事项

  • 模型必须支持：并非所有模型都接受图片/音频，先确认 supports_images / supports_audio。
  • Token 消耗大：图片通常按「图块（tile）」计费，高清图成本高，必要时先压缩。
  • 本地模型：Ollama 的 llava、qwen2-vl 等支持视觉，调用方式与上面一致。
  • Agent 中使用：多模态消息同样可以进入 agent.invoke({"messages": [...]})。

第十二章：LangGraph 图编排框架

12.1 什么是 LangGraph

LangGraph 是 LangChain 生态中用于构建有状态、多角色（multi-actor）LLM 应用的底层编排框架。如果说 LangChain 的 create_agent 是「开箱即用的智能体」，那 LangGraph 就是「搭智能体的乐高」——它让你用**图（Graph）**精确控制每一步流程：模型调用、工具执行、条件分支、循环、人工审批等。

关键关系：第十三章的 create_agent() 返回的对象，本质就是一个 LangGraph 编译后的 CompiledStateGraph。理解 LangGraph，才能读懂 Agent 的内部运行机制。

12.2 四大核心概念

概念 说明
State（状态） 在节点间传递的数据，通常用 TypedDict 定义，可带「归约函数（reducer）」合并更新
Node（节点） 一个函数，接收当前 State，返回对 State 的部分更新
Edge（边） 节点之间的连接；普通边顺序执行，条件边按函数返回值路由
Graph（图） 由节点和边组成，编译后变成一个可 invoke/stream 的 Runnable

控制节点：START（入口）、END（出口）是 LangGraph 内置的虚拟节点。

12.3 最小示例：第一个图

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    count: int

def increment(state: State) -> dict:
    """节点：把 count 加 1"""
    return {"count": state["count"] + 1}

builder = StateGraph(State)
builder.add_node("inc", increment)
builder.add_edge(START, "inc")     # 入口 → inc 节点
builder.add_edge("inc", END)       # inc 节点 → 出口

graph = builder.compile()
print(graph.invoke({"count": 0}))  # {'count': 1}

12.4 条件边与分支路由

用 add_conditional_edges 根据状态动态选择下一个节点：

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    text: str
    lang: str

def detect(state: State) -> str:
    """路由函数：判断文本语言，返回分支名"""
    return "zh" if any("\u4e00" <= c <= "\u9fff" for c in state["text"]) else "en"

def to_chinese(state: State) -> dict:
    return {"lang": "中文"}
def to_english(state: State) -> dict:
    return {"lang": "English"}

builder = StateGraph(State)
builder.add_node("zh", to_chinese)
builder.add_node("en", to_english)
builder.add_conditional_edges(START, detect, {"zh": "zh", "en": "en"})
builder.add_edge("zh", END)
builder.add_edge("en", END)

graph = builder.compile()
print(graph.invoke({"text": "你好，世界", "lang": ""}))  # {'text': '...', 'lang': '中文'}

12.5 编译与调用

compile() 之后，图就是一个标准 Runnable，支持全部六种调用方式：

# 同步
result = graph.invoke({"text": "Hello", "lang": ""})

# 流式（适合长流程逐步观察）
for chunk in graph.stream({"text": "你好", "lang": ""}):
    print(chunk)

# 异步
# await graph.ainvoke({...})

可视化（需安装 pygraphviz 或 graphviz）：

png = graph.get_graph().draw_mermaid_png()
with open("graph.png", "wb") as f:
    f.write(png)

12.6 持久化：Checkpointer

编译时传入 Checkpointer，即可实现断点续跑与多轮记忆（第十五章短期记忆即基于此）：

from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "t1"}}

graph.invoke({"count": 0}, config=cfg)
# 同一 thread_id 下次调用可读取上次状态

12.7 人在回路（Human-in-the-loop）

用 interrupt 在执行中暂停，等待人工输入后再继续——这是 LangGraph 比普通链更强大的地方：

from langgraph.types import interrupt
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    approved: bool

def need_approval(state: State) -> dict:
    decision = interrupt({"question": "确定要执行删除吗？"})
    return {"approved": decision}

builder = StateGraph(State)
builder.add_node("approve", need_approval)
builder.add_edge(START, "approve")
builder.add_edge("approve", END)

graph = builder.compile()
thread = {"configurable": {"thread_id": "h1"}}

# 第一次：暂停等待人工
graph.invoke({"approved": False}, config=thread)
# 人工批准后继续
graph.invoke(Command(resume=True), config=thread)

12.8 与 Agent 的关系

create_agent(model, tools, ...) 在底层做的事情，等价于用 LangGraph 搭一张「思考 → 调用工具 → 把结果喂回模型」的循环图。掌握 LangGraph 后，你可以：

  • 用 SubagentMiddleware / ToolRetryMiddleware 等中间件（第十四章）精细控制这张图；
  • 自定义节点与条件边，实现标准 Agent 做不到的复杂工作流；
  • 用 interrupt 实现关键操作的「人工审批」。

补充实战示例

带归约函数的状态合并（多轮累加）：

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
import operator

class State(TypedDict):
    # 每次节点返回都「追加」而不是覆盖
    logs: Annotated[list, operator.add]

def step_a(state: State) -> dict:
    return {"logs": ["step_a done"]}
def step_b(state: State) -> dict:
    return {"logs": ["step_b done"]}

builder = StateGraph(State)
builder.add_node("a", step_a)
builder.add_node("b", step_b)
builder.add_edge(START, "a")
builder.add_edge("a", "b")
builder.add_edge("b", END)

print(builder.compile().invoke({"logs": []}))
# {'logs': ['step_a done', 'step_b done']}

第十三章：智能体 Agent

13.1 什么是 Agent

Agent 是以大语言模型为推理与决策核心，结合记忆、工具调用与环境交互能力，能够进行规划决策并执行复杂任务的软件系统。

Agent 的关键能力：

理解用户问题 → 拆解任务 → 判断是否需要工具 → 调用哪些工具
→ 利用工具结果 → 生成回答并推进任务

核心组件（不一定全部需要）：

组件 作用 必需性
模型（Model） 推理与决策核心 ✅ 必须
工具（Tools） 执行外部操作 ⚙️ 几乎总是需要
规划（Planning） 任务拆解与执行计划 🔄 有条件存在
记忆（Memory） 存储上下文信息 📝 最容易被省略

agent 本质上是 LangGraph 的 CompiledStateGraph 实例，底层由图结构驱动。这意味着：

13.8 Agent 执行循环（ReAct 循环）

Agent 的底层执行逻辑是一个 思考-行动-观察（Think-Act-Observe）循环，本质是经典的 ReAct 结构：

用户问题 → AI 思考 → 调用工具 → 观察结果 → 继续思考 → ... → 最终答案

当 AIMessage 的 tool_calls 字段为空数组时，表示本轮不再调用工具，循环结束。当 AIMessage 的 tool_calls 非空时，Agent 会自动执行工具并将 ToolMessage 回填到消息列表，继续下一轮推理，直到最终回答。

判断 Agent 是否完成：

for msg in response['messages']:
    if isinstance(msg, AIMessage):
        if hasattr(msg, 'tool_calls') and msg.tool_calls:
            print("还在调用工具:", msg.tool_calls)
        else:
            print("完成！最终答案：", msg.content)

13.9 工具调用重试机制

Agent 支持在工具调用失败时自主重试，无需手动捕获异常。通过在 system_prompt 中告知模型"遇到临时故障应重试"，模型会自行决定重试次数：

from langchain.agents import create_agent
from langchain_core.tools import tool
from langchain_core.messages import SystemMessage, HumanMessage

flag = 0

@tool
def get_weather(city: str) -> str:
    """获取指定城市的天气信息"""
    global flag
    flag += 1
    if flag < 3:
        return "TEMP_UNAVAILABLE: 天气服务暂时不可用，请稍后重试"
    return f"{city}今天天气挺好"

messages = [
    SystemMessage(
        "你是一个天气助手。"
        "当工具返回以 'TEMP_UNAVAILABLE:' 开头时，说明是临时故障，"
        "不要立即放弃，应再次调用同一工具，最多重试 3 次。"
    ),
    HumanMessage("杭州今天的天气如何？")
]

agent = create_agent(model, tools=[get_weather])
response = agent.invoke({"messages": messages})

for msg in response["messages"]:
    msg.pretty_print()

模型会连续调用 get_weather 三次，前两次收到临时错误后继续重试，第三次获得正常结果后给出最终回答。

13.10 限制工具调用次数（recursion_limit）

默认情况下 Agent 调用工具没有次数限制，直到得到最终答案。可以通过 config 参数中的 recursion_limit 限制最大步数：

config = {
    "recursion_limit": 5  # 最多 5 步（包含模型调用和工具调用）
}

response = agent.invoke(
    {"messages": [{"role": "user", "content": "问题"}]},
    config=config
)

13.13 Agent 选错工具的原因与解决方案

原因：@tool 装饰器的 docstring 是 AI 理解工具用途的唯一依据。如果描述模糊或多个工具功能相似，AI 容易选错。

# ❌ 不好：docstring 太模糊
@tool
def tool1(x: str) -> str:
    """做一些事情"""

# ✅ 好：docstring 清晰具体
@tool
def get_weather(city: str) -> str:
    """
    获取指定城市的实时天气信息

    Args:
        city: 城市名称，如"北京"、"上海"
    """

工具数量控制：一般建议 2-5 个工具最佳，工具太多会导致混淆。

第十四章：中间件 Middleware

14.1 什么是中间件

Middleware（中间件）是 Agent 执行过程中的钩子函数，在"模型调用前"、"模型调用后"、"工具调用前后"等关键节点插入自定义逻辑，而无需修改 Agent 主流程。

没有中间件的流程：

用户输入 → 拼接提示词 → 调用模型 → 返回结果

有中间件的流程：

用户输入 → [中间件拦截点] → 拼接提示词
→ [中间件拦截点] → 调用模型 → [中间件拦截点]
→ 返回结果

14.2 为什么需要中间件

需求 无中间件 有中间件
根据问题复杂度动态切换模型 修改主流程 添加 Middleware
限制某些用户的工具权限 修改主流程 添加 Middleware
工具报错时自动重试 手动 try-catch ToolRetryMiddleware
模型调用前插入额外提示 修改 Prompt Middleware 注入
记录每一步执行日志 到处 print LoggingMiddleware
敏感信息出现时阻断执行 手动检查 PIIDetectionMiddleware
工具执行前人工审批 无法实现 HumanInTheLoopMiddleware

14.3 内置中间件分类

类型一：成本与资源控制

  • SummarizationMiddleware：上下文快满时自动摘要历史消息，减少 Token 消耗
  • ModelCallLimitMiddleware：限制模型调用次数，防止费用失控
  • ToolCallLimitMiddleware：限制工具调用次数，避免死循环

类型二：稳定性与容错保障

  • ModelRetryMiddleware：模型调用失败自动重试
  • ToolRetryMiddleware：工具调用失败自动重试
  • ModelFallbackMiddleware：主模型失败时切换备用模型

类型三：安全与合规风控

  • HumanInTheLoopMiddleware：关键操作前暂停，等人工审批
  • PIIDetectionMiddleware：检测并处理个人敏感信息

类型四：决策增强与智能编排

  • ToDoListMiddleware：任务规划、分步骤执行和状态跟踪
  • LLMToolSelectorMiddleware：工具太多时用子模型预筛选

类型五：执行能力扩展

  • ShellToolMiddleware：给 Agent 持久执行命令的能力
  • FileSearchMiddleware：文件搜索能力（Glob/Grep）

14.4 SummarizationMiddleware 使用示例

当对话历史太长导致 Token 消耗过大时，中间件会自动调用大模型对历史进行摘要：

from langchain.agents.middleware import SummarizationMiddleware
from langchain.agents import create_agent

# 需要指定 max_input_tokens（DeepSeek 默认 128K）
custom_profile = {"max_input_tokens": 128_000}
summary_model = init_chat_model(
    model="qwen-plus",
    model_provider="openai",
    profile=custom_profile
)

agent = create_agent(
    model=summary_model,
    middleware=[
        SummarizationMiddleware(
            model=summary_model,
            trigger=[
                ("tokens", 100),        # 历史 token 达到 100 触发摘要
                ("messages", 6),        # 消息条数达到 6 触发摘要
                ("fraction", 0.001)     # 达到上下文比例触发
            ],
            keep=("messages", 2)        # 摘要后保留最近 2 条消息
        )
    ]
)

14.6 中间件的钩子拦截点机制

中间件在 Agent 循环的关键节点进行拦截，形成四类钩子：

钩子位置 触发时机 常见用途
模型调用前 LLM 请求发出前 注入提示词、过滤输入、PII 检测
模型调用后 LLM 响应返回后 摘要历史、记录日志、输出审查
工具调用前 工具执行前 人工审批、参数校验、权限检查
工具调用后 工具返回结果后 重试处理、结果摘要、审计日志

create_agent() 底层由 LangGraph 驱动，中间件挂载在这些节点上，以"插入式"逻辑修改行为，而不侵入主流程代码。

14.7 自定义中间件的写法

LangChain 支持完全自定义中间件，只需实现一个函数签名，接受 state 和 config 参数：

from langchain.agents import create_agent
from langchain.chat_models import init_chat_model

def my_custom_middleware(state: dict, config: dict) -> dict:
    """
    自定义中间件示例：在模型调用前打印消息数量，
    在工具调用后为结果添加后缀。
    """
    messages = state.get("messages", [])
    print(f"[MyMiddleware] 当前消息数: {len(messages)}")

    # 如果有工具返回结果，在其 content 后追加标记
    for msg in messages:
        if hasattr(msg, "type") and msg.type == "tool":
            original = msg.content
            if not original.endswith(" [processed]"):
                msg.content = original + " [processed by MyMiddleware]"

    return state  # 返回修改后的 state

model = init_chat_model("qwen-plus", model_provider="openai")

agent = create_agent(
    model=model,
    tools=[],
    middleware=[my_custom_middleware]  # 直接传入函数即可
)

response = agent.invoke({
    "messages": [{"role": "user", "content": "你好"}]
})

关键点：middleware 参数接受一个可调用对象列表，可以是函数、BaseMiddleware 子类实例，或 LangChain 内置中间件类的实例。

    model=summary_model,                          # 用于执行摘要的模型（必填）
    trigger=[
        ("tokens", 100),         # 历史 token 累计达 100 触发
        ("messages", 6),         # 历史消息条数达 6 触发
        ("fraction", 0.001),     # 达 max_input_tokens*fraction 触发（需 profile 含 max_input_tokens）
    ],
    keep=("messages", 2),        # 摘要后保留最近 2 条原始消息（与 trigger 不同，keep 同一时间只接受一种条件）
    token_counter=None,            # 统计 token 的函数，默认 langchain.utils.langchain.count_tokens_approximately
    summary_prompt="对历史消息摘要，消息列表如下\n{messages}",  # 自定义摘要提示词，必须含 {messages} 占位符
    trim_token_to_summarize=4000,  # 摘要时历史消息的最大 token 数，超过则先裁剪
)

DeepSeek 注意事项：DeepSeek 模型的 profile 不含 max_input_tokens，使用 fraction 触发条件时必须手动指定：

15.1 为什么需要记忆

大模型本身是无状态的，每次 agent.invoke() 调用都是全新开始，不记得之前的对话。

举例：

# 第一轮

# 第二轮（不传历史 = 失忆）
response2 = agent.invoke({"messages": [HumanMessage("我叫什么？")]})  # AI: 我不知道

15.2 短期记忆（会话级）

LangChain 1.x 的短期记忆由三部分组成：

  • State：存储历史消息列表
  • Checkpointer：持久化 State 的快照
  • Thread ID：唯一标识会话

使用 InMemorySaver 实现短期记忆

from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent
from langchain_core.messages import HumanMessage

# 创建内存持久化器
checkpointer = InMemorySaver()

# 创建 Agent 时传入 checkpointer
agent = create_agent(
    model=model,
    checkpointer=checkpointer
)

# 配置会话 ID
config = {"configurable": {"thread_id": "session_001"}}

# 第一轮对话
r1 = agent.invoke({"messages": [HumanMessage("我叫张三")]}, config=config)
print(r1['messages'][-1].content)  # 你好，张三！

# 第二轮对话（相同 thread_id，自动记住上下文）
r2 = agent.invoke({"messages": [HumanMessage("我叫什么？")]}, config=config)
print(r2['messages'][-1].content)  # 你叫张三。

# 换一个新 thread_id = 新会话，记忆消失
config2 = {"configurable": {"thread_id": "session_002"}}
r3 = agent.invoke({"messages": [HumanMessage("我叫什么？")]}, config=config2)
print(r3['messages'][-1].content)  # 我不知道你的名字

15.5 短期记忆：InMemorySaver 自动追加机制与状态查看

现有文档仅展示了 checkpointer=InMemorySaver() 的基础用法，缺少对自动追加逻辑和状态查看 API 的说明。

每次调用 agent.invoke(...) 时，checkpointer 在内部自动完成四步：

  1. 读取该 thread_id 之前保存的历史消息
  2. 将本次传入的新消息追加到历史中
  3. 调用模型（传入完整的消息列表）
  4. 将包含新回复的历史保存为新的 checkpoint

调用者只需传入新消息，框架自动维护历史，无需手动拼接 messages 列表。

查看当前会话状态使用 agent.get_state(config)，返回 StateSnapshot 对象，包含：

from langchain_core.messages import HumanMessage
from rich import print as rprint  # pip install rich

agent = create_agent(model=model, checkpointer=checkpointer)
config = {"configurable": {"thread_id": "1"}}

# 第一轮
agent.invoke({"messages": [HumanMessage("我叫张三")]}, config=config)
# 第二轮
agent.invoke({"messages": [HumanMessage("我叫什么？")]}, config=config)

# 查看当前完整状态

rprint(snapshot)

# StateSnapshot 关键字段：
# snapshot.values        → 包含 messages 列表的字典
# snapshot.config        → 包含 thread_id、checkpoint_id 的配置
# snapshot.metadata      → {'source': 'loop', 'step': N, ...}
# snapshot.parent_config → 上一个 checkpoint 的配置（用于回退）
# snapshot.created_at    → checkpoint 创建时间

15.6 短期记忆：PostgreSQL 持久化（PostgresSaver）完整流程

生产环境需要状态跨进程持久化，使用 PostgresSaver 而非 InMemorySaver。

前置条件：安装 langgraph-checkpoint-postgres（已在 requirements.txt 中）。

from langchain.agents import create_agent
from langchain_core.messages import HumanMessage
from langgraph.checkpoint.postgres import PostgresSaver

DB_URL = "postgresql://langchain_user:abcd1234@118.195.128.47:5432/langchain_db?sslmode=disable"

with PostgresSaver.from_conn_string(DB_URL) as checkpointer:
    # 首次运行：初始化数据库表（幂等操作，可重复调用）
    checkpointer.setup()

    agent = create_agent(model=model, checkpointer=checkpointer)
    config = {"configurable": {"thread_id": "1"}}

    r1 = agent.invoke({"messages": [HumanMessage("你好，我是谁？")]}, config=config)
    r2 = agent.invoke({"messages": [HumanMessage("我是老王")]}, config=config)
    r3 = agent.invoke({"messages": [HumanMessage("你好，我是谁？")]}, config=config)

    for msg in r3["messages"]:
        msg.pretty_print()

setup() 方法：调用 CREATE TABLE IF NOT EXISTS 初始化 4 张表，只需首次执行，后续重复调用安全无副作用。

PostgreSQL 中 4 张 checkpoint 表的用途：

表名 用途
checkpoints 主表，存储每个 thread 在某时刻的完整状态快照
checkpoint_blobs 存储不适合内联进 checkpoints 的复杂 channel 值（大对象）
checkpoint_writes 存储中间写入/pending writes，非最终 checkpoint
checkpoint_migrations 迁移版本表（框架内部使用，非业务数据）

15.7 InMemorySaver 与 PostgresSaver 的关键区别

特性 InMemorySaver PostgresSaver
存储位置 进程内存 PostgreSQL 数据库
进程重启后 数据丢失 数据保留（持久化）
跨进程共享 不支持 支持
适用场景 本地测试、快速验证 生产环境
同一 thread_id 跨 Saver 实例 历史丢失（每次 Saver 实例独立） 只要连接同一 DB，历史可串联

重要陷阱：如果每次运行都 InMemorySaver()（重新创建实例），即便 thread_id 相同，历史也会丢失，因为状态没有持久化到外部存储。外部存储（PostgreSQL）天然支持跨进程、跨重启的持久化。

15.8 短期记忆：thread_id 隔离机制与常见问题排查

thread_id 是会话隔离的核心开关，背后原理是：checkpointer 以 thread_id 为键来读写 checkpoint 快照。不同 thread_id 的存储完全独立，互不干扰。

常见问题排查清单：

# ❌ 错误1：没有 checkpointer，每次调用都是全新开始

# ❌ 错误2：没有传入 config

agent.invoke({"messages": [...]})  # 丢失历史

# ❌ 错误3：两次调用的 thread_id 不同
agent.invoke({"messages": [...]}, config={"configurable": {"thread_id": "1"}})
agent.invoke({"messages": [...]}, config={"configurable": {"thread_id": "2"}})  # 完全独立

# ✅ 正确
agent = create_agent(model=model, checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "1"}}
agent.invoke({"messages": [...]}, config=config)
agent.invoke({"messages": [...]}, config=config)  # 共享记忆

# 清空某会话历史的唯一方式：换一个新的 thread_id
config_new = {"configurable": {"thread_id": "2"}}
# 或者重新创建 Agent 实例（InMemorySaver 时）

15.9 记忆治理：消息裁剪（before_model 中间件）

before_model 中间件在模型调用前拦截消息列表，可对即将传给 LLM 的上下文进行裁剪。适合控制 token 用量，保留系统消息和最近若干条。

from langchain_core.messages import HumanMessage
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent, AgentState
from langchain.agents.middleware import before_model
from langgraph.runtime import Runtime
from langchain_core.runnables import RunnableConfig
from typing import Any

@before_model
def trim_messages(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    messages = state["messages"]
    if len(messages) <= 3:
        return None  # 不裁剪

    # 保留第一条消息 + 最近4条
    new_messages = [messages[0]] + messages[-4:]
    return {
        "messages": [
            RemoveMessage(id=REMOVE_ALL_MESSAGES),  # 清除所有旧消息
            *new_messages                            # 写入裁剪后的消息
        ]
    }

agent = create_agent(
    model=model,
    middleware=[trim_messages],
    checkpointer=InMemorySaver(),
)

config: RunnableConfig = {"configurable": {"thread_id": "1"}}
agent.invoke({"messages": [HumanMessage("你好，我是老王")]}, config=config)
agent.invoke({"messages": [HumanMessage("从现在起你叫小王")]}, config=config)
agent.invoke({"messages": [HumanMessage("今天天气不错")]}, config=config)
final = agent.invoke({"messages": [HumanMessage("告诉我，你是谁？我是 谁？")]}, config=config)
# 最终只保留裁剪后的消息，而非全部历史

15.10 记忆治理：消息删除（after_model 中间件）

after_model 中间件在模型调用完成后拦截消息列表，将某些消息永久从状态中移除。适合需要明确"遗忘"某些历史的场景。

from langchain.messages import RemoveMessage
from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent, AgentState
from langchain.agents.middleware import after_model
from langgraph.runtime import Runtime
from langchain_core.runnables import RunnableConfig

@after_model
def delete_old_messages(state: AgentState, runtime: Runtime) -> dict | None:
    messages = state["messages"]
    # 永远只保留最近 5 条消息
    if len(messages) > 5:
        to_delete = len(messages) - 5
        # 精准删除最老的前 to_delete 条
        return {"messages": [RemoveMessage(id=m.id) for m in messages[:to_delete]]}
    return None

agent = create_agent(
    model=model,
    middleware=[delete_old_messages],
    checkpointer=InMemorySaver(),
)

config: RunnableConfig = {"configurable": {"thread_id": "1"}}
agent.invoke({"messages": "你好，我是老王"}, config=config)
agent.invoke({"messages": "从现在起，你叫小王"}, config=config)
agent.invoke({"messages": "今天天气不错"}, config=config)
final = agent.invoke({"messages": "告诉我，你是谁？我是谁？"}, config=config)
# 消息总数永远不超过 5 条，超过时自动清理最老的

15.11 记忆治理：RemoveMessage 墓碑机制

RemoveMessage 并不是真正从内存数组中删除消息，而是向状态中追加一条墓碑标记（tombstone）。当框架后续读取消息时，内置的 Reducer 会将"原始消息"与"墓碑标记"合并，自动过滤掉被标记删除的消息后，才将列表传给 LLM。

# 内部执行逻辑：
# 消息池: [Msg(id="1", "你好"), Msg(id="2", "你好老王！"), RemoveMessage(id="1")]
#                   ↑ 原始消息           ↑ 墓碑标记

# 框架读取时自动执行合并：
# 原始消息 id="1" 遇到墓碑 id="1" → 对外隐藏（不再传给 LLM）
# 最终 LLM 看到：[Msg(id="2", "你好老王！")]

15.12 记忆治理：SummarizationMiddleware 完整参数

SummarizationMiddleware 支持精确的触发条件配置，适用于长会话的语义压缩。

from langchain.agents.middleware import SummarizationMiddleware
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

# 用小模型做摘要，节省成本
summary_model = init_chat_model(
    model="qwen-plus",
    model_provider="openai",
)

agent = create_agent(
    model=model,
    tools=[],
    checkpointer=InMemorySaver(),
    middleware=[
        SummarizationMiddleware(
            model=summary_model,
            # 触发条件（三选一，均可叠加）：
            trigger=[
                ("tokens", 100),       # 历史 token 超过 100 触发
                ("messages", 6),       # 消息条数超过 6 触发
                ("fraction", 0.5),    # 达到上下文窗口 50% 触发
            ],
            keep=("messages", 2),     # 摘要后保留最近 2 条消息
            summary_prompt="对以下历史消息做中文摘要，保留关键信息：\n{messages}",
        )
    ],
)

15.14 上下文工程：三上下文类型概述

LangChain 的上下文工程建立在 LangGraph 之上，从可变性和生命周期两个维度划分为三种上下文：

上下文类型 生命周期 可变性 访问方式 说明
动态运行时上下文 单次运行 动态 state 对象 单次 invoke 中演变的可变数据（如 messages 列表）
动态跨会话上下文 跨对话 动态 store 对象 会话间共享的持久数据（用户偏好、历史洞察等）

理解这三种上下文的边界，有助于在实际开发中选择正确的存储方式。

第十六章：Skill 技能系统

16.1 什么是 Skill

在 AI Agent 开发中，Skill（技能） 指可复用的、封装了特定领域知识与操作流程的能力单元。它比单一「工具（Tool）」更高一层 —— 一个 Skill 可以包含：

  • 一套领域提示词 / 系统指令（告诉模型「该按什么思路做」）
  • 一组配套工具（检索、计算、调用 API 等）
  • 一份操作流程 / 工作流（多步骤的标准做法）
  • 可选的参考资料（术语表、示例、规范）

类比：

  • Tool = 一把螺丝刀（单一动作）
  • Skill = 一套「组装家具」的说明书 + 工具包（组合能力）
  • Agent = 工人（拿技能包去完成目标）

16.2 为什么需要 Skill

维度 只用 Tool 引入 Skill
能力粒度 原子操作，模型易「用错」 领域封装，模型按最佳实践执行
可复用性 散落各处 一次定义，多处加载
知识沉淀 提示词写死在代码里 独立文件，便于维护与版本管理
组合方式 手动接 声明式挂载，Agent 自动发现

16.3 Skill 的典型结构

一个 Skill 通常以目录 + 元数据文件的形式存在：

my_skill/
├── SKILL.md          # 技能说明（触发条件、使用步骤、注意事项）
├── tools.py          # 配套工具函数（@tool 定义）
├── prompts/          # 提示词模板
│   └── system.txt
└── references/       # 参考资料（术语表、示例）
    └── glossary.md

SKILL.md 示例：

---
name: pdf-extractor
description: 当用户需要「从 PDF 中提取表格/文本并整理成结构化数据」时使用本技能
trigger: ["提取PDF", "PDF转表格", "读取PDF内容"]
---

# PDF 提取技能

## 使用步骤
1. 用 PyPDFLoader 加载文档
2. 用表格识别工具提取表格区域
3. 调用结构化输出转换为 Pydantic 对象

## 注意事项
- 扫描件需先 OCR
- 大文件启用 lazy_load 延迟加载

16.4 在 LangChain 中落地 Skill

LangChain 本身没有内置名为「Skill」的独立类，但可以用已有组件组合出等价能力：

方案 A：Skill = 工具集 + 系统提示词

from langchain.chat_models import init_chat_model

# ---- Skill 的工具包 ----
@tool
def search_docs(query: str) -> str:

    return f"检索结果: {query} 的相关内容..."

@tool

    """将长文本压缩为要点"""
    return f"摘要: {text[:50]}..."

# ---- Skill 的领域提示词 ----

你是一个专业的文档分析助手。处理用户请求时请遵循：
1. 先用 search_docs 检索相关资料
2. 再用 summarize 提炼要点
3. 最后用中文清晰作答，并标注引用来源
"""

# ---- 组装成 Agent（即一个「文档分析 Skill」的实例）----
model = init_chat_model("qwen-plus", model_provider="openai")

doc_skill_agent = create_agent(
    model=model,
    tools=[search_docs, summarize],
    system_prompt=SKILL_SYSTEM_PROMPT,
)

result = doc_skill_agent.invoke({
    "messages": [{"role": "user", "content": "帮我分析一下 Q2 财报的核心数据"}]
})
print(result["messages"][-1].content)

16.5 Skill 与 MCP / Tool 的关系

层次：  Tool  <  Skill  <  Agent

Tool    → 原子能力（一次动作），如 get_weather()
Skill   → 领域能力包（提示词 + 工具 + 流程），如「财报分析」
Agent   → 编排者（按需调用多个 Skill / Tool 完成目标）

MCP     → Skill/工具 的「标准传输协议」，让能力可跨应用共享

16.6 设计良好 Skill 的原则

  1. 单一职责：一个 Skill 解决一类问题，不要贪大。
  2. 清晰的触发描述：在 description 中写清「何时用」，便于 Agent 自动选择。
  3. 自带最佳实践：把领域经验写进系统提示词，减少模型试错。
  4. 可组合：Skill 之间尽量解耦，能被不同 Agent 复用。
  5. 安全边界：涉及写操作/外部调用的工具，配合 HumanInTheLoop 中间件做审批。

第十七章：MCP 模型上下文协议

17.1 什么是 MCP

MCP（Model Context Protocol，模型上下文协议）是由 Anthropic 于 2024 年 11 月推出的开放标准协议，旨在标准化「大模型应用」与「外部数据源 / 工具」之间的连接方式。

用一句话理解：MCP 之于 AI 工具生态，就像 USB-C 之于硬件接口 —— 一套标准，插上即用。

在 MCP 出现之前，每接入一个工具，开发者都要为特定的大模型框架写一套定制集成代码，形成 N×M 的碎片化问题（N 个应用 × M 个工具 = N×M 套适配代码）。MCP 把这一关系收敛为 N+M（每个应用实现一次客户端，每个工具实现一次服务端），极大降低了集成成本。

17.2 为什么需要 MCP

痛点 没有 MCP 有 MCP
工具接入 每个框架各写一套适配 服务端一次实现，处处可用
跨应用复用 重复造轮子 标准协议，Claude、LangChain、IDE 等通用
安全管控 散落各处，难统一 服务端统一授权与审计
本地/远程 混在一起 传输层标准化（stdio / HTTP）

MCP 与 Function Calling（函数调用）的关系：

  • Function Calling 是「模型决定调哪个函数」的能力，属于模型侧特性。
  • MCP 是「函数/数据如何被暴露和调用」的传输与协议标准，属于架构侧规范。
  • 二者互补：MCP Server 暴露的能力，最终仍通过模型的函数调用来触发。

17.3 MCP 架构

MCP 采用客户端-服务器架构，包含三个核心角色：

角色 说明 举例
Host（宿主） 运行大模型的 AI 应用，用户直接交互的入口 Claude Desktop、Cursor、VS Code、LangChain Agent
Client（客户端） Host 内部维护的协议客户端，负责与单个 Server 通信 每个 MCP Server 对应一个 Client
Server（服务端） 独立进程，暴露具体能力（工具/资源/提示词） 文件系统服务、数据库服务、GitHub 服务 
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│   Host      │     │   Client     │     │   Server     │
│ (AI 应用)   │◄───►│ (协议客户端) │◄───►│ (能力提供方) │
│             │     └──────────────┘     │ Tools        │
│  LLM + UI   │                          │ Resources    │
└─────────────┘                          │ Prompts      │
                                         └─────────────┘

17.4 MCP 三大核心原语

MCP Server 可以对外暴露三类能力：

原语 类型 说明 类比
Tools（工具） 模型可调用 执行动作、产生副作用（如写文件、发请求） 函数 / API
Resources（资源） 应用可读 只读数据源（如文件内容、数据库记录） 文件 / 变量
Prompts（提示词） 用户触发 预定义的提示词模板，供用户选择使用 宏 / 快捷指令

其中 Tools 与 LangChain 第九章的 @tool 概念直接对应，是 Agent 调用 MCP 能力的主要入口。

17.5 传输方式

传输层 场景 说明
stdio（标准输入输出） 本地进程 Server 作为本地子进程启动，通过 stdin/stdout 通信，最常用
HTTP + SSE 远程服务 Server 部署在远端，通过 HTTP 流式推送，适合云端共享能力

第十八章：RAG 检索增强生成

18.1 为什么需要 RAG

大模型存在三大固有问题：

问题 表现 后果
知识滞后 训练数据有截止日期，无法获取最新信息 回答过时、不准确
知识缺失 特定领域/私有数据未在训练集中 生成幻觉、不专业
幻觉 模型可能"胡言乱语"，编造不存在的事实 金融、医疗等场景存在致命风险

RAG 的核心思路：在提问时，检索相关文档作为上下文，连同问题一起发给大模型，让模型"看参考资料再回答"。

18.2 RAG 工作流程

Source（数据源）→ Load（加载）→ Transform（转换）→ Embed（嵌入）
→ Store（存储）→ Retrieve（检索）→ Generate（生成）

各环节详解：

  1. Source：PDF、CSV、JSON、网页、数据库、API 等数据源
  2. Load：DocumentLoader 将各种格式的文件加载为 Document 对象
  3. Transform：TextSplitter 将长文档切分成小块（Chunk）
  4. Embed：Embedding 模型将文本转换为向量
  5. Store：向量数据库（如 Chroma、FAISS）存储向量
  6. Retrieve：根据问题检索最相关的 Top-K 文档块
  7. Generate：将检索结果 + 问题发给 LLM 生成答案

18.3 文档加载器 Document Loaders

LangChain 提供了丰富的文档加载器：

18.4 文档拆分器 TextSplitter

文档拆分（Chunking）是 RAG 中最具挑战性的环节，直接影响检索效果：

from langchain.text_splitter import RecursiveCharacterTextSplitter

# 最常用的拆分器，适合大多数文本
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # 每个块的最大字符数
    chunk_overlap=50,    # 块之间的重叠字符数（保持上下文连续性）
    length_function=len  # 用 len() 计算文本长度
)

# 拆分文档
chunks = splitter.split_documents(docs)
print(f"共拆分为 {len(chunks)} 个块")

# 也可以直接拆分文本列表
texts = ["长文本段落1...", "长文本段落2..."]
text_chunks = splitter.split_text(texts)

拆分策略小技巧：

策略 说明 适用场景
小块（200-500字符） 精确匹配，噪声少 问答、事实查找
大块（1000+字符） 上下文丰富 总结、推理任务
重叠（Overlap） 50-100字符重叠 边界信息丢失的场景
按语义拆分 按句子/段落边界拆分 代码、Markdown

18.7 RAG 优缺点总结

优点 缺点
✅ 不需要重新训练模型 ❌ 每次问答都涉及检索，响应时延较高
✅ 可接入最新/私有数据 ❌ 引用外部知识消耗大量 Token
✅ 保护数据隐私（不离库） ❌ 检索质量依赖文档质量和拆分策略
✅ 答案可追溯（可查看引用来源） ❌ 检索不到相关内容时回答质量下降

18.10 TextSplitter 全家桶：从 CharacterTextSplitter 到 SemanticChunker

CharacterTextSplitter（separator 优先原则，keep_separator）

from langchain_text_splitters import CharacterTextSplitter

# 关键：separator 优先——先在分隔符处切，再考虑 chunk_size
# chunk_overlap 仅在合并后片段之间生效，若 chunk_size 过小导致不合并则 overlap 失效
splitter = CharacterTextSplitter(
    separator="。",           # 优先按句号切，保持语义完整
    chunk_size=20,
    chunk_overlap=8,
    keep_separator=True,     # True：在 chunk 末尾保留分隔符（如保留"。"）
)
chunks = splitter.split_text("这是第一段文本。这是第二段内容。最后一段结束。")

RecursiveCharacterTextSplitter（最常用，渐进式分割）

默认分隔符列表按优先级尝试：["\n\n", "\n", " ", ""]，即：段落 → 换行 → 空格 → 字符级。底层逻辑：

  1. 先拆分：按当前分隔符切块；若块 > chunk_size，递归用下一级分隔符继续细分
  2. 后合并：按 chunk_overlap 合并相邻小块，组织为最终块列表
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 完整参数版
splitter = RecursiveCharacterTextSplitter(
    chunk_size=220,
    chunk_overlap=80,
    separators=[              # 自定义分隔符优先级（适合中文）
        "\n==============================\n",
        "\n\n",
        "\n",
        "。", "！", "？", "……", "，",  # 中文标点优先
        " ",
        "",
    ],
    length_function=len,
    add_start_index=True,    # metadata 中加入 start_index 字段
    keep_separator=True,
)

# split_text(str) → List[str]
texts = splitter.split_text(long_text)

# create_documents(List[str]) → List[Document]
docs = splitter.create_documents([long_text])
# 每个 Document 的 metadata 含 start_index

# split_documents(List[Document]) → List[Document]（最常用）
# 取出已有 Document 的 page_content + metadata，重新切分
docs = splitter.split_documents(existing_docs)

TokenTextSplitter / CharacterTextSplitter.from_tiktoken_encoder（按 Token 切分）

按 Token 而非字符切分，确保每块不超过 LLM 的 Token 上限：

from langchain_text_splitters import TokenTextSplitter

splitter = TokenTextSplitter(
    chunk_size=33,           # 最大 token 数
    chunk_overlap=0,
    encoding_name="cl100k_base",  # OpenAI 的编码器（GPT-4/3.5 同款）
    # 其他可用编码器：gpt2, p50k_base, o200k_base 等
)
chunks = splitter.split_text(text)
# 注意：字符数 ≠ Token 数（中文尤为明显）

# 通过 tiktoken 实现按 Token 切分（CharacterTextSplitter + tiktoken）
from langchain_text_splitters import CharacterTextSplitter
import tiktoken

splitter = CharacterTextSplitter.from_tiktoken_encoder(
    encoding_name="cl100k_base",
    chunk_size=18,           # 按 token 计数的 chunk_size
    chunk_overlap=0,
    separator="。",
    keep_separator=False,
)
chunks = splitter.split_text(text)

SemanticChunker（语义分块，按向量相似度动态切分）

先按句子切分，再计算相邻句子的嵌入向量余弦距离，超过阈值则切分：

# pip install langchain_experimental
from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings
import os
from dotenv import load_dotenv

load_dotenv(override=True)

embedding_model = OpenAIEmbeddings(
    model="Pro/BAAI/bge-m3",
    base_url=os.getenv("SILICONFLOW_BASE_URL"),
    api_key=os.getenv("SILICONFLOW_API_KEY"),
    dimensions=1024,
)

splitter = SemanticChunker(
    embeddings=embedding_model,
    # breakpoint_threshold_type：断点检测算法
    # "percentile"   → 取第 N 百分位（默认值 95，值越小切分越细）
    # "standard_deviation" → 均值 + N 倍标准差（适合技术文档）
    # "interquartile" → 四分位距（适合长文档/书籍）
    breakpoint_threshold_type="percentile",
    breakpoint_threshold_amount=65.0,  # 65 表示只有语义差距超过 65% 的句子间距时才切分
    sentence_split_regex=r"(?<=[。？！])\s+",  # 中文句子切分正则
)

docs = splitter.create_documents(texts=[long_text])

18.12 LCEL 完整 RAG 链路（替代已废弃的 RetrievalQA）

RetrievalQA 在 LangChain 1.x 中已被废弃，标准做法是使用 LCEL 手动构建 RAG 链，灵活性更高：

from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

# 1. 定义检索器（来自 vectorstore.as_retriever）
retriever = vectorstore.as_retriever(
    search_kwargs={"k": 3}      # 每次召回 top-3 相关文档
)

# 2. 定义 Prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个问答助手。请仅根据以下上下文回答用户问题。\n{context}"),
    ("user", "{question}"),
])

# 3. 组装 LCEL RAG 链
rag_chain = (
    {
        "context": retriever,              # 检索器 → 返回 List[Document]
        "question": RunnablePassthrough(), # 原样透传用户问题
    }
    | prompt
    | ChatOpenAI(model="qwen-plus", temperature=0)
    | StrOutputParser()
)

# 4. 调用
answer = rag_chain.invoke("试用期最长可以多久？")
print(answer)

# 流式调用（适合前端展示）
for chunk in rag_chain.stream("试用版有什么限制？"):
    print(chunk, end="", flush=True)

LCEL 链中，retriever 作为 Runnable 直接在字典槽位中被调用，会自动对用户问题执行 invoke，返回 List[Document]。Document 对象会自动转为字符串（调用其 __str__ 方法）填入 context 占位符。

创建 Collection：metric_type 参数详解

from pymilvus import MilvusClient

client = MilvusClient(uri="http://localhost:19530")

# 切换/创建数据库
client.create_database(db_name="my_rag_db")
client.use_database(db_name="my_rag_db")

# 删除旧 collection（如有）
if client.has_collection(collection_name="docs"):
    client.drop_collection(collection_name="docs")

# 创建 collection
client.create_collection(
    collection_name="docs",
    dimension=1024,              # 必须与 embedding 模型维度一致（BGE-M3 = 1024）
    metric_type="COSINE",       # 相似度度量标准
)

metric_type（距离度量方式）：

类型 含义 取值范围 说明
COSINE 余弦相似度 0~1（越大越相似） 方向相似性——文本方向一致则值高，最适合语义检索
L2 欧氏距离 0~∞（越小越相似） 适合几何距离敏感的检索
IP 内积 -1~1（越大越相似） 未归一化向量的相似度度量

检索结果中的 distance 字段含义取决于 metric_type：COSINE 模式下 distance 越大代表越相似。
