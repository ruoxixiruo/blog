Kafka 面试学习文档

整理日期：2026-06-14 | 像快递分拣中心一样理解 Kafka：消息来了 → 分类 → 暂存 → 配送

1. 先搞懂：Kafka 到底是什么？

  ┌──────────┐      ┌─────────────────────────┐      ┌──────────┐
  │ Producer │ ────→│     Kafka Cluster        │────→ │ Consumer │
  │ (发消息)  │      │  ┌──────┐ ┌──────┐       │      │ (收消息)  │
  │          │      │  │Topic1│ │Topic2│ ...   │      │          │
  │ 订单系统  │      │  │ 分区0│ │ 分区0│       │      │ 短信系统  │
  │ 日志采集  │      │  │ 分区1│ │ 分区1│       │      │ 数据仓库  │
  └──────────┘      │  └──────┘ └──────┘       │      └──────────┘
                    └─────────────────────────┘
                    消息持久化在磁盘，消费完不删除

1.1 用快递分拣中心来理解

把 Kafka 想象成一个超大型快递分拣中心：

  1. 各地包裹不断送来（生产者）
  2. 按目的地分类到不同传送带（Topic），每个目的地再细分几条子传送带（Partition）
  3. 配送员按负责区域取走包裹（消费者）
  4. 每个包裹有编号，取到哪一号都记录着（Offset）
  5. 包裹不销毁，保留一段时间方便对账（消息持久化）

Kafka 本质上就是一个超大容量、超高速度的消息分拣中心。

1.2 官方定义（用大白话说）

Apache 开源的分布式消息系统，LinkedIn 最早研发它来处理海量用户行为日志。一句话：帮你在系统间可靠、快速地搬运数据的管道。

1.3 Kafka 的三个身份

身份 能干什么 举个例子
消息队列 系统间异步传递消息 下单后发短信——订单系统丢消息给 Kafka，短信系统慢慢处理
数据管道 把数据从源头搬到目的地 数据库变更日志 → Kafka → 数据仓库
流处理平台 实时处理流式数据 用户点击 → Kafka Streams → 每 5 分钟点击量统计

1.4 为什么 Kafka 这么快？

每秒百万级消息，靠 6 个技巧：

① 顺序写磁盘 (Append Only)
   只往尾巴追加，不随机读写，速度接近内存

② Page Cache
   热点数据留在 OS 缓存，不用每次读磁盘

③ 零拷贝 (Zero Copy)
   数据从磁盘 DMA → 网卡，跳过 CPU 内存拷贝

④ 批量发送
   攒够一批再发，减少网络往返

⑤ 数据压缩
   支持 Snappy / LZ4 / GZIP，减小传输量

⑥ 分区并行
   一个 Topic 拆多个 Partition，多台机器同时读写

2. 核心组件：谁在干活？

2.1 一句话认识每个角色

Producer（生产者）
  → 发消息的人。如订单系统创建订单后发给 Kafka

Broker（代理节点）
  → Kafka 服务器。消息存在这里

Topic（主题）
  → 消息的分类标签。如 "订单主题"、"日志主题"

Partition（分区）
  → Topic 拆成多份，分散到不同机器。类似把一本书拆成多个分册

Consumer（消费者）
  → 收消息的人。如短信系统从 Kafka 取订单消息然后发短信

Consumer Group（消费者组）
  → 一组消费者抱团消费。组内分摊，不同组独立

Offset（偏移量）
  → 消息在分区里的位置编号，记录消费进度

2.2 整体架构图

                     ZooKeeper / KRaft (元数据)
                          │
  ┌─────────┐     ┌───────┴───────┐     ┌──────────────┐
  │Producer A│────→│               │────→│Consumer Group A│
  └─────────┘     │               │     │ Consumer-1    │
                  │ Kafka Cluster │     │ Consumer-2    │
  ┌─────────┐     │               │     └──────────────┘
  │Producer B│────→│ Topic: orders │
  └─────────┘     │  ├─Partition-0│────→┌──────────────┐
                  │  ├─Partition-1│     │Consumer Group B│
                  │  └─Partition-2│     │ (独立消费)     │
                  └───────────────┘     └──────────────┘

3. 生产者：怎么发消息？

发送流程：

  Producer.send(msg)
      │
      ▼
  ① 序列化 ──→ 对象 → 字节数组
      │
      ▼
  ② 选分区 ──→ 有 key → hash(key) % 分区数
      │         没 key → 轮询
      ▼
  ③ 攒批次 ──→ 消息进缓冲区 (RecordAccumulator)
      │         凑够 batch.size 或等够 linger.ms
      ▼
  ④ 发送   ──→ Sender 线程发往目标 Broker
      │
      ▼
  ⑤ 确认   ──→ Broker 返回 RecordMetadata
               (topic, partition, offset)
             失败则重试 (retries 次)

3.1 发送流程（5 步）

① 序列化 → 把对象变成字节数组
② 选分区 → 有 key 就 hash，没 key 就轮询
③ 攒批次 → 消息先放进缓冲区，凑够一批再发
④ 发送 → Sender 线程把批次发给目标 Broker
⑤ 确认 → Broker 返回元数据 (topic/partition/offset)，失败则重试

3.2 核心配置（面试要记住的）

Properties props = new Properties();
props.put("bootstrap.servers", "kafka1:9092,kafka2:9092");
props.put("key.serializer", StringSerializer.class.getName());
props.put("value.serializer", StringSerializer.class.getName());

// ⭐ 这三个是面试必问
props.put("acks", "all");              // 消息确认级别
props.put("retries", 3);               // 失败重试次数
props.put("enable.idempotence", true); // 开启幂等（防止重复）

// 性能相关
props.put("batch.size", 16384);        // 批次大小（16KB）
props.put("linger.ms", 10);            // 等 10ms，攒够了再发
props.put("compression.type", "lz4");  // 用 LZ4 压缩

3.3 acks 参数——消息可靠性的关键

acks 值 什么意思 可靠性 性能
0 发了就不管，不等人确认 最低 最高
1 Leader 收到就确认 中 中
all (-1) 所有 ISR 副本都收到才确认 最高 最低

面试话术："生产环境用 acks=all + enable.idempotence=true，保证消息不丢也不重。"

3.4 幂等生产者——防止消息重复

网络波动导致消息重发？开启幂等即可：

props.put("enable.idempotence", true);
// 原理：每个 Producer 有唯一 PID，每条消息带序列号
//       Broker 发现序列号重复就直接丢弃

4. 消费者：怎么收消息？

4.1 消费者组——面试必考

核心规则：组内竞争，组间广播。

  • 组内：一个 Partition 只能被同组一个 Consumer 消费
  • 组间：不同 Consumer Group 各自独立消费，互不影响
Topic: order-topic (3 个分区: P0, P1, P2)

Consumer Group A (2 个消费者):
  ┌── P0 ──┐
  │  P1    │──→ Consumer-A1 (负责 P0 + P2, 一个人干两摊)
  │  P2 ──┘
  └── P1 ────→ Consumer-A2 (只负责 P1)

Consumer Group A (3 个消费者):
  ┌── P0 ──→ Consumer-A1
  │  P1 ──→ Consumer-A2           (刚刚好，各司其职)
  └── P2 ──→ Consumer-A3

Consumer Group A (4 个消费者):
  ┌── P0 ──→ Consumer-A1
  │  P1 ──→ Consumer-A2
  │  P2 ──→ Consumer-A3
  └── ?? ──→ Consumer-A4 (空闲！消费者数 > 分区数，多的闲着)

Consumer Group B (2 个消费者):
  ┌── P0 ──→ Consumer-B1
  │  P1 ──→ Consumer-B1          (B 组独立消费同一份数据)
  └── P2 ──→ Consumer-B2

结论：Topic 的并行消费上限 = 分区数。消费者超过分区数就是浪费。

4.2 Offset 提交——记录消费到哪了

方式 怎么做的 会丢消息吗 会重复吗
自动提交 后台定时提交，不管业务处理完没 容易丢 不会
手动同步提交 业务处理完再提交 不丢 可能重复
手动提交 + 幂等 业务处理完提交 + 数据库去重 不丢 不重复 
// 推荐写法：先处理业务，成功了再提交 offset
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        processRecord(record);  // 处理业务逻辑
    }
    consumer.commitSync();  // 处理完一批，提交一次
}

4.3 重平衡（Rebalance）——消费者变动时的自动调整

消费者加入或离开组时，Kafka 重新分配分区。重平衡期间整个消费者组暂停消费。

避免频繁重平衡：

  • session.timeout.ms 别太短（默认 10s）
  • max.poll.interval.ms 别太小（默认 5 分钟），确保业务处理不会超时
  • 用 CooperativeSticky 策略（增量重平衡，减少停顿）

5. 主题和分区：消息怎么组织？

5.1 分区怎么设？

分区数 = 最大并行消费数

经验值：
  小型应用：3-6 个分区
  中型应用：6-12 个分区
  大型应用：12-64 个分区

注意：分区不是越多越好
  分区太多 → 文件句柄多、内存占用高、端到端延迟增加

5.2 消息保留策略

Kafka 不会消费完就删消息（和 RabbitMQ 不同），按时间或大小保留：

log.retention.hours=168          # 保留 7 天
log.retention.bytes=1073741824   # 或者每个分区最大 1GB

6. 副本和高可用：坏了怎么办？

6.1 ISR——哪些副本跟上了？

每个分区有多个 Replica（副本）：

  Partition-0:
    ┌──────────────────────────────────┐
    │  Leader (Broker-1)    ← 负责读写  │
    │  Follower (Broker-2)  ← 只同步    │ ← ISR 集合 (同步中的副本)
    │  Follower (Broker-3)  ← 只同步    │
    └──────────────────────────────────┘

  写入流程 (acks=all):
    Producer → Leader 写入 → Follower-2 同步 → Follower-3 同步
                                ↓                  ↓
                         全部 ISR 确认 ←───── 返回成功

  Leader 挂了怎么办？
    从 ISR 中选一个新 Leader，保证数据不丢。

  落后超过 replica.lag.time.max.ms (默认 30s) → 踢出 ISR

6.2 消息不丢的配置

生产端：acks=all + retries + 幂等
Broker端：副本数 ≥ 3 + min.insync.replicas ≥ 2
消费端：手动提交 offset + 幂等消费

7. Kafka Streams：实时处理

7.1 一句话理解

Kafka Streams 让你直接在 Kafka 内部对消息流做实时计算——过滤、聚合、统计——无需额外部署 Spark 或 Flink。

// 经典例子：实时统计单词出现次数
KStream<String, String> source = builder.stream("input-topic");

KTable<String, Long> counts = source
    .flatMapValues(value -> Arrays.asList(value.toLowerCase().split("\\W+")))
    .groupBy((key, word) -> word)
    .count();

counts.toStream().to("output-topic");

8.2 发送和接收

// 发送
@Service
public class OrderProducer {
    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    public void sendOrder(Order order) {
        kafkaTemplate.send("order-topic", order.getId(), JSON.toJSONString(order));
    }
}

// 接收（手动 ACK）
@Component
public class OrderConsumer {
    @KafkaListener(topics = "order-topic", groupId = "order-consumer-group")
    public void handleOrder(ConsumerRecord<String, String> record, Acknowledgment ack) {
        Order order = JSON.parseObject(record.value(), Order.class);
        processOrder(order);
        ack.acknowledge();  // 处理成功才确认
    }
}

9. 性能优化

9.1 三端优化速查

生产端：
  ✅ batch.size 调大（32KB）
  ✅ linger.ms 适当（10-20ms）
  ✅ 开启压缩（LZ4）

消费端：
  ✅ max-poll-records 调大（500-1000）
  ✅ 并发数 = 分区数
  ✅ 手动提交

Broker端：
  ✅ num.network.threads 调大
  ✅ num.io.threads 调大
  ✅ log.flush.interval.ms 适当

11. 面试会怎么问？

面试速记三个词: 高性能(顺序写/零拷贝) 高可用(ISR/副本) 可靠性(acks/手动提交)

Q1：Kafka 为什么这么快？

六个原因：顺序写磁盘、Page Cache、零拷贝、批量发送、数据压缩、分区并行。类比流水线：货物排一队上传送带（顺序写），缓冲区暂存（Page Cache），直接搬上卡车（零拷贝），凑满一车发（批量），真空袋压缩（压缩），多条传送带同时工作（分区并行）。

Q2：怎么保证消息不丢失？

  • 生产端：acks=all + 重试 + 幂等
  • Broker 端：副本数 >= 3 + min.insync.replicas >= 2
  • 消费端：手动提交 offset + 业务幂等

Q3：消息顺序怎么保证？

  • 同一 Partition 内：消息严格有序
  • 相同 Key 的消息：hash 到同一分区，有序
  • 不同 Partition 之间：不保证顺序

Q4：消费者组是什么？

组内消费者分摊干活（一个分区只能给一个消费者），不同组独立消费。并行消费上限 = 分区数。

Q5：什么是 ISR？

In-Sync Replicas——和 Leader 保持同步的副本集合。acks=all 时，消息必须被所有 ISR 副本确认才算写入成功。落后超过 30 秒的副本会被踢出 ISR。

Q6：怎么实现精确一次（Exactly-Once）？

  • 幂等生产者：enable.idempotence=true
  • 事务：跨分区原子写入
  • 消费者：手动提交 + 业务层去重（Redis/DB）

💡 学习建议：Kafka 面试记三个词——高性能（顺序写/零拷贝）、高可用（ISR/副本）、可靠性（acks/手动提交）。先理解整体架构图，再搞懂生产者和消费者的核心配置，面试就够了。

与面试岗位的关联：Kafka 常出现在后端 / 大数据 / 架构方向面试中，通常和分布式系统、消息队列选型、流处理（Flink/KSQL）等话题一起考察。
