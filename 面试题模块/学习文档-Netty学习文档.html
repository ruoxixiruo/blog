Netty 面试学习文档

Netty 是 Java 网络编程的事实标准——把复杂、坑多的 Java NIO 封装成简单好用的 API。Dubbo、RocketMQ、ES 等中间件的底层通信都基于它。

整理日期：2026-06-26 | 目标：用最简练的语言覆盖 Netty 面试核心

1. Netty 是什么？为什么要用？

1.1 用大白话说

Java 网络编程有三条路：原生 Socket（BIO，一连接一线程，连接多了就崩）、Java NIO（高效但 API 反人类，flip()/compact() 折腾死人，还有 epoll 空轮询 bug）、Netty（封装 NIO 复杂性，你只写业务逻辑）。

         应用层
    ┌──────┼──────┐
    │ Dubbo│ RocketMQ│ ES │  ← 各种中间件
    └──────┼──────┘
           │
    ┌──────▼──────┐
    │    Netty     │  ← 统一的网络通信层
    └──────┬──────┘
           │
    ┌──────▼──────┐
    │ Java NIO/Epoll│  ← 操作系统级 IO
    └─────────────┘

1.2 核心原因

问题 Java NIO Netty
API 易用性 flip/compact 反人类 读写指针分离，不需要 flip
内存池 没有 PooledByteBuf 复用内存
拆包/粘包 自己写 内置多种解码器
epoll 空轮询 JDK 经典 bug 自旋计数 + 重建 Selector 修复
性能 需要专家调优 零拷贝 + 内存池 + 无锁化

1.3 Netty 的使用场景

  • RPC 框架底层：Dubbo、gRPC Java 版
  • 消息中间件：RocketMQ、Kafka 部分组件
  • 搜索引擎：Elasticsearch 节点间通信
  • API 网关：Spring Cloud Gateway（底层 Netty + WebFlux）
  • IM 服务：推送系统、即时通讯
  • 游戏服务器：多人实时在线游戏

2. 线程模型——Boss & Worker 的双线程模型

2.1 核心结构

              Netty Boss-Worker 线程模型
              ============================

    客户端连接
    ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
    │ Conn1│  │ Conn2│  │ Conn3│  │ ConnN│  ... 数千连接
    └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘
       │         │         │         │
       └─────────┼─────────┼─────────┘
                 │         │
        ┌────────▼─────────▼──────────────┐
        │         BossGroup (1 线程)       │
        │   只做 accept() 接收连接         │
        │   收到后注册到 Worker            │
        └────────┬────────────────────────┘
                 │ 轮询分发
                 ▼
    ┌─────────────────────────────────────┐
    │         WorkerGroup (N 线程)         │
    │  ┌──────┐  ┌──────┐  ┌──────┐      │
    │  │  W1  │  │  W2  │  │  W3  │      │
    │  │ read │  │ read │  │ read │      │
    │  │decode│  │decode│  │decode│      │
    │  │process│ │process│ │process│     │
    │  │encode│  │encode│  │encode│      │
    │  │ write │  │ write│  │ write│      │
    │  └──────┘  └──────┘  └──────┘      │
    └─────────────────────────────────────┘
                 │
                 ▼
           Pipeline 链式处理
  • Boss 线程（通常 1 个）：只负责接收客户端连接，接收后注册到 Worker
  • Worker 线程（默认 CPU 核数 x 2）：负责读写 IO 和业务处理

2.2 关键设计——一个 Channel 绑定一个线程

    Worker 线程 1                Worker 线程 2
    ┌──────────────────┐       ┌──────────────────┐
    │ Channel A        │       │ Channel C        │
    │ Channel B        │       │ Channel D        │
    │ Channel E        │       │                  │
    │                  │       │                  │
    │ 全部串行处理      │       │ 全部串行处理      │
    │ 无需锁!          │       │ 无需锁!          │
    └──────────────────┘       └──────────────────┘

为什么快：每个 Channel 的所有 IO 事件都在同一个 Worker 线程处理，天然串行化，不需要加锁。

2.3 Boss 线程一个够吗？

对于大多数场景够了。一个线程用 epoll 管理几千个连接的建立绰绰有余。百万级连接时可以配多个 Boss 线程监听不同端口。真正的工作瓶颈在 Worker 线程，按 CPU 核数配。

面试话术："Netty 线程模型的核心是 Reactor 模式的变体——Boss-Worker 模型。Boss 负责 accept，Worker 负责 read/write。关键设计是一个 Channel 绑定一个 EventLoop（线程），串行化执行无需锁。生产上 Worker 数配 CPU 核数 x 2，Boss 默认 1 个就够了。"

3. Netty 为什么快？——五大法宝

3.1 五大核心技术

# 技术 说明
1 NIO 多路复用（epoll） 单线程管理数千个连接，不用为每个连接开一个线程
2 零拷贝 DirectBuffer + sendfile，减少内存拷贝
3 内存池 复用 ByteBuf，减少 GC 压力
4 无锁化 每个 Channel 绑定单个线程，串行处理无需锁
5 对象池 ChannelHandler 等可复用，减少对象创建

3.2 epoll 对比传统 BIO

传统 BIO（一个连接一个线程）：
   连接1 → 线程1（阻塞等待）
   连接2 → 线程2（阻塞等待）
   连接3 → 线程3（阻塞等待）
   ...
   问题：1 万连接 = 1 万线程，线程切换开销巨大

epoll 模型（一个线程管所有连接）：
   线程1 ← 连接1、连接2、连接3、... 连接10000
         ↓  epoll_wait() 只返回就绪的连接
         ↓  只处理活跃连接，不空转

3.3 解决 JDK epoll 空轮询 bug

JDK NIO 有个经典 bug：Selector.select() 在特定条件下不阻塞，直接返回 0，导致 CPU 100%。

// Netty 的解决策略（自旋计数）
int SELECTOR_AUTO_REBUILD_THRESHOLD = 512;

// 如果 select() 空转次数超过 512 次，重建 Selector
if (selectCnt > 512) {
    rebuildSelector();  // 新建 Selector，迁移注册的 Channel
}

4. 零拷贝——四大实现方式

4.1 什么是零拷贝？

零拷贝 = 数据不经过用户态拷贝到用户缓冲区，全程在内核态完成。减少 CPU 复制数据的开销。

          零拷贝数据流全景图
          ====================

  传统 IO（4 次拷贝，2 次 CPU 拷贝 + 2 次 DMA 拷贝）：
  ┌──────┐    DMA     ┌──────────┐   CPU    ┌──────────┐   CPU    ┌──────────┐    DMA     ┌──────┐
  │ 磁盘  │ ────────→ │ 内核缓冲区 │ ──────→ │ 用户缓冲区 │ ──────→ │ Socket缓冲区│ ────────→ │ 网卡  │
  └──────┘           └──────────┘         └──────────┘         └──────────┘           └──────┘
                        (1)                 (2)                  (3)                    (4)

  零拷贝 sendfile（2 次 DMA 拷贝，0 次 CPU 拷贝）：
  ┌──────┐    DMA     ┌──────────┐    DMA     ┌──────┐
  │ 磁盘  │ ────────→ │ 内核缓冲区 │ ────────→ │ 网卡  │
  └──────┘           └──────┘           └──────┘
                        (1)                (2)
                   CPU 不参与数据搬运！

4.2 Netty 的四种零拷贝实现

Netty 的零拷贝是组合拳，不是单一技术：

1. CompositeByteBuf（组合缓冲区）
   Header Buffer(请求头) + Body Buffer(请求体)
              ↓ 不拷贝数据，逻辑组合
   CompositeByteBuf（对外表现为一个整体）
   = 零拷贝合并多个 ByteBuf

2. wrap / slice（包装/切片）
   原始 ByteBuf [H][E][L][L][O]
     slice(1,3) →  [E][L][L]（共享同一块内存！）
   不复制数据，只创建新的视图指针

3. FileRegion（文件传输，底层 sendfile）
   ┌──────┐    DMA     ┌──────────┐    DMA     ┌──────┐
   │ 磁盘  │ ────────→ │ 内核缓冲区 │ ────────→ │ 网卡  │
   └──────┘           └──────────┘           └──────┘
   全程不经过用户态，FileChannel.transferTo() → sendfile()

4. 池化内存（PooledByteBufAllocator）
   = 对象复用而非每次 new，减少 GC 压力

4.3 和 OS 零拷贝的区别

层次 技术 说明
OS 级 sendfile()、mmap() 系统调用，避免内核态和用户态间拷贝
Netty 级 CompositeByteBuf、slice() JVM 层面的零拷贝，避免 Buffer 间复制数据

两者互补。Netty 的 FileRegion 封装了 transferTo()（底层是 sendfile），把文件直接写到网卡。

面试话术："Netty 的零拷贝是一套组合策略。FileRegion 依赖 OS 的 sendfile 零拷贝，CompositeByteBuf 是 JVM 层面的零拷贝——两者解决的问题不同，但目的一样：减少不必要的数据复制。"

5. ByteBuf——比 ByteBuffer 好在哪里

5.1 ByteBuffer 的致命缺陷

// JDK ByteBuffer 的使用痛苦
ByteBuffer buf = ByteBuffer.allocate(1024);
buf.putInt(42);           // 写模式
buf.flip();               // 切换为读模式（不翻转就读不了）
int value = buf.getInt(); // 读取
buf.compact();            // 读完了切换回写模式（或 clear()）
// 忘了 flip / compact → 数据错乱或读不到

5.2 ByteBuf 的改进

       读指针(readerIndex)    写指针(writerIndex)
              ↓                    ↓
┌─────────────────────────────────────────────┐
│  已读区  │   可读区   │   可写区    │  可扩容  │
│ (discard) │ (readable) │ (writable) │(动态扩容)│
└─────────────────────────────────────────────┘
特性 ByteBuffer ByteBuf
读写切换 需要 flip/compact 读写指针分离，不需要切换
长度 固定 动态扩容（写满自动扩展）
池化 无 PooledByteBufAllocator
引用计数 无 reference counting 自动释放
零拷贝 无 slice / composite 等

5.3 引用计数管理

ByteBuf buf = ByteBufAllocator.DEFAULT.buffer(1024);
buf.retain();   // 引用计数 +1
buf.release();  // 引用计数 -1，减到 0 自动回收

// 错误：忘记 release → 堆外内存泄漏！
ByteBuf buf = ...;
process(buf);
// 忘了 release! 堆外内存永远不会被 GC 回收

5.4 三种 ByteBuf 类型

类型 分配方式 适用场景
Heap ByteBuf 堆内存，GC 管理 普通业务处理
Direct ByteBuf 堆外内存，零拷贝 高性能网络 IO
Composite ByteBuf 逻辑组合，无拷贝 多 Buffer 合并

调试内存泄漏：启动参数加 -Dio.netty.leakDetection.level=PARANOID，如果日志中出现 LEAK: ByteBuf.release() was not called before it's garbage-collected，说明有 ByteBuf 没释放。

6. ChannelPipeline——责任链模式的艺术

6.1 Pipeline 结构

ChannelPipeline = 一条双向流水线。入站数据从 Head 流向 Tail，出站数据从 Tail 流向 Head。

          ChannelPipeline 双向处理流
          ============================

  入站方向 (Inbound: Head → Tail, InboundHandler 顺序执行)
  ════════════════════════════════════════════════════════▶

  ┌──────┐   ┌──────────────┐   ┌────────────┐   ┌──────────────┐   ┌──────┐
  │ Head │ → │ FrameDecoder │ → │  Protocol  │ → │  Business    │ → │ Tail │
  │      │   │ (字节→帧)    │   │  Decoder   │   │  Handler     │   │      │
  └──────┘   └──────────────┘   │ (帧→对象)  │   │ (处理业务)   │   └──────┘
                                └────────────┘   └──────────────┘

  ◀════════════════════════════════════════════════════════
  出站方向 (Outbound: Tail → Head, OutboundHandler 逆序执行)

  ┌──────┐   ┌──────────────┐   ┌────────────┐   ┌──────────────┐   ┌──────┐
  │ Head │ ← │ FrameEncoder │ ← │  Protocol  │ ← │  Business    │ ← │ Tail │
  │      │   │ (加长度头)   │   │  Encoder   │   │  Handler     │   │      │
  └──────┘   └──────────────┘   │ (对象→字节)│   │ (返回结果)   │   └──────┘
                                └────────────┘   └──────────────┘

6.2 核心规则

  • InboundHandler（入站处理器）：按添加顺序执行，数据从 Head 到 Tail
  • OutboundHandler（出站处理器）：按添加的逆序执行，数据从 Tail 到 Head
  • ctx.fireChannelRead(msg)：传给下一个 InboundHandler——忘调 = 数据丢了
  • ctx.write(msg)：从当前 Handler 往前（Tail 方向）找 OutboundHandler 开始写出站

6.3 典型配置

ch.pipeline()
    .addLast(new LengthFieldBasedFrameDecoder(...))  // Inbound 1: 拆帧
    .addLast(new ProtobufDecoder(...))               // Inbound 2: 解码
    .addLast(new ProtobufEncoder())                  // Outbound 1: 编码
    .addLast(new LengthFieldPrepender(2))            // Outbound 2: 加帧头
    .addLast(new BusinessHandler());                 // Inbound 3: 业务

执行顺序：

入站：Head → LengthFieldBasedFrameDecoder → ProtobufDecoder → BusinessHandler → Tail
出站：Tail → BusinessHandler → ProtobufEncoder → LengthFieldPrepender → Head

6.4 注意事项

  • 不要在 Pipeline 里做耗时操作（如 IO、复杂计算）——会阻塞整个 EventLoop 线程，影响该线程上所有 Channel
  • 耗时操作丢进业务线程池：用 DefaultEventExecutorGroup 指定独立线程池

面试话术："ChannelPipeline 是责任链模式的典型实现，每个 Channel 有独立的 Pipeline。出站和入站的双向流动设计让编解码可以放在同一管道中。记住：Handler 里调用 ctx.fireChannelRead() 把数据传给下一个，不调就断了。"

7. 拆包/粘包——TCP 流式协议的难题

7.1 问题根源

TCP 是流式协议——没有消息边界，多个发送可能合并（粘包）或拆分（拆包）。

发送方：  消息1(16B) | 消息2(32B) | 消息3(8B)
                           │
            TCP 缓冲区（可能合并发送）
                           ▼
接收方读取到的可能情况：

粘包：  消息1+消息2(48B) ← 两个包粘在一起
拆包：  消息1前半(10B) | 消息1后半+消息2(38B) ← 一个包被拆开

7.2 四种解决方案

方案 解码器 适用场景 缺点
固定长度 FixedLengthFrameDecoder 定长协议 浪费带宽
换行分隔 LineBasedFrameDecoder 文本协议（如 Redis） 消息不能含换行
自定义分隔符 DelimiterBasedFrameDecoder 特殊分隔符 同上
长度字段 LengthFieldBasedFrameDecoder 二进制协议（最通用） 参数配置复杂

7.3 LengthFieldBasedFrameDecoder 详解

// 消息格式：
// ┌───────────┬─────────────┬─────────────┐
// │ 长度(4B)  │  版本(2B)   │   数据(NB)  │
// │ length    │   version   │    body     │
// └───────────┴─────────────┴─────────────┘

new LengthFieldBasedFrameDecoder(
    1024,   // maxFrameLength: 最大帧长度
    0,      // lengthFieldOffset: 长度字段偏移
    4,      // lengthFieldLength: 长度字段占 4 字节
    6,      // lengthAdjustment: 长度值到 body 的偏移（4+2）
    4       // initialBytesToStrip: 解码后去掉长度字段
);

大多数 RPC 框架（Dubbo、gRPC）都用长度字段方案。LengthFieldBasedFrameDecoder 是按长度拆包的核武器，值得花时间搞懂参数含义。

8. 心跳与断线重连——连接保活机制

8.1 心跳机制

心跳 = 定期给对方发"我还在"。如果对方几次没回应，就判对方断了。

心跳机制：

  Client                        Server
    │                              │
    │──── PING ──────────────────→ │  （客户端发心跳）
    │←─── PONG ───────────────────│  （服务端回应）
    │                              │
    │  ... 5 秒一次 ...            │
    │                              │
    │──── PING ──→ X  （超时）     │
    │  ... 3 次没回 ...            │
    │                              │
    │  判断断连 → 执行重连逻辑      │

8.2 Netty 实现

// 服务端：30 秒没读到数据 → 认为空闲 → 断开
ch.pipeline().addLast(new IdleStateHandler(30, 0, 0, TimeUnit.SECONDS));

// 客户端：5 秒没写数据 → 主动发 PING
ch.pipeline().addLast(new IdleStateHandler(0, 5, 0, TimeUnit.SECONDS));

8.3 断线重连

public void connect() {
    bootstrap.connect(host, port).addListener((ChannelFutureListener) future -> {
        if (!future.isSuccess()) {
            // 断线后延迟 5 秒重连
            future.channel().eventLoop().schedule(this::connect, 5, TimeUnit.SECONDS);
        }
    });
}

生产注意事项：心跳间隔别设太短——1 秒 1 次心跳 x 10 万连接 = 每秒 10 万次 IO，服务器撑不住。一般 30~60 秒一次。IdleStateHandler 判断的是"没读写"而非"连接断没断"——TCP 半开连接可能还在但对方已经挂了，要靠心跳这种应用层探测。

9. 内存池——Slab 分配算法

9.1 为什么要池化？

直接申请 ByteBuf 的问题：
  - 每次分配都调用系统 malloc()
  - GC 回收时需要 C free()
  - 频繁分配/释放造成内存碎片
  - 高并发下 malloc 成为性能瓶颈

池化的解决方案：
  - 预分配内存池，按大小分组
  - 申请时从池中取，释放时归还池（不真的释放）
  - 减少 90%+ 的 malloc/free 调用

9.2 Slab 分配算法

Chunk（16MB 大块）分为多个 Page（默认 8KB）：

Tiny 池: 16B, 32B, 48B, ..., 496B（每 16B 递增）→ Page 内按序分配
Small 池: 512B, 1KB, 2KB, 4KB                   → Page 内分配
Normal 池: 8KB, 16KB, 32KB...                    → 多页组合
Huge 池: > 16MB                                   → 非池化，每次直接分配

思路：申请 64 字节 → 从 Tiny 池拿一块；申请 1KB → 从 Small 池拿一块。不存在"在 64KB 的块里分配 1KB"这种浪费。

9.3 性能对比

分配方式 分配速度 GC 压力 适用场景
UnpooledHeapByteBuf 快 大 普通业务
UnpooledDirectByteBuf 慢（malloc） 无 少量堆外
PooledDirectByteBuf 极快（池化） 极小 高性能网络（推荐）

Netty 4.x 默认使用 PooledByteBufAllocator，3.x 是非池化。这是 4.x 性能大幅提升的关键之一。

10. 异步回调——ChannelFuture 与 Promise

10.1 传统 Future 的问题

Future future = executor.submit(() -> doRequest());
String result = future.get();  // 阻塞等待！线程空转

10.2 Netty 的异步回调

ChannelFuture future = channel.writeAndFlush(msg);
future.addListener((ChannelFutureListener) f -> {
    if (f.isSuccess()) {
        System.out.println("发送成功");
    } else {
        System.out.println("发送失败：" + f.cause());
    }
});
// 不阻塞！继续干别的事 ← 异步回调

10.3 链式异步调用

// 链式：连接成功 → 发送数据 → 处理结果
bootstrap.connect(host, port)
    .addListener(f -> {
        if (f.isSuccess()) {
            Channel ch = ((ChannelFuture) f).channel();
            ch.writeAndFlush(msg)
                .addListener(f2 -> {
                    if (f2.isSuccess()) {
                        System.out.println("发送成功");
                    }
                });
        }
    });

10.4 Future vs Promise

概念 可写 监听 类比
Future 只读结果 addListener 外卖订单（只能查状态）
Promise 可以设置结果 addListener 空白支票（可以填金额） 
// Promise 是可写的 Future
Promise promise = eventLoop.newPromise();
promise.addListener(f -> System.out.println("完成：" + f.get()));
// 在另一个线程设置结果
promise.setSuccess("Hello");

Dubbo 的异步调用就是基于 Netty ChannelFuture 实现的。注意：回调里不要做耗时操作，否则阻塞 EventLoop 线程。

11. Netty vs Tomcat——怎么选？

维度 Netty Tomcat
定位 通用网络通信框架 Web 应用容器（Servlet）
协议 自定义协议（TCP/UDP） 主要 HTTP
IO 模型 原生 NIO/Epoll 早期 BIO，新版才支持 NIO

抽象层次 底层（给你字节流自己处理） 上层（Request/Response 已封装）
学习曲线 陡峭 平缓

一句话：Tomcat 是"开箱即用的 Web 服务器"，Netty 是"造通信系统用的乐高积木"。

选型指南：

做 Web 应用（HTTP REST API） → Tomcat / Spring Boot（内嵌 Tomcat）
做 RPC 框架 / IM / 网关    → Netty
做高性能 HTTP 服务         → Spring WebFlux（底层是 Netty）

12. 高频面试题——临门一脚

12.1 基础篇

1. Netty 是什么？为什么要用 Netty 而不是 Java NIO？

Netty 是高性能网络通信框架，封装了 Java NIO 的复杂 API。Java NIO 的 flip/compact 操作反人类，ByteBuffer 不自动扩容，有 epoll 空轮询 bug。Netty 提供了 ByteBuf（读写指针分离）、内存池、拆包粘包解码器、零拷贝等开箱即用的能力。

2. Netty 的线程模型是怎样的？

Boss-Worker 双线程模型。Boss 线程（通常 1 个）负责接收连接，Worker 线程（默认 CPU 核数 x 2）负责读写 IO 和业务处理。每个 Channel 绑定一个 Worker 线程，串行化执行，天然无锁。

3. Netty 为什么快？

五大法宝：NIO 多路复用（epoll），单线程管数千连接；零拷贝（DirectBuffer + sendfile）；内存池（复用 ByteBuf，减少 GC）；无锁化（Channel 绑定线程，无需加锁）；对象池（复用 Handler 等对象）。

4. Netty 的零拷贝是怎么实现的？

一套组合拳： - CompositeByteBuf：合并多个 Buffer 不拷贝数据 - slice()/wrap()：创建共享内存的视图 - FileRegion：封装 sendfile，内核态直传文件到网卡 - PooledByteBufAllocator：池化复用减少 malloc 调用

12.2 进阶篇

5. ChannelPipeline 的工作原理是什么？

责任链模式的双向流水线。入站从 Head 到 Tail（InboundHandler 顺序执行），出站从 Tail 到 Head（OutboundHandler 逆序执行）。关键方法：ctx.fireChannelRead(msg) 传给下一个 InboundHandler，ctx.write(msg) 往前找 OutboundHandler。不调 fireChannelRead = 数据被吞掉。

6. 拆包/粘包怎么解决？

四种方案：固定长度、换行分隔、自定义分隔符、长度字段。最通用的是 LengthFieldBasedFrameDecoder——从消息头中读取长度字段，按长度拆包。大多数 RPC 框架（Dubbo、gRPC）都用长度字段方案。

7. Netty 的心跳机制怎么实现？

用 IdleStateHandler。服务端配 readerIdleTime=30s——30 秒没读到数据判空闲，断开连接。客户端配 writerIdleTime=5s——5 秒没写数据主动发 PING。心跳间隔别太短，生产上 30~60 秒一次足够。

8. ByteBuf 和 ByteBuffer 的区别？

ByteBuf 读写指针分离不需要 flip，支持动态扩容，支持池化（PooledByteBufAllocator），有引用计数自动释放内存（release() 到 0 自动回收），支持 slice/composite 等零拷贝操作。ByteBuffer 这些都没有。

9. Netty 如何实现异步回调？

ChannelFuture + GenericFutureListener。channel.writeAndFlush().addListener() 在 IO 完成时自动回调，不阻塞主线程。Promise 是可写的 Future，可以手动设置成功/失败结果。

10. Netty 和 Tomcat 的区别？

Netty 是通用网络通信框架（乐高积木），Tomcat 是 Web 应用容器（整栋房子）。Netty 支持自定义协议（TCP/UDP），Tomcat 主要处理 HTTP。Netty 底层用 NIO/Epoll，Tomcat 传统用 BIO。选型：做 RPC/IM/网关用 Netty，做 Web 应用用 Tomcat。

12.3 综合实战篇

11. 用 Netty 实现一个简单的 RPC 框架需要哪些步骤？

  1. 定义协议：长度字段 + 序列化类型 + 请求 ID + 方法名 + 参数
  2. 拆包解码：LengthFieldBasedFrameDecoder 按长度拆包
  3. 反序列化：收到字节数组 → Protobuf/Kryo 反序列化
  4. 路由调用：根据方法名反射调用本地 Bean
  5. 结果返回：序列化结果 → 按协议编码 → 写回 Channel

12. 生产上 Netty 有哪些常见坑和调优点？

坑 / 调优点 解决方案
ByteBuf 内存泄漏 ResourceLeakDetector.PARANOID 检测 + .release() 配对检查
EventLoop 线程阻塞 耗时操作丢进业务线程池（DefaultEventExecutorGroup）
epoll 空轮询 Netty 已自动修复（自旋计数 512 次重建 Selector）
心跳间隔不合理 设 30~60s，太短压力大，太长检测慢
Netty 版本选择 生产务必用 4.x，3.x 不带内存池，性能差距 5 倍+
Worker 线程数 默认 CPU x 2，IO 密集型可以更多（CPU x 4）

总结：Netty 面试核心就四点——线程模型（Boss-Worker + 串行无锁）、零拷贝（四种实现）、ByteBuf（池化 + 读写指针 + 引用计数）、Pipeline（责任链 + 拆包粘包）。大多数问题都围绕这四点展开，搞懂这些就能覆盖 80% 的 Netty 面试题。
