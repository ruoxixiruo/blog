Elasticsearch 零基础入门教程

像查字典一样搜数据 —— 从零到面试通关，这一篇就够了

1. 先搞懂：ES 到底是个啥？

用大白话说

在淘宝搜"华为手机"，一两秒就出来一堆结果，还能按价格排序、按品牌筛选。后台如果用 MySQL 的 LIKE '%华为手机%'，数据一大就卡成狗——因为那是全表扫描。

ES 就像一本超级字典。传统数据库是"先告诉你第几页有什么内容"，ES 反过来——"告诉你哪个词出现在第几页"。搜起来直接翻字典，不用翻遍整本书。

一张表看懂区别

场景 MySQL 的做法 ES 的做法
搜商品 SELECT * FROM goods WHERE name LIKE '%手机%' GET goods/_search → 毫秒级返回 + 按相关性打分
统计分类 SELECT category, COUNT(*) FROM goods GROUP BY category 一个聚合查询，瞬间出结果
分词搜索 做不到（只能前缀匹配） "华为手机" → 自动拆成 "华为" "手机" 两个词搜

ES 到底解决了什么问题？

传统数据库搜东西：
  用户搜 "苹果手机" → LIKE '%苹果手机%' → 逐行扫描 → 慢死

ES 搜东西：
  存的时候：苹果、手机、pro、256GB（提前拆好词）
  搜的时候：苹果、手机（也拆词）
  交叉匹配 → 毫秒级返回 → 还给你相关性打分

ELK 技术栈

ELK 三件套：
  Elasticsearch → 存数据 + 搜数据  ← 你学这个
  Logstash      → 采集数据 + 清洗数据
  Kibana        → 可视化图表 + 控制台

面试第一句话："ES 是一个基于 Lucene 的分布式搜索和分析引擎，核心是倒排索引，搜索速度比传统数据库快几个数量级。"

2. 核心概念 — 用大白话讲透

图书馆比喻

图书馆里的东西 ES 里叫啥 什么意思
整个图书馆系统 Cluster（集群） 一堆机器组成的 ES 集群
一个书柜 Node（节点） 集群里的一台机器
"科技类"那个书架 Index（索引） 一类数据的集合，类似 MySQL 的 Table
一本书 Document（文档） 一条数据，类似 MySQL 里的一行
一本厚书拆成几册放不同书柜 Shard（分片） 索引太大，拆成多份散到不同机器上
每册再复印一份防丢 Replica（副本） 一台机器挂了，副本顶上，不影响用

对照公式

MySQL:   Database → Table    → Row     → Column
ES:      Index    → (Type已废弃) → Document → Field

面试场景直接记：
  ES Index    ≈  MySQL Table
  ES Document ≈  MySQL Row
  ES Field    ≈  MySQL Column

倒排索引 — ES 快的终极秘密

传统数据库像一本正常的书——目录说"第1页讲了苹果，第5页讲了手机"。你要搜"苹果手机"，得把所有页翻一遍。ES 的倒排索引则像一本反向字典：

正排索引（传统DB）:
  第1页  → 苹果
  第5页  → 手机
  第10页 → 苹果、手机

倒排索引（ES核心）:
  苹果 → [第1页, 第10页]
  手机 → [第5页, 第10页]

搜 "苹果手机" → 拆成 "苹果" 和 "手机"
  "苹果"的文档: [1, 10]
  "手机"的文档: [5, 10]
  取交集 → 第10页命中！
  时间: O(1) 查词典，不用扫全表


ASCII 流程图 — 倒排索引结构：

  原始文档（3条）:
  ┌──────────────────────────────────────────────────────────┐
  │ Doc1: "华为 Mate 60 Pro 麒麟芯片"                       │
  │ Doc2: "iPhone 15 Pro Max A17芯片"                       │
  │ Doc3: "华为 P60 Pro 卫星通话"                            │
  └──────────────────────────────────────────────────────────┘
                              │
                              ▼
  ┌────────────────────── 分词 & 建立倒排 ──────────────────────┐
  │                                                             │
  │  华为 ──→ [Doc1, Doc3]        麒麟 ──→ [Doc1]              │
  │  Mate ──→ [Doc1]              芯片 ──→ [Doc1, Doc2]        │
  │  60   ──→ [Doc1]              Pro  ──→ [Doc1, Doc2, Doc3]  │
  │  Pro  ──→ [Doc1, Doc2, Doc3]  Max  ──→ [Doc2]              │
  │  iPhone──→ [Doc2]             P60  ──→ [Doc3]              │
  │  15   ──→ [Doc2]              卫星 ──→ [Doc3]              │
  │  A17  ──→ [Doc2]              通话 ──→ [Doc3]              │
  └─────────────────────────────────────────────────────────────┘
                              │
                              ▼
  搜索 "华为 Pro":
    华为 → [Doc1, Doc3]       ←── O(1) 词典查找
    Pro  → [Doc1, Doc2, Doc3] ←── O(1) 词典查找
    取交集: [Doc1, Doc3]       ←── 内存 bitmap 交集，极快
    返回 Doc1、Doc3，按相关性打分排序

面试金句："ES 的核心是倒排索引，它把文档中的每个词和文档 ID 建立映射关系。搜索时直接查词典就能定位到文档，时间复杂度 O(1)，不用扫全表，这就是 ES 快的根本原因。"

     │        │        │        │        │

         │             │            │
         ▼             │            ▼
   ┌──────────┐        │     ┌──────────┐
   │merged_1  │        │     │merged_2  │

        │              │          │

               │                  │

  一句话: 每1s的refresh产生小段，后台TieredMergePolicy自动

4. 动手撸 CRUD

RESTful API 格式速记

请求格式:  <HTTP方法> /<索引名>/_doc/<文档ID>

  POST  /goods/_doc       → 新增（自动生成 ID）
  PUT   /goods/_doc/1     → 新增/覆盖（指定 ID）
  GET   /goods/_doc/1     → 查询一条
  POST  /goods/_update/1  → 更新
  DELETE /goods/_doc/1    → 删除
  DELETE /goods           → 删除整个索引

5.1 最简单的搜索

// 搜索所有
GET /goods/_search

// 搜名字里带"手机"的
GET /goods/_search
{
  "query": {
    "match": {

    }
  }
}

5.2 match vs term（面试必问！记住这个就不怕了）

// match：会先分词再搜索（analyzed）
// 搜 "华为手机" → 拆成 "华为" 和 "手机" → OR 搜索
GET /goods/_search
{
  "query": {
    "match": {
      "title": "华为手机"
    }
  }
}

// match_phrase：必须连续匹配，顺序不变
// "华为手机" 必须紧挨着出现
GET /goods/_search
{
  "query": {
    "match_phrase": {
      "title": "华为手机"
    }
  }
}

// term：精确匹配，不分词
// 用于 keyword 类型字段，如品牌名 "华为" 完全一致
GET /goods/_search
{
  "query": {
    "term": {
      "brand.keyword": "华为"
    }
  }
}

// terms：多值匹配，相当于 SQL 的 IN
GET /goods/_search
{
  "query": {
    "terms": {
      "brand.keyword": ["华为", "Apple"]
    }
  }
}

一句话记住：match 会分词，搜"华为手机"能匹配到"华为 Mate 60 手机"。term 不分词，必须完全一样。keyword 类型的 field 不会分词，存的就是原始值。

5.3 布尔查询（组合条件，相当于 SQL 的 WHERE）

// 价格在 5000-8000 之间，品牌是华为或Apple，排除小米
GET /goods/_search
{
  "query": {
    "bool": {
      "must": [                    // 必须满足（AND）
        { "range": { "price": { "gte": 5000, "lte": 8000 } } }
      ],
      "should": [                  // 应该满足（OR，加分）
        { "term": { "brand.keyword": "华为" } },
        { "term": { "brand.keyword": "Apple" } }
      ],
      "must_not": [                // 必须不满足（NOT）
        { "term": { "brand.keyword": "小米" } }
      ],
      "filter": [                  // 过滤（不参与打分，更快）
        { "term": { "category.keyword": "手机" } }
      ]
    }
  }
}
子句 含义 影响打分 缓存
must 必须匹配（AND） 影响 否
should 应该匹配（OR） 影响 否
must_not 必须不匹配（NOT） 不影响 是
filter 精确过滤，不参与打分 不影响 自动缓存

面试话术："filter 不参与相关性评分，ES 会缓存 filter 结果，所以对高频查询的性能更好。"

5.4 分页 & 排序

GET /goods/_search
{
  "query": { "match_all": {} },
  "from": 0,              // 跳过前 N 条
  "size": 20,             // 返回 N 条
  "sort": [
    { "price": "asc" },   // 按价格升序
    { "created_at": "desc" }
  ],
  "_source": ["title", "price", "brand"]  // 只返回指定字段
}

深分页问题：from + size 之和超过 10000 默认会报错。解决方案：search_after 或 scroll API。

6. 聚合：一秒钟出报表

聚合（Aggregation）相当于 SQL 的 GROUP BY，但强大得多 —— 可以一键分组 + 统计 + 排序 + 取 TOP N。

6.1 桶聚合（分组统计）

// 按品牌分组，统计每个品牌有多少商品
GET /goods/_search
{
  "size": 0,                    // 不需要文档，只看统计结果
  "aggs": {
    "by_brand": {
      "terms": {
        "field": "brand.keyword",
        "size": 10
      }
    }
  }
}

// 等价 SQL:
// SELECT brand, COUNT(*) FROM goods GROUP BY brand LIMIT 10;

6.2 指标聚合（计算）

// 平均价格、最高价、最低价
GET /goods/_search
{
  "size": 0,
  "aggs": {
    "avg_price": { "avg": { "field": "price" } },
    "max_price": { "max": { "field": "price" } },
    "min_price": { "min": { "field": "price" } },
    "sum_stock": { "sum": { "field": "stock" } }
  }
}

6.3 嵌套聚合（分组后计算）

// 每个品牌 → 平均价格 → 按平均价格排序
GET /goods/_search
{
  "size": 0,
  "aggs": {
    "by_brand": {
      "terms": {
        "field": "brand.keyword",
        "order": { "avg_price": "desc" }
      },
      "aggs": {
        "avg_price": { "avg": { "field": "price" } },
        "top_hits": {
          "top_hits": { "_source": ["title"], "size": 3 }
        }
      }
    }
  }
}

// 等价 SQL:
// SELECT brand, AVG(price) FROM goods GROUP BY brand ORDER BY AVG(price) DESC;
// 同时还拿了每个品牌的前3个商品！

6.4 聚合类型速查

聚合类型 用途 例子
terms 分组统计 按品牌分组
avg / sum / max / min 数值计算 平均价格
range 区间分组 0-5000, 5000-10000
date_histogram 按时间间隔分组 按天统计订单量
top_hits 取每组前 N 条 每个品牌取 top3
cardinality 近似去重计数 统计 UV
percentiles 百分位数 P99 延迟

7. 面试高频 20 问（带答案，直接背）

基础概念

Q1: ES 的索引和 MySQL 的索引有什么区别？

这两个"索引"是两码事。MySQL 的索引是 B+ 树数据结构，让数据库查询更快。ES 的 Index 是一类数据的逻辑容器（类似 Database/Table），它内部用倒排索引来实现搜索加速。面试时一定要说清楚这个区别，很多人在这翻车。

Q2: 什么是倒排索引？

把文档中的词（term）和文档 ID 建立映射。比如 "苹果" → [doc1, doc5, doc10]。搜索时直接查词 → 找到文档列表 → 取交集/并集。时间 O(1) 查词典，不用扫全表。

Q3: ES 为什么近实时？

写入数据后，默认每 1 秒执行一次 refresh，把内存中的数据写入一个新的 Segment 并打开，此时数据才能被搜索到。所以有最多 1 秒的延迟。这叫 Near Real-Time (NRT)。

Q4: ES 的数据可靠性如何保证？

通过 Translog（事务日志）。写入时先记录 Translog 到磁盘，再写内存 Buffer。即使宕机，重启后从 Translog 恢复数据。默认每个请求都 fsync Translog（durability=request）。

集群 & 架构

Q5: Master 节点和 Data 节点的区别？

Master 节点负责集群管理（创建/删除索引、分配分片、维护集群状态），不处理数据读写。Data 节点负责存储数据、执行搜索和聚合。一般小集群可以混用，生产环境必须分离。

Q6: 什么是分片？什么是副本？

分片（Primary Shard）：把一个大索引用 hash(_id) % 分片数 切成多份，分散到不同节点上，实现分布式存储和并行搜索。副本（Replica）：每个主分片的拷贝，用于容灾和分担读压力。

Q7: 分片数怎么定？

主分片数创建后不可改。经验公式：节点数的 1.5-3 倍。一个分片控制在 10-50GB 之间。比如 5 个数据节点，分片数可以设 10。日志场景可以更多。

Q8: ES 如何选主？

基于 Bully 算法变体。所有 master-eligible 节点互相 ping，节点 ID 最小的成为 Master。需要 discovery.seed_hosts 配置种子节点列表。ES 7 以后不需要 minimum_master_nodes。

写入 & 读取

Q9: 写一个文档的完整流程？

见 2.5.3 写入全流程。

  1. 客户端发请求到协调节点
  2. 协调节点根据 _id hash 算出目标分片号
  3. 转发给主分片所在节点
  4. 主分片：写 Translog → 写内存 Buffer → 转发给副本
  5. 所有副本写完 → 主分片返回成功
  6. 协调节点返回给客户端
  7. 1s 后 refresh → 可搜索
  8. 30min 或 512MB 后 flush → 磁盘 commit

Q10: 搜索一个文档的完整流程？

见 2.5.4 搜索全流程。

Query Phase（查询阶段）: 协调节点 → 广播给所有相关分片 → 每个分片返回 Top N 文档 ID + Score

Fetch Phase（获取阶段）: 协调节点 → 合并排序 → 确定全局 Top N → 去对应分片拉完整文档

Q11: 如何优化写入性能？

- 用 _bulk API 批量写入 - 提高 refresh_interval（比如改成 30s） - 写入期间把副本数设为 0，写完再改回来 - 关闭 _all / _source（如果不需要） - Translog 改成 async 模式（牺牲一点可靠性）

Q12: 如何优化搜索性能？

- filter 代替 must（不参与评分 + 缓存） - _source 只返回需要的字段 - 减少返回条数（size 不要太大） - 用 routing 路由到指定分片，避免全分片搜索 - 冷热分离（SSD 热数据 + HDD 冷数据）

进阶

Q13: ES 如何处理分词？

存的时候用 Analyzer 分词。默认 standard 分词器：按空格和标点拆，转小写。中文需要装 ik 分词器（"华为手机" → "华为"、"手机"、"华为手机"）。

Q14: keyword 和 text 的区别？

text：会分词，用于全文搜索。不支持排序和聚合。 keyword：不分词，存原始值。用于精确匹配、排序、聚合。 字符串字段 ES 默认同时创建两种：field (text) 和 field.keyword。

Q15: ES 怎么保证分布式一致性？

写操作：主分片先写，等所有活跃副本写完才返回成功（wait_for_active_shards）。 读操作：默认从主分片读（强一致），也可以从副本读（最终一致）。 集群状态：Master 两阶段提交发布 Cluster State。

Q16: ES 和 MySQL 如何同步数据？

方案：Canal / Maxwell 监听 MySQL binlog → 解析成 JSON → 写 Kafka → 消费写入 ES。或者直接用 Logstash 的 JDBC input 定时全量/增量同步。

Q17: ES 的段合并是什么？为什么需要？

见 2.5.5 段合并。

每个 refresh 生成一个新的 immutable Segment。Segment 太多会降低搜索性能。ES 后台自动把多个小 Segment 合并成大 Segment（TieredMergePolicy），合并时顺便物理删除已标记删除的文档。

Q18: 深分页问题怎么解决？

from + size 超过 10000 会报错或性能极差。解决方案： - search_after：用上一页最后一条的 sort value 做游标，实时翻页 - scroll：生成快照游标，适合全量导出，不适合实时翻页

Q19: ES 有哪些节点类型？

Master / Data / Coordinating / Ingest / ML / Transform / Remote-eligible。最常用的是 Master + Data + Coordinating。

Q20: 你在项目里怎么用 ES 的？

见下一节。

  └──────────┘     └──────────┘     └──────────┘     └──────────┘

  面试话术: "日志场景用 ILM 自动管理——Hot 阶段在 SSD 写入，
  30天或50GB后 Rollover 到 Warm 只读索引，ForceMerge 成1个段
  节省资源，Cold 阶段挂载为可搜索快照，最终到期自动删除。"
