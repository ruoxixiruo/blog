1. Django 的请求生命周期?

浏览器
  ↓
Nginx / uWSGI(接待--HTTP → WSGI 协议转换)
  ↓
Middleware(请求阶段--安检排队)
  ↓  process_request() 按注册顺序执行
URL Router(找到对应窗口)
  ↓
View(处理业务逻辑)
  ↓  ORM 查数据库 / 模板渲染 / 调外部 API
Middleware(响应阶段--出门盖章)
  ↓  process_response() 按注册逆序执行
浏览器 ← 响应

扩展:django-debug-toolbar 可视化各阶段耗时;4.0+ 异步视图需 sync_to_async 包装 ORM。

2. Django 中间件的执行顺序?

中间件是洋葱模型:请求从外到内,响应从内到外。

请求 →
  1 SecurityMiddleware     ← 最先处理请求,最后处理响应
  2 SessionMiddleware
  3 AuthenticationMiddleware  ← 请求最后到,响应最先出
  ... View 处理业务 ...
  3 AuthenticationMiddleware(处理响应)
  2 SessionMiddleware
  1 SecurityMiddleware     ← 最后处理响应
响应 ←

MIDDLEWARE = [
    '安全中间件',     # 1 请求先过我这,响应最后过
    'Session中间件',  # 2
    '认证中间件',     # 3 请求最后到我这,响应先过
]

扩展:自定义中间件实现 process_request/process_response 等;process_exception 做全局异常兜底;勿滥用以免拖慢性能。

3. ORM 中 select_related 和 prefetch_related 的区别?

select_related:  SQL JOIN,一次查询全部带出
prefetch_related:多条 SQL,Python 层面手动关联
select_related prefetch_related
实现方式 SQL JOIN 多条 SQL + Python 关联
适用关系 一对一、外键(多对一) 多对多、反向外键
SQL 次数 1 条 2 条(N+1 → 2)
数据量 JOIN 太多表反而慢 每个关联独立查询
  • select_related:用 SQL JOIN 一次查询把所有关联数据都拿出来。适合一对一、多对一(外键在你这边)。但 JOIN 太多表反而慢
  • prefetch_related:发两条 SQL,Python 里手动关联。适合多对多、反向外键

简单记:select_related 是"一锅出",prefetch_related 是"分开炒然后拼盘"。

扩展:Prefetch() 对象可以自定义预取查询的过滤和排序。django-debug-toolbar 的 SQL 面板能直观看到每种方案发了多少条 SQL,是排查 N+1 的神器。

4. Django 的认证系统原理?

Django 自带用户认证体系:

authenticate(username, password)
    ↓ 验证通过
login(request, user) → 写入 session
    ↓
AuthenticationMiddleware → 每次请求查 session → request.user
    ↓
{% if user.is_authenticated %} / @login_required
  • authenticate() 验证用户名密码对不对
  • login() 在 session 里标记"这个人登录了"
  • 中间件 AuthenticationMiddleware 每次请求自动把 user 对象挂到 request.user 上
  • 模板里直接用 {% if user.is_authenticated %} 判断登录状态

就像商场会员系统:进门刷卡(authenticate)→ 发个手环(session)→ 每次路过商店扫手环就知道你是谁(中间件查 session)。

扩展:实际项目建议第一时间自定义 User 模型(AbstractUser 或 AbstractBaseUser),后期改成本极高。Django 的 Permission 和 Group 模型可以做细粒度权限控制。JWT 认证适合前后端分离项目,可以用 djangorestframework-simplejwt 集成。

5. CBV 和 FBV 的对比?

FBV CBV
代码量 简单接口少 通用 CRUD 少(复用)
灵活性 高,随意写 受限于类结构
复用性 差,靠装饰器 好,靠继承/Mixin
学习曲线 低 中
  • FBV(函数视图):简单直接,适合小接口
  • CBV(类视图):不同HTTP方法对应不同方法(get()/post()),可继承复用

扩展:通用CBV覆盖80%场景;Mixin组合行为比装饰器更灵活。

6. Django 的信号是什么?

信号是事件广播系统：模型保存/删除时自动通知注册的接收者。同步执行，影响性能，重要逻辑勿放信号中。

模型保存 → pre_save 信号发出 → 接收者收到
         → post_save 信号发出 → ...

扩展:复杂逻辑放signals.py难追踪，替代方案在Model的save()中显式调用hook。

7. QuerySet 的惰性求值是什么意思?

QuerySet 创建时不执行SQL，只在真正需要数据时才查询。支持链式追加条件，最后一次性高效执行。

# 触发执行的时刻:
list(qs) / qs[0] / len(qs) / bool(qs) / qs.get()

扩展:explain()查看执行计划;iterator()分批获取;exists()比len(qs)>0更高效。

8. values() 和 values_list() 的区别?

Model.objects.all()        → [<User: 张三>, <User: 李四>]  完整对象,最重
Model.objects.values()     → [{'name':'张三','age':25}, ...] 字典列表
Model.objects.values_list()→ [('张三', 25), ...]             元组列表,最轻
values_list('name', flat=True) → ['张三', '李四']             扁平列表
  • values():返回字典列表
  • values_list():返回元组列表,flat=True取单列返回扁平列表

扩展:返回ValuesQuerySet,不能调用模型方法;only()/defer()是折中方案。

9. 如何优化 Django 的 N+1 查询?

N+1问题：循环中每次访问关联对象都触发一次SQL。用select_related()/prefetch_related()预取关联数据。

# 修复
users = User.objects.prefetch_related('post_set')  # 2条SQL搞定

扩展:模板中关联属性访问也会触发N+1;用django-debug-toolbar排查。

10. F 对象和 Q 对象的作用?

  • F对象:数据库层原子操作,F('age')+1直接在SQL中计算,防竞态
  • Q对象:构建复杂查询条件,支持&/|/~组合AND/OR/NOT
F 对象: UPDATE user SET age = age + 1   ← 数据库层原子操作
Q 对象: WHERE name LIKE '%张%' OR email LIKE '%zhang%'  ← 动态拼条件

F是原子操作(防竞态),Q是条件工厂(拼AND/OR/NOT)。

扩展:F支持算术和跨表引用;~Q()取反;搭配annotate()/aggregate()做复杂统计。

11. Django 的缓存机制?

Django 缓存分四个层级,从粗到细:

全站缓存(最粗)
  ↓
视图缓存 @cache_page(60)
  ↓
模板片段缓存 {% cache 60 sidebar %}
  ↓
底层 API cache.set(key, value, 60)(最细)
  • 全站缓存:UpdateCacheMiddleware + FetchFromCacheMiddleware,整站套一层
  • 视图缓存:@cache_page(60),缓存整个视图 60 秒
  • 模板片段:{% cache 60 sidebar %},只缓存侧边栏
  • 底层 API:cache.set('key', value, 60),手动控制

后端支持 Redis、Memcached、数据库、文件系统等。生产环境优先用 Redis。

扩展:缓存 key 的设计很重要--建议用 业务:实体:ID 的命名规范(如 user:123:profile)。缓存更新策略:旁路缓存(查询时缓存,更新时删缓存)是最常用的。django-cacheops 提供了自动缓存失效的 QuerySet。

12. ForeignKey 的 on_delete 参数有哪些?

外键关联的对象被删了,该级联的数据怎么办:

选项 效果
CASCADE(默认) 一起删
PROTECT 抛异常阻止删除
SET_NULL 外键设null(需null=True)
SET_DEFAULT 外键设默认值
SET() 外键设指定值
DO_NOTHING 让数据库报错

扩展:2.0+强制指定on_delete;业务上PROTECT最安全;软删除是更好的方案。

13. 什么是 Django REST Framework(DRF)?

DRF核心三板斧：Serializer(对象↔JSON+校验)、ViewSet(CRUD封装)、Router(自动生成URL)。附带认证、权限、限流、分页等。

扩展:ModelSerializer自动生成字段;ModelViewSet一行实现CRUD;BasePermission自定义权限。

14. uWSGI 和 Gunicorn 是什么?

两者都是WSGI应用服务器，负责HTTP→WSGI协议转换。uWSGI(C实现，性能高但配置复杂) vs Gunicorn(Python实现，pre-fork模型，简单好用)。

扩展:Gunicorn worker数=(2*CPU核数)+1;3.0+支持ASGI搭配Uvicorn/Daphne;用supervisord/systemd管理进程。

15. Django 中如何自定义用户模型?

Django 推荐用 AbstractUser 扩展用户模型。在 settings.py 设置 AUTH_USER_MODEL。

from django.contrib.auth.models import AbstractUser
class User(AbstractUser):
    phone = models.CharField(max_length=11, unique=True)

需在第一次迁移前配置。用邮箱登录时继承 AbstractBaseUser + BaseUserManager。

16. DRF 的请求生命周期?

HTTP 请求
  → Django 中间件
  → URL 路由匹配
  → 认证 (Authentication) - "你是谁?"
  → 权限 (Permission) - "你能做什么?"
  → 限流 (Throttling) - "请求太频繁了吗?"
  → 视图 (View/ViewSet)
    → 获取数据 (get_queryset)
    → 序列化 (Serializer) - 模型对象 → JSON
    → 数据校验 (validate) - 字段级 → 对象级
    → 保存/返回 (create/update)
  → 渲染 (Renderer) - JSON/HTML/XML
  → HTTP 响应

就像机场安检:先看护照(认证)→ 看舱位等级(权限)→ 排队长了限流(限流)→ 进入候机厅(视图处理业务)。

面试话术:"DRF 的请求先经过 Django 中间件,路由匹配后依次执行认证、权限、限流三道安检,然后进入视图层--获取查询集、序列化、校验、持久化,最后渲染为客户端期望的格式返回。"

17. Serializer 和 ModelSerializer 的区别?

类型 字段定义 create/update 适用场景
Serializer 手动逐个定义字段 需自己实现 复杂逻辑、非 Model 数据
ModelSerializer 根据 Model 自动生成 自动实现 标准 CRUD、快速开发

选择建议:能用 ModelSerializer 就用它,省代码;复杂业务逻辑(多表嵌套、非 Model 数据源)用 Serializer。

18. 认证和权限的区别?

认证(Authentication):确认"你是谁"
  → 返回 (user, auth) 元组 → request.user 设置
  → 失败 → 401 Unauthorized

权限(Permission):确认"你能做什么"
  → 在认证之后执行
  → 失败 → 403 Forbidden

记忆: 认证在前,权限在后。先验身份再查权限。

19. 多个认证类的调用顺序是怎样的?(高频)

DRF 按 authentication_classes 列表顺序依次调用每个类的 authenticate() 方法:

JWT 认证 → Session 认证 → Basic 认证
   │            │            │
   ▼            ▼            ▼
返回(user,auth) 返回 None  抛出异常
   │            │            │
   ▼            ▼            ▼
认证成功!    继续下一个  认证失败!
立即停止      直到找到      返回 401

三种返回结果: - 返回 (user, auth) → 认证成功,立即停止遍历后续类 - 返回 None → 该认证类不适用,继续尝试下一个 - 抛出 AuthenticationFailed → 认证失败,立即返回 401

配置建议:把最常用、最快的认证方式放前面(如 JWT 放首位)。

20. 如何实现 JWT 认证?

JWT 认证流程:

  1 登录 → 验证用户名密码
  2 服务端生成 access_token(短期,如 30min)+ refresh_token(长期,如 7天)
  3 客户端存储 token
  4 后续请求带 Authorization: Bearer <access_token>
  5 access_token 过期 → 用 refresh_token 换新的 access_token
  6 refresh_token 也过期 → 重新登录

使用 djangorestframework-simplejwt 实现,提供 /api/token/ 获取 token,/api/token/refresh/ 刷新。

21. ViewSet 和 Generic View 的区别?

代码量对比:

Generic View(每个操作一个类):
  class ArticleList(ListCreateAPIView):    # 列表+创建
  class ArticleDetail(RetrieveUpdateDestroyAPIView): # 详情+更新+删除
  → 两个类,手动写 URL 映射

ViewSet(一个类搞定所有):
  class ArticleViewSet(ModelViewSet):     # 全部 CRUD
  → 一个类 + Router 自动生成 URL
  → 额外操作用 @action 装饰器

ViewSet 更简洁,配合 Router 自动生成 URL;Generic View 更灵活,每个视图独立配置。常规 CRUD 用 ViewSet,复杂定制用 Generic View。

22. DRF 如何做接口分页?

分页方式 原理 SQL 适用场景
PageNumberPagination 页码 + 每页条数 LIMIT N OFFSET M 简单直观,小数据量
LimitOffsetPagination 偏移量 + 条数 LIMIT N OFFSET M 灵活翻页
CursorPagination 游标 ID WHERE id > N LIMIT M 大数据量,无 COUNT 查询

面试亮点:CursorPagination 不需要 SELECT COUNT(*),数据量越大优势越明显,但只能前后翻页不能跳页。

23. 如何优化 DRF 接口性能?

优化金字塔(从下到上):

  5 缓存层: Django cache / Redis 缓存热点数据
  4 序列化层: 按场景用不同 Serializer,避免字段过多
  3 分页层: 大数据量用 CursorPagination(免 COUNT)
  2 字段层: only()/defer() 控制 SELECT 字段
  1 数据库层: select_related() 解决 FK N+1, prefetch_related() 解决 M2M N+1

面试话术:"DRF 性能优化从数据库层开始--用 select_related 做 JOIN 预取外键,prefetch_related 预取多对多;再到序列化层,按场景精简字段;最后到缓存层,热点数据走 Redis。核心是减少 SQL 查询次数和查询数据量。"

24. Serializer 的校验顺序?

数据进入 Serializer → 四层校验流水线:

  1 字段类型校验      CharField 的 max_length、IntegerField 的 min_value
        ↓ 通过继续
  2 字段 validators 列表  字段定义时传入的 validator 函数
        ↓ 通过继续
  3 validate_<field>()   字段级别自定义校验(如 validate_email)
        ↓ 通过继续
  4 validate()           对象级别校验(跨字段联合校验,如 开始时间<结束时间)
        ↓ 通过
  数据存入 validated_data,返回给视图

面试话术:"校验从宽到严、从通用到具体。字段类型校验最基础,validate() 做跨字段联合校验。面试中常被问到--'密码和确认密码一致在哪校验?'答:在 validate() 做跨字段校验。"

25. DRF 中 @action 装饰器的用法?

# detail=True: 操作单个对象,URL 含 pk → /api/articles/{pk}/publish/
@action(detail=True, methods=['post'], url_path='publish')
def publish(self, request, pk=None):
    article = self.get_object()
    article.status = 'published'
    article.save()
    return Response({'status': 'published'})

# detail=False: 操作集合,URL 不含 pk → /api/articles/stats/
@action(detail=False, methods=['get'], url_path='stats')
def stats(self, request):
    total = self.get_queryset().count()
    return Response({'total': total})

参数说明:detail=True 含 pk(单个对象),False 不含 pk(集合);methods 允许的 HTTP 方法;url_path 自定义 URL 路径;permission_classes 可单独设置权限。

26. 如何实现搜索和过滤?

class ArticleViewSet(ModelViewSet):
    queryset = Article.objects.all()
    serializer_class = ArticleSerializer

    filterset_fields = ['category', 'status']       # 精确过滤
    search_fields = ['title', 'content']             # 模糊搜索 (icontains)
    ordering_fields = ['created_at', 'views']        # 排序

# GET /articles/?category=tech&search=django&ordering=-views
# → 先筛 category=tech → 再搜标题含django → 按浏览量倒序

需要 django-filter 包支持。search_fields 可加前缀精确控制:^field 前缀匹配、=field 精确匹配、@field 全文搜索。

27. DRF 的渲染器(Renderer)是什么?

渲染器负责将响应数据序列化为客户端期望的格式。DRF 通过请求的 Accept 头自动选择渲染器:

Accept: application/json → JSONRenderer(返回 JSON)
Accept: text/html → BrowsableAPIRenderer(浏览器可视化界面)

生产环境通常只保留 JSONRenderer,关闭 BrowsableAPIRenderer 以减小暴露面。

28. DRF 如何处理异常和限流?

异常处理:DRF 自带 exception_handler 处理 APIException 及子类。可自定义 EXCEPTION_HANDLER 统一格式化异常响应。

1. 核心机制：APIView → exception_handler

def custom_exception_handler(exc, context):
    # 1. 先调用 DRF 默认处理
    response = exception_handler(exc, context)

    # 2. 自定义额外处理
    if isinstance(exc, IntegrityError):
        return Response(
            {"error": "数据冲突", "detail": str(exc)},
            status=status.HTTP_409_CONFLICT
        )

    # 3. 未处理的异常统一包装
    if response is None:
        return Response(
            {"error": "服务器内部错误"},
            status=status.HTTP_500_INTERNAL_SERVER_ERROR
        )

    return response


# 注册到 settings
REST_FRAMEWORK = {
    'EXCEPTION_HANDLER': 'myapp.utils.custom_exception_handler',
}

限流配置:

REST_FRAMEWORK = {
    'DEFAULT_THROTTLE_CLASSES': [
        'rest_framework.throttling.AnonRateThrottle',  # 匿名用户
        'rest_framework.throttling.UserRateThrottle',  # 认证用户
    ],
    'DEFAULT_THROTTLE_RATES': {
        'anon': '100/day',    # 匿名用户每天 100 次
        'user': '1000/day',   # 认证用户每天 1000 次
    }
}

限流支持:AnonRateThrottle(按 IP)、UserRateThrottle(按用户)、ScopedRateThrottle(按 API 视图)。

29. Django ORM 如何处理 N+1 查询问题?

N+1 问题:查询 100 条订单时,先查 orders(1 条 SQL),再逐条查关联 user(100 条 SQL),共 101 条。

# 错误:触发 N+1
orders = Order.objects.all()
for order in orders:
    print(order.user.name)  # 每次循环都查一次 user 表!

# 正确:select_related 预取外键(1 条 SQL JOIN)
orders = Order.objects.select_related('user').all()
for order in orders:
    print(order.user.name)  # 已预取,无额外查询

解决方案:一对一/外键用 select_related(JOIN),多对多用 prefetch_related(IN 查询+Python 关联)。

扩展:django-debug-toolbar 可直观展示 SQL 数量;prefetch_related(Prefetch('items', queryset=Item.objects.only('name'))) 可精确控制预取字段。

30. Django 中如何实现乐观锁?

乐观锁假设冲突较少,更新时检查数据是否被他人修改。Django 用 F 表达式+WHERE 条件实现。

from django.db.models import F

# 扣减库存(乐观锁):库存>0才更新,返回影响行数
rows = Product.objects.filter(
    id=product_id,
    stock__gt=0  # WHERE stock > 0
).update(stock=F('stock') - 1)

if rows == 0:
    raise Exception('库存不足或商品不存在')

对比悲观锁(select_for_update() 间隙锁):乐观锁不锁行,高并发下性能更好。但需处理更新失败的重试逻辑。

扩展:秒杀场景推荐 Redis 预扣库存 + 异步落库;乐观锁适合中低冲突场景;悲观锁适合强一致要求如金融转账。

31. Django 如何实现高并发？生产环境怎么部署？

Django 本身是同步的，高并发靠外部机制：

请求链路:
  Nginx(反向代理+静态文件)
    → Gunicorn/uWSGI(WSGI服务器，进程池)
      → Django(业务逻辑)
        → Gunicorn workers × N(每 worker 一个 Python 进程)

每 worker 处理一个请求：Gunicorn 启动多个 worker 进程（如 gunicorn wsgi:app -w 4），每个 worker 独立处理请求，绕过 GIL 实现并发。

异步方案：Django 3.1+ 支持 ASGI（用 uvicorn 运行），可接入 async def 视图，性能接近 FastAPI。

扩展：Nginx + Gunicorn(4 workers) + Django 是经典组合；CPU 密集用多 worker，IO 密集用 gevent（协程补丁）或 ASGI；uWSGI 功能最全但配置复杂，Gunicorn 简单够用。
