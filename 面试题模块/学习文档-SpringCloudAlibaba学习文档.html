1. 先搞懂：Spring Cloud Alibaba到底是个啥？

1.1 用大白话说

2018年，Spring Cloud Netflix 全家桶（Eureka/Hystrix/Zuul）的核心组件陆续停更。阿里巴巴将自家双十一打磨十年的中间件（Nacos、Sentinel、Seata、Dubbo、RocketMQ）打包成 Spring Cloud Alibaba，无缝接入 Spring Cloud 生态。

一句话：Netflix 停更，阿里接盘，并且组件更强、更全、更经实战考验。

1.2 技术定义

Spring Cloud Alibaba 是阿里开源的一站式微服务解决方案，提供配置管理、服务发现、流量控制、分布式事务、消息驱动等能力。

  • GitHub：https://github.com/alibaba/spring-cloud-alibaba
  • 定位：补齐 Spring Cloud 在国内场景的短板（注册/配置/流量/事务）

4. Sentinel 流量控制——交通管制中心

4.1 用大白话说 Sentinel

热门景区管理：每天限流入园（QPS限流），景点拥挤就关闭入口（熔断），热门项目排队领号（匀速排队），特殊时段增派安保（自适应保护）。

Sentinel 就是景区的总控中心，实时监控每个"景点"（接口）的流量，超出阈值直接拦截，保护系统不崩溃。

4.3 流量控制（Flow Rule）

// 编程方式配置限流规则
@Component
public class SentinelConfig {

    @PostConstruct
    public void initFlowRules() {
        List<FlowRule> rules = new ArrayList<>();

        // QPS 限流
        FlowRule qpsRule = new FlowRule("user-service")
            .setGrade(RuleConstant.FLOW_GRADE_QPS)      // QPS 模式
            .setCount(100)                               // 阈值：每秒 100 次
            .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT)  // 直接拒绝
            .setStrategy(RuleConstant.STRATEGY_DIRECT);  // 直接限流

        rules.add(qpsRule);

        // 关联限流（当关联资源超过阈值时，限流本资源）
        FlowRule relatedRule = new FlowRule("order-service")
            .setGrade(RuleConstant.FLOW_GRADE_QPS)
            .setCount(10)
            .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT)
            .setStrategy(RuleConstant.STRATEGY_RELATE)  // 关联限流
            .setRefResource("user-service");           // 关联 user-service

        rules.add(relatedRule);

        FlowRuleManager.loadRules(rules);
    }
}

4.4 流控效果——三种模式

效果 说明
直接拒绝（default） QPS 超过阈值，直接返回 Blocked by Sentinel
冷启动（Warm Up） 冷启动时间窗口内逐步提升 QPS 到阈值（适合秒杀场景）
匀速排队（Rate Limiter） 匀速通过，适合削峰填谷（超时时间内的请求排队等待）

FlowRule rule = new FlowRule("order-service")
    .setGrade(RuleConstant.FLOW_GRADE_QPS)
    .setCount(10)  // 每秒 10 个请求
    .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER)
    .setMaxQueueingTimeMs(5000);  // 最大排队时间 5s，超时直接拒绝

4.5 熔断降级（Degrade Rule）

// 熔断规则配置
@PostConstruct
public void initDegradeRules() {
    List<DegradeRule> rules = new ArrayList<>();

    // 策略1：慢调用比例熔断
    DegradeRule slowRule = new DegradeRule("user-service")
        .setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType())
        .setCount(0.5)                    // 响应时间阈值（秒）
        .setSlowRatioThreshold(0.5)       // 慢调用比例阈值
        .setMinRequestAmount(5)           // 最小请求数（触发熔断的最小请求量）
        .setStatIntervalMs(10000)        // 统计时间窗口（ms）
        .setTimeWindow(10);               // 熔断持续时间（s）

    rules.add(slowRule);

    // 策略2：异常比例熔断
    DegradeRule errorRule = new DegradeRule("order-service")
        .setGrade(CircuitBreakerStrategy.ERROR_RATIO.getType())
        .setCount(0.5)                    // 异常比例阈值（50%）
        .setMinRequestAmount(5)
        .setTimeWindow(10);

    rules.add(errorRule);

    // 策略3：异常数熔断
    DegradeRule errorCountRule = new DegradeRule("payment-service")
        .setGrade(CircuitBreakerStrategy.ERROR_COUNT.getType())
        .setCount(10)                     // 10 个异常
        .setTimeWindow(60);

    rules.add(errorCountRule);

    DegradeRuleManager.loadRules(rules);
}

4.8 Sentinel vs Hystrix

对比项 Sentinel Hystrix
维护状态 阿里巴巴活跃维护 Netflix 停止维护
社区活跃度 高 低（已归档）
实时监控 可视化 Dashboard Hystrix Dashboard
规则配置 Dashboard + 动态推送（Nacos） 仅本地配置
限流维度 QPS + 并发线程数 仅并发线程数
熔断策略 慢调用比例/异常比例/异常数 异常比例
匀速排队 支持 不支持
热点参数限流 支持 不支持
系统自适应保护 支持 不支持

面试话术："Sentinel 相比 Hystrix 有三个明显优势：一是限流维度更丰富（QPS + 并发线程数），二是支持 Dashboard 可视化配置和动态推送，三是支持热点参数限流和系统自适应保护。这些在双十一这种大流量场景下非常关键。"

5. Seata 分布式事务——跨服务的银行转账

5.1 用大白话说：什么是分布式事务？

下单买商品背后三件事：订单服务创建订单、库存服务扣减库存、账户服务扣减余额。三者分布在不同服务（数据库）中。任一失败，前置操作必须回滚，否则出现"钱没扣但库存少了"或"钱扣了但订单没创建"的严重数据不一致。

Seata 就是保证这三个操作"要么全成功，要么全失败"的协调者。

5.3 四种事务模式——怎么选？

模式 说明 优点 缺点 适用场景
AT 自动补偿（主流模式） 零业务入侵、配置简单 性能损耗、一致性弱 大部分业务场景
TCC Try-Confirm-Cancel 性能高、无锁 业务入侵、需补偿逻辑 高性能/高一致性要求场景
Saga 长事务编排 性能高 无隔离性、补偿复杂 长流程业务
XA 两阶段提交 强一致性 性能低、锁定资源 一致性要求极高的场景

5.5 TCC 模式（性能更高，但需要手写补偿逻辑）

┌─────────────────────────────────────────────────────────────┐
│                TCC 模式（Try-Confirm-Cancel）                 │
│                                                             │
│  Try 阶段：                                                  │
│    - 预留资源（冻结/锁定）                                    │
│    - 检查业务前置条件                                         │
│    - 所有服务 Try 成功 → 进入 Confirm                        │
│    - 任一服务 Try 失败 → 全部 Cancel                        │
│                                                             │
│  Confirm 阶段：                                               │
│    - 确认使用预留的资源                                       │
│    - 幂等操作                                               │
│    - 空回滚（Try 未执行则 Confirm 直接返回）                   │
│                                                             │
│  Cancel 阶段：                                                │
│    - 释放预留的资源                                           │
│    - 幂等操作                                               │
│    - 空回滚（Try 未执行则 Cancel 直接返回）                   │
└─────────────────────────────────────────────────────────────┘

// TCC 模式实现
@Service
public class AccountTCCService {

    @TwoPhaseBusinessAction(
        name = "decreaseAccount",
        commitMethod = "confirm",
        rollbackMethod = "cancel")
    @Transactional
    public void tryDecrease(@BusinessActionContextParameter Long userId,
                            @BusinessActionContextParameter BigDecimal amount) {
        // Try 阶段：冻结余额（记录冻结记录）
        accountRepository.freezeBalance(userId, amount);
    }

    public void confirm(BusinessActionContext context) {
        Long userId = context.getActionContext(Long.class, "userId");
        BigDecimal amount = context.getActionContext(BigDecimal.class, "amount");
        accountRepository.confirmFreeze(userId, amount);
    }

    public void cancel(BusinessActionContext context) {
        Long userId = context.getActionContext(Long.class, "userId");
        BigDecimal amount = context.getActionContext(BigDecimal.class, "amount");
        accountRepository.cancelFreeze(userId, amount);
    }
}

6. Dubbo 微服务框架——高性能高速公路

6.1 用大白话说 Dubbo vs Feign

Feign 像普通公路——基于HTTP，每次请求"建立连接-发送-收到-断开"。简单直接但速度有限。

Dubbo 像高速公路——基于TCP长连接，一次建连持续复用，延迟低、吞吐高、支持多序列化协议。

6.2 Dubbo vs Feign 对比

对比项 Dubbo Feign
通信协议 TCP（Dubbo 协议）/ HTTP / gRPC HTTP（REST）
序列化 高性能序列化（Hessian/Protobuf） JSON
连接方式 长连接（TCP） 短连接（HTTP）
性能 高（约 10 万 TPS） 中（约 2 万 TPS）
使用场景 内部微服务调用 对外暴露的 HTTP API
服务治理 完整（负载均衡/熔断/路由） 基础
注册中心 Nacos / Zookeeper Nacos / Eureka
配置方式 @DubboReference / @DubboService @FeignClient

面试话术："内部微服务高频调用用 Dubbo，对性能和延迟要求高；对外开放 API 用 Feign/REST，标准化好对接。两者可在同一项目中共存。"

7. RocketMQ 消息队列——异步快递系统

7.1 用大白话说 RocketMQ

淘宝下单背后的事：订单创建（同步，必须立刻返回）、发短信（异步，晚几秒没关系）、增加积分（异步，最终一致即可）、推荐算法更新（异步，完全不急）。

RocketMQ 处理后面的"异步活"：A服务发消息到 RocketMQ 就能继续忙别的，B服务从 RocketMQ 取消息慢慢处理，系统间解耦。

7.2 核心概念

概念 说明
Producer 消息生产者
Consumer 消息消费者
Broker 消息存储和转发中心（Topic 存储）
Topic 消息主题（一级分类）
Tag 消息标签（二级分类）
Message Queue 物理队列（一个 Topic 可对应多个 Queue）
Consumer Group 消费者组（集群消费/广播消费）

7.3 消息发送模式

// 1. 同步发送
@Service
public class OrderMessageProducer {

    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    public void sendOrderCreatedMessage(Order order) {
        rocketMQTemplate.asyncSend("order-topic:created", order, new SendCallback() {
            @Override
            public void onSuccess(SendResult result) {
                log.info("消息发送成功: {}", result.getMsgId());
            }
            @Override
            public void onException(Throwable e) {
                log.error("消息发送失败", e);
            }
        });
    }

    // 2. 异步发送
    public void sendOrderPaidMessage(Long orderId) {
        rocketMQTemplate.asyncSend("order-topic:paid", orderId, new SendCallback() { ... });
    }

    // 3. 单向发送（无回调，最高吞吐）
    public void sendLogMessage(String log) {
        rocketMQTemplate.sendOneWay("log-topic", log);
    }

    // 4. 事务消息（最重要的特性）
    public void sendTransactionalMessage(Order order) {
        rocketMQTemplate.execute(
            new TransactionMQProducerTemplate.TransactionCallback<Order>() {
                @Override
                public Message onExecute(Order order) {
                    orderService.process(order);
                    return MessageBuilder.withPayload(order)
                        .setHeader("KEYS", order.getId().toString())
                        .build();
                }

                @Override
                public void onCheck(Order order) {
                    // 检查本地事务状态（由 RocketMQ Broker 回调）
                    // 用于解决"本地事务成功但消息发送失败"的半消息问题
                }
            },
            order
        );
    }
}

        new MessageQueueSelector() {

11. 高频面试题——临门一脚

Q1：Spring Cloud Alibaba 包含哪些组件？各自作用？

答案： - Nacos：注册中心 + 配置中心（配置热推送、多环境隔离） - Sentinel：流量控制 + 熔断降级（QPS/并发限流、熔断策略） - Seata：分布式事务（AT/TCC/Saga/XA 四种模式） - Dubbo：高性能 RPC 框架（替代 Feign，用于内部服务调用） - RocketMQ：消息队列（事务消息、异步解耦） - SchedulerX：分布式任务调度（Cron 任务、失败重试）

Q2：Sentinel 的限流算法原理？

答案： - 计数器算法：固定时间窗口内统计请求数，超过阈值拒绝（简单但有临界突变问题） - 滑动窗口算法：基于时间窗口的改进版，解决临界问题（Sentinel 默认） - 令牌桶算法：以固定速率放入令牌，请求获取令牌后放行（允许突发流量） - 漏桶算法：以固定速率消费请求，超出桶容量拒绝（严格限流）

Sentinel 使用滑动窗口算法，通过 StatisticSlot 实时统计每个资源的 QPS 和并发线程数。

Q3：Seata AT 模式的工作原理？

答案：

1. TM 向 TC 发起全局事务（获取 XID）
2. 各 RM 执行本地事务，Seata 自动生成 Undo Log（记录修改前后数据）
3. RM 向 TC 注册分支事务
4. TM 向 TC 提交/回滚全局事务
5. TC 协调各 RM：
   - 提交：异步删除 Undo Log
   - 回滚：基于 Undo Log 生成反向 SQL 补偿

关键点：
  - Undo Log 自动生成（对业务零入侵）
  - 全局锁保证隔离性（不同全局事务间）
  - 性能损耗约 5-10%（远低于 XA）

Q4：Sentinel 和 Hystrix 的区别？

（详见第 4.8 节对比表）

面试要点： - Sentinel 是 Hystrix 的全面升级（阿里巴巴实际生产验证） - Sentinel 支持可视化 Dashboard + 动态规则推送 - Sentinel 支持热点参数限流、系统自适应保护

Q5：RocketMQ 事务消息解决什么问题？

答案：解决本地事务成功但消息发送失败的分布式一致性问题。

传统 MQ 消息问题：
  业务数据库操作（成功）
    → 发送 MQ 消息（失败）
    → 消息未发送，但业务已提交
    → 下游系统收不到消息，数据不一致

RocketMQ 事务消息解决方案：
  1. TM 向 MQ 发送半消息（Half Message，此时消费者不可见）
  2. 执行本地事务
  3. 本地事务成功 → Commit 半消息 → 消费者可见
     本地事务失败 → Rollback 半消息 → 消费者不可见
  4. MQ Broker 定期回调 TM 检查事务状态（解决网络闪断问题）

使用场景：
  - 订单创建 → 库存扣减（强一致性）
  - 支付成功 → 积分增加、优惠券发放（可异步）

Q6：Dubbo 和 Feign 的区别？如何选型？

答案：

对比项 Dubbo Feign
协议 Dubbo 协议（TCP）/ HTTP / gRPC HTTP/REST
性能 高（约 10 万 TPS） 中（约 2 万 TPS）
连接 长连接（Netty） 短连接
适用场景 内部高性能 RPC 对外 HTTP API
服务治理 完整（限流/路由/权重） 基础

选型建议： - 内部微服务调用：优先 Dubbo（高性能、低延迟） - 对外暴露 API / 与前端交互：使用 Feign/Spring MVC（标准化 REST） - 异构语言：Sidecar 接入

Q8：Nacos 的 CP+AP 双模式如何工作？

答案：

Nacos 根据一致性需求自动切换：

配置管理（CP 模式）：
  - 使用 Raft 协议（Leader-Follower）
  - 写请求经 Leader 复制到多数节点后返回
  - 读取可在任意节点（最终一致）
  - 保证配置变更的强一致性

服务注册（AP 模式）：
  - 使用 Distro 协议（最终一致）
  - 各节点独立处理注册请求
  - 异步同步到其他节点
  - 分区时各节点独立工作（高可用）

总结：
  - 配置中心必须 CP（一致性优先）
  - 注册中心可选 AP（高可用优先，注册不阻塞）

Q9：Seata 的四种事务模式如何选型？

答案：

场景 推荐模式 原因
大部分业务（库存、订单） AT 零入侵、自动补偿、配置简单
性能要求极高（高并发下单） TCC 无全局锁、性能高
长流程（多步骤审批） Saga 编排式、无锁
强一致性要求（金融核心） XA 两阶段提交、强一致
不允许预留资源（库存有限） TCC AT 需要预扣库存

Q10：Sentinel 的熔断策略有哪几种？

答案：

策略 说明 参数
慢调用比例 响应时间超过阈值的比例超过设定值时熔断 count（阈值秒）、slowRatioThreshold（比例）
异常比例 异常请求比例超过阈值时熔断 count（异常比例 0-1）
异常数 异常请求数量超过阈值时熔断 count（异常次数）

熔断状态变化：

Closed（正常）
  → 失败率/慢调用比例超过阈值
  → Open（熔断，所有请求直接拒绝）
  → 等待时间窗口到期
  → Half-Open（尝试放行一个请求）
  → 成功 → Closed
  → 失败 → Open

Q12：如何保证微服务架构的稳定性？

答案：

Spring Cloud Alibaba 全链路稳定性保障：

1. 流量控制（Sentinel）
   - QPS 限流（保护下游）
   - 并发限流（保护线程池）
   - 热点参数限流（防止突发热点）

2. 熔断降级（Sentinel / Dubbo 集群容错）
   - 慢调用比例熔断
   - 异常比例熔断
   - 降级策略（返回默认值 / 走兜底逻辑）

3. 隔离策略
   - Dubbo 服务分组隔离
   - Nacos 命名空间隔离（dev/test/prod）
   - 线程池隔离（不同服务用不同线程池）

4. 超时控制
   - 各层设置合理的超时时间
   - Dubbo 默认 3000ms
   - Feign 默认 1000ms
   - 防止线程阻塞

5. 幂等设计
   - 消息消费幂等（去重表 / 唯一键）
   - 接口幂等（Token / 乐观锁）

6. 监控告警
   - Sentinel Dashboard 实时监控
   - RocketMQ 消息堆积监控
   - Nacos 健康检查
   - 日志聚合（ELK）
