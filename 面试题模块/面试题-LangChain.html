LangChain

LangChain 就像给大模型装上了"工具箱"和"大脑"--让 LLM 能查资料、用工具、记住对话、自己做决策。本文基于 LangChain 1.3.8 + DeepSeek。

1. LangChain 1.x 相比 0.x 最大的变化是什么?

LangChain 1.x 是一次从"工具包"到"框架运行时"的质变。打个比方:0.x 是给你一堆零件让你自己组装,1.x 是给你一条智能流水线。

LangChain 架构演进:

0.x(工具箱时代)                  1.x(框架运行时时代)
┌─────────────────────┐          ┌─────────────────────────┐
│ AgentExecutor        │          │ create_agent            │
│ (笨重,需手写循环)    │   →      │ (一行代码,基于 LangGraph) │
│ Chain                │          │ LCEL (声明式管道)        │
│ ConversationBuffer   │          │ Checkpointer (自动持久化) │
│ 无中间件             │          │ Middleware (可组合插件)   │
│ 各自为政的输出格式    │          │ Content Blocks (统一输出) │
└─────────────────────┘          └─────────────────────────┘

三大核心变化:

  1. create_agent 取代 AgentExecutor:旧版需要手写 ReAct 循环逻辑,新版一行 create_agent(model, tools=[...]) 就构建一个 Agent。

  2. 中间件系统:Agent 的"横切关注点"(安全审批、日志、脱敏)抽成独立中间件,可任意组合。就像 Express/Koa 的中间件一样,不用改 Agent 代码,加一个中间件就多一种能力。

  3. Content Blocks + v3 流式:无论底层用的是 GPT-4、Claude 还是 DeepSeek,输出都被统一成 content_blocks 格式。v3 流式协议提供类型化的事件流,可以精确追踪"现在是文本流"还是"工具调用"。

面试话术:"LangChain 1.x 的核心转变在于从功能库升级为有状态的 Agent 运行时。LangGraph 提供了执行引擎,Checkpointer 提供了持久化,中间件提供了可扩展性。这使得 LangChain 从'快速原型工具'变成了'可生产部署的 Agent 框架'。"

2. create_agent 的执行原理是什么?

create_agent 内部基于 ReAct(Reasoning + Acting) 循环,这是 Agent 最核心的执行模型:

┌─────────────────────────────────────────────────────────────┐
│                 create_agent 执行循环                        │
│                                                             │
│  用户输入:"帮我查天气然后推荐穿什么"                          │
│     │                                                       │
│     ▼                                                       │
│  ┌──────────────┐          ┌─────────────┐                 │
│  │ 1 Model Call │─────────→│ 2 检查结果  │                 │
│  │  LLM 分析意图 │          │  是tool_call│                 │
│  │  决定下一步   │          │  还是text?  │                 │
│  └──────────────┘          └──────┬──────┘                 │
│       ▲                           │                          │
│       │              text (最终回答)                          │
│       │              ┌────────────┘                          │
│       │              ▼                                       │
│       │     ┌──────────────┐                                │
│       │     │  返回答案给用户│  ← 循环结束                    │
│       │     └──────────────┘                                │
│       │                           tool_call                  │
│       │              ┌────────────┘                          │
│       │              ▼                                       │
│       │     ┌──────────────┐                                │
│       │     │ 3 Tool Exec  │  执行工具函数                   │
│       │     │  调 weather() │  拿到结果                      │
│       │     └──────┬───────┘                                │
│       │            │                                         │
│       │            ▼                                         │
│       │     ┌──────────────┐                                │
│       │     │ 4 Observation│  将工具结果追加到消息历史        │
│       │     │  追加到上下文 │                                │
│       │     └──────┬───────┘                                │
│       │            │                                         │
│       └────────────┘  回到 1,LLM 基于新信息继续决策          │
│                                                             │
│  中间件的介入点:                                             │
│    before_model ──→ 1 Model Call ←── after_model            │
│    wrap_tool_call ──→ 3 Tool Exec                           │
│    before_agent / after_agent: Agent 启动/结束时的钩子        │
└─────────────────────────────────────────────────────────────┘

和旧 AgentExecutor 的关键区别: - 每步自动通过 Checkpointer 保存状态--如果执行到一半崩溃,恢复后从断点继续 - 中间件可以在任一环节介入,不需要修改 Agent 核心逻辑 - 结构化输出集成在主循环中,不需要额外 LLM 调用来解析格式

面试话术:"Agent 的执行本质是 LLM 在观察-思考-行动的循环中不断推进。LangGraph 运行时提供了执行引擎,Checkpointer 保证状态可恢复,中间件提供可扩展性。这个架构让 Agent 从玩具变成了可生产部署的组件。"

4. LangChain 1.x 如何管理记忆?

1.x 不再推荐旧的 ConversationBufferMemory(需要手动管理消息列表、token 预算、存储),改用 LangGraph Checkpointer 全自动处理。

记忆方案对比:

旧方案(0.x ConversationBufferMemory):
┌──────────────────────────────────────┐
│  开发者手动管理:                       │
│  1 创建 Memory 对象                   │
│  2 每次对话后手动保存                  │
│  3 控制 token 预算(超过要截断)       │
│  4 自己实现持久化(Redis/DB)          │
│  → 繁琐、易错、难维护                  │
└──────────────────────────────────────┘
                  ↓ 升级为
新方案(1.x LangGraph Checkpointer):
┌──────────────────────────────────────┐
│  框架自动管理:                         │
│  1 Agent 每步执行 → 自动 checkpoint   │
│  2 thread_id 隔离 → 不同对话天然隔离  │
│  3 支持 SQLite/Postgres → 开箱即持久 │
│  4 断点续传 → 崩溃后恢复继续执行       │
│  5 可回溯 → 查看任意时间点状态        │
│  → 全自动、可靠、生产级               │
└──────────────────────────────────────┘

# 使用方式
from langgraph.checkpoint.sqlite import SqliteSaver

checkpoint = SqliteSaver.from_conn_string("checkpoints.db")
agent = create_agent(model, tools, checkpointer=checkpoint)

# 同一 thread_id → 自动继承历史
agent.invoke({"messages": [{"role": "user", "content": "我叫张三"}]},
             config={"configurable": {"thread_id": "1"}})
agent.invoke({"messages": [{"role": "user", "content": "我叫什么名字?"}]},
             config={"configurable": {"thread_id": "1"}})
# → "你叫张三"  ← 自动记住了!

面试话术:"LangChain 1.x 用 LangGraph Checkpointer 替代了旧 Memory 机制。Agent 每执行一步自动存入检查点,通过 thread_id 隔离对话。相比旧方案,开发者无需手动管理消息列表、token 预算和存储,框架全自动处理。关键是还支持断点续传--Agent 执行到一半崩溃,恢复后从断点继续。"

5. LCEL 和 create_agent 怎么选?

决策树:

需要 LLM 运行时动态决策调哪些工具?
  │
  ├── 是 → create_agent
  │       适合: ChatBot、自动化任务、多步骤编排
  │       例子: "帮我查天气、算预算、写行程"
  │
  └── 否 → LCEL (管道式)
          适合: RAG 问答、文本处理、固定 Pipeline
          例子: 用户问题 → 检索 → 拼接 Prompt → LLM 生成 → 输出
维度 LCEL create_agent
控制流 固定的 A→B→C LLM 动态决策
工具调用 手动编排 自动选择和执行
中间件 不支持 支持(HITL/摘要/脱敏)
记忆 需手动管理 Checkpointer 自动
适用场景 纯数据流处理 需要推理和决策的复杂任务
学习成本 低 中

关键判断标准:流程是否在编码时就定死了? 定死 → LCEL,运行时要判断 → create_agent。

6. LangChain 中间件系统是什么?有什么用?

中间件就像给 Agent 装上"安检、监控、审批"插件--不改 Agent 代码,加一个中间件就多一种能力。

Agent 执行流程中的中间件介入点:

  ┌──────────────┐
  │ 用户输入消息   │
  └──────┬───────┘
         │
         ▼
  ┌──────────────────┐
  │ before_agent     │  ← 中间件: 日志记录、权限校验
  └──────┬───────────┘
         │
         ▼
  ┌──────────────────┐
  │ before_model     │  ← 中间件: 消息摘要、PII 脱敏
  ├──────────────────┤
  │ 1 LLM 调用       │
  ├──────────────────┤
  │ after_model      │  ← 中间件: 审计日志、内容审查
  └──────┬───────────┘
         │
    ┌────┴────────┐
    ▼             ▼
  文本响应     工具调用
    │             │
    │    ┌────────┴────────┐
    │    │ wrap_tool_call  │  ← 中间件: HITL 人工审批、频率限制
    │    ├─────────────────┤
    │    │ 执行工具函数     │
    │    └────────┬────────┘
    │             │
    └──────┬──────┘
           ▼
  ┌──────────────────┐
  │ after_agent      │  ← 中间件: 最终审查、日志存储
  └──────────────────┘

三类内置中间件: - HumanInTheLoop:关键操作(删库、发送邮件)需人工点"同意"才执行 - Summarization:对话太长时自动摘要历史消息,控制 token 消耗 - PIIRedaction:自动检测身份证号/手机号/银行卡号并脱敏后才发给 LLM

面试话术:"中间件是 LangChain 1.x 的特色能力,本质是 AOP(面向切面编程)在 Agent 领域的应用。把安全、审计、脱敏这些正交关注点从 Agent 逻辑中解耦出来,可任意组合。相当于给 Agent 装了一套可插拔的'中间件插件系统'。"

8. LangChain 的 Tool 调用失败时怎么处理?

核心结论:Tool 调用失败是 Agent 生产环境的常态,必须有容错机制。LangChain 1.x 提供三种策略:

from langchain_core.tools import tool
from langchain_core.messages import HumanMessage

# 策略1:Tool 内部重试(最简单)
@tool(retry_config={'max_retries': 3, 'stop_after_attempt': 10})
def search_database(query: str) -> str:
    # 网络超时自动重试3次
    return db.search(query)

# 策略2:中间件统一拦截(Tier2)--所有 Tool 失败都走降级
# 在中间件里捕获 ToolException,返回预设降级响应

# 策略3:Agent 层面 fallback--定义备用 Tool
agent = create_agent(
    model,
    tools=[primary_tool, fallback_tool],  # 主备 Tool
    prompt="优先用第一个工具,失败了用第二个"
)

面试回答:"Tool 失败分三层处理:Tool 内部重试解决瞬时故障,中间件统一拦截做监控告警,Agent 层面定义 fallback Tool 做降级。生产环境必须加上 LangSmith 追踪,否则 Tool 失败了你都不知道。"

9. LangChain Agent 的 Token 消耗怎么控制?

核心结论:Agent 的 Token 消耗主要来自三部分:系统 Prompt + 对话历史 + 工具调用结果。控制策略:

# 1. Checkpointer 自动裁剪对话历史
from langgraph.checkpoint.memory import MemorySaver
memory = MemorySaver()
# 滑动窗口保留最近 N 轮对话

# 2. 工具返回结果截断(最容易被忽视)
@tool
async def search_api(query: str) -> str:
    result = await api.search(query)
    return result[:2000]  # 截断到 2000 字符,防止把整个文档塞进 Prompt

# 3. 用结构化输出减少来回对话
structured_model = model.with_structured_output(SearchQuery)
# 一次调用就能拿到结构化参数,不用 LLM 多轮猜测

实际经验:一个 RAG Agent 处理一次查询,Token 消耗可能达到普通对话的 5-10 倍。关键优化点:(1)工具返回值必须截断;(2)对话历史用 Checkpointer 滑动窗口;(3)能用结构化输出就别用自由对话;(4)Embedding 和 Rerank 也算 Token 成本,要选性价比高的模型。

10. LangChain 多 Agent 协作怎么设计?

核心结论:复杂任务拆成多个专职 Agent,用 Supervisor 模式编排。LangGraph 是官方推荐的方案:

from langgraph.graph import StateGraph, MessagesState

# 定义多个专职 Agent
def researcher(state):  # 搜索研究员
    return {"messages": [search_tool.invoke(state["messages"][-1].content)]}

def writer(state):  # 内容撰写者
    return {"messages": [model.invoke(f"基于资料撰写: {state['messages'][-1]}")]}

# Supervisor 路由:根据用户意图分配 Agent
def supervisor(state):
    last = state["messages"][-1].content
    if "搜索" in last or "查询" in last:
        return "researcher"
    return "writer"

# 构建协作图
graph = StateGraph(MessagesState)
graph.add_node("researcher", researcher)
graph.add_node("writer", writer)
graph.add_conditional_edges("supervisor", supervisor, {"researcher": "researcher", "writer": "writer"})

面试回答:"多 Agent 协作的核心是职责分离 + 统一状态管理。Supervisor 负责路由和编排,每个 Agent 只做一件事。相比单 Agent,多 Agent 可并行处理子任务,延迟更低。但要警惕 Agent 间来回对话导致 Token 消耗失控,必须设最大轮次上限。"

11. 如何设计一个生产级 RAG 系统?

生产级 RAG 五层架构:

┌─────────────────────────────────────────────────────────────┐
│  5 评估层 (Evaluation)                                      │
│     RAGAS (Faithfulness / AnswerRelevancy / ContextPrecision)│
│     LangSmith 追踪 · A/B 测试 · 线上反馈(踩/赞/引用点击率)  │
├─────────────────────────────────────────────────────────────┤
│  4 生成层 (Generation)                                      │
│     Prompt 注入检索上下文 · 标注引用来源 · 不知道就说不知道   │
│     ┌──────────────────────────────────────────────┐       │
│     │  系统 Prompt: "根据以下参考资料回答。          │       │
│     │  如果资料中没有相关信息,请如实说明'未找到'。"  │       │
│     │  参考资料: {retrieved_chunks}                  │       │
│     │  用户问题: {question}                          │       │
│     └──────────────────────────────────────────────┘       │
├─────────────────────────────────────────────────────────────┤
│  3 检索层 (Retrieval)                                       │
│     Query 改写 → 混合检索(向量+关键词)                       │
│     → Rerank(Cross-Encoder 精排) → 元数据过滤               │
│     🎯 关键优化: Re-ranking + HyDE 显著提升准确率            │
├─────────────────────────────────────────────────────────────┤
│  2 向量存储层 (Vector Store)                                │
│     原型: Chroma | 生产: FAISS / Qdrant / Pinecone         │
│     Embedding: sentence-transformers / text2vec / OpenAI    │
├─────────────────────────────────────────────────────────────┤
│  1 文档处理层 (Document Processing)                         │
│     PDF/HTML/Word → 结构感知分割(按标题/段落)               │
│     → 加元数据(来源/时间/标题) → 向量化入库                  │
│     ⚠️  中文场景: 选择中文 Embedding 模型,注意 PDF 解析质量   │
└─────────────────────────────────────────────────────────────┘

面试亮点:加上 Re-ranking(用 Cross-Encoder 对检索结果二次排序)和 HyDE(先生成假设文档再检索)可以显著提升检索准确率。这两招是从 60 分到 90 分的关键。

12. LangChain 如何实现 RAG（检索增强生成）？

LangChain 的 RAG 流程分为 索引阶段 + 查询阶段：

索引阶段（离线）：
  文档 → Chunk（切分）→ Embedding（向量化）→ 存入向量数据库

查询阶段（在线）：
  用户问题 → Embedding → 向量检索 → Top-K 相关文档 → 拼 Prompt → LLM → 回答

完整代码实现：

from langchain_community.document_loaders import WebPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.embeddings import OpenAIEmbeddings
from langchain_community.vectorstores import Chroma
from langchain_openai import ChatOpenAI
from langchain.chains import RetrievalQA

# Step1: 加载文档并切分
loader = WebPDFLoader("report.pdf")
docs = loader.load()
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)

# Step2: 向量化存入向量数据库
vectorstore = Chroma.from_documents(chunks, OpenAIEmbeddings())
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# Step3: 构建 RAG Chain
llm = ChatOpenAI(model="gpt-4", temperature=0)
qa = RetrievalQA.from_chain_type(llm=llm, retriever=retriever)

# Step4: 查询
result = qa.invoke({"query": "报告的主要结论是什么？"})
print(result["result"])

RAG 优化策略：

优化方向 方法
检索质量 HyDE（生成假设答案再检索）、混合检索（向量+关键词）
分块策略 Small-to-Big（小块检索，大块输入）、元数据过滤
答案质量 query 改写（Rephrasing）、多跳推理

扩展：LangGraph 是 LangChain 的状态机版本，支持复杂的多步骤 Agent；RAG 评测用 RAGAS 框架（ faithfulness、answer relevance、context precision）；生产环境推荐 Chroma（轻量）或 Qdrant（分布式高性能）。
