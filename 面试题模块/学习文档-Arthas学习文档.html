1. Arthas 概述

1.1 是什么

Arthas（阿尔萨斯）是阿里巴巴开源的 Java 在线诊断工具。它允许开发者在不重启、不修改代码、不打断点的情况下，实时诊断生产环境中的 Java 应用问题。

面试话术：Arthas 最大的价值在于 动态诊断——生产环境通常无法远程 debug、无法加日志重新发布。Arthas 通过 Java Instrumentation + ASM 字节码增强，运行时注入诊断代码，用完即卸载，对业务零侵入。

1.2 核心优势

特性 说明
零侵入 不需要修改代码、不需要重启应用、不需要额外配置
实时生效 Attach 到目标 JVM 后立即开始诊断
命令丰富 涵盖线程、内存、类加载、方法调用、JVM 参数等
安全可控 支持权限控制、不持久化改动、用完即卸载
热修复 支持在线修改字节码并重新加载（临时应急）
开源免费 Apache 2.0 许可，社区活跃

1.3 适用场景

┌─────────────────────────────────────────────────────┐
│                Arthas 适用场景                        │
├─────────────────────────────────────────────────────┤
│ 1. CPU 飙高 → 找到最耗 CPU 的线程和方法              │
│ 2. 内存泄漏 → dump 堆分析、查看对象统计               │
│ 3. 接口慢 → trace 追踪方法调用耗时                     │
│ 4. 参数验证 → watch 方法入参和返回值                    │
│ 5. 死锁检测 → thread -b 一键查找                     │
│ 6. 热修复 → 修改字节码并 redefine                     │
│ 7. 查看配置 → ognl 获取运行时配置值                   │
│ 8. 类冲突 → sc 查看类加载器                            │
│ 9. 调用栈 → stack 查看方法被谁调用了                  │
└─────────────────────────────────────────────────────┘

2. 安装与启动

# 方式一：一键安装（推荐）

# 方式二：下载完整包
curl -O https://arthas.aliyun.com/arthas-packaging.tar.gz

# 方式三：从 IDE 插件启动（不推荐生产用）

# 会列出所有 Java 进程，输入编号选择目标进程

# 2. 直接指定 PID
java -jar arthas-boot.jar <pid>

# 3. 非交互模式（脚本化）

4. 诊断命令

4.1 watch（方法观察）

实际场景中最常用的命令，观察方法调用时的入参、返回值、异常。

# 观察方法入参和返回值
watch com.example.UserService getUser '{params,returnObj}' -x 2

# 观察异常
watch com.example.OrderService createOrder '{params,throwExp}' -e

# 条件过滤：只观察特定入参
watch com.example.UserService getUser '{params,returnObj}' 'params[0] > 100'

# 观察方法执行耗时
watch com.example.UserService getUser '#cost > 1000'

# 输出详解:
#  -x 2   展开结果深度
#  -e     观察异常场景
#  params[0] > 100  条件过滤
#  #cost > 1000  耗时 > 1000ms 才输出

$ watch com.example.UserService getUser '{params,returnObj}' -x 2

    id=1001L

4.2 trace（方法追踪）

追踪方法内部调用链路，找出哪一步最慢。性能诊断的明星命令。

# 追踪方法调用树
trace com.example.OrderService createOrder

# 只显示耗时超过阈值的节点
trace com.example.OrderService createOrder '#cost > 50'

# 跳过 JDK 方法
trace --skipJDKMethod false com.example.OrderService createOrder

$ trace com.example.OrderService createOrder
`---[cost=235.45ms] com.example.OrderService.createOrder()
    +---[cost=1.23ms] com.example.OrderMapper.insert()
    +---[cost=200.45ms] com.example.PaymentService.pay()   ← 耗时点！
    |   `---[cost=198.21ms] com.example.PaymentClient.call()
    +---[cost=2.11ms] com.example.MessageService.notify()
    `---[cost=1.05ms] com.example.OrderService.afterCreate()

面试话术：trace 是"慢接口排查的第一武器"。200ms 的接口，trace 一下就知道哪一步花了 180ms——可能是 Redis 慢查询、DB 连接池等待、第三方调用超时。不用猜，直接看数据。

# 查看方法被谁调用了（反向查找调用者）

`---[cost=1.23ms] com.example.UserService.getUser()
    +---[0.32ms] com.example.OrderService.getUserInfo()    ← 谁在调用
    +---[0.15ms] com.example.UserController.getUser()

4.5 tt（时空隧道）

# 记录方法调用，回放请求（类似"录像机"）

# 查看记录

# 回放某次调用（重放入参，观察结果）

5. 高级命令

5.1 profiler（火焰图）

# 启动 CPU 采样（Arthas 3.6+）
profiler start

# 采样一段时间后停止并生成火焰图
profiler stop --format html

# 采样 30 秒
profiler start --duration 30

# 输出火焰图（SVG/HTML）
profiler stop --file /tmp/flamegraph.svg

# 内存采样
profiler start --event alloc
profiler stop --format html

# 火焰图解读:
#   - X 轴: 按字母排序，不代表时间轴
#   - Y 轴: 调用栈深度
#   - 宽度: 占用 CPU 时间比例
#   - 越宽的方法越有可能是性能瓶颈

5.2 vmtool

# 强制 GC
vmtool --action forceGc

# 获取 Spring Bean 实例（无需 ognl 绕来绕去）
vmtool --action getInstances \
  --className org.springframework.context.ApplicationContext \
  --express '#instances[0]'

5.3 heapdump

# 生成堆转储文件（类似 jmap -dump）
heapdump /tmp/dump.hprof

# 只 dump 存活对象
heapdump --live /tmp/dump-live.hprof

# 注意：大堆 dump 会触发 STW，建议在低峰期执行
# 或开启 -XX:+HeapDumpOnOutOfMemoryError 自动 dump

5.4 mc / redefine / retransform

# 热修复三步走

# 1. 反编译要修改的类
jad --source-only com.example.UserService > /tmp/UserService.java

# 2. 修改源码（vim），然后编译
mc /tmp/UserService.java -d /tmp

# 3. 重新加载字节码
redefine /tmp/com/example/UserService.class

# 或使用 retransform（推荐，更安全）
retransform /tmp/com/example/UserService.class

# retransform vs redefine:
#   - redefine: 直接替换，不支持新增字段/方法
#   - retransform: 支持回退（retransform --deleteAll），更安全

6. 排查实战

6.1 CPU 飙高排查

CPU 飙高 -> Arthas 排查流程:

  1. thread -n 3           # 找出 CPU 占用最高的 3 个线程
  2. thread <tid>          # 查看该线程的堆栈，定位到具体代码行
  3. trace 相关方法         # 追踪方法内部调用，确认耗时代码
  4. watch 入参/返回值       # 检查是否有异常数据导致死循环
  5. profiler start + stop  # 生成火焰图，全局视角

  常见原因:
    - 死循环 / while(true) 未 break
    - 频繁 GC（GC 线程占 CPU）
    - 正则回溯（ReDoS）
    - 序列化/反序列化大对象
    - 无限创建线程

6.2 OOM 排查

OOM -> Arthas 排查流程:

  1. dashboard              # 查看堆/非堆内存使用情况
  2. heapdump /tmp/dump.hprof  # dump 堆快照
  3. 用 MAT 分析 dump 文件  # Leak Suspects → 找到泄漏嫌疑人

  或者用 Arthas 在线分析:
  4. ognl 获取大对象统计     # 查看特定集合大小
  5. vmtool 获取实例数       # 查看某个类有多少实例

  OOM 常见原因:
    - 集合类未释放（static List/LruCache 只增不减）
    - ThreadLocal 未 remove（线程池中复用）
    - 连接/流未关闭（DB/IO/NIO ByteBuffer）
    - 大对象频繁分配（超大数组、大文件读入内存）

6.3 慢接口定位

接口响应慢 -> Arthas 排查流程:

  1. trace <Controller> <method> '#cost > 1000'
     # 看整个接口的调用树，哪一步耗时最长

  2. 根据 trace 结果深入
     - 慢在 SQL:  检查索引、数据量、连接池
     - 慢在 Redis: 检查 bigkey、慢查询
     - 慢在 RPC:  检查下游服务、网络、超时配置
     - 慢在计算:  检查算法复杂度、循环逻辑

  3. stack <service> <method>
     # 反向查谁在调用，确认调用链路是否合理

  4. monitor <service> <method> -c 60
     # 持续监控一分钟，看平均耗时和成功率

  $ trace UserController getUser '#cost > 1000'
  `---[cost=2345ms] UserController.getUser()
      +---[cost=3ms] AuthService.check()
      +---[cost=2200ms] UserService.getUserDetail()  ← 这里慢
      |   +---[cost=1800ms] OrderService.getOrders()  ← SQL 慢
      |   +---[cost=350ms]  CouponService.getCoupons()
      +---[cost=5ms]  UserService.formatResult()

7. 热修复

7.1 什么是热修复

线上遇到紧急 bug（如 NPE、if 条件反了），改代码 → 编译 → 发版 → 重启 需要十几分钟甚至更久。Arthas 的热修复允许直接替换内存中的字节码，秒级修复。

重要：热修复是临时止血手段，仅用于争分夺秒的生产故障。修复后仍需走正常流程发布修复版本。重启后热修复失效。

7.2 操作流程

# ─── 热修复完整流程 ───

# 1. 启动 Arthas 并 attach 到目标进程
java -jar arthas-boot.jar <pid>

# 2. 反编译有问题的类
jad --source-only com.example.XXXService > /tmp/XXXService.java

# 3. 修改源码
vim /tmp/XXXService.java
# 比如: 将 if (user == null) return null 改为 return User.defaultUser()

# 4. 编译修改后的源码
mc /tmp/XXXService.java -d /tmp

# 5. 重新加载类
retransform /tmp/com/example/XXXService.class

# 6. 验证修复效果
watch com.example.XXXService methodX '{params,returnObj}'

# 7. 提交修复代码到 Git，走正常发布流程

8. 原理与架构

8.1 工作原理

Arthas 底层技术栈:

  +----------------------------------------------------+
  |                   Arthas 客户端                       |
  |  (CLI / Web Console / HTTP API)                     |
  +------------------------+---------------------------+
                           |
  +------------------------v---------------------------+
  |              Java Attach API                        |
  |  VirtualMachine.attach(pid)  → 连接目标 JVM        |
  |  VirtualMachine.loadAgent(agent.jar)  → 加载 Agent |
  +------------------------+---------------------------+
                           |
  +------------------------v---------------------------+
  |              Instrumentation API                    |
  |  ClassFileTransformer.transform()                   |
  |  → 当类被加载/重定义时，拦截字节码                   |
  +------------------------+---------------------------+
                           |
  +------------------------v---------------------------+
  |              ASM 字节码框架                          |
  |  直接操作字节码，插入诊断逻辑（不修改源文件）         |
  |  - watch: insert System.currentTimeMillis()         |
  |  - trace: insert 方法进入/退出埋点                   |
  |  - jad:   读取常量池中的字节码反编译                 |
  +------------------------+---------------------------+
                           |
  +------------------------v---------------------------+
  |           目标 JVM 中的用户代码                       |
  |  字节码被增强处插入 Arthas 的 Instrumentation         |
  |  诊断结束 → restore 恢复原始字节码                   |
  +----------------------------------------------------+

关键点:
  - attach: Arthas 通过 Attach API "挂载"到目标 JVM
  - transform: 利用 Instrumentation 在类加载时拦截
  - ASM: 直接操作字节码，比反射更底层、更快
  - 无侵入: 不改源文件，不改 classpath，不持久化

8.2 架构设计

Arthas 整体架构:

+---------------+     +----------------+     +-------------+
|   Arthas CLI  |     |  Tunnel Server  |     | Web Console |
|  (arthas-boot)|     |  (远程管理)      |     | (浏览器)    |
+-------+-------+     +-------+--------+     +------+------+
        |                     |                      |
        +----------+----------+----------+-----------+
                   |                     |
          +--------v--------+   +--------v--------+
          | Arthas Server   |   | Tunnel Client   |
          | (目标 JVM 内)    |   | (反向连接)       |
          |                 |   |                 |
          | instrumentation |   | 支持远程诊断     |
          | ASM 字节码增强  |   | 跨越防火墙       |
          | 诊断结果收集     |   | 集中管理         |
          +-----------------+   +-----------------+

部署模式:
  1. 直连模式: CLI → Attach → 目标 JVM（最常用）
  2. Tunnel 模式: 目标 JVM + Tunnel Client → Tunnel Server → Web UI
  3. Agent 模式: 启动时 -javaagent 自动加载

10. 高频面试题

Q1：Arthas 是什么？解决了什么问题？

Arthas（阿尔萨斯）是阿里开源的 Java 在线诊断工具。它解决了生产环境无法 debug、无法加日志、无法重启的痛点——可以在不重启、不修改代码的情况下，实时查看方法调用、参数、返回值、耗时、内存状态等。

Q2：Arthas 和 jstack / jmap / jstat 有什么区别？

JDK 内置工具（jstack/jmap/jstat）能力分散且需要分别执行不同命令，Arthas 将线程、内存、GC、方法追踪等所有能力集成到一个命令行中。更重要的是 Arthas 能追踪方法级调用（watch/trace），这是 JDK 工具做不到的。另外 Arthas 的交互式命令行体验更好。

Q3：Arthas 的工作原理？

底层基于 Java Attach API + Instrumentation API + ASM 字节码框架。Attach API 连接到目标 JVM 并加载 Agent；Instrumentation API 拦截类加载过程；ASM 直接修改字节码，在目标方法前后插入诊断逻辑。诊断完成后卸载增强，恢复原始字节码，对业务零侵入。

Q4：watch 和 trace 的区别？

对比项 watch trace
输出 入参/返回值/异常 方法内部调用树 + 每步耗时
关注点 方法层面的数据 调用链路的性能
典型场景 参数校验、异常数据定位 慢接口瓶颈分析
条件过滤 支持按入参/耗时过滤 支持按耗时过滤

Q5：Arthas 如何实现热修复？

jad 反编译 → 修改源码 → mc 编译 → retransform 重新加载。先用 jad 反编译目标类，修改后 mc 编译，retransform 将新字节码注入 JVM。retransform 比 redefine 更安全（支持回退）。注意：热修复仅限临时应急，不能新增字段/方法，重启后失效。

Q6：用 Arthas 排查 CPU 飙高的步骤？

1. thread -n 3          → 找到 CPU 最高的 3 个线程
2. thread <tid>         → 查看线程堆栈，定位代码
3. trace 目标方法        → 确认耗时代码路径
4. watch 入参/返回值     → 检查是否异常数据导致死循环
5. profiler start/stop   → 火焰图全局视角

Q7：ognl 命令能做什么？

ognl 可以在线执行任意 Java 表达式——读取/修改静态字段、调用静态方法、获取 Spring Bean、修改运行时配置。典型场景：紧急关闭某个功能、切换降级开关、查看配置中心的值是否生效。不需要发版即可修改内存状态。

Q8：Arthas 安全性如何？

Arthas 有安全机制：支持 IP 白名单（arthas.ip.whitelist）限制连接来源；--tunnelServer 模式下支持认证；操作可审计；默认只绑定 127.0.0.1 不暴露外网。但本质上 Arthas 是强诊断工具（类似 root 权限），生产环境应限制使用权限，避免滥用 ognl 修改线上数据。

学习建议：Arthas 是"实践出真知"的工具——不用背命令，用几次就熟了。建议先在自己电脑上启动一个 Spring Boot 应用，练习 dashboard/thread/trace/watch/jad/ognl 这 6 个最常用的命令。面试时重点说 watch/trace 的区别、CPU 飙高的排查流程 和 热修复流程 即可。
