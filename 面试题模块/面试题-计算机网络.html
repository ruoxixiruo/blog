计算机网络

1. OSI 七层模型和 TCP/IP 四层?

OSI 七层 vs TCP/IP 四层:

OSI(理论模型)          TCP/IP(实际标准)
─────────────────────────────────────────
应用层    ↘
表示层     →  应用层      HTTP, DNS, SMTP, FTP
会话层    ↗
─────────────────────────────────────────
传输层    →  传输层      TCP, UDP
─────────────────────────────────────────
网络层    →  网际层      IP, ICMP, ARP
─────────────────────────────────────────
数据链路层 ↘
          → 网络接口层    MAC, 网卡驱动
物理层    ↗
─────────────────────────────────────────

每层是干嘛的(从下到上): - 物理层:0101 电信号怎么传(网线、光纤、无线电) - 数据链路层:相邻节点间怎么可靠传输(MAC 地址、帧) - 网络层:跨网络怎么找到目的地(IP 地址、路由) - 传输层:端到端怎么可靠/不可靠传输(TCP 保证送到、UDP 发了不管) - 应用层:应用程序怎么用网络(HTTP、DNS、SMTP)

记忆口诀:物数网传会表应。实际面试只关注下面 4 层(特别是传输层和网络层)。

扩展:OSI 是理论模型,TCP/IP 是实际标准。五层模型(物理→数据链路→网络→传输→应用)更实用。

2. TCP 三次握手和四次挥手?

三次握手(建立连接):

Client                         Server
  │                               │
  ├── SYN, seq=x ──────────────→ │  1 客户端:我想连接你
  │                               │
  │ ←── SYN+ACK, seq=y, ack=x+1 ─┤  2 服务端:收到,我也想连接你
  │                               │
  ├── ACK, seq=x+1, ack=y+1 ───→ │  3 客户端:收到,开始传数据
  │                               │
  双方 ESTABLISHED                双方 ESTABLISHED

四次挥手(断开连接):

Client(主动关闭)                 Server
  │                               │
  ├── FIN, seq=u ──────────────→ │  1 客户端:我说完了
  │                               │
  │ ←── ACK, ack=u+1 ────────────┤  2 服务端:知道了(但可能还有话说)
  │                               │
  │ ←── FIN, seq=v, ack=u+1 ─────┤  3 服务端:我也说完了
  │                               │
  ├── ACK, ack=v+1 ────────────→ │  4 客户端:知道了
  │                               │
  等 2MSL(TIME_WAIT)            收到 ACK 立即 CLOSED

扩展:为什么挥手要四次而握手只三次?因为挥手时 Server 收到 FIN 后可能还有数据要发--ACK 和 FIN 分开发。如果 Server 也没有数据了,可以 FIN+ACK 一起发(变成三次挥手)。CLOSE_WAIT 状态积累是服务器常见问题--说明你的程序没有主动 close 连接。

3. 为什么需要三次握手?

核心目的:确认双方的收发能力都正常。

第一次:Server 知道 Client 的发送正常
第二次:Client 知道 Server 的收发正常
第三次:Server 知道 Client 的接收正常

三次之后 → 双方都确认了收发正常 ✓
两次     → Server 不知道 Client 是否能收到自己的消息 ✗

防止旧的 SYN 建立无效连接:如果只有两次握手,Client 发了一个旧 SYN(之前网络延迟的),Server 收到后直接进入 ESTABLISHED 分配资源。Client 自己知道这个 SYN 是旧的,不理它。Server 资源被浪费。

扩展:SYN Flood 攻击利用三次握手。对策:SYN Cookie(用 Cookie 验证)、减少 SYN 超时、增加半连接队列大小。

4. TIME_WAIT 为什么等 2MSL?

两个原因:

1 确保最后一个 ACK 被对方收到
   Client → ACK → Server
   如果这个 ACK 丢了:
     Server 没收到 → 重发 FIN
     Client 还在 TIME_WAIT → 能再发 ACK
   如果 Client 不等直接关了→ Server 永远收不到 ACK

2 让旧连接的数据包"死透"
   旧连接的数据包如果还在网络里漂
   新连接复用相同的四元组(IP+Port对)
   旧数据包到达 → 新连接被搞乱
   等 2MSL 保证所有旧包都已消失

MSL = Maximum Segment Lifetime(报文最大生存时间,Linux 默认 30 秒,所以 TIME_WAIT 默认 60 秒)。

扩展:高并发短连接场景 TIME_WAIT 过多会导致端口耗尽。解决:tcp_tw_reuse(复用端口)、长连接替代短连接。服务端端口固定,不受此影响。

5. TCP 和 UDP 的区别?

维度 TCP UDP
连接 面向连接(三次握手) 无连接,直接发
可靠性 确认应答 + 重传 + 序号 不保证(丢了就丢了)
有序性 保证顺序 不保证(可能后发先到)
头部开销 20 字节 8 字节
流量/拥塞控制 有(滑动窗口+拥塞算法) 无(想发多快发多快)
适用场景 网页、文件、邮件(不能丢) 直播、视频通话、DNS、游戏

为什么直播用 UDP:视频通话卡一帧比等一帧好(实时性 > 可靠性)。TCP 丢包会重传阻塞后续数据--你宁愿看到花屏也不愿意画面冻结。

为什么 HTTP 3.0 用 UDP(QUIC):TCP 的队头阻塞问题无法根治--一个包丢了,后面所有包都被堵住。QUIC 在 UDP 上实现了可靠传输,同时避免了 TCP 的队头阻塞。

扩展:UDP 头部 8 字节,TCP 头部 20 字节起。QUIC 证明可靠性和拥塞控制可以在应用层实现。

6. HTTP 1.0 → 3.0 演进?

HTTP 演进路线:

HTTP/1.0(1996):
  每次请求 → 建立 TCP → 发请求 → 收响应 → 断开 TCP
  一个页面 10 张图 = 10 次 TCP 握手 + 10 次挥手
  浪费!

HTTP/1.1(1997):
  Keep-Alive 持久连接 → 一次 TCP 多次请求
  Pipelining → 不等响应就继续发下一个请求
  但有队头阻塞:第一个请求慢,后面全排队等

HTTP/2.0(2015):
  多路复用:一个 TCP 连接上同时跑多个 Stream 互不阻塞
  头部压缩(HPACK):请求头只发增量
  服务端推送:Server 主动把 CSS/JS 推给客户端
  但仍基于 TCP → TCP 层面的队头阻塞还在

HTTP/3.0(2022):
  基于 QUIC(UDP)→ 彻底解决 TCP 队头阻塞
  0-RTT 握手:连接过的主机不用等,直接发数据
  连接迁移:WiFi 切 4G 连接不中断

扩展:HTTP/2 多路复用但 TCP 丢包仍阻塞所有 Stream。HTTP/3 的 QUIC 在 UDP 上为每个 Stream 独立保证可靠性。

7. HTTPS 的加密过程?

HTTPS TLS 握手流程:

1 ClientHello:
   Client → Server: 我支持的加密套件 + 随机数1

2 ServerHello:
   Server → Client: 选一个加密套件 + 随机数2 + 证书(含公钥)

3 客户端验证证书:
   → 证书链是否受信任?
   → 证书域名和访问的域名是否一致?
   → 证书是否过期?

4 交换密钥:
   Client 生成随机数3(Pre-Master Secret)
   → 用 Server 公钥加密 → 发给 Server
   → 只有 Server 的私钥能解密拿到随机数3

5 双方各用 随机数1+2+3 生成会话密钥:
   → 此后用对称加密通信(AES 等)

为什么混合加密:非对称加密(RSA/ECDHE)安全但慢,适合交换小数据(密钥);对称加密(AES)快,适合加密大数据(传输内容)。

扩展:RSA 密钥交换私钥泄露则历史流量全解密(无前向安全)。ECDHE 每次生成临时密钥对,有完美前向安全性(PFS)。TLS 1.3 只保留 ECDHE。

8. 状态码 301 和 302 的区别?

对比 301 Moved Permanently 302 Found(临时重定向)
含义 永久搬家,地址改了 临时借地方,还会回来
浏览器行为 记住新地址,下次直接去 每次还是先访问原地址
SEO 权重转到新 URL 权重留在原 URL
适用 域名迁移、HTTP→HTTPS 登录后跳转、活动页临时跳

其他常用状态码: - 200 OK:正常 - 304 Not Modified:没变化,用缓存 - 400 Bad Request:你的请求有问题 - 401 Unauthorized:没登录 - 403 Forbidden:没权限 - 404 Not Found:资源不存在 - 500 Internal Server Error:服务器内部出错 - 502 Bad Gateway:网关/反向代理从上游拿到无效响应 - 503 Service Unavailable:服务暂时不可用

扩展:301 转移搜索权重给新 URL,302 权重留在原 URL。307/308 不改变请求方法。

9. GET 和 POST 的区别?

维度 GET POST
语义 获取数据 提交/创建数据
参数位置 URL 查询字符串 请求体
长度限制 URL 长度有限(浏览器~2KB) 理论上无限制
缓存 可缓存、可收藏 不可缓存(通常)
幂等性 幂等(查多少次一样) 不幂等(多次创建多条)
安全性 参数暴露在 URL 参数在请求体中(相对隐蔽,但非加密)
书签 可以 不行

语义 > 技术差异:GET 和 POST 本质上没有安全差别(HTTP 本身都是明文),参数在 URL 还是请求体只是位置不同。真正的区别是语义--GET 是获取,POST 是提交。这也是为什么浏览器对待它们不同(GET 可缓存、可回退不提示)。

扩展:GET 的"长度限制"来自浏览器限制(约 2KB),HTTP 协议本身没有限制。RFC 7231 明确 GET 请求不应该有请求体。

10. Cookie、Session、Token 的区别?

三种方案对比:

Cookie:
  [浏览器] ← 自动携带 Cookie → [服务器]
  服务器 Set-Cookie → 浏览器下次请求自动带上
  4KB 限制,不可跨域

Session:
  [浏览器] ← Cookie: session_id=abc → [服务器]
  服务器内存/Redis: {abc: {userId: 1, name: "张三"}}
  状态在服务端,分布式需要共享 Session(Redis)

Token(JWT):
  [浏览器] ← Authorization: Bearer eyJhbG... → [服务器]
  服务器不存,解密验证签名就行
  无状态,天生分布式友好
对比 Cookie Session Token (JWT)
存储位置 浏览器 服务端 客户端(浏览器/APP)
跨域 不行 需共享 Session 天然支持
分布式 不涉及 需额外方案 天然支持
安全性 HttpOnly 防 XSS 安全 不存敏感信息

JWT 的缺点:不能主动失效(发了就有效,除非加入黑名单/用短过期+Refresh Token)。体积大(Header+Payload+Signature,每次请求都带)。

扩展:JWT Payload 不是加密的——不要存敏感信息!OAuth 2.0 + JWT 是主流认证方案。Refresh Token 有效期长,Access Token 短(15min-2h)。

11. 跨域问题及解决方案?

同源策略:
  http://a.com:8080 的页面想请求 http://b.com/api
  协议不同? domain 不同? 端口不同? → 任一不同即"跨域"
  浏览器直接拦截!这是浏览器的安全机制

三种解决方案:

1 CORS(推荐):
   服务端加响应头:
   Access-Control-Allow-Origin: https://a.com
   Access-Control-Allow-Credentials: true
   Access-Control-Allow-Methods: GET,POST,PUT

   复杂请求先发 OPTIONS 预检请求 → 服务端允许 → 再发正式请求

2 Nginx 反向代理(最彻底):
   前端请求 Nginx → Nginx 转发给后端
   前端永远只跟一个域名打交道,根本不存在跨域

3 JSONP(老办法,仅 GET):
   <script> 标签不受跨域限制
   动态创建 script → 请求带 callback 参数 → 服务端返回函数调用
   仅限 GET,安全风险大,基本不用了

扩展:跨域 Cookie 需前端 withCredentials: true + 后端 Allow-Credentials: true。Allow-Origin 不能是 * 且同时设 Credentials。生产在网关层统一处理 CORS。

12. DNS 解析完整流程?

DNS 解析流程(迭代查询):

浏览器输入 example.com:

1 浏览器 DNS 缓存 → 没找到
2 操作系统 hosts 文件 → 没找到
3 本地 DNS 服务器(ISP/8.8.8.8)→ 没缓存
4 本地 DNS → 根域名服务器:".com 归谁管?"
   根服务器:"我不知道具体 IP,但 .com 的 NS 是 xxx,你去问它"
5 本地 DNS → 顶级域名服务器(TLD):"example.com 是哪个 NS 管?"
   TLD 服务器:"ns1.example.com,这是它的 IP"
6 本地 DNS → 权威 DNS 服务器:"www.example.com 的 IP 是?"
   权威服务器:"1.2.3.4"
7 本地 DNS 缓存结果 → 返回给浏览器

两种查询模式: - 递归查询:客户端 → 本地 DNS → ... 一路往下找,最终结果原路返回(客户端省事) - 迭代查询:本地 DNS 问根、问 TLD、问权威--每次别人给"方向"而不是直接给答案

扩展:CDN DNS 基于用户 IP 做 GeoDNS,返回最近节点 IP。A(→IPv4)、AAAA(→IPv6)、CNAME(别名)。DoH/DoT 将 DNS 请求加密防篡改。

13. TCP 如何保证可靠传输?

TCP 可靠传输四大保障机制:

1 确认应答(ACK)
   发送方发 seq=1, data(100字节)
   接收方回 ACK, ack=101 → "我收到了1-100,下一个期望101"
   没收到 ACK → 发送方知道丢了

2 超时重传
   发了数据没收到 ACK,等超时 → 重发
   超时时间 RTO 是动态计算的(RTT 加权平均 + 偏差)
   超时后 RTO 翻倍(指数退避),避免网络已经拥堵你还猛发

3 流量控制(滑动窗口)
   接收方:"我缓冲区还有 X 字节"(Window Size)
   发送方控制未确认数据的量 ≤ 接收方窗口大小

4 拥塞控制
   不是服务端,是整个网络:"路上堵了,都慢点"
   慢启动 + 拥塞避免 + 快重传 + 快恢复

扩展:TCP 初始序号随机生成(防旧包干扰)。快重传=收到 3 个重复 ACK 立刻重传丢失包。SACK 让发送方只重传真正丢失的部分。

14. TCP 流量控制和拥塞控制的区别?

流量控制 vs 拥塞控制:

┌────────────────────────────────────────────┐
│ 流量控制(Flow Control)                    │
│ 范围:发送方 ↔ 接收方(端到端)            │
│ 手段:接收方通告窗口大小(rwnd)            │
│ 目的:别把接收方撑死                        │
│ 比喻:我碗满了,别给我夹菜了               │
├────────────────────────────────────────────┤
│ 拥塞控制(Congestion Control)              │
│ 范围:发送方 ↔ 整个网络(全局)             │
│ 手段:拥塞窗口(cwnd),根据丢包调整        │
│ 目的:别把网络堵死                          │
│ 比喻:路上堵车了,所有车都得慢              │
└────────────────────────────────────────────┘

发送方实际能发送的量 = min(rwnd, cwnd)

扩展:滑动窗口大小在 TCP 头 Window Size 字段通告(无选项最大 65535 字节)。窗口为 0 时发送方定期发窗口探测包防止死锁。拥塞窗口由发送方自己维护。

15. 拥塞控制的四个阶段?

拥塞窗口(cwnd)变化曲线:

cwnd ↑
    │    慢启动        拥塞避免         快恢复
    │    (指数)       (线性)          (降到一半)
    │        ╱                       ╱
    │      ╱   ╲  ← ssthresh       ╱
    │    ╱       ╲                ╱
    │  ╱           3-ACK触发     ╱
    │╱               ↓         ╱
    └──────────────────────────────→ 时间

四个阶段:

  1. 慢启动:刚开始不知道网络能承受多少 → 指数增长试探(cwnd 从 1 → 2 → 4 → 8 → ...)。名字叫"慢"启动其实增长非常快
  2. 拥塞避免:达到慢启动阈值(ssthresh)后改为线性增长(每次 RTT 加 1),小心翼翼探网络的天花板
  3. 快重传:收到 3 个重复 ACK(说明后续数据到了但中间丢了一个)→ 立刻重发缺失的包,不等超时计时器
  4. 快恢复:快重传后不是回到慢启动(降到 1),而是降到当前 cwnd 的一半,然后直接进入拥塞避免(线性增长)。因为收到 3 个重复 ACK 说明后续包能到,网络没有彻底堵死

扩展:超时丢包→慢启动(cwnd=1 重来);三次重复 ACK→快重传+快恢复(降到一半)。BBR 基于带宽和 RTT 实时测量,不再基于丢包判断拥塞。

16. 滑动窗口是什么?

没有滑动窗口(停等协议):
  发送 → 等 ACK → 发送 → 等 ACK → ...
  效率极低!RTT 越大越慢

有滑动窗口(窗口=4):
  发送 seq=1,2,3,4 →
  ← ACK 1 → 窗口右移 → 发送 seq=5 →
  ← ACK 3 → 窗口右移 → 发送 seq=6,7

  窗口内可以连续发,未确认的包数 ≤ 窗口大小

窗口大小决定了在等 ACK 的时候可以发多少数据。窗口越大,对带宽的利用率越高。但窗口大小受限于接收方缓冲区(rwnd)和网络拥塞(cwnd),取两者最小值。

扩展:滑动窗口本质是"累计确认"。SACK 让接收方告诉发送方具体收到哪些段,发送方只重传丢失部分。

17. WebSocket 和 HTTP 的区别?

HTTP vs WebSocket:

HTTP(半双工,请求-响应):
  Client → Request → Server
  Client ← Response ← Server
  客户端不请求,服务端没法推送

WebSocket(全双工,双向自由通信):
  Client ⇄ Messages ⇄ Server
  建立连接后双方随时可以发,就像打电话

WebSocket 建立过程:

1 HTTP 握手(Upgrade):
   Client → GET /chat HTTP/1.1
            Upgrade: websocket
            Connection: Upgrade
   Server → HTTP/1.1 101 Switching Protocols

2 协议升级完成 → TCP 连接保持 → 双向收发消息

适用场景:聊天应用、在线协作、实时推送(股票/体育)、网页游戏。不适合简单场景(REST API 够用就别加 WebSocket)。

扩展:Socket.IO 是 WebSocket 封装,增加了自动重连、房间、fallback。SSE 是服务端单向推送方案,比 WebSocket 简单,但不支持双向通信。

18. select、poll、epoll 的区别?

select/poll/epoll 都是"一个线程同时监视多个 socket"的机制

select:
  把所有 socket 的 fd 拷贝到内核 → 内核轮询检查 → 返回就绪的
  O(n) 轮询,最多 1024 个(fd_set 位图限制)

poll:
  和 select 一样,但用链表替代位图 → 无连接数上限
  还是 O(n) 轮询,连接多了性能还是下降

epoll(Linux 2.6+):
  1 epoll_create → 创建 epoll 对象
  2 epoll_ctl → 注册要监听的 fd,用红黑树管理
  3 epoll_wait → 只返回就绪的 fd(事件驱动,O(1) 获取)

  不是轮询!是回调通知--哪个 socket 有数据了内核直接回调通知

为什么 epoll 强:就像快递员送 10000 户--select/poll 是挨家挨户敲门(没快递也敲),epoll 是保安亭通知"3号楼501、7号楼302 有快递,去送"。

扩展:Nginx 和 Redis 基于 epoll 高并发。Java NIO(Selector)在 Linux 底层也是 epoll。Windows 用 IOCP,macOS/BSD 用 kqueue。

19. CDN 的原理?

CDN 工作流程:

用户请求 cdn.example.com:
  1 DNS 解析 → CDN 的 DNS 服务器根据用户 IP 判断位置
     → 返回离用户最近的边缘节点 IP
  2 用户 → 边缘节点请求资源
  3 边缘节点有缓存 → 直接返回(命中)
     边缘节点没缓存 → 回源站拉取 → 缓存 → 返回(未命中)

加速原理:
  物理距离短(RTT 从 200ms 降到 5ms)+ 源站压力小(99% 请求被 CDN 挡掉)

核心组件:DNS 调度系统(决定去哪个节点)+ 边缘缓存节点 + 回源机制(没命中时去源站拉)+ 缓存策略(多久过期、怎么刷新)。

扩展:CDN 可加速动态内容(边缘转发,利用优质骨干网)。Purge 主动刷新,Prefetch 预热到边缘节点。国内 CDN 需备案域名。

20. HTTP 的 Keep-Alive 是什么?

没有 Keep-Alive(HTTP/1.0):
  请求1 → TCP握手 → 发请求 → 收响应 → TCP挥手
  请求2 → TCP握手 → 发请求 → 收响应 → TCP挥手
  请求3 → TCP握手 → ...
  每个请求都要三次握手+四次挥手,浪费!

有 Keep-Alive(HTTP/1.1 默认):
  请求1 → TCP握手 → 发请求 → 收响应
  请求2 ────→ 发请求 → 收响应    ← 同一个 TCP 连接!
  请求3 ────→ 发请求 → 收响应
  ...空闲超时后 → TCP挥手

Keep-Alive 让一个 TCP 连接可以被多次请求复用,省了重复握手的 RTT 和 CPU 开销。HTTP/1.1 默认开启,Connection: keep-alive。

不过 Keep-Alive 也带来了新问题:连接长期占用不释放 → 服务端连接数上涨。所以服务端一般设 keepalive_timeout(Nginx 默认 75 秒),超时没新请求就断开。

扩展:HTTP/2 的多路复用进一步升级--不仅连接复用,同一连接内还能并行传多个请求/响应(不用排队)。Keep-Alive 在 HTTP/2 中不再是可选项--连接默认就复用。前端构建时,小图标合并成雪碧图(CSS Sprite)的目的就是复用连接减少请求--但在 HTTP/2 时代这种优化反而是不必要的。

21. TCP 的黏包/拆包怎么解决?

黏包/拆包原因:

发送方:write("ABC")  write("DEF")
  ↓ TCP 是流,没消息边界 ↓
接收方可能收到:
  "ABC" "DEF"        正常
  "ABCDEF"           黏包(两条消息粘在一起)
  "AB" "CD" "EF"     拆包(被切碎了)

根本原因:TCP 是流式协议,不收发消息边界,只保证字节顺序

四种解决方案:

1 定长消息
   每个消息固定 100 字节,不够的补空格
   简单但浪费空间

2 分隔符
   消息以 \r\n 结尾,读到分隔符就截断
   Redis 的 RESP 协议用这个

3 消息头 + 消息体(最推荐)
   [4字节长度][消息内容]
   先读 4 字节知道多长 → 再读那么长的内容
   Dubbo、gRPC 都用这种方式

4 Netty 的编解码器
   LengthFieldBasedFrameDecoder → 自动帮你拆
   LineBasedFrameDecoder → 按行拆分

扩展:UDP 没有黏包问题--UDP 是基于数据报的,每次 sendto() 对应一个完整的数据报。这也是为什么有些需要明确边界的协议(如 DNS,单次查询通常在一个 UDP 包内完成)选择 UDP。TCP 黏包问题的本质是--TCP 协议栈为了提高效率会合并小数据包发送(Nagle 算法)或分拆大数据包(MSS 限制)。

22. 什么是 ARP 协议?

将 IP 解析为 MAC 地址。先查本地缓存,未命中则广播请求,目标回复 MAC。ARP 欺骗是常见局域网攻击手段。

23. HTTP/3（QUIC）为什么更快？底层原理是什么？

HTTP/3 基于 QUIC 协议（UDP 实现），解决了 TCP 的三大痛点：

TCP 的问题:
  1. 连接建立慢：3次握手（HTTP/2 多路复用也要重新握手）
  2. 线头阻塞：TCP 层丢包会阻塞所有 stream
  3. 拥塞控制僵硬：操作系统内核实现，无法优化
       ↓
QUIC 的改进:
  1. 0-RTT/1-RTT 建立连接（TLS 1.3 集成到 QUIC）
  2. stream 级别流控：丢包只影响一个 stream，不阻塞其他
  3. 用户态实现：应用层优化拥塞算法，无需等 OS 更新
  4. 连接迁移（Connection Migration）：切换网络时连接 ID 不变

HTTP/3 vs HTTP/2：

HTTP/2 HTTP/3
传输层 TCP + TLS 1.2 UDP + QUIC
队头阻塞 TCP 层，阻塞所有流 QUIC 层，只阻塞单流
连接建立 1 RTT（多路复用） 0~1 RTT
移动网络切换 需重建连接 连接 ID 迁移，无感知

扩展：HTTP/3 已写入 RFC 9114；Nginx 1.25+、Cloudflare、Chrome 默认支持；丢包率高（>5%）时 HTTP/3 优势明显；国内 BAT 已大规模部署。
