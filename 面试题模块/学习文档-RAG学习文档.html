RAG 面试学习文档

让大模型学会"翻书"——检索增强生成从入门到面试通关

整理于 2026-06-14 | 目标：彻底搞懂 RAG，面试能讲、项目会用

1. RAG 到底是什么？

大白话定义

RAG = Retrieval-Augmented Generation（检索增强生成）：把搜索引擎和大语言模型撮合到一起——先搜文档，再把文档喂给 LLM，让它基于真实资料回答。

类比：普通 LLM 是靠记忆答题的学霸（知识截止到训练那天）；RAG 是给学霸发了一本随时更新的"小抄本"，考试时先翻小抄找到相关内容，再结合理解给出答案。答案又准又有出处。

RAG 核心架构：Query → Retrieve → Generate
=============================================

   用户提问 (Query)
        │
        ▼
 ┌──────────────┐
 │  1. 向量化     │  问题 → Embedding 模型 → 向量
 └──────┬───────┘
        │
        ▼
 ┌──────────────┐
 │  2. 语义检索   │  在向量数据库搜 Top-K 相关文档
 │  (Retrieve)   │  混合检索 = 向量检索 + BM25 关键词
 └──────┬───────┘
        │
        ▼
 ┌──────────────┐
 │  3. 增强 Prompt │  用户问题 + 检索文档 → 组装 Prompt
 └──────┬───────┘
        │
        ▼
 ┌──────────────┐
 │  4. LLM 生成   │  基于参考资料生成答案 + 引用来源
 │  (Generate)   │
 └──────┬───────┘
        │
        ▼
    最终回答 + 出处引用

对比：没用 RAG
  用户 → LLM → 可能瞎编（幻觉）

用了 RAG
  用户 → 检索 → 文档 → LLM → 有据可查的回答

为什么用 RAG？LLM 的痛点

LLM 的毛病 RAG 怎么治
知识过时：训练完就定格 知识库随时更新
幻觉：自信地胡说八道 答案必须基于搜到的真实文档
碰不到私有数据 公司文档建库，想搜就搜
长尾知识盲区 专业知识文档往里灌
说不清出处 每个回答标引用来源

面试话术："RAG 解决大模型三大痛点：知识过时、幻觉、私有数据不可达。核心是让模型在推理时动态获取外部知识，而非把知识全记在参数里。"

2. RAG 完整工作流程

离线 + 在线两阶段

离线索引（提前准备）：文档加载 → 分块 → 向量化 → 存入向量数据库。

在线查询（用户提问时触发）：问题向量化 → 语义检索 → 组装 Prompt → LLM 生成答案。

Prompt 怎么写？

# RAG 增强 Prompt——告诉 LLM："别瞎编，照着我给你的材料回答"
RAG_PROMPT = """
你是一个专业的 AI 助手。请根据以下参考资料回答用户的问题。

参考资料：
{context}

用户问题：{question}

要求：
1. 只根据参考资料回答，不要编造信息
2. 如果参考资料中没有相关信息，请如实说明
3. 在回答中引用参考资料来源
4. 回答要准确、简洁、有条理

回答：
"""

def build_rag_prompt(question: str, retrieved_docs: list) -> str:
    context = "\n\n".join([
        f"[来源 {i+1}: {doc.metadata.get('source', '未知')}]\n{doc.content}"
        for i, doc in enumerate(retrieved_docs)
    ])
    return RAG_PROMPT.format(question=question, context=context)

面试话术："RAG 分离线和在线两阶段。离线做文档向量化建库，在线做检索 + Prompt 增强生成。Prompt 必须显式约束 LLM 不编造、要引用来源。"

3. 文档处理与分块（Chunking）

为什么要分块？

1000 页的书不能整本扔给 LLM——它读不完，有效信息被淹没。分块的核心矛盾：块太大检索不精准，块太小上下文不完整，得找一个平衡点。

分块策略全景


分块策略决策流程
==================

  原始文档
     │
     ├─→ 有自然边界？（标题、段落、章节）
     │     ├─ 是 → 语义分块 / 按段落切（推荐）
     │     └─ 否 → 固定大小切 / 递归分块
     │
     ▼
  ┌──────────────────────────────────────────────────────────────┐
  │ 策略              │ 块大小         │ 适用场景                │
  ├──────────────────────────────────────────────────────────────┤
  │ 固定大小切         │ 500-1000 字符  │ 通用场景（新手默认）    │
  │ 按句子切           │ 1-3 句         │ 简单问答                │
  │ 按段落切           │ 1-3 段         │ 文档理解                │
  │ 递归分块(推荐)     │ 自适应         │ 结构复杂文档            │
  │ 语义分块           │ 按语义边界     │ 高质量要求              │
  │ Agent 分块         │ AI 判断        │ 特殊格式                │
  └──────────────────────────────────────────────────────────────┘
     │
     ▼
  chunk_overlap = chunk_size × 10%~20%
  防止一句话被切在两块之间

  示例（chunk_size=500, overlap=50）:
    块1: [0 ───────────────── 500]
    块2:             [450 ──────────────── 950]
    块3:                         [900 ──────────────── 1400]

分块代码 & 参数调优

from langchain.text_splitter import (
    RecursiveCharacterTextSplitter,
    CharacterTextSplitter,
    TokenTextSplitter,
)

# 递归字符分块（最常用，推荐！）
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,         # 每块 500 个字符
    chunk_overlap=50,       # 块间重叠 50 字符（防信息被切断）
    separators=["\n\n", "\n", "。", "！", "？", " "],  # 优先在自然断点切
)

# 按 Token 分块（对 LLM 计费更精确）
token_splitter = TokenTextSplitter(chunk_size=500, chunk_overlap=50)

chunks = text_splitter.split_documents(docs)

chunk_size 经验值：
  - 100-300：简单问答、提取人名地名
  - 500-1000：文档摘要、代码生成（⭐ 最常用区间）
  - 1000-2000：复杂推理、跨段落理解
  - >2000：读长文档全文

chunk_overlap：设为 chunk_size 的 10%-20%

面试话术："分块策略直接影响检索质量。我一般用 recursive character splitter，chunk_size 500-800，overlap 10%-15%。中文场景注意用句号和换行作为分隔符优先级。如果效果不好，第一反应就是调分块参数。"

4. 向量数据库与 Embedding

为什么用向量数据库？

传统数据库做精确匹配（"关键词 = 关键词"），向量数据库做语义匹配（"意思最接近"）。把文本变成高维向量坐标，用余弦相似度算距离——距离越近，语义越近。

主流向量数据库

数据库 一句话 什么时候用
Chroma 最轻量，pip install 就用 Demo、快速验证
Pinecone 全托管，省心但花钱 有预算、不想运维
Milvus 开源最强，功能最全 大规模生产环境
Qdrant Rust 写，性能怪兽 高并发、低延迟
Weaviate 原生混合搜索 既要语义又要关键词
Faiss Facebook 出品，离线王者 离线批量检索
PGvector PostgreSQL 插件 已有 PG，不想引入新库

新手建议：先用 Chroma 上手，生产用 Milvus 或 Qdrant。

向量检索原理

相似度算法：
  - 余弦相似度：看向量夹角，角度越小越像（最常用）
  - 欧氏距离：看直线距离，距离越短越像
  - 点积：相乘结果越大越像

加速索引（百万级向量不可能逐个比）：
  - HNSW（默认首选）：多层图，上层粗定位、下层精搜索，O(log N)
  - IVF：先聚类，只搜最近的几个类
  - PQ：向量压缩编码，省内存

精确检索 O(N)  vs  近似检索 ANN O(log N)

5. 检索策略

三种检索层次

  • 基础检索：向量相似度搜 Top-K（最简单，但容易漏专有名词）
  • MMR：既相关又多样，避免全是同类型结果
  • 混合检索：向量语义 + BM25 关键词双管齐下（效果最佳）

基础检索

retriever = vectorstore.as_retriever(
    search_type="similarity",  # similarity / similarity_score_threshold / mmr
    search_kwargs={
        "k": 5,                        # 返回 Top-5
        "score_threshold": 0.8,        # 相似度低于 0.8 的不要
    }
)

results = retriever.get_relevant_documents("用户问题")

MMR（最大边际相关性）

# 不用 MMR：可能返回 5 个都说优点，缺点一个没提
# 用 MMR：优缺点都覆盖，信息更全面

retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={
        "k": 5,
        "fetch_k": 20,              # 先从库拿 20 条候选
        "lambda_mult": 0.5,         # 0=只要多样，1=只要相关（推荐 0.5）
    }
)

混合检索

# 向量检索懂语义但漏专名，BM25 精准命中专名但不懂同义词
# 两者结合 = 双保险

from langchain.retrievers import EnsembleRetriever

vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
bm25_retriever = BM25Retriever.from_documents(chunks)

# RRF 融合排序
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.3, 0.7]  # BM25 30%, 向量 70%
)

# 用户问题可能很口语、很模糊，需要"翻译"再搜

# HyDE：让 LLM 先假装写一个"假设答案"，用答案去搜
#   原理：答案和文档的语言风格更接近，比直接用问题搜效果好
from langchain.chains import HyDE

# Query Decomposition：复杂问题拆成子问题分别搜
# Step-back Prompting：先问更大的背景问题，再问原问题
# Re-phrasing：把口语化问题改写成规范表述

面试话术："单一向量检索对专有名词召回差。实际项目用混合检索：向量做语义召回，BM25 做关键词召回，RRF 融合排序。加上 query rewriting 和 rerank 两层，检索准确率提升 20-30%。"

6. 生成阶段

核心：控制幻觉

前几步找到了"最新鲜的食材"（相关文档），现在交给"大厨"（LLM）。但大厨有个坏毛病——一不留神就自己往里加料（幻觉）。你得盯着他，反复强调："照菜谱来，别瞎加！"

用 LangChain 搭生成链

from langchain.chat_models import ChatOpenAI
from langchain.chains import RetrievalQA

qa_chain = RetrievalQA.from_chain_type(
    llm=ChatOpenAI(model="gpt-4", temperature=0),  # temperature=0 = 不要创意
    chain_type="stuff",
    retriever=retriever,
    return_source_documents=True,  # 返回引用来源
)

result = qa_chain({"query": "用户问题"})
print(result["result"])            # 答案
print(result["source_documents"])  # 引用

四种生成链类型

链类型 行为 适用
Stuff 所有文档塞进一个 Prompt 文档少（<5），要速度
Map Reduce 每篇单独小结，再汇总 文档多，各自独立
Refine 第一篇出初稿，后续逐篇润色 需要答案连贯流畅
Map Rerank 每篇打分，挑最高分用 追求最佳答案

# 第 3 板斧：后处理校验（Self-RAG / Corrective RAG）
# 生成答案后，再让 LLM 检查：答案和参考资料是否一致

面试话术："生成阶段核心是控制幻觉。三个关键：System Prompt 约束、temperature=0、后处理校验。return_source_documents=True 是必选项，回答带引用才有说服力。"

7. RAG 评估

两个维度

  • 检索质量：搜回来的东西，有没有正确答案？排第几？
  • 生成质量：LLM 有没有瞎编？回答和问题对得上吗？

检索指标

指标 解释 公式
Hit Rate Top-K 里答案命中了没 HR@K = 命中查询数 / 总查询数
MRR 正确答案首次出现排第几 MRR = 所有查询 (1/排名) 的平均值
NDCG 兼顾有没有 + 排序好不好 NDCG@K = DCG@K / IDCG@K

生成指标

指标 解释 怎么评
Faithfulness（忠实度） 答案是否全来自参考资料 LLM 自动评估
Answer Relevance 答跟问是不是一回事 LLM 自动评估
Context Precision 搜回来的文档有用的占多少 LLM 自动评估
Context Recall 该搜到的都搜到了吗 跟标准答案对比

RAGAS：一键评估

from ragas import evaluate
from ragas.metrics import (
    faithfulness, answer_relevancy,
    context_precision, context_recall,
)

result = evaluate(
    dataset=test_dataset,  # question, answer, contexts, ground_truth
    metrics=[
        faithfulness,       # 忠实度
        answer_relevancy,   # 相关性
        context_precision,  # 精确率
        context_recall,     # 召回率
    ],
)

df = result.to_pandas()
print(df)

面试话术："评估分两层：检索层看 Hit Rate 和 MRR，生成层看 Faithfulness 和 Answer Relevance。用 RAGAS 做自动化评估，重点关注 Faithfulness——低于 0.8 说明幻觉严重。"

8. Advanced RAG：从 60 分到 90 分

三层优化概述

基础 RAG 能跑通但效果 60 分。进阶在三阶段叠加优化：

预处理优化


预处理优化清单
================
📄 文档解析：
   ✅ PDF 表格、Word 层级标题精准提取
   ✅ 保留文档结构（标题层级）—— 对理解很有帮助
   ✅ 每块贴标签（来源、时间、类型）—— 方便过滤
   ✅ OCR 提取图片文字，图表描述不丢

✂️ 分块升级：
   ✅ 按语义边界切（段落、标题），不暴力按字数
   ✅ Small-to-Big：先搜小块，找到后扩展到完整章节
   ✅ 元数据过滤 + 向量检索一起用

🔢 Embedding 升级：
   ✅ Fine-tune Embedding：让向量"更懂"你的领域
   ✅ ColBERT：比普通向量更精细的交互方式

检索优化


检索优化清单
=============
❓ Query 改写：
   ✅ HyDE：先写假答案，用假答案搜（效果出奇好）
   ✅ Step-back：先问更大背景问题，再问原问题
   ✅ 问题分解：复杂问题拆成 2-3 个子问题分别搜

🔍 检索升级：
   ✅ 混合检索（向量 + BM25）← 标配
   ✅ 迭代检索：第一次搜完，让 LLM 说还需要啥，再搜
   ✅ Rerank（重排序）：先粗搜 50 条，用 Cross-Encoder 精排 5 条

⭐ Rerank 为什么重要？
   向量检索快但不精确 → 先召回 Top-50（海选）
   Cross-Encoder 精确但慢 → 对 50 条精排（复赛 → 决赛）
   性价比最高的优化：加一个 Cross-Encoder 带来 10-15% 提升

from langchain.retrievers.document_compressors import CohereRerank

compressor = CohereRerank(cohere_api_key=api_key, top_n=5)

compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever,
)

生成优化


生成优化清单
=============
📝 Prompt 工程：
   ✅ Few-shot Examples：给 LLM 看两三个例子
   ✅ Chain of Thought：引导"一步步思考"
   ✅ Self-RAG：LLM 自己判断"检索结果够不够，要不要再搜"
   ✅ Corrective RAG：生成后自检，不对就修正

📤 输出规范：
   ✅ 每条引用标注出处（哪个文档第几段）
   ✅ 结构化输出（JSON / 表格），方便下游用
   ✅ 不确定时说"不确定"，别硬编（降级策略）

🤖 模型选型：
   ✅ 小模型微调：成本低 + 懂行话（高频场景）
   ✅ GPT-4 / Claude：质量最好（高要求场景）

面试话术："进阶优化三刀：预处理做好文档解析和元数据，检索加混合搜索和 Rerank，生成加 Few-shot + CoT。Rerank 是性价比最高的优化，加一个 Cross-Encoder 精排能带来 10-15% 的效果提升。"

9. RAG vs 微调

一句话类比

  • RAG：考试时允许翻书。书可以随时换，最新知识都有。翻书需要时间。
  • Fine-tuning：考前把知识"灌进脑子"。答题飞快，但知识固定。

最佳策略：两者结合。微调让模型学会"怎么答题"，RAG 注入"最新内容"。

核心区别

对比项 RAG Fine-tuning
知识更新 随时更新，立等可用 需重新训练，耗时烧钱
可解释性 答案带引用，有据可查 答案藏在参数里
幻觉控制 基于真实文档 仍可能编造
训练成本 几乎为零 GPU 跑几天
推理成本 多一次检索，稍慢 纯推理，快
领域适配 取决于文档质量 可深度适配行业术语
时效性 新闻级 截止到训练前一天

选型指南

选 RAG：
  → 知识库经常变（产品手册、新闻、政策）
  → 答案必须能追踪出处
  → 想马上用起来，不想花钱训练

选 Fine-tuning：
  → 需要固定风格（客服话术、品牌文案）
  → 推理速度是首要因素
  → 领域极度专业，通用模型听不懂术语

最佳实践：RAG + Fine-tuning 组合
  → Fine-tuning 学风格、学行话、学推理模式
  → RAG 注入最新事实、私有数据
  → 结果：有深度 + 有实效 + 有据可查

面试话术："RAG 和微调不是互斥的，是互补的。大部分企业场景先上 RAG 快速验证，效果 OK 就省了微调的钱。风格或推理不够好，再加精调 + RAG 双打。分期投入，风险可控。"

LangChain 完整流程

from langchain.document_loaders import TextLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import Chroma
from langchain.chat_models import ChatOpenAI
from langchain.chains import RetrievalQA

# 1. 加载
docs = TextLoader("document.txt", encoding="utf-8").load()

# 2. 切块
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)

# 3. 向量化 + 存库
vectorstore = Chroma.from_documents(chunks, OpenAIEmbeddings())

# 4. 搭 QA 链
qa_chain = RetrievalQA.from_chain_type(
    llm=ChatOpenAI(model="gpt-4", temperature=0),
    chain_type="stuff",
    retriever=vectorstore.as_retriever(),
    return_source_documents=True,
)

# 5. 开问
result = qa_chain({"query": "用户问题"})

11. 面试 6 连问

Q1：RAG 的核心原理？

三个环节环环相扣：离线建向量索引 + 在线语义检索 + 增强 Prompt 生成。本质是把外部知识"动态注入"到 LLM 的生成过程中，让模型先查资料再回答，而不是凭记忆瞎猜。

Q2：RAG 效果不好，怎么排查？

检索环节：Embedding 模型对吗？中文用了英文模型 = 自废武功。分块大小合理吗？Top-K 合适吗？

生成环节：Prompt 有没有约束"不准瞎编"？LLM 碰到不知道的会说"不知道"还是乱说？要不要加后处理校验？

基建环节：PDF 解析对了吗？表格提取出来了吗？元数据够不够丰富？

Q3：怎么提升召回率？

  1. Query 改写：把口语化问题翻译成规范表述
  2. 混合检索：向量 + BM25 双管齐下
  3. 元数据过滤：先按时间/类型缩小范围，再向量检索
  4. Rerank 精排：粗搜 50 条，Cross-Encoder 精挑 5 条
  5. 迭代检索：搜一次 → LLM 说还缺什么 → 再搜一次补全

Q4：RAG 和微调怎么选？

知识经常变吗？ → 是 → RAG
需要解释来源吗？ → 是 → RAG
追求推理速度吗？ → 是 → 微调
要固定风格/语气吗？ → 是 → 微调
预算充足想两全其美？ → RAG + 微调组合拳

推荐路线：先上 RAG 快速出 MVP → 验证效果 → 不够好再加微调 → 双剑合璧

Q5：RAG 有什么局限性？

  1. 检索是天花板：Embedding 和分块没调好，后面全白搭
  2. 上下文长度有限：超长文档得特殊处理
  3. 多跳推理吃力："A 公司 CEO 多大了？"需要先搜 CEO 是谁，再搜年龄
  4. 多一次检索 = 多一份延迟 + 多一份成本
  5. 数学计算、复杂逻辑推理：纯 RAG 不行，得上 Agent + 工具调用

Q6：怎么评估 RAG 系统好不好用？

两把尺子：

  • 检索尺：Hit Rate（搜到没）、MRR（对的排第几）、NDCG（排序好不好）
  • 生成尺：Faithfulness（有没有瞎说）、Answer Relevance（有没有离题）

实操：用 RAGAS 一键跑评估，重点关注 Faithfulness——低于 0.8 说明幻觉严重，得回改 Prompt 或加校验。

另外：线上看用户反馈更真实——点"踩"比例、是否追问、引用点击率，这些才是最终指标。

学习心法：RAG 面试就三个关键词——检索怎么搜得准（Embedding / 向量数据库 / 混合检索）、生成怎么不乱说（Prompt / 幻觉控制）、优化怎么做（Rerank / HyDE / Small-to-Big）。吃透完整流程，再深入向量检索原理，最后用 Advanced RAG 的优化思路拔高。

考察关系：RAG 主要出现在 AI 应用 / 大模型 / 后端方向面试中，常和以下知识点一起考察：LLM 基础、向量数据库选型、Embedding 模型、Prompt Engineering、LangChain/LlamaIndex 框架。AI 应用开发岗几乎必问。
