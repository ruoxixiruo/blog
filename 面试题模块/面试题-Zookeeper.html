Zookeeper

1. ZK 和 Nacos 作为注册中心有什么区别?

维度 Zookeeper Nacos
一致性 CP(强一致,ZAB 协议) AP 为主(也支持 CP)
健康检查 临时节点 + 会话超时 心跳保活
大规模 Watch 机制大集群性能差 支持百万级实例
功能 仅服务发现 服务发现 + 配置中心一体化

新项目推荐 Nacos,已有 ZK 的老系统继续用。

ZK (CP):一致性强,但可能暂时不可用
  ┌──┐  ┌──┐  ┌──┐    Leader 挂了 → 重新选举 → 选举期间整个集群不可写
  │L │  │F │  │F │
  └──┘  └──┘  └──┘    ← 要过半同意才能写

Nacos (AP):永远可用,但可能有短暂不一致
  ┌──┐  ┌──┐  ┌──┐    一个节点挂了 → 其余继续工作 → 数据最终一致
  │N1│  │N2│  │N3│
  └──┘  └──┘  └──┘    ← 各记各的,定期同步

扩展:Nacos 的混合模式--AP 做服务发现(不能因为选主就发现不了服务),CP 做配置中心(配置绝对不能错)。这个设计很巧妙--同一个系统对不同数据用不同一致性策略。ZK 做不到这一点--它所有数据都是 CP,所以在大规模、高频率变更场景下会有性能瓶颈。

2. ZK 是怎么选 Leader 的?

基于 ZAB 协议,过程很简单:

  1. 所有节点初始为 LOOKING,投自己一票
  2. 互相交换投票,优先比 zxid(事务 ID),大的当选;zxid 一样比 myid(节点编号)
  3. 获得过半票数的成为 Leader,其他为 Follower
三个节点的选举:

Node1: zxid=100, myid=1  ──投票→ 投自己(100,1)
Node2: zxid=200, myid=2  ──投票→ 投自己(200,2)
Node3: zxid=100, myid=3  ──投票→ 投自己(100,3)

交换投票后:
Node1 发现 Node2 zxid 更大 → 改投 Node2
Node3 发现 Node2 zxid 更大 → 改投 Node2
Node2 已经两票(自己+Node1) → 过半 → 当选 Leader

扩展:为什么 zxid 比 myid 重要?因为 zxid 高的节点有最新数据--选它是为了让最新数据不丢失。myid 只是 zxid 相同时的"打破平局"的手段。另外 ZK 用过半(majority)而不是全票--3 台可以挂 1 台,5 台可以挂 2 台,这是典型的分布式共识权衡。

3. ZK 怎么实现分布式锁?

步骤: 1. 每个客户端在 /lock 下创建临时顺序节点(如 /lock/seq-0001、/lock/seq-0002) 2. 查自己是不是序号最小的 → 是则获得锁,不是则 watch 前一个节点 3. 释放锁时删除自己的节点(或会话断开自动删除--临时节点的精髓)

/lock
  ├── seq-0001 (最小 → 获得锁)
  ├── seq-0002 (watch seq-0001,等)
  ├── seq-0003 (watch seq-0002,等)

seq-0001 释放 → seq-0002 收到通知 → 发现自己最小 → 获得锁

优点:强一致,自动释放(断连就删)。缺点:性能比 Redis 锁低。

扩展:ZK 分布式锁和 Redis 分布式锁的核心区别--ZK 是公平锁(按排队顺序),Redis 是非公平锁(谁 SETNX 成功谁拿锁)。ZK 锁更适合对公平性有要求的场景;Redis 锁更快,适合高并发且容忍非公平的场景。

4. ZK 能同时当注册中心和配置中心吗?

能,但大规模场景下不推荐。ZK 是 CP 系统,网络抖动时可能短暂不可用--这意味着服务发现和配置获取都可能失败。Nacos 的设计更成熟:AP 模式做服务发现 + CP 模式做配置中心,灵活切。

扩展:阿里当年从 ZK 迁移到 Nacos 的核心动力就是--大规模微服务集群下 ZK 的 Watch 性能成为瓶颈。Eureka 2.0 停更后,国内社区基本倒向 Nacos。如果你是公司选型:新项目直接 Nacos 省心;已有 ZK 且规模不大的继续用,别为换而换。

5. ZK 的数据模型和节点类型?

ZK 的数据模型 = 一个类文件系统的树,但每个"文件"(ZNode)既能存数据又能有孩子。

/ (根节点)
├── /services           ← 持久节点
│   ├── /order-service  ← 持久节点
│   │   ├── /node-1     ← 临时节点(Provider 在线)
│   │   └── /node-2     ← 临时节点(Provider 在线)
│   └── /user-service
├── /config             ← 持久节点
│   └── /db-config      ← 持久节点
└── /locks              ← 持久节点
    └── /order-lock     ← 临时顺序节点

四种节点类型:

持久节点        → 创建后一直存在,除非主动删除(存配置、元数据)
持久顺序节点     → 名字自动加递增序号(分布式锁排队)
临时节点        → 客户端断连自动删除(服务注册)
临时顺序节点     → 临时 + 自动编号(分布式锁、选主)

扩展:ZK 的节点不擅长存大数据--每个 ZNode 默认最大 1MB,但官方推荐控制在 1KB 以内。因为 ZNode 的更新是整个覆盖的(没有 append),而且所有数据都同步到内存,太大影响集群性能。配置中心用 ZK 存配置的时候,注意别把配置文件一股脑塞进去。

6. Watcher 机制是什么?有什么坑?

Watcher = 订阅推送,但只通知一次--就像快递到了只通知你一次,你要持续关注就得每次重新订阅。

生命周期:
  Client 注册 Watcher(getData(path, watcher))
      ↓
  ZNode 数据变化 → ZK Server 通知 Client
      ↓
  Watcher 被触发一次 → 自动销毁 ❗
      ↓
  Client 需要在回调里重新注册 Watcher

三大坑:

  1. 一次性触发(最大坑):Watcher 触发后自动销毁,必须在回调里重新注册,否则丢了事件不知道
  2. 串行通知:同一个 Client 的 Watcher 事件是串行处理的,一个慢 Watcher 会拖累后面所有
  3. 先通知后读:ZK 通知你说节点变了,但在你读到最新数据之前,节点可能又变了一次--Watcher 不保证你读到的是触发那次变更的数据
// 正确的 Watcher 使用:在回调里重新注册
Watcher watcher = event -> {
    if (event.getType() == EventType.NodeDataChanged) {
        // 1. 业务处理(先读最新数据)
        byte[] newData = zk.getData(path, false, null);
        // 2. 重新注册 Watcher(关键!)
        zk.getData(path, this, null);
    }
};

扩展:Curator(ZK 的 Java 客户端框架)封装了反复注册的痛点,提供了 NodeCache(监听单个节点)、PathChildrenCache(监听子节点变化)、TreeCache(监听整棵树)三种缓存监听器,内部自动重新注册。生产上永远用 Curator 而不要裸用 ZK 原生 Watcher。

7. ZAB 协议的核心流程?

ZAB(ZooKeeper Atomic Broadcast)= ZK 内部保证副本数据一致的协议。

两阶段:

┌────────── Leader 选举 ──────────┐
│                                 │
│  节点启动 → 投自己一票           │
│     ↓                           │
│  收到别人投票 → 比 ZXID(谁的日志新)│
│     ↓                           │
│  ZXID 大的赢 → 票数过半 → Leader │
│                                 │
├────────── 消息广播 ────────────┤
│                                 │
│  Leader 收到写请求              │
│     ↓                           │
│  Proposal(发给所有 Follower)   │
│     ↓                           │
│  Follower 写日志 → 回复 ACK      │
│     ↓                           │
│  过半 ACK → Leader Commit        │
│     ↓                           │
│  通知所有 Follower Commit        │
│                                 │
└─────────────────────────────────┘

关键设计:过半即可提交(不是全票),所以 ZK 集群推荐奇数台(3/5/7),容忍 (N-1)/2 台宕机。

扩展:ZAB 和 Raft 很像但不完全一样--ZAB 的选主看重 ZXID(日志新旧),Raft 则看 Term(任期的先后)。崩溃恢复时,ZAB 会确保所有已提交的 proposal 都在新 Leader 上任前同步到所有节点。这就是为什么 ZK 选择 CP 而不是 AP--宁可短暂不可用,也不让数据不一致。

8. ZK 的会话机制?临时节点和持久节点的区别?

Session = ZK 给每个客户端发的"门禁卡",刷卡过期了就自动清理你留下的东西。

Session 生命周期:

  Client 连接 ZK → Server 分配 SessionID + Timeout
      ↓
  Client 定期发心跳(ping)
      ↓
  Server 在 timeout / 2 时间内没收到心跳 → Session 过期
      ↓
  Session 过期 → 该 Client 创建的临时节点全部自动删除 !?️
      ↓
  其他 Client 的 Watcher 收到子节点变化事件

临时 vs 持久:

临时节点:跟随 Session 存活,客户端断连自动删除,不能有子节点。典型用途是服务注册、分布式锁。

持久节点:永远存在(除非主动删),可以有子节点。典型用途是配置、元数据目录。

扩展:临时节点没有子节点是 ZK 的设计限制--因为如果临时节点有了孩子,父节点断连后子节点"孤儿"谁来管?分布式锁用临时顺序节点就是这个原因:Lock 节点是持久的,每个客户端在 Lock 下创建临时顺序子节点,客户端挂了子节点自动消失,下一个客户端自动拿到锁,完美实现公平锁。

9. ZK 的角色有哪些?

Leader 写请求 + 事务提交,Follower 读 + 投票,Observer 读不投票。Observer 扩容读能力不降写性能。

10. ZK 分布式锁实现原理?如何解决羊群效应?

核心结论:临时顺序节点 + watch 前一个节点 = 公平锁 + 避免羊群效应。

传统分布式锁问题(羊群效应):

/lock 节点
  ├── seq-0001 (持有锁)
  ├── seq-0002 (watch /lock 子节点变化)
  ├── seq-0003 (watch /lock 子节点变化)
  └── seq-0004 (watch /lock 子节点变化)

问题:seq-0001 释放锁后,所有等待者都收到通知,全部抢锁 → 惊群效应!

优化后(只 watch 前一个节点):

/lock 节点
  ├── seq-0001 (持有锁)
  ├── seq-0002 (只 watch seq-0001)
  ├── seq-0003 (只 watch seq-0002)
  └── seq-0004 (只 watch seq-0003)

seq-0001 释放 → 只通知 seq-0002 → seq-0002 拿锁

Curator InterProcessMutex 实现:

InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");

try {
    // 获取锁(阻塞)
    lock.acquire();

    // 业务逻辑
    processOrder();
} finally {
    // 释放锁
    lock.release();
}

// 带超时的获取
if (lock.acquire(5, TimeUnit.SECONDS)) {
    try {
        processOrder();
    } finally {
        lock.release();
    }
}

扩展:ZK 锁和 Redis 锁的核心区别--ZK 是公平锁(顺序排队),Redis SETNX 是非公平锁(谁抢到算谁的)。ZK 锁更可靠(会话断开自动释放),但性能比 Redis 低。Curator 还提供了读写锁 InterProcessReadWriteLock、信号量 InterProcessSemaphoreV2 等高级锁实现。

11. ZK 集群脑裂怎么解决?

核心结论:过半机制 + 唯一 Leader + Fencing Token = 根治脑裂。

脑裂场景:

5 节点集群,ZK 1/2 和 3/4/5 网络分区:

分区 A (ZK1, ZK2):       分区 B (ZK3, ZK4, ZK5):
  2 票 ← 不够过半           3 票 ← 过半! 选出 Leader
  无法选主                  正常服务

如果分区 A 也"选主" → 两个 Leader → 脑裂!

ZK 解决方案:
1. 过半机制:只有 ≥3 票才能当选 Leader
2. 分区 A 只有 2 票 → 无法选主 → 自然不会出现双主

Leader 选举的三大保障:

机制 作用
过半选举 票数 < N/2+1 无法当选
ZXID 比较 优先选数据最新的节点
Fencing Token 每次选举 epoch+1,旧 Leader 自动失效

实际案例:

Kafka Controller 脑裂问题:

旧方案:ZK watch /controller 节点,注册成功就当 Controller
问题:网络抖动导致多个节点都认为自己注册成功

改进方案(CURP):
1. 增加 epoch(纪元号)字段
2. 每次选主 epoch+1
3. 其他节点收到 epoch 更大的请求时,自动降级

扩展:虽然 ZK 本身不会脑裂,但用 ZK 做选主的业务可能脑裂。比如 Kafka 早期版本就有"僵尸 Controller"问题--Controller 挂了但 Session 还没过期,新 Controller 上任后,两个 Controller 同时工作。解决方案是增加 activeControllerPath + epoch 双重校验。HBase、HDFS 等用 ZK 做选主的系统都要注意这个问题。

12. Zookeeper 如何保证分布式锁？

ZooKeeper 实现分布式锁的核心是 临时顺序节点 + Watcher：

// 加锁流程
public boolean tryLock() {
    // 1. 创建临时顺序节点
    String path = zk.create("/locks/", null,
        ZooDefs.Ids.OPEN_ACL_UNSAFE,
        CreateMode.EPHEMERAL_SEQUENTIAL);

    // 2. 获取所有子节点
    List<String> children = zk.getChildren("/locks", false);

    // 3. 判断自己是否最小（最小则持锁成功）
    children.sort(String::compareTo);
    if (path.equals("/locks/" + children.get(0))) {
        return true;  // 持锁成功
    }

    // 4. 监听比自己小的那个节点
    String prevNode = "/locks/" + children.get(
        getRank(path) - 1  // 找到自己的排名
    );
    zk.exists(prevNode, new Watcher() {
        public void process(WatchedEvent e) {
            // 持锁者释放了，触发重新抢锁
            notifyAll();
        }
    });
    return false;
}

羊群效应优化：

无优化：所有等待者都监听最小节点（锁释放时全部被唤醒）
       → N 个等待者同时抢锁，ZK 压力巨大

优化后：每个等待者只监听比自己小的那个节点
       → 锁释放时只唤醒一个
       → ZK 压力 O(N) → O(1)

扩展：Curator 客户端封装了完整的可重入锁、公平锁、读写锁实现；ZooKeeper 的临时节点在客户端断连后自动删除（保证锁释放）；Redisson 是 Redis 实现的分布式锁（更轻量，但依赖 Redis 持久化）。
