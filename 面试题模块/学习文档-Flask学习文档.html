Flask 面试学习文档

1. Flask 是什么

1.1 一句话

Flask 是 Python 轻量级 Web 微框架，核心精简（只含 Werkzeug WSGI 工具箱 + Jinja2 模板引擎），功能靠扩展按需装配。

1.2 技术定义

  • 微框架 (Microframework)：核心极简，扩展生态丰富
  • Werkzeug：底层 WSGI 工具箱（路由、请求/响应、调试器）
  • Jinja2：模板引擎
  • 默认不含 ORM、表单验证、认证等，但都有官方/社区扩展

1.3 Flask vs Django

对比项 Flask Django
设计哲学 微框架，灵活扩展 全栈，开箱即用
上手难度 低 中（需学整套体系）
可定制性 高 中
内置功能 核心+扩展 全功能（ORM/Admin/认证）
适用场景 微服务、API、中小项目 大型应用、CMS、企业级
学习曲线 平缓 陡峭

面试话术："Flask vs Django 不是优劣问题，是场景问题。大而全的项目用 Django；灵活度要求高、做微服务或 API 用 Flask。我偏向 Flask，因为它能让人吃透 Web 框架底层原理。"

5.1 两个上下文：是什么、为什么分开

  • 请求上下文 (Request Context)：每次请求创建，含 request（请求数据）+ session（用户会话）。请求结束即销毁。
  • 应用上下文 (Application Context)：含 current_app（应用实例）+ g（请求级临时存储）。Web 请求中自动随 RequestContext 创建；CLI/脚本中手动 with app.app_context() 使用。

分开的原因：

  1. 线程安全：底层 threading.local，并发请求各自独立栈，数据不串
  2. 非请求场景可用：CLI 脚本、Celery 任务不需要 request，但需要 current_app.config 和 ORM

# wsgi_app() 源码结构
def wsgi_app(self, environ, start_response):
    ctx = self.request_context(environ)
    error = None
    try:
        try:
            ctx.push()
            response = self.full_dispatch_request()
        except Exception as e:
            error = e
            response = self.handle_exception(e)
        return response(environ, start_response)
    finally:
        ctx.auto_pop(error)

5.2 底层原理：LocalStack + LocalProxy

Flask 上下文机制建立在 Werkzeug 的两个基础设施之上。

LocalStack：线程隔离的栈

# Werkzeug LocalStack 简化原理
class LocalStack:
    def __init__(self):
        self._local = Local()  # 底层是 threading.local，按线程 ID 隔离

    def push(self, obj):
        rv = getattr(self._local, 'stack', None)
        if rv is None:
            self._local.stack = rv = []
        rv.append(obj)

    def pop(self):
        stack = getattr(self._local, 'stack', None)
        if stack is None:
            return None
        elif len(stack) == 1:
            self._local.stack = None
            return stack[-1]
        else:
            return stack.pop()

    @property
    def top(self):
        try:
            return self._local.stack[-1]
        except (AttributeError, IndexError):
            return None

# Flask 全局维护两个栈（globals.py）
_request_ctx_stack = LocalStack()   # 请求上下文栈
_app_ctx_stack = LocalStack()       # 应用上下文栈

线程隔离示意图

线程 A                            线程 B
+----------------------+          +----------------------+
|  _local.stack        |          |  _local.stack        |
|  +----------------+  |          |  +----------------+  |
|  | AppContext     |  |          |  | AppContext     |  |
|  +----------------+  |          |  +----------------+  |
|  | RequestContext |  |          |  | RequestContext |  |
|  +----------------+  |          |  +----------------+  |
+----------------------+          +----------------------+
    独立 LocalStack，物理隔离，完全不串！

LocalProxy：延迟绑定的代理

request、session、current_app、g 都是 LocalProxy。你写 request.method 时，它不是访问全局变量，而是动态去当前线程栈顶取真实对象。

class LocalProxy:
    def __init__(self, local, name):
        object.__setattr__(self, '_LocalProxy__local', local)
        object.__setattr__(self, '__name__', name)

    def _get_current_object(self):
        return self.__local()  # 调用查找函数取真实对象

    def __getattr__(self, name):
        return getattr(self._get_current_object(), name)

# 四个核心变量的定义
# request      = LocalProxy(lambda: _request_ctx_stack.top.request)
# session      = LocalProxy(lambda: _request_ctx_stack.top.session)
# current_app  = LocalProxy(lambda: _app_ctx_stack.top.app)
# g            = LocalProxy(lambda: _app_ctx_stack.top.g)

关键话术："request 不是真正的全局变量，它是 LocalProxy，每次访问动态从当前线程的 LocalStack 栈顶取真实对象。写起来像全局变量，用起来线程安全。"

5.3 请求生命周期（源码路径）

PUSH 时（RequestContext.push()）：

ctx.push()
  |
  +-- _app_ctx_stack.top 是空的？
  |     YES --> 自动创建 AppContext 并 push 到 _app_ctx_stack
  |           记录到 _implicit_app_ctx_stack (标记为"隐式创建")
  |     NO  --> 跳过（已有手动创建的 AppContext）
  |
  +-- push RequestContext 到 _request_ctx_stack
  +-- 加载 session

POP 时（RequestContext.pop()）：

ctx.pop()
  |
  +-- 保存 session（如果被修改过）
  +-- pop RequestContext
  +-- 弹掉所有 _implicit_app_ctx_stack 中的 AppContext
      (手动创建的不会被弹掉)

AppContext 创建时机——核心结论：每个请求创建一个，用完销毁。

请求1: _app_ctx_stack: [] --> push 创建 AppContext① --> 处理 --> pop 销毁 --> []
请求2: _app_ctx_stack: [] --> push 创建 AppContext② --> 处理 --> pop 销毁 --> []
请求3: _app_ctx_stack: [] --> push 创建 AppContext③ --> ...

常见误解："应用启动时创建一次 AppContext，之后一直存在"
正确理解：Web 请求场景下是 per-request，每个请求创建新的、结束销毁。只有手动 with app.app_context() 才可能跨请求存活。

5.4 RequestContext 和 AppContext 内部结构

class RequestContext:
    def __init__(self, app, environ):
        self.app = app
        self.request = app.request_class(environ)  # Request 对象
        self.session = None                         # 稍后从 Cookie 加载
        self._implicit_app_ctx_stack = []           # 记录隐式创建的 AppContext

    def push(self):
        if _app_ctx_stack.top is None:
            app_ctx = self.app.app_context()
            app_ctx.push()
            self._implicit_app_ctx_stack.append(app_ctx)  # 标记，pop 时会清理
        _request_ctx_stack.push(self)
        if self.session is None:
            self.session = self.app.open_session(self.request)

    def pop(self, exc=None):
        self.app.save_session(self.session, ...)
        _request_ctx_stack.pop()
        while self._implicit_app_ctx_stack:           # 只清理隐式创建的
            self._implicit_app_ctx_stack.pop().pop()


class AppContext:
    def __init__(self, app):
        self.app = app
        self.g = app.app_ctx_globals_class()          # g 在此创建

    def push(self):
        _app_ctx_stack.push(self)

    def pop(self, exc=None):
        _app_ctx_stack.pop()

四个变量与栈的对应：

变量 所属上下文 代理来源 说明
request ReqContext _request_ctx_stack.top.request 请求数据
session ReqContext _request_ctx_stack.top.session 用户会话（默认存 Cookie）
current_app AppContext _app_ctx_stack.top.app 当前应用实例
g AppContext _app_ctx_stack.top.g 请求级临时存储

5.5 g 对象专题（面试深挖核心）

创建：随 AppContext 实例化

class AppContext:
    def __init__(self, app):
        self.g = app.app_ctx_globals_class()  # 空 _AppCtxGlobals

重置：每个请求结束后替换为新对象

# 不是清空 g 的属性，而是直接把 g 换成全新空对象！
def do_teardown_appcontext(self, exc=None):
    app_ctx = _app_ctx_stack.top
    if app_ctx is not None:
        app_ctx.g = self.app_ctx_globals_class()  # 换新对象

两层保障

保障1: do_teardown 把 g 替换为新对象
       --> 即便 AppContext 被复用，g 也是干净的（换对象 != 清属性）

保障2: AppContext 本身 per-request 创建和销毁
       --> 下一个请求拿到全新 AppContext + 全新 g

使用示例

@app.before_request
def before_request():
    g.request_id = str(uuid.uuid4())   # 每个请求开始，g 是全新的
    g.user = load_user_from_token()

@app.route('/order')
def order():
    user = g.user                      # 同一请求内共享
    return f'Order for {user.name}'

@app.teardown_request
def teardown(exc):
    pass  # g 即将被 teardown 重置，可在此清理资源

并发安全：多请求 g 会弄混吗？——不会

防线1 (并发): LocalStack 线程隔离 -- threading.local
  线程A: g.user --> 线程A的栈顶 --> {user:A}
  线程B: g.user --> 线程B的栈顶 --> {user:B}
  不同的栈，物理上不可能串

防线2 (同线程先后): do_teardown_appcontext 换新对象
  请求1 --> g 填充 --> teardown 换新对象
  请求2 --> g 是全新的空对象
  不会看到请求1的残留数据

面试话术："g 不会串数据，有两条防线。并发层面——LocalStack 底层是 threading.local，不同线程走不同栈，物理隔离。同线程先后——do_teardown_appcontext 把 g 替换成新对象（不是清属性），即使有遗漏字段也绝对看不到。再加上 AppContext 本身 per-request 创建销毁，已是双重保障。"

5.6 面试深挖：追问三连

追问 1：应用上下文什么时候创建？只创建一次吗？

错误："应用启动时创建一次。"
正确：每个请求创建一个，结束就销毁。来几个请求创建几次。

请求1: [] --> 创建 AppContext① --> 销毁 --> []
请求2: [] --> 创建 AppContext② --> 销毁 --> []
请求3: [] --> 创建 AppContext③ --> 销毁 --> []

跨请求存在的唯一情况：手动 app.app_context().push()（一般不推荐）。

追问 2：g 什么时候创建？什么时候销毁？

错误："g 随请求创建和销毁。"（不够精确）
正确：创建：AppContext.__init__ 中 self.g = _AppCtxGlobals()。重置：do_teardown_appcontext 把 g 替换成全新空对象（换对象，不是清属性）。

追问 3：多个请求同时进来，g 会弄混吗？

错误："不会，因为 Flask 是单线程的。"（Flask 支持多线程/多进程）
正确：不会。并发用 LocalStack（threading.local）物理隔离，同线程先后用 do_teardown 换新对象逻辑隔离。两道防线。

5.9 速查表 + 终极面试话术

变量 来源 何时可用
request _request_ctx_stack.top.request 请求上下文中
session _request_ctx_stack.top.session 请求上下文中
current_app _app_ctx_stack.top.app 应用上下文中
g _app_ctx_stack.top.g 应用上下文中（请求级生命周期）

终极面试话术：

"Flask 的上下文机制基于 Werkzeug 的 LocalStack + LocalProxy 实现线程隔离。两个全局栈——_request_ctx_stack 和 _app_ctx_stack——底层是 threading.local，不同线程互不干扰。request、session、current_app、g 都是 LocalProxy，访问时动态从当前线程栈顶取真实对象，写起来像全局变量，用起来线程安全。

AppContext 在 Web 请求场景下是 per-request 的——每个请求通过 RequestContext.push() 自动创建，结束后一起销毁，不是启动时创建一次。g 随 AppContext 创建而诞生，每个请求结束后由 do_teardown_appcontext 替换为新对象（换对象而非清属性），配合 AppContext 的 per-request 生命周期，形成双重保障。

分开两个上下文的设计，让没有 HTTP 请求的场景（CLI、测试、Celery）也能使用 current_app.config 和 ORM，这是 Flask 设计最精妙的地方。"

13. 中间件与钩子

13.1 概念

Flask 在请求处理的不同阶段提供钩子函数，让你插入自定义逻辑：

  • before_request：请求到来后、视图处理前（可中断并返回响应）
  • after_request：视图处理后、响应返回前（必须接收并返回 response）
  • teardown_request：请求完全结束后（无论是否异常，用于清理）

13.2 请求全局钩子

@app.before_request
def before_request():
    """每次请求前执行"""
    g.start_time = time.time()
    g.user = None
    app.logger.info(f'{request.method} {request.path}')

@app.after_request
def after_request(response):
    """每次请求后执行（接收响应，返回响应）"""
    elapsed = time.time() - g.get('start_time', 0)
    app.logger.info(f'{request.method} {request.path} -> {response.status_code} ({elapsed:.3f}s)')
    return response

@app.teardown_request
def teardown_request(exc=None):
    """请求结束清理（无论是否发生异常）"""
    db.session.close()

class RequestTimingMiddleware:
    """自定义中间件：为每个请求添加 X-Request-Time 头"""
    def __init__(self, app):
        self.app = app

    def __call__(self, environ, start_response):
        start = time.time()

        def custom_start_response(status, headers, *args):
            elapsed = time.time() - start
            headers.append(('X-Request-Time', f'{elapsed:.3f}s'))
            return start_response(status, headers, *args)

        return self.app(environ, custom_start_response)

app.wsgi_app = RequestTimingMiddleware(app.wsgi_app)

18. 高频面试题

Q1：Flask 的请求上下文和应用上下文是什么？调用顺序？（必考！）

两个上下文：

  • 请求上下文 (Request Context)：含 request（请求数据）和 session（用户会话），请求期间活跃，请求结束销毁
  • 应用上下文 (Application Context)：含 current_app（应用实例）和 g（请求级临时存储），可脱离请求独立存在

底层实现：LocalStack + LocalProxy

  • 两个全局 LocalStack：_request_ctx_stack 和 _app_ctx_stack，底层 threading.local 实现线程隔离
  • request/session/current_app/g 都是 LocalProxy，访问时动态从当前线程栈顶取真实对象

一次请求的调用链：

1. wsgi_app() 创建 RequestContext
2. ctx.push() --> 如果 _app_ctx_stack 为空，自动创建并 push AppContext --> push RequestContext
3. 视图函数执行，request/session/current_app/g 全部可用
4. ctx.pop() --> pop RequestContext --> 弹掉隐式创建的 AppContext

AppContext 创建时机（高频深挖）： 不是"应用启动时创建一次"，而是每个请求创建一个，结束销毁。只有手动 with app.app_context() 才跨请求存活。

g 的并发安全： 两条防线——并发用 LocalStack（threading.local）线程间物理隔离；同线程先后用 do_teardown_appcontext 替换新对象请求间逻辑隔离。g 绝对不会串。

面试话术："Flask 的上下文机制基于 LocalStack + LocalProxy 实现线程隔离。AppContext 是 per-request 的，每个请求创建销毁。g 随 AppContext 创建而诞生，teardown 时换新对象而非清属性，双重保障数据不串。两个上下文分开是为了让非 HTTP 场景也能用 current_app。"

Q2：Flask 的 g 对象是做什么的？

g 是请求级别的全局变量空间，在每个请求内共享。典型用法：

@app.before_request
def load_user():
    g.user = get_user_by_token(request.headers.get('Authorization'))

@app.route('/profile')
def profile():
    return render_template('profile.html', user=g.user)

注意：g 只存活于一个请求周期，不跨请求。不适合存 Login 状态（用 session）。

Q6：Flask 的 after_request 和 teardown_request 区别？

钩子 触发时机 特点

Q8：Flask 的路由如何工作？Werkzeug 的作用是什么？

  2. 请求到来时 Werkzeug 匹配 URL，调用对应视图函数
