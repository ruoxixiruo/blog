2. 如何查找日志中的错误?

# 基础查找
grep "ERROR" app.log | tail -20                  # 最近 20 条错误
grep "2024-01-01.*ERROR" app.log | wc -l         # 某天错误数量

# 统计接口访问频率(Top N)
awk '{print $1, $3}' app.log | sort | uniq -c | sort -rn | head -20

# 按时间范围过滤
sed -n '/2024-01-01 10:00/,/2024-01-01 11:00/p' app.log | grep ERROR

# 查看异常前的上下文(前后各 3 行)
grep -B 3 -A 3 "Exception" app.log

# 统计各接口耗时分布
awk '{print $NF}' app.log | sort -n | awk '{
    if ($1<100) fast++; else if ($1<1000) mid++; else slow++
} END {print "fast:",fast,"mid:",mid,"slow:",slow}'

扩展:zgrep 可直接搜索 .gz 压缩日志。生产推荐 ELK 集中分析。

3. 软链接和硬链接的区别?

硬链接 vs 软链接:

硬链接(ln file link):
  file → inode(1234) → 数据块
  link → inode(1234) → 数据块     ← 同一个 inode!
  删掉 file,link 仍指向 inode(1234),数据还在
  就像数据的"第二个名字",不是副本

软链接(ln -s file link):
  file → inode(1234) → 数据块
  link → inode(5678) → 存了 "/path/to/file"(字符串)
  删掉 file → link 指向不存在的路径 → 坏链
  就像 Windows 的快捷方式
对比 硬链接 软链接
inode 相同 不同
删源文件 不影响 链接失效
跨文件系统 不行 可以
链接目录 不行 可以
本质 同一数据的多个名字 快捷方式(路径)

扩展:硬链接计数在 inode 中(ls -l 第二列),计数归零文件才删除。目录的硬链接被禁止以防循环引用。

4. > 和 >> 的区别?

重定向速查:

>   覆盖写入:echo "hello" > file.txt     → 先清空再写
>>  追加写入:echo "hello" >> file.txt    → 追加到末尾
<   读取输入:cmd < input.txt             → 文件作为命令的输入
2>  错误重定向:cmd 2> error.log         → 只重定向 stderr
2>&1 错误合并到标准输出:cmd > all.log 2>&1  → stdout+stderr 都进 all.log
&>  标准输出和错误都重定向:cmd &> all.log   → 同上,简写

常用组合:
  nohup java -jar app.jar > app.log 2>&1 &   ← 后台跑,所有输出到日志
  cmd > /dev/null 2>&1                        ← 所有输出扔黑洞(只要执行结果)

/dev/null 是"黑洞"设备文件--写进去的数据直接丢弃,读出来永远是 EOF。适合"我只要成功/失败,不要输出"的场景。

扩展:2>&1 顺序很关键--> file 2>&1(正确),2>&1 > file(错误,stderr 还在终端)。

5. select、poll、epoll 的区别?

IO 多路复用就像一个餐厅服务员同时服务多桌客人--不用每桌配一个服务员,一个服务员监视所有桌,哪桌举手就去哪桌服务。

维度 select poll epoll
fd 上限 默认 1024(数组) 无上限(链表) 无上限(红黑树)
通知方式 遍历所有 fd(O(n)) 遍历所有 fd(O(n)) 内核回调 + 就绪链表(O(1))
内存拷贝 每次调用拷贝全部 fd 每次调用拷贝全部 fd 仅注册时拷贝一次
触发模式 仅水平触发 仅水平触发 水平触发 + 边缘触发 
select/poll 的工作方式:
  每次调用 → 把所有 fd 从用户态拷到内核 → 内核遍历检查 → 返回就绪的 → 再拷回来
  就像每次收作业都要把所有学生的名字点一遍

epoll 的工作方式:
  注册时拷一次 → 内核用回调机制,fd 就绪时主动加到就绪链表 → 调用时直接拿链表
  就像学生写完作业主动举手,老师只看见举手的人

扩展:LT(水平触发)= fd 就绪后持续通知,编程简单。ET(边缘触发)= fd 就绪后只通知一次,效率高但编程复杂。Nginx 用 ET 模式。

6. 僵尸进程和孤儿进程的区别?

  • 僵尸进程:子进程结束了,父进程没有调用 wait()/waitpid() 回收子进程的退出状态,子进程的 PCB(进程控制块)一直占着不释放。就像人死了但户口一直没注销--浪费系统的进程表项(PID)。

  • 孤儿进程:父进程先于子进程退出,子进程变成"孤儿",被 init(PID=1)进程收养并自动回收。就像父母去世了,孩子被福利院(init)接管。

正常流程:
  父进程 fork() → 子进程运行 → 子进程退出 → 父进程 wait() → 回收

僵尸进程:
  父进程 fork() → 子进程运行 → 子进程退出 → 父进程(忙着,没调 wait) → 僵尸!
                                                          ↓
                                                   ps aux 看到 Z 状态

孤儿进程:
  父进程先退出 → 子进程还在运行 → init(PID=1) 收养 → 正常回收

扩展:解决僵尸进程:1 SIGCHLD 处理中调用 waitpid();2 双 fork() 让孙子进程被 init 接管;3 signal(SIGCHLD, SIG_IGN) 让内核自动回收。

7. 什么是零拷贝(Zero-Copy)?

传统文件传输(如 Nginx 发静态文件)需要 4 次数据拷贝 + 4 次上下文切换:

传统方式:read() + write()
  磁盘 → 内核缓存(1) → 用户态缓存(2) → 内核 Socket 缓存(3) → 网卡(4)
  其中 (2)(3) 是 CPU 做的,代价很高

零拷贝 sendfile:Linux 2.4+
  磁盘 → 内核缓存(1) → 网卡(2)(DMA 直接传输,CPU 不参与拷贝)
  只有 2 次 DMA 拷贝,CPU 完全解放

传统 IO                          sendfile 零拷贝

App:        读 → 写              App:  sendfile() 一次调用
             │    ▲                    │
用户态       │    │                    不经过用户态
─────────────┼────┼───────      ─────────────
内核态       ▼    │                     ▼
       磁盘 → 内核缓存 → Socket    磁盘 → 内核缓存 → 网卡
       (DMA)  (CPU)   (CPU)          (DMA)  (DMA)

CPU拷贝:2 次                    CPU拷贝:0 次
上下文切换:4 次                  上下文切换:2 次

扩展:Nginx、Kafka、RocketMQ 都用 sendfile + DMA scatter/gather 实现零拷贝。mmap 减少 1 次 CPU 拷贝,但不如 sendfile 彻底。

8. kill 信号的类型和应用?

信号 编号 含义 能否捕获
SIGTERM 15 优雅终止,让进程有机会清理资源 能捕获
SIGKILL 9 强制杀死,内核直接干掉的"核武器" 不可捕获
SIGHUP 1 挂断信号,常用于重载配置(如 nginx -s reload) 能捕获
SIGINT 2 中断信号,相当于 Ctrl+C 能捕获
SIGSTOP 19 暂停进程(不可恢复,除非 SIGCONT) 不可捕获
SIGCHLD 17 子进程状态变化时发给父进程 能捕获 
K8s 优雅停机流程:

  kubectl delete pod
       │
       ▼
  K8s 发 SIGTERM → Pod 收到
       │
       ├── 摘除流量(Readiness 探针失败)
       ├── 处理完进行中的请求
       └── 关闭连接、释放资源
       │
       ▼
  terminationGracePeriodSeconds(默认 30s) 超时
       │
       ▼
  还没退出 → SIGKILL 强制杀死

扩展:K8s 优雅停机用 SIGTERM 通知、给 30 秒清理、超时 SIGKILL。

9. 文件权限 755、644 等是什么?SUID/SGID/Sticky Bit?

Linux 文件权限用 3 组 3 位表示:所有者 | 所属组 | 其他人

权限数字:
  r(读) = 4    w(写) = 2    x(执行) = 1

-rwxr-xr-x  →  755
 │││││││││
 │└┬┘└┬┘└┬┘
 │ rwx r-x r-x
 │ 7   5   5
 文件类型(-=普通文件, d=目录, l=软链接)

chmod 755 file   →  所有者全部权限 + 其他人只读执行
chmod 644 file   →  所有者读写 + 其他人只读
chmod 777 file   →  所有人都全部权限(危险!)

特殊权限: - SUID (4xxx):以文件所有者身份执行。passwd 就是 SUID,普通用户才能改密码文件 /etc/shadow - SGID (2xxx):继承目录所属组。团队共享目录用 SGID,任何人创建的文件都属于团队组 - Sticky Bit (1xxx):只有所有者和 root 能删除文件。/tmp 目录就用这个--谁都能创建临时文件,但只能删自己的

扩展:生产禁止 chmod 777。"Permission denied"时:ls -l 看权限,whoami/id 看身份。

10. inode 是什么?和文件名什么关系?

inode(索引节点)存储文件的元数据(权限、大小、所有者、时间戳、数据块指针),但不存文件名。

文件名存在目录项(directory entry)中,目录项只做一件事:把文件名映射到 inode 号。

文件系统结构:

  目录                         inode 表                 数据块
┌────────────┐           ┌──────────────┐         ┌──────────┐
│ file.txt   │───映射───▶│ inode 1024    │───指向──▶│ Hello    │
│ (目录项)    │           │ 权限: 644     │         │ World!   │
│            │           │ 大小: 12 字节  │         └──────────┘
│            │           │ 块指针: [5,6] │
└────────────┘           └──────────────┘

这就是为什么: - 硬链接(相同 inode):删源文件没影响,因为 inode 还在 - 软链接(不同 inode,存的是路径):删源文件就断链 - mv 重命名很快(只改目录项,不改 inode),cp 复制慢(要新建 inode + 拷贝数据块)

扩展:df -i 看 inode 使用量。inode 用完即使磁盘有空间也无法创建文件。

11. Linux 下如何排查端口被占用?

ss -tlnp | grep 8080(推荐)、lsof -i :8080(更直观)、fuser 8080/tcp。kill -9 PID 结束进程。非 root 绑定 <1024 端口需 authbind。

12. 如何用 strace / perf / ebpf 排查性能问题？

strace——追踪系统调用：

# 跟踪最慢的系统调用（按耗时排序）
strace -c -p <pid>

# 跟踪某个命令的所有调用
strace -tt -T ls /

# 跟踪指定系统调用（如 open/read/write）
strace -e trace=openat,read,write -p <pid>

perf——CPU 热点分析：

# 采样 CPU 热点（30秒）
perf record -F 99 -p <pid> -- sleep 30
perf report

# 生成火焰图（需要火焰图工具）
perf script | stackcollapse-perf.pl | flamegraph.pl > out.svg

bpftrace（eBPF，无需改代码）：

# 追踪磁盘 IO 最慢的文件
bpftrace -e 'block:block_rq_issue { @["path"] = args->dev; }'

# 查看高频系统调用
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

组合使用：先用 top/htop 定位进程 → perf top 定位函数 → strace 定位系统调用 → bpftrace 深入分析。

扩展：perf 需要 root 权限；bpftrace 在生产环境安全（只读）；火焰图是定位 CPU 热点最直观的方式。
