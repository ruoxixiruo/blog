Git

1. git merge 和 git rebase 的区别?

  • merge:合并两个分支,产生一个新"合并提交"。保留完整历史,但提交线复杂。
  • rebase:把当前分支的提交"搬到"目标分支末尾,提交线干净直线。但改写了提交历史(commit hash 变了)。
merge:                         rebase:

主:  A → B → C                 主:  A → B → C
         ↗   ↘                            ↘
特性:  D → E → M (合并提交)    特性:  D → E (被搬到 C 后面)
                                            ↘
                                        A → B → C → D' → E'
                                                  (新 hash)

简单记:公开分支用 merge(不改历史),自己分支用 rebase(保持整洁)。

扩展:rebase 的黄金法则--永远不要 rebase 已经 push 到公共仓库的提交。因为 rebase 会改 commit hash,别人的分支基于旧的 hash,你 rebase 后 push force 会把别人基于旧提交的工作全毁掉。就像你把房子地基换了,别人在旧地基上建的墙全塌了。

2. git reset 和 git revert 的区别?

  • reset:回退到某个 commit,删除之后的提交。--soft(保留暂存区)、--mixed(保留工作区)、--hard(全删)
  • revert:新增一个"反向 commit"来抵消之前的改动。历史不丢失,适合已经 push 的代码
reset:                         revert:

A → B → C → D                  A → B → C → D → D-1
         ↑ 删                            ↑ 新增反向提交
     回到这里

历史: A → B                   历史: A → B → C → D → D-1
(D 消失了)                      (D 和"撤销D"都在记录里)

一句话:reset 是"时光倒流",revert 是"打个补丁抵消掉"。已推送到远程的用 revert。

扩展:reset --soft 的妙用--如果你 commit 完发现漏了一个文件,用 git reset --soft HEAD~1 把最近一次 commit 撤回到暂存区,补上文件再重新 commit。工作区的改动完好无损。

3. 常用 Git 命令速查

场景 命令
暂存当前工作(未完成切换任务) git stash
恢复暂存 git stash pop
查看提交图 git log --oneline --graph
删除远程分支 git push origin --delete feature/xx
修改最近一次 commit 信息 git commit --amend
撤销工作区修改 git checkout -- <file> 或 git restore <file>
cherry-pick 一个提交 git cherry-pick <commit-hash>

扩展:git stash 不仅能暂存工作区,还能暂存特定文件(git stash push <file>)、加备注(git stash save "WIP: 修复中")、查看 stash 列表(git stash list)。stash 是一个栈结构--pop 弹出最顶上的,apply 用但不删除。

4. 代码冲突怎么处理?

两个分支改了同一个文件的同一行。解决步骤: 1. 打开冲突文件,找到 <<<<<<< / ======= / >>>>>>> 标记 2. 决定保留哪一部分(或合并两者),删除标记 3. git add 标记已解决,git commit 完成合并

<<<<<<< HEAD         ← 当前分支的内容
const name = "张三"
=======              ← 分隔线
const name = "李四"   ← 合并进来的分支内容
>>>>>>> feature-branch

解决后保留其中一个(或合并两者),删除标记行。

扩展:日常减少冲突的技巧--1 经常从主分支拉最新代码(别攒一个月才合并一次);2 小粒度提交、小粒度 PR;3 IDE 的三路合并工具(VS Code / IntelliJ 自带)比手动改标记高效得多。

5. Git 的三大核心区域(工作区、暂存区、版本库)?

Git 有三个区域,文件在不同区域之间流转:

工作区 (Working Directory)     暂存区 (Staging Area)      版本库 (Repository)
  ┌──────────────┐          ┌──────────────┐          ┌──────────────┐
  │  你正在编辑的  │ git add  │  准备提交的    │ git commit│  已提交的     │
  │  文件         │ ────────▶│  文件快照     │ ────────▶│  历史记录     │
  └──────────────┘          └──────────────┘          └──────────────┘
         ▲                                                  │
         └──────── git checkout / git restore ──────────────┘
                    (从版本库恢复文件到工作区)
区域 作用 查看命令
工作区 你实际看到的文件,随便改 直接看文件
暂存区 git add 后、git commit 前的"待提交区" git diff --staged
版本库 git commit 后的历史记录 git log

扩展:git diff 看的是工作区和暂存区的差异;git diff --staged 看的是暂存区和版本库的差异。理解了三个区域,对 reset/checkout/revert 这些"穿梭"命令就不会搞混了。

6. git fetch 和 git pull 的区别?

  • fetch:只从远程下载最新数据到本地(更新 origin/main 指针),但不合并到你的工作分支。就像取快递--你把包裹拿到家门口了,但还没拆。
  • pull = fetch + merge:下载并自动合并到当前分支。就像取快递并直接拆开。
git fetch:
  origin/main: A → B → C → D(新)
  local/main:  A → B → C
  结果:本地知道远程有新提交 D,但你的分支没变

git pull:
  origin/main: A → B → C → D(新)
  local/main:  A → B → C → D(新)
  结果:本地分支直接包含了 D

扩展:推荐习惯:用 git fetch + git merge 而不是 git pull。因为 pull 直接合并,出了问题你都不知道是谁改的。先 fetch 看远程有什么更新,再决定 merge 还是 rebase。

7. git reflog 的作用?

git reflog 记录了 HEAD 的所有移动历史(包括被 reset 掉的、被 rebase 掉的、被 branch -D 删掉的)。只要 ref 还在 reflog 里(默认 90 天),就能找回来。

# 场景:git reset --hard 后发现搞错了,想回去
$ git reflog
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
e4f5g6h HEAD@{1}: commit: 重要的提交(被我误删了!)
i7j8k9l HEAD@{2}: commit: 另一个提交

$ git reset --hard e4f5g6h   # 回到"被删掉"的提交--完美恢复!

扩展:reflog 救命的场景--误 reset --hard、误 rebase、误删分支。git reflog expire --expire=now --all 可以手动清空 reflog,但没事别执行。reflog 是本地的,不存在远程--所以你只能恢复本地误操作。

8. git cherry-pick 的使用场景?

使用场景:你在 feature-A 分支上修了一个 bug(commit abc123),现在想把这个 bug fix 也应用到 master 上,但不想把 feature-A 的其他提交合并过来。

git checkout master
git cherry-pick abc123   # 把 abc123 这个提交的改动复制到 master

feature-A: A → B → C → D(bug修复)
                        ↑
                    cherry-pick
                        ↓
master:    E → F → D'(D 的复制,新 hash)

扩展:cherry-pick 会产生新的 commit hash(因为父提交不同)。如果 cherry-pick 有冲突,解决后 git cherry-pick --continue;想取消 git cherry-pick --abort。虽然好用,但 cherry-pick 后两个分支有了相同内容的提交但不同 hash,后续合并可能重复冲突--少用为妙。

9. Git 分支的本质是什么?

Git 分支本质上是一个指向某个 commit 对象的可变指针(一个 41 字节的文件,里面写着一个 SHA-1 哈希值)。

HEAD → main → a1b2c3d (commit)
                   ↑
              feature → a1b2c3d (同一个 commit)

这就是为什么: - 创建分支几乎是瞬间的(只创建了一个 41 字节的指针文件) - 切换分支很快(只改 HEAD 指向和工作区文件) - Git 的分支可以随意创建删除,成本极低

相比 SVN 的分支是完整目录拷贝(慢且重),Git 的分支轻量得多。

扩展:HEAD 是一个特殊的指针,指向当前你所在的分支。当 HEAD 直接指向某个 commit(而不是通过分支名),就是"detached HEAD"(游离状态)。在游离状态做的提交如果没有新建分支,切换走就丢了。

10. 如何撤销一个已推送的 commit?

公共分支用 git revert HEAD 生成反向 commit(安全可追溯)。私有分支可用 git reset --hard HEAD~1 后 git push --force。revert 是企业标准做法。

11. git stash 的数据存在哪?drop 后能恢复吗?

git stash 把改动存到 .git/refs/stash 和 Git 对象库中。drop 只是删了引用,对象还在(90 天内可通过 git fsck --unreachable --no-reflogs 找到 dangling commit 恢复)。结论:drop 后大概率能恢复,别慌。

# 恢复被 drop 的 stash
git fsck --unreachable --no-reflogs | grep commit
# 找到 dangling commit 的 hash
git stash apply <hash>

面试话术:"stash 的底层就是一个特殊的 merge commit(工作区+暂存区的合并)。drop 只删引用不删对象,所以能恢复。但如果跑了 git gc --prune=now,对象就被真正回收了,彻底没救。"

12. 如何把一个文件从 Git 历史中彻底删除?(包含大文件清理)

用 git filter-branch 或 git filter-repo。推荐 git filter-repo(更快更安全)。

# 从所有历史中删除某个文件
git filter-repo --path data/large_file.zip --invert-paths

# 清理所有历史中超过 10MB 的文件
git filter-repo --strip-blobs-bigger-than 10M

# 之后必须 force push
git push --force --all

注意:改写历史后所有人的 commit hash 都变了,需要通知团队成员 git pull --rebase。如果是公开仓库(如 GitHub),建议先用 gh repo delete 删旧仓库再重新 push。

13. .git 目录里都存了什么？

.git/
├── HEAD              # 当前指向的分支（ref: refs/heads/main）
├── config            # 本仓库配置
├── refs/
│   ├── heads/        # 本地分支（每个分支一个文件）
│   └── remotes/      # 远程分支引用
├── objects/           # 所有 git 对象（blob/tree/commit/tag）
│   ├── pack/         # 打包后的对象（节省空间）
│   └── info/         # 包的辅助信息
├── index             # 暂存区（staging area）的二进制索引
├── logs/             # 所有 ref 的变更历史
├── hooks/            # 客户端/服务端钩子脚本
├── description       # 仓库描述（给 GitWeb 用）
└── info/             # exclude 等配置

objects 目录四种对象：

对象类型 内容
blob 文件内容（无文件名，无权限）
tree 目录快照（文件名 + 权限 + blob/tree 指针）
commit 快照引用 + 作者 + 提交信息 + 父 commit
tag 指向某个 commit 的别名 
# 查看对象内容
git cat-file -t <hash>  # 类型
git cat-file -p <hash>   # 内容

# 理解 Git 的本质
# Git 不是存差异，是存每个提交时刻的完整快照
# 对象去重：相同内容的文件只存一份 blob

扩展：git reflog 记录所有 HEAD 移动历史，可恢复"丢失"的 commit；git fsck --lost-found 找到 dangling 对象；.git/objects/pack 是 packfile（压缩后的对象集合），比松散对象省 60-80% 空间。
